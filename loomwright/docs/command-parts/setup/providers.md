## Module: providers

Routes pipeline **seats** to another AI CLI: read seats (reviewers, graders, analysis passes) and write seats (the code-edit step of a worker or fix task). Claude stays the default everywhere: a repo with no `routing` block behaves exactly as before, and a seat leaves Claude only when BOTH the repo's config asks for it AND you have granted that provider for this repo; a write seat ALSO needs its own per-seat write grant. The seat lists are `bash "${CLAUDE_PLUGIN_ROOT}/scripts/resolve-routing.sh" seats` and `… write-seats` (never restated here); the routed-seat procedure and the consent rule are `docs/PROVIDER_ROUTING.md`.

Two scripts, split on purpose. `${CLAUDE_PLUGIN_ROOT}/scripts/setup-providers.sh check` is the READ-ONLY probe of the provider table (it writes nothing). `${CLAUDE_PLUGIN_ROOT}/scripts/setup-routing.sh` (`status` / `apply` / `remove`) is the one writer. It writes `<project>/.supervisor/config.json` key `.routing` ONLY and the user-scope `~/.claude/loomwright/egress.json` keys `repos.<slug>.providers` and `repos.<slug>.write_grants` ONLY (this repo's slug) — a jq merge / `del`, backup-first, parse-gated, atomic, byte-compare idempotent, every other key preserved. Every refusal or abort writes nothing and exits 0 with a named headline.

**Check.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-providers.sh" check` and keep its output (it starts each installed provider CLI with a fixed prompt and no repo content, so it can take a while — say so first). Then run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-routing.sh" status` for the config's raw `.routing`, this repo's slug, its user-scope grants and write grants, the providers the repo merely requests, and one resolved line per read and write seat.

**Report.** Print `check`'s table and verdicts VERBATIM — never a hard-coded provider list — then `status`'s output. A repo-requested provider with no grant resolves to Claude with `reason=provider_not_granted` (a write seat without its write grant: `reason=write_not_granted`); say so rather than implying it routes. For `status`, STOP after the report — no offer, no writes.

**Offer — CONSENT-BEARING.** `remove` names its action and runs directly. For `apply` (explicit, or chosen from bare `/setup providers`), offer ONLY providers whose verdict reads `usable for read-only seats` or `usable for write seats`; if there are none, report that and stop. Anything else (`not usable: …`) is never offered, and `setup-routing.sh` refuses it anyway. Use `AskUserQuestion` (cap 4 options):
1. **Which provider?** — one option per usable provider (up to the cap, plus `Cancel`).
2. **Which seats?** — print the `resolve-routing.sh seats` ids, plus the `write-seats` ids ONLY when the chosen provider's verdict is exactly `usable for write seats` (a write seat is never offered to any other provider; `setup-routing.sh` refuses it with `provider_not_write_usable`), then ask for the ids to route (free text, comma-separated) with `Cancel` as the other option. `/setup providers apply --seat <id>=<provider>[:<model>] …` supplies them and skips this question; it never skips questions 3 and 4.
3. **Grant?** — asked unless the `status` grants cell already lists the provider. The question NAMES the provider and states what is sent to it: "Allow `<provider>` to receive, for `<slug>`, the diff under review and each routed seat's prompt? The provider CLI also gets read access to every tracked file at the reviewed commit (even for seats with no diff), and the runner does not block its network egress." Options: `Grant <provider>` / `Route only — no grant (seats stay on Claude until you grant)` / `Cancel`. Only the first writes a grant; a declined ask writes none.
4. **Write grant?** — a SEPARATE question per chosen write seat, asked unless the `status` write-grants cell already lists `<seat>:<provider>`. It NAMES the provider and the seat and states what the grant allows: "Allow `<provider>` to run the `<seat>` edit step for `<slug>`? It may edit files in the subtask's checkout, the prompt and every tracked file it can read there are sent to the vendor, and its network egress is not blocked. Claude still runs the tests and gates, and only Claude commits or pushes." Options: `Write-grant <provider> for <seat>` / `Route only — no write grant (the seat stays on Claude)` / `Cancel`. Only the first writes a write grant; a declined ask writes none.

Can't ask (non-interactive, or inside a subagent): report and stop with `Setup: providers — not changed (cannot ask)`; nothing is written.

**Apply.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-routing.sh" apply --seat <id>=<provider>[:<model>] …` and add `--grant <provider>` ONLY after the Grant answer above was yes, and `--grant-write <seat>=<provider>` ONLY after that seat's Write grant answer was yes; `--on-unavailable strict` only if the user asked for it (the default is `fallback_to_default`). Repeating `--seat` for one id makes an ordered preference list. It re-probes the provider before writing. Relay each headline verbatim — one per target, `apply routing:`, `apply grant:` and `apply write grant:`:
- `applied` (+ `backup: <path>`) / `applied (created <file>)` — written; a `verify:` status follows.
- `no-op — …` — nothing written, no backup.
- `REFUSED (unknown_seat | invalid_provider_name | invalid_model | provider_not_probed | provider_not_usable | provider_not_write_usable | claude_needs_no_grant | no_repo_slug)` — nothing written, even for the other target of the same call.
- `ABORTED (<reason>)` — `config_unparseable`, `routing_unexpected_shape`, `egress_unparseable`, `egress_unexpected_shape`, `symlink`, `path_outside_repo` (the repo config's real location is outside the repo; the user-scope grant file is exempt), `containment_unavailable`, `no_home`, `jq_unavailable`, `no_backup_name`, `backup_failed`, `write_failed`. Nothing written; **never repair a file to get past it**.

**Verify.** Success is claimed ONLY from the `verify:` block: each seat just routed must show `provider=<provider>` with an empty `reason=`. A seat that still shows `reason=provider_not_granted` (no grant yet), `write_not_granted` (a write seat with no write grant yet) or `provider_unavailable` (the CLI is not on PATH) is reported as such, never as routed.

**Subflow: `/setup providers remove`.** Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-routing.sh" remove` and relay `remove routing:` and `remove grant:`. It deletes the `routing` key and THIS repo's `providers` grant and `write_grants` only; a second run reports `no-op`. Removing narrows what is sent, so it asks nothing.

**Idempotency note.** A second identical `apply` reports `no-op`, leaves each file byte-identical and makes no backup. The grant and each seat's write grant are additive (a new provider is appended, existing entries keep their order); a seat write writes neither, and neither grant writes a seat or the other grant.
