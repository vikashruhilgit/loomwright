## Module: memory

Puts this repo's Twin memory stores — `.claude/agent-memory/`, `.supervisor/memory/`, the judgement trail (`.supervisor/requirements/`, `.supervisor/jobs/done/` and `jobs/failed/`, `.supervisor/automate/*.md`; in-flight `jobs/pending/`+`in-progress/`, `*.config-backup.json` sidecars and any `.supervisor/` a hook left nested inside a requirements folder stay ignored — v15.84.0), and (behind a fail-closed gate) the findings ledger `.supervisor/postmortem/results.jsonl` — under version control **IN PLACE**, by un-ignoring them where they already sit. **No move, no symlink, no generated copy, no bridge of any kind.** Nothing moves, so the harness keeps injecting agent memory from its own fixed path and every `memory: project` agent still receives its store from the unchanged path.

> **The findings ledger is the THIRD store, and it is GATED.** It is structurally CROSS-REPO: a `/pr-postmortem` append lands in the CURRENT working `.supervisor/`, never in the analysed repo's, so a ledger accumulates records belonging to OTHER repos. `apply` therefore **fails closed** on it — the negation is emitted only while every record's `.repo` sits inside the resolved allowlist. Otherwise the negation is WITHHELD, the offending slugs are NAMED, readiness reports the third verdict `gated`, and **the exit code is still 0** (fail-closed in the WRITE dimension, never in the exit status). Only `results.jsonl` is re-included — every other file under `.supervisor/postmortem/` stays ignored.
>
> **Honest limits — relay these, do not soften them.** (a) The gate is evaluated **at apply time only**: a ledger that gains a foreign record after a clean apply stays un-ignored until the next apply, and a routine `git add -A` can commit it in between — tell the user to run `filter-ledger` before committing. (b) Withdrawal does **NOT** un-track an already-committed ledger; `.gitignore` only governs UNTRACKED files, so an already-published ledger needs `git rm -r --cached` plus a re-commit. (c) The gate keys on each record's `.repo` field ONLY — it does not read finding TEXT.

The deterministic engine is `${CLAUDE_PLUGIN_ROOT}/scripts/setup-memory.sh` — its header comment (`--help`) is the authority for the subcommand list and the exit codes; this paragraph does not restate them. It is fail-safe (exit 0 on every normal path — except `valid-branch`, a predicate whose exit code IS its answer: 0 accepted, 1 refused), write-contained to `<project>/.gitignore` (+ one timestamped backup) and `<project>/.supervisor/config.json` — plus ONE user-scope file, the learning-store consent record `~/.claude/loomwright/meta-sync-consent.json`, written only by `consent grant` / `consent decline` (see "Learning-store consent" below) — and it NEVER runs `git add` / `git rm` / `git commit`. This command owns the INTERACTIVE half — the consent-bearing offer.

> **The ONE scoped exception to this module's never-`git add` / `git rm` / `git commit` rule** is the engine of the `migrate` subflow, `${CLAUDE_PLUGIN_ROOT}/scripts/migrate-branch-mode.sh`: its `mode-pr`, `untrack-pr` and `rollback` steps each commit on a NEW branch, push that branch and open a PR — and NEVER merge it (merging is always the owner's step). Nothing in this module commits to the default branch, and `setup-memory.sh` itself keeps its header invariant: it never runs `git add` / `git rm` / `git commit`.

**Why this exists:** those stores are gitignored in every repo, so a fresh clone, a second machine, CI and every `git worktree` checkout start COLD, and a bad curation pass is irreversible (there is no `git checkout` to undo it). Committing them also closes a real gap — committed files exist inside `git worktree` checkouts; gitignored ones do not, so workers in worktrees currently cannot see lessons or agent memory.

**The naive negation silently fails.** `.claude/` + `!.claude/agent-memory/` looks correct and does nothing: git cannot re-include a file whose parent DIRECTORY is excluded. The working form excludes the directory's CONTENTS (`.claude/*` + `!.claude/agent-memory/`), which leaves the directory traversable. Both forms are asserted in `test-setup-memory.sh` — the failure is proven by test, not by comment. Any pre-existing bare `.claude/` / `.supervisor/` line is therefore COMMENTED OUT by apply (neutralised, not merely out-ordered) and restored verbatim by `remove`.

> **Tracked-write risk — stated here, mitigated elsewhere (deliberate).** Once `.claude/agent-memory/` is tracked, every memory write becomes a working-tree modification: it shows in `git status`, can be swept into an unrelated commit by a `git add -A` (the exact failure already recorded in project memory about concurrent heal loops), and `MEMORY.md` becomes a merge-conflict surface under parallel workers. Today that is near-theoretical (hand-written, rare). The mitigation belongs to the **memory-writer item (item 04)** — agent writes land in a gitignored proposal queue and only `/dreaming`-promoted entries touch the tracked store. **Building a proposal queue is OUT OF SCOPE for this module by design; do not add one here.**

Read-only — `check` writes nothing. When `jq` is unavailable **or non-functional** the ledger row reads `not probed (jq unavailable — gate not evaluated)`: report that as UNVERIFIED, never as clean. On a repo where the negation was ALREADY applied the row instead reads the real ignore status followed by `^ PRESERVED, not re-verified` plus the reason — also UNVERIFIED, but nothing was withdrawn and no contamination is claimed (emitting a NEW negation needs an examined `pass`; WITHDRAWING an existing one needs an examined `refuse` naming real slugs).

### Apply

1. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/setup-memory.sh" apply` ONLY after an explicit confirm.
2. Read its **headline status line** and report it verbatim. Exactly ONE of these is printed:
   - `apply: applied` — the managed block was written; a timestamped `.gitignore.backup.<ts>` sits beside it (pid-suffixed, then counter-suffixed, if that name was already taken, so a backup never overwrites another — and if every candidate name is taken the apply ABORTS rather than clobber an existing backup), and the allowlist was seeded into `.supervisor/config.json` as a JSON ARRAY **unless an `allowlist: SKIPPED` line says otherwise** (see step 3).
   - `apply: applied (ledger negation WITHDRAWN)` — the block was written AND the findings-ledger negation was removed because foreign records appeared since the last apply. A dedicated `apply: ledger negation WITHDRAWN — <slugs>` block follows it. Relay both; never present this as a plain `applied`.
   - `apply: no-op — already configured` — nothing was written (idempotent second run).
   - `apply: no-op — the two memory stores are already configured, but the findings ledger is GATED …` — the gated form of the no-op. It is a DISTINCT headline: do not report it as `already configured`.
   - `apply: ABORTED — <reason>` — nothing was written, no partial write, no backup. Surface the reason (absent `.gitignore`, unresolved conflict markers, unbalanced managed-block sentinels, NUL bytes, non-regular file, no free backup name) and STOP. Never "repair" the file to get past an abort.
3. **Then check for the ADDITIONAL lines — they are extra output, not one of the three headlines above.** Two can appear, each CO-OCCURRING with the `applied` or `no-op` headline rather than replacing it. **Report the headline AND every additional line** — reporting only the headline would silently drop them and present a half-done apply as a success.
   - `apply: WITHHELD — …` is printed AFTER the headline when readiness is `gated`. It does NOT mean the apply failed: the two memory stores ARE applied and the findings ledger is deliberately withheld. It names the offending repo slugs, the `filter-ledger` / extend-the-allowlist remedy, and the fact that withholding does not un-track an already-committed ledger. Relay it verbatim, present the memory half as a success and the ledger half as withheld, and do NOT hand the user any "comment out the surviving exclude" advice — that advice belongs to the under-inclusion case below and would publish the contaminated ledger here.
   - `apply: WARNING — readiness is '<verdict>', not 'configured'` is printed AFTER the headline (both paths run the same post-write verify). It means the block WAS written but the negation did not take effect; the helper names each intended path still ignored and the rule that wins for it (from `git check-ignore -v`). Relay that verbatim too and do NOT present the apply as a success; the usual cause is a deeper or parent-`.gitignore` exclude the rewriter does not neutralise.
   - `allowlist: SKIPPED — <reason>` means the `.gitignore` half succeeded but `.supervisor/config.json` was left UNCHANGED, so the allowlist was NOT seeded (the helper still exits 0 — the skip is fail-safe, never fatal). Seeding runs on both the applied and the no-op path, so this line can accompany either headline. Surface the reason and tell the user the allowlist still needs seeding by hand. Reasons: `jq` not available; the config exists but is not valid JSON; no git remote to default from and nothing configured; the merge/create could not be written; and — the backup-first contract holding here exactly as it does for `.gitignore` — `could not write a backup of <cfg>; refusing to rewrite it unbacked-up (unchanged)`.
4. **The stores are only UN-IGNORED — nothing is committed.** Tell the user to review `git status --short .claude/agent-memory .supervisor/memory .supervisor/requirements .supervisor/jobs .supervisor/automate .supervisor/postmortem/results.jsonl` and commit deliberately — and, on a PUBLIC repo, to skim the trail first: requirement files and briefs are prose the allowlist gate does not read, and the real corpus carried a pasted CLI login line with a work e-mail (found and redacted 2026-09-21) (the ledger is the third store and is NOT under either memory directory, so a two-path `git status` would let it be committed unreviewed). This command never stages or commits on their behalf.

**The repo allowlist** (`.setup_memory.repo_allowlist` in `<project>/.supervisor/config.json`) is a **JSON ARRAY, never a string**, and is never derived from the live remote at read time. A repo RENAME is the documented reason: records written before a rename carry the old slug, so a live-remote-keyed filter would silently drop the older half of a ledger. It defaults to the CURRENT remote's `owner/repo` on a fresh install (never a hardcoded owner — the plugin ships to other users) and is extended by hand afterwards:
```bash
jq '.setup_memory.repo_allowlist += ["owner/old-name"]' .supervisor/config.json
```
`setup-memory.sh filter-ledger --ledger <path>` applies it to a JSONL ledger and is the reusable predicate for any later item that decides which records belong to this repo. An EMPTY allowlist retains NOTHING (fail-closed), and a record with no `repo` field is excluded as unattributable.

**`config.json` does not travel; the request file does, but can only REQUEST.** `.supervisor/config.json` is gitignored, so a second machine or a fresh clone has none. The tracked `.agent/meta-allowlist.txt` (one `owner/repo` per line; `#` comments and blank lines skipped) lists the slugs the repo REQUESTS. `setup-memory.sh allowlist` resolves, first non-empty layer wins: `--allow` → `$LOOMWRIGHT_MEMORY_REPO_ALLOWLIST` → the `config.json` array → the current remote's `owner/repo` PLUS the request file's GRANTED entries. A request entry is granted ONLY when `gh api repos/<slug> --jq .id` equals origin's id — a renamed repo's old slug that GitHub redirects to this repository is granted; a slug naming any OTHER repository is ignored and named on stderr (`allowlist: ignored <slug> — not this repository`). It must never grant on its own, because the ledger collects records about OTHER repos analysed from this checkout, and a committed list that granted would let whoever controls the file publish them. **`gh` is a new OPTIONAL dependency, reached only on that layer:** missing, unauthenticated or failing, NO request entry is granted (fail closed) and the layer yields the remote alone, as before. **github.com origins only:** `gh api` asks github.com, so for a GitLab, Bitbucket or GitHub Enterprise origin it would compare a github.com namesake — such an origin grants nothing and makes no `gh` call (`allowlist: ignored <slug> — origin is not on github.com …`). **Bounded:** every `gh` call is killed after `LOOMWRIGHT_ALLOWLIST_GH_TIMEOUT` seconds (default 10) and counted as failing — together with every process it started (its process group), so a child left holding the output pipe cannot outlast the bound either — and after one timeout no further call is made, so a hung `gh` cannot stall `validate-entry.sh` (every memory write) or `meta-sync.sh` (every push) for more than two bounds plus a 1s kill grace each. (Limit: a descendant that deliberately leaves `gh`'s process group, as a daemon does, is not covered; `gh` does not do that.) **Capped:** the request file is untrusted input, so at most 20 non-own entries are compared per resolution (`LOOMWRIGHT_ALLOWLIST_MAX_ENTRIES`, clamped to 100) — at most 21 `gh` calls even when each answers just inside the bound — every later entry is named (`allowlist: ignored <slug> — over the 20-entry cap`) and never passed to `gh`, and reading stops after 200 lines. The bounded runner writes no temp file. **Not cached across invocations, by design:** origin's URL is read once and origin's id looked up at most once per resolution, but each `allowlist` process starts from scratch — a cross-invocation cache would have to be a file, and `allowlist` writes none (a caller-supplied cached id is refused too, since a stale or forged value could then grant). The lazy lookup, the bound and the 20-entry cap bound the cost; a caller that resolves often (`validate-entry.sh` per entry, `meta-sync.sh` per push) and wants zero `gh` calls should set `.supervisor/config.json` `.setup_memory.repo_allowlist`, which wins before the request file is read. A request file that exists but is not a readable regular file (mode 000, a directory) is named on stderr (`allowlist: ignored .agent/meta-allowlist.txt — not readable …`) and grants nothing; an absent one is silent. Origin's own slug never needs `gh`; an entry that is not `owner/repo`-shaped is never passed to `gh`; a filesystem-path origin grants nothing; and a present `config.json` (or `--allow`, or the env var) means the request file is not read at all. Every status line goes to STDERR — stdout stays one entry per line, because `meta-sync.sh`'s push scrub and `validate-entry.sh` read stdout as the list; the `# source:` line names the request file when it contributed. On a machine with no `config.json`, `apply` seeds the granted entries into config with the remote.

### Branch mode (opt-in, default OFF)

`setup-memory.sh apply --branch-mode <branch>` (offer `loomwright-meta` — `meta-sync.sh`'s own default — as the suggested value; the value is REQUIRED, a bare `--branch-mode` or an option-shaped value such as `--branch-mode --root X` is a usage error with nothing written, and the name must pass BOTH `git check-ref-format --branch <name>` with the output unchanged AND meta-sync.sh's own `git check-ref-format refs/heads/<name>`, and must not be option-shaped (`-…`), `HEAD`/`@`, or `off` — the intersection, so a recorded name is always one meta-sync.sh accepts; `mode` applies the same check, so a hand-written invalid mode line reads `unknown`; **`off` is reserved** — it is the switch-off spelling, so it can never be a metadata branch name, and a hand-written `# loomwright-meta-branch: off` reads `unknown`, never `on off` and never silently `off`) writes a block that keeps the two memory stores but OMITS every run-history re-include (requirements/, jobs/done|failed/, automate/*.md) and the ledger lines, and records ONE line `# loomwright-meta-branch: <branch>` inside the sentinels. `--branch-mode off` writes the default block again; a plain `apply` PRESERVES the mode line already there; `remove` deletes the whole block, mode included. `setup-memory.sh mode` prints exactly one line — `off` | `on <branch>` | `unknown <reason>` — and is the one reader the engine uses (`skills/automate-loop/SKILL.md` §13). **Switching does NOT untrack existing files:** it only rewrites `.gitignore`; already-committed run history stays tracked until a separate, deliberate operator migration removes it.

In branch mode the report and the copy describe the branch-mode block, not the default one: `check` lists the findings ledger as `branch mode — on <branch>, stays ignored here` and probes it in the must-stay-ignored set (the repo-allowlist ledger gate does not apply, because this block never un-ignores the ledger); the disclosure says only the two memory stores become version-controlled, run history lives on the metadata branch so there is nothing to commit for it here, and untracking already-committed run history is the `migrate` subflow below (it starts with `migrate-branch-mode.sh plan`), never this helper; and `apply`'s `Next:` hint lists only `.claude/agent-memory .supervisor/memory`. Show that disclosure verbatim, exactly as for the default block.

### Subflow: `/setup memory migrate`

Takes a repo from the default mode to branch mode (run history on a metadata branch synced by `meta-sync.sh`), one owner-gated, resumable step at a time. **The split is strict: this command owns ONLY the asking; `migrate-branch-mode.sh` owns every step** — case detection, preconditions, the scrub dry run, the rehearsal, branch creation, the PRs, the seed / A-B checks and the post-merge restore. Never perform a step by hand from here, never re-implement one of its checks, and never re-run a refused step with different flags to get past the refusal.

1. Run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/migrate-branch-mode.sh" plan` — read-only, it writes nothing (no state file, no ref, no index). Relay its output verbatim. `already in branch mode on <b>` ⇒ STOP, nothing to do. A refusal (exit 1, the reason named, e.g. a mode line that reads `unknown`) ⇒ relay it and STOP. Otherwise it names the case (`fresh` or `history`) and prints the step sequence — that printed sequence is the authority; do not restate or reorder it here.
2. Before EACH step, ask with `AskUserQuestion` (`Run <step>` / `Stop here`; an ambiguous answer is `Stop here`), then run `migrate-branch-mode.sh <step>` and relay its output verbatim. Exit 0 = the step passed; exit 1 = refused or failed, with a reason line (STOP and relay); exit 2 = usage error. Every step except `plan`, `state` and `rollback` refuses while the recorded preflight result is not PASS (the exemptions and why: `migrate-branch-mode.sh --help`, `preflight`). `migrate-branch-mode.sh state` prints the state file and the next step, so a stopped flow resumes there — in a later session too.
3. **Owner-only steps — this command stops and hands them over, it never does them:** creating the ruleset (`protect` prints the exact ruleset JSON and the `gh api` command the OWNER runs; afterwards `protect --verify` records PASS only when an active ruleset covers the branch); and merging every PR the script opens (`mode-pr`, `untrack-pr`, `rollback` — none is ever merged by the script or by this command). In the `history` case, `verify-pr <n>` must run IMMEDIATELY before the owner merges the untrack PR; an early merge skips that re-check.
4. After the merge, run `after-merge` in THIS checkout. What it checks, and the follow-up round it records when managed paths are still tracked (seed → untrack-pr → verify-pr → merge → after-merge again), is in `migrate-branch-mode.sh --help` (`after-merge`) — the authority; relay its output verbatim and, on a FAIL, follow the recovery it names. It then prints the two commands for every OTHER checkout (`git pull`, then `meta-sync.sh pull --branch <b>`). **Honest limit — order for other checkouts:** those two commands alone are safe only in a checkout that never synced against the metadata branch before the untrack merge. A checkout that DID sync earlier can read the files `git pull` deletes as local deletions and lose them. In such a checkout, do what `after-merge` does: note `HEAD` before `git pull`, put back each path `git diff --name-only --diff-filter=D <pre-pull HEAD> HEAD -- .supervisor` lists (from that pre-pull commit), and only then run `meta-sync.sh pull --branch <b>`. No step automates this for other checkouts.
5. **Rollback** is `migrate-branch-mode.sh rollback --commit <sha of the merged untrack commit>`: the corrected recipe (push local edits to the branch first, revert without committing, re-track the CURRENT branch files, drop paths deleted on the branch since the migration) on a NEW branch, then a PR that the owner merges. Nothing written since the migration is lost.
6. **Rehearsal:** `rehearse` runs `meta-sync-rehearsal.sh` with the recorded branch on a scratch clone and a local bare remote — nothing reaches the real remote. Run `meta-sync-rehearsal.sh --no-config` directly to rehearse without the checkout's configuration; "configuration" there means `.supervisor/config.json` (the repo allowlist) plus `.agent/meta-sync-deny.txt` (the scrub deny patterns). The tracked request file `.agent/meta-allowlist.txt` is NOT "configuration" — it travels with every clone, so `--no-config` keeps it, exactly as a fresh clone would; but a rehearsal against a local bare origin cannot show its grant (a filesystem-path origin has no `owner/repo`, so no request entry is granted), so the old-slug hits a `--no-config` rehearsal reports are expected there — the proof of the request/grant fix is `test-meta-sync.sh`'s request-file leg, not the rehearsal.

**Honest limits.** The `gh` and ruleset behaviour (`protect --verify`, and PR creation in `mode-pr` / `untrack-pr` / `rollback`) is exercised by the self-tests only against stubs, never against the real GitHub API — treat the first real run's output as the check, and read it. The state file's keys are documented in `docs/RESULT_SCHEMAS.md` §MIGRATE_BRANCH_MODE_STATE.

### Idempotency note

A second `/setup memory` on an already-applied repo reports "already configured" and writes nothing — apply compares the file it WOULD write against the file on disk byte-for-byte before touching anything, and an existing non-empty allowlist is never overwritten (a hand-added pre-rename slug must survive re-apply).

**Restated precisely, now that the ledger gate exists:** the managed block is a pure function of (the pre-existing `.gitignore` contents, **the ledger gate outcome**). For a FIXED gate outcome it is byte-stable across runs, which is what idempotency requires — but the gate outcome is an INPUT. A repo that applied cleanly and LATER gains a foreign-slug record WILL legitimately rewrite `.gitignore` on the next apply to withdraw the ledger negation. That is correct fail-closed behaviour, it is ANNOUNCED (never a bare `apply: applied`), and it does not un-track an already-committed ledger.
