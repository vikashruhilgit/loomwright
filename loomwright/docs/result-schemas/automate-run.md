## AUTOMATE_RUN

The on-disk layout of the `/automate` engine's run file, `.supervisor/automate/<run_id>.md` (v14.41.0+; `schema_version: 1`). It is the contract, the dashboard, and the resume state for a `/automate` run — one markdown file per run holds the Source, the resolved Queue, the current item, and an append-only Progress log. Its sections, the item-status enum, and the item lifecycle are coined in `skills/automate-loop/SKILL.md` (the single source of truth — §3 the single run file, §4 resume, §6 the per-item loop); this section documents that layout verbatim and **must not re-coin or rename** any of it.

> ⚠️ **This is a markdown STATE-FILE contract, NOT a hook-validated emitted result block.** Unlike `SUPERVISOR_RESULT`, `CODE_REVIEW_RESULT`, `WORKER_RESULT`, and `REVIEW_HEAL_RESULT` — each of which a `SubagentStop` hook in `hooks.json` enumerates and validates — **NOTHING validates `AUTOMATE_RUN`.** No hook enumerates it; there is no SubagentStop validator. It is the persisted state of an inline main-thread workflow (`/automate` is inline-only, no `-runner` agent), written and re-read directly by the engine on each `/loop` tick. The closest precedent in this file is `AUTONOMOUS_RUN` (another inline-workflow state artifact that is "Not subject to hook validation"); `AUTOMATE_RUN` differs in that it is the live, rewritten-in-place run file rather than a terminal summary.

**Single-file principle.** There is **no manifest, no registry, no `progress.jsonl`, no dashboard file** — this ONE markdown file holds everything. "Find prior runs" = glob `.supervisor/automate/*.md` for run files — those carrying the `# Automate Run:` title line (`is_run_file` in `automate-helpers.sh`; rule owned by `skills/automate-loop/SKILL.md` §4) — not marked `## Status: done`. The only other on-disk artifacts are sidecars, never runs: a *transient* config-backup sidecar (`<run_id>.config-backup.json`) that exists only during a tick (see `skills/automate-loop/SKILL.md` §7), and the per-run result sidecars `<run_id>.supervisor-result.md` / `<run_id>.review-heal-result.md` written verbatim at §6 steps 2–3; they carry no `# Automate Run:` title, so RESUME never lists them.

### Run-file layout (`.supervisor/automate/<run_id>.md`)

```md
# Automate Run: <title>
## Status: running          # running | paused | done   (paused = stopped, work remains; done only when the Queue is fully resolved)
## Source
- <user prompt text | folder <dir> | backlog <_BACKLOG.md> | ...>
## Run Config
- mode: safe|auto-merge | limit: 5 | trust_unprotected: false
- auto_review_original: <true|false|absent> | config_backup: <run_id>.config-backup.json
- max_tokens: <N|absent>          # red-team-hardening/06 — ONLY present when --max-tokens was passed; PERSISTED (unlike --cheap/--notify) so a bare --resume still enforces it
- parallel: <N|absent>            # parallel-automate/05 — present on any --parallel parent run, 1 included (N = 1 = single-lane mode, skills/automate-loop/lanes.md)
## Queue                    # `- [ ]` queued · `- [x]` done (merged) · `- [x] … # skipped|abandoned:` excluded; order = processing order
- [ ] <requirement path or generated file>
- [x] <... merged ...>
- [x] <... path ...>  # skipped: <reason>     # checked-off so "next unchecked" never re-picks it; reason also in ## Progress
## Current
- item: <path> | status: running|awaiting_merge|ready_for_release|escalated|failed|rate_limit|drain_died|done | pr: <url> | branch: <name>
- pause_reason: awaiting_merge|ready_for_release|awaiting_go|escalated|limit_reached|resume_ambiguous|rate_limit|drain_died|token_ceiling|run_lock_held|meta_unreachable|trail_pr_open|closeout_leftover|live_lane|null
- wave: <k> | items: <i1>, <i2>     # parallel-automate/05 — present ONLY on a --parallel N>1 parent run; written only by `automate-helpers.sh current-wave`
- escalation_cause: check_pending|check_red_unrelated|check_red|findings|validation_unrun|other | check: <name|null> | run_id: <id|null> | attempt: <n|null> | sha: <sha|null>     # automate-followups/31 — present ONLY at an `escalated` park; written only by `current-escalation`
- owned_drain_started: <ts> | owned_drain_result: READY|ESCALATED|died|superseded_by_merge | suppressed_default_dispatch: true
- pending_decisions: <n> | fix_now_reentered: <true|false>     # automate-followups/12 — present ONLY when this item produced dismissed-finding drafts
## Progress                 # APPEND-ONLY (never rewritten)
- <ts> picked <item>
- <ts> session_id <id> (<item>)     # red-team-hardening/06 — read-token-ledger.sh --run-id sums every session_id line in this file
- <ts> ran /autonomous → PR <url>
- <ts> drain READY → awaiting_merge
```

### `## Current` fields

| Field | Values | Notes |
|---|---|---|
| `status` (item-level) | `running` \| `awaiting_merge` \| `ready_for_release` \| `escalated` \| `failed` \| `rate_limit` \| `drain_died` \| `done` | The state of the in-flight item. Distinct from the run-level `## Status` enum above. `rate_limit`/`drain_died` mirror `pause_reason` exactly the way `awaiting_merge`/`escalated` already do — never a separate `parked` placeholder. |
| `pause_reason` | `awaiting_merge` \| `ready_for_release` \| `awaiting_go` \| `escalated` \| `limit_reached` \| `resume_ambiguous` \| `rate_limit` \| `drain_died` \| `token_ceiling` \| `run_lock_held` \| `meta_unreachable` \| `trail_pr_open` \| `closeout_leftover` \| `live_lane` \| `null` | Non-null whenever `## Status: paused`; `null` while `running`/`done`. `awaiting_go`: the `## Current` item was closed out by `closeout` (its PR merged; item `status: done`) and the next item waits for the owner's explicit `--resume` — written ONLY by `closeout`, ONLY when `## Current` names that item and PR and `## Status` is `paused` (a `running` run gets `null`) — see `skills/automate-loop/SKILL.md` §3 "After a close-out". `rate_limit`: the loop's own `agent_lifecycle: failed` row (main-scope, `reason: rate_limit`) fired during RUN, before a PR existed — see `skills/automate-loop/SKILL.md` §6 "Rate-limit park". `drain_died`: RECONCILE (§4) found a `.supervisor/review-dispatch/*.died` marker for this item's PR — a DETACHED `dispatch-pr-review.sh` drain exited without ever producing a `REVIEW_HEAL_RESULT` — see `skills/automate-loop/SKILL.md` §4. `token_ceiling` (red-team-hardening/06): PICK-time `automate-helpers.sh ceiling-check` found the run's summed ledger over `## Run Config`'s `max_tokens`, or the reader answered `LEDGER_UNREADABLE=1` (fail CLOSED) — see §6 step 1. `run_lock_held`: PICK-time `run-lock.sh acquire` found `.supervisor/run.lock` held by another run/process — see §6 step 1 / §11. Both new values are RUN-level-only parks fired BEFORE an item is picked, so — like `limit_reached`/`resume_ambiguous` — they have no item-level `status` counterpart in the enum above. `meta_unreachable`: branch mode's `automate-helpers.sh meta-entry` failed on a `--resume <id>` of an existing local run file (pull exit non-zero or mode `unknown`) — the `## Progress` line names the reason (a conflict names its path); a RUN-level park with no item-level `status` counterpart, like `limit_reached` / `resume_ambiguous` — see `skills/automate-loop/SKILL.md` §13. `trail_pr_open`: the PICK-time `automate-helpers.sh trail-gate` found this run's own trail PR (`chore/<run_id>-trail-<n>`) open, or could not read its state (fail CLOSED) — the single-open-PR invariant counts the trail PR, because its merge would move the base under the next item's PR (`BEHIND` under `strict` required checks); the `## Progress` line names the PR. Written after RECONCILE, with the run-lock held and released at the park; no item-level `status` counterpart (the `## Current` item is the previous, closed-out one) — see `skills/automate-loop/SKILL.md` §6 step 1 / §8. `closeout_leftover` (automate-followups/32): a close-out could not safely finish one of its steps (a kept worktree or branch, a refused sync, a result line nobody classified) and the owner chose Stop — or the run is non-interactive, which never proceeds past a leftover silently; a RUN-level park with no item-level `status` counterpart, written with `automate-helpers.sh current-set`'s run-level form. The verdict comes from `automate-helpers.sh closeout-classify` (one `closeout` invocation at a time; anything but `complete` is a leftover); each leftover gets one `closeout leftover: <run_id> <step> <detail>` `## Progress` line — see `skills/automate-loop/SKILL.md` §6 step 1 "Close-out leftover gate". `live_lane` (parallel-automate/05): the PICK-time lane guard `automate-helpers.sh pick-guard .supervisor/automate` printed `refuse: live_lane <lane_run_id> <lane>` (a lane of an open `--parallel` wave is verifiably live, or holds an unanswered question) right after the run lock was acquired — the case where the coordinator's `automate-lanes:<run_id>` lock was reclaimed while its lanes run on; a RUN-level park with no item-level `status` counterpart, written with `current-set`'s run-level form, the run lock released at the park; the `## Progress` line quotes the refusal — see `skills/automate-loop/SKILL.md` §6 step 1 / §14. |
| `pr` / `branch` | string / `null` | The in-flight item's PR URL and feature branch. When the item changes, `current-set` resets an omitted `pr`/`branch` to `null`, so the previous item's PR never rides into the next item. |
| `wave` / `items` | `<k>` / comma-separated item paths | parallel-automate/05 — OPTIONAL, present only on a `--parallel N>1` parent run while a wave is planned. Written only by `automate-helpers.sh current-wave <rf> --wave <k> --items <i1,i2,…>` (replaced if present; `--wave null` clears it). Never present inside a lane or on a sequential run. |
| `owned_drain_started` | `<ts>` | Timestamp the engine's OWNED inline `/review-pr --until-mergeable` drain started (the latest pass's — an owner-requested fix-now re-drain overwrites it, together with `owned_drain_result`). A fix-now re-drain's `## Progress` lines are pinned (Part T02): start `<ts> owned drain started (fix-now re-drain) — <drain invocation> @ <head sha>` (still prefixed `owned drain started`, so the `current_not_set` guard is unchanged) and terminal `<ts> fix-now re-drain <READY\|ESCALATED> (<termination_reason>, <n> rounds, <k> fix cycles)`; `automate-helpers.sh dismissed-cost` derives the fix-now cost from them (legacy wordings matched tolerantly). Authority: `skills/automate-loop/SKILL.md` §6 "Dismissed-findings decision step (before the park)" step 3. |
| `owned_drain_result` | `READY` \| `ESCALATED` \| `died` \| `superseded_by_merge` | The drain's terminal `REVIEW_HEAL_RESULT.decision`, read synchronously. `READY` is "ready, left open for a human" — the drain **never merges**. `died` is not a `REVIEW_HEAL_RESULT` decision at all — it records a DETACHED drain's `.died` marker found at RECONCILE (see `pause_reason: drain_died` above), never this engine's own inline drain (which cannot die silently — it runs in this same turn). `superseded_by_merge` (automate-followups/20) is not a `REVIEW_HEAL_RESULT` decision either: the owned drain for this item started but ended WITHOUT a terminal `REVIEW_HEAL_RESULT` — in practice the owner merged the PR mid-drain and the drain was stopped — and `automate-helpers.sh reconcile-item <pr>` reads `merged`. The engine writes it, never a script, at one of two points: §6 step 3 DRAIN, when the drain returns without a terminal block; or §4 RECONCILE, when a resumed run's `## Current` item has an `owned drain started` `## Progress` line after its last `picked` line, no terminal drain line after it, and a merged PR. Either way no `<run_id>.review-heal-result.md` sidecar is written, GATE never runs for the pass, the item goes to `closeout` exactly as a RECONCILE-merged item does, and the `## Progress` line names the value (`<ts> drain superseded_by_merge — PR merged before a terminal REVIEW_HEAL_RESULT`). It is never merge-eligible: `gate-eval` condition 1 parks any `drain_result` other than `READY` (`drain_not_ready`). Never `null`, and never omitted while the line is present: the line is absent only while no owned drain has run in this run file. |
| `suppressed_default_dispatch` | `true` | Records that the engine suppressed `/autonomous`'s default detached until-mergeable drain (`.auto_review:false` around the RUN phase) so exactly ONE owned inline drain runs per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent; `skills/automate-loop/SKILL.md` §6 "Dismissed-findings decision step (before the park)"). Verifiable via these fields **plus** the absence of any detached `dispatch-pr-review.sh` artifact for the PR (`skills/automate-loop/SKILL.md` §7). |
| `escalation_cause` | `check_pending` \| `check_red_unrelated` \| `check_red` \| `findings` \| `validation_unrun` \| `other` | automate-followups/31 — OPTIONAL, present only at an `escalated` park (mirrors the `pending_decisions` OPTIONAL-line precedent). Its line also carries `check`, `run_id`, `attempt` and `sha` (each `null` when not check-driven or unreadable) — the drain's `REVIEW_HEAL_RESULT` `escalation_*` fields (`docs/result-schemas/review-heal-result.md`). `validation_unrun` (af36-remainder/01) is ENGINE-SIDE, never a `REVIEW_HEAL_RESULT` value: the drain said `READY`, but `automate-helpers.sh validation-gate` found a "Running system" step of the item's `## Validation` section with no pasted evidence in the PR body (or could not read it — fail CLOSED) and the owner did not waive it (`AUT-WAIVE`, human-only); its `check` is `V<n> <title>` (the step), `sha` the PR head, `run_id`/`attempt` `null`. The merge watcher never re-checks it; `--resume`'s RECONCILE re-runs the gate and, on `ok`/`waived`, writes the READY park (`skills/automate-loop/per-item-loop.md` §6 step 4 "Re-check at RECONCILE (step 1)"; the gate itself is `automate-next-step.sh`'s `validation` step). The ONLY writer is `automate-helpers.sh current-escalation <runfile> --cause <c> [--check … --run-id … --attempt … --sha …]` (enum-checked, `\|`/newline refused, file byte-unchanged on refusal; placed after `- pause_reason:`, else at the end of the block; `--cause null` removes it). An item-form `current-set` that leaves `escalated` or changes the item removes it (per-item state: closeout's `done`, PICK's `running` and every non-escalated park clear it). Informational only — no gate reads it and it never permits a merge. |
| `pending_decisions` | `<n>` (integer ≥ 0) \| `unknown` | automate-followups/12 — OPTIONAL, present only when this item's GATE produced dismissed-finding drafts in `.supervisor/requirements/proposed/` (`automate-helpers.sh dismissed-drafts`). The count of this run's drafts still `undecided` after the gate's decision step, or `unknown` when `dismissed-pending` cannot tell (any of the run's drafts with no readable Decision line, an unreadable ledger) — treated as non-zero by every reader, and recorded rather than refused so the park, watcher, notify and run-lock release always complete (always the full count under `--non-interactive-fallback` and at a successful `--auto-merge` MERGE, where nothing is asked). At a sequential interactive READY park (automate-speed/01, park first) it is written WITH the park, before any question — the full undecided count — and rewritten after the asks under a re-acquired run lock; drafts still unanswered when the PR merges mid-question (the watcher's `closeout` ran) or when `park-ask-gate` refused stay counted. The next interactive PICK asks them (Follow-up / Drop) before RECONCILE's `closeout`. Never a new `pause_reason` value. Authority: `skills/automate-loop/SKILL.md` §6 "Dismissed-findings decision step (before the park)". |
| `fix_now_reentered` | `true` \| `false` | automate-followups/12 — OPTIONAL, same line as `pending_decisions`. `true` once the owner answered `Fix now on this PR` and the item ran its ONE fix-now DRAIN → GATE re-pass; fix-now is never offered again for this item, and the loop passes `--after-fix-now` to `dismissed-drafts` only on that post-re-pass run. |

### next-step instruction (`automate-next-step.sh`)

`loomwright/scripts/automate-next-step.sh <runfile> [--start pick|run|drain] [--result <json> | --result-file <f>] [--mode safe|auto-merge] [--non-interactive] [--trust-unprotected] [--root <checkout>] [--session-id <sid>] [--notify] [--cheap] [--max-tokens <N>]`, and its resume entry `automate-next-step.sh --resume <automate_dir> [--run <run_id>|latest] --session-id <sid> [the same flags]` (automate-speed/06 the tail, automate-speed/07 RUN and DRAIN, automate-speed/08 PICK, RECONCILE and resume) is the single reader and writer of the run file for the whole per-item loop — resume, PICK, RECONCILE, RUN's and DRAIN's bookkeeping, GATE, the dismissed-findings decision step, the park writes and the close-out (`skills/automate-loop/` §4, §6, §7, §8, §9, §10). The model's loop is: run next-step; do the one instruction; report the result. Each call runs every deterministic step it can and prints **exactly ONE** instruction: one compact JSON object on stdout. The model does what it says and reports back with `--result`. The protocol stays the skill's. This section owns only the instruction's shape, and the driver emits nothing outside it.

**Entry points.** Before any of them the coordinator runs what stays its own: `init-check` (with `--parallel`), `meta-entry` (branch mode) and, for a new run, intake (source → Queue → run file, `queue-confirm`).
- **`--resume <automate_dir>`** — every start that may continue a run. A bare `/automate` start passes no `--run`; `/automate --resume` passes `--run latest`; `/automate --resume <id>` passes `--run <id>` (an id naming no incomplete run exits 2 `run_not_incomplete`, nothing written). It needs `--session-id` (exit 2 `session_id_missing` otherwise) and takes no `--result`. It runs the start order's ground-truth steps — `closeout-others <automate_dir>` (`--record <runfile>` with `--run <id>`), then `resume-glob <automate_dir> --finalize` — and targets the named run, else the most recent incomplete one (run ids sort by their timestamp). No incomplete run ⇒ `{"do":"done","step":"resume","status":"stopped","choice":"start_new",…}`: intake is the model's. Otherwise, without `--run <id>`: interactive ⇒ the `AUT-RESUME` ask (`Continue` · `Start new` · `Archive`; its `run_file` and `answer_with` name the call that answers it, `<run_file> --result …`); can't ask (`--non-interactive`, or `{"cant_ask":true}`) with exactly one incomplete run and no `--run` ⇒ the stop `{"do":"done","status":"stopped","stop":"resume_requires_flag_non_interactive",…}` whose `message` starts `automate: resume_requires_flag_non_interactive <run_id>`, with nothing written — not the run file, not the sidecar; with more than one (and no `--run <id>`) ⇒ the `resume_ambiguous` park (`current-set --pause-reason resume_ambiguous`; the run lock is never taken). Both carry the start's `closeout-others` record lines and `leftover` rows verbatim (`closeout_others` / the park `message`). `Start new` / `Archive` ⇒ `done` `stopped` with `choice` `start_new` / `archive`, nothing written (the model carries the choice out). A coordinator run (`## Run Config` carries `- parallel: N`) stops first, without the ask: `{"do":"done","status":"stopped","stop":"coordinator_run",…}`, nothing written — `rebuild` and `pick` (so `--start pick` too) refuse it the same way. Continue (the answer, `--run <id>`, or `--run latest` with one run) ⇒ `rebuild`: `current-rebuild` (it appends its own `current_rebuilt: …` line); a rebuilt `## Current` asks `AUT-RESUME` again with it shown, or parks `resume_ambiguous` when it cannot ask; then `resume-continue`: each `closeout-others: record — <line>` becomes `<ts> <line>`, and the start's `leftover` rows go through the close-out leftover gate (a `run_lock_held` row is not a leftover — the next start retries it); then PICK, with the `reconcile-status` dry-run lines due after RECONCILE.
- **`--start pick`** — the per-item entry: the first item of a new run, and every `{"do":"done","status":"running"}`. It needs `--session-id` (the PICK lock is acquired with it; RECONCILE's `closeout` re-enters it). PICK's order: `pick` (the run-lock acquire FIRST — `run_lock_held …` ⇒ `## Status: paused`, `current-set --pause-reason run_lock_held`, one `<ts> run_lock_held owner=… pid=… age=…` line, nothing released, nothing else touched; a `run_lock_degraded…` answer ⇒ one `<ts> run_lock_degraded… — the run lock is TTL-only; proceeding` note — then `## Status: running`) → `lane-guard` (`pick-guard <automate_dir>`: anything but `ok` ⇒ `<ts> refuse: live_lane …` and the `live_lane` park) → `ceiling` (`--max-tokens N`, else `## Run Config`'s `max_tokens`: `ceiling-check`'s `OK …` goes on; `PARK: …` — or any other answer, fail CLOSED — ⇒ `<ts> PARK: …` and the `token_ceiling` park) → `meta-push` (a non-empty `meta-push-failed` answer ⇒ one `<ts> meta-push-failed: <answer>` line, a report) → `pending` (interactive only: `dismissed-pending` non-zero or `unknown` ⇒ this run's undecided drafts are asked — per-finding drafts under `AUT-PENDING`, ≤ 4 a call, `Follow-up (keep draft)` · `Drop`; a summary draft under `AUT-SUMMARY` in a call of its own; each answer is one `dismissed-decide`; fix-now is never offered here) → `reconcile` → (`reconcile-status` on a resume) → `trail-gate` → `trail-unstage` → `picked` (`current-set … --status running --pr null --branch null --pause-reason null` BEFORE `<ts> picked <item>`, the first `- [ ]` row; none ⇒ `terminate`) → `run`, whose `/autonomous` spawn it prints. `--start pick` while an ask of this PICK is pending re-prints it; while a spawn of the pass it started is pending it exits 2 `pick_already_started`; on a `## Status: done` run it exits 2 `run_done`.
- **`reconcile`** — RECONCILE (`skills/automate-loop/` §4 steps 2–3, §6 step 1, §8): a crash-stranded `<run_id>.config-backup.json` is restored first (`config-restore`, no line); a `## Current` item a human checked off `# skipped:` / `# abandoned:` gets `trail-pr <runfile> --reason skipped|abandoned` (its line `<ts> trail-pr: …`, once — not when a `trail-pr:` line already follows the last `picked` line) and no longer blocks the pick; a `## Current` item `done`, or without a PR, has nothing to reconcile; a `.supervisor/review-dispatch/*.died` marker for its PR ⇒ the `drain_died` park (`current-set --item … --status drain_died --pause-reason drain_died`, `owned_drain_result: died`, one `<ts> drain_died — …` line); then `reconcile-item <pr>`: `merged` ⇒ (when the item's last drain line is an `owned drain started` with no terminal line after it, the superseded-by-merge lines first) `closeout <runfile> <item> <pr> --session-id <sid>`, its output classified ONCE by `closeout-classify --record` — anything but exactly `complete` goes to the close-out leftover gate (`leftover`: the `AUT-LEFTOVER` ask, `Clean up now` · `Keep and continue` · `Stop`, ≤ 4 leftovers a call; can't ask ⇒ the `closeout_leftover` park, one `<ts> closeout leftover: <run_id> <step> <detail>` line per leftover, no `trail-pr`); `awaiting_merge` (OPEN, or unreadable — reconcile-item's safe belief) ⇒ for an `escalated` item with `escalation_cause: validation_unrun` whose PR reads `OPEN` (`gh pr view <pr> --json state`) the read-only `validation-gate` re-check (`ok` / `waived` ⇒ its line, then the READY park through the item form of `current-set` — in an N > 1 lane `ready_for_release` plus `lane-park-notify` / `lane-readiness`; anything else writes nothing), then — the single-open-PR invariant — the open-PR park: `## Status: paused`, `pause_reason` unchanged, the run lock released, NO `current-set` and NO `picked` line for a new item (an item still `running` with an open PR instead gets its pass's ONE owned-drain spawn, or `done` `stopped` when that drain already ran); `gone` ⇒ a park for a human (`pause_reason` unchanged). RECONCILE arms no merge watcher and runs no `gate-eval`.
- **`trail-gate`** — `trail-gate <runfile>`'s line is appended verbatim; `trail-gate: PARK — …` (this run's own trail PR open, or its state unreadable), or any answer that is not `trail-gate: clear …` (fail CLOSED), ⇒ the `trail_pr_open` park (run-level `current-set`, the run lock released, no `trail-pr`). `trail-unstage <runfile>`'s line is appended verbatim.
- **`--start run`** right after PICK (`## Current` `status: running`, `pr: null`, the last `picked` line naming the item; `--start pick` reaches it by itself): the driver runs `config-suppress` and prints the `/autonomous` spawn; the RUN report answers it; the driver then prints the owned-drain spawn, and its DRAIN report starts GATE. `--start drain` prints the owned-drain spawn for a running item that already has its PR. The tail's own entry stays (back-compat): with nothing pending, a bare drain report (below) starts GATE. `--non-interactive` adds `--non-interactive-fallback` to the `/autonomous` invocation; `--notify`, `--cheap` and `--max-tokens N` (else `## Run Config`'s `max_tokens:`) pass through to it and are never written to the run file.

**`do` — a CLOSED enum** (the driver's emitter and `scripts/test-automate-next-step.sh` mirror it; no other value is ever printed):

| `do` value | Meaning | The model's next call |
|---|---|---|
| `spawn` | Spawn the named work, then report its result. `what` is one of: `"/autonomous run"` — run its `invocation` (`/autonomous --single-iteration --requirement <item>` plus the passthrough flags); `.auto_review` is already suppressed. `"owned drain"` — run its `invocation` (`/review-pr <pr> --until-mergeable --no-auto-postmortem`) inline: the pass's ONE owned drain. `"fix-now re-drain"` — ONE fix worker on the PR branch (`skills/review-heal/SKILL.md` §U3.5, the findings inside the EXTERNAL_TEXT envelope), then one full inline DRAIN (`drain_invocation`) | `/autonomous run`: `--result <the RUN report>`; `owned drain` and `fix-now re-drain`: `--result <the DRAIN report>` (below; the fix-now re-drain still takes a bare drain report too) |
| `ask` | Ask the owner. Each instruction is ONE ask-tool call | `--result {"answers": [<label>, …], "note": "<free text>"}`, or `--result {"cant_ask": true}` when the ask tool is unavailable |
| `park` | The run is parked: the park state, merge watcher, notify and run-lock release are already done (a PICK-time park arms no watcher; a park taken before the lock was acquired releases none). Stop the loop | none — the next start's RECONCILE / `--resume` takes over |
| `done` | The item's tail is finished. `status: "done"` = the Queue is resolved (`trail-pr --reason done` and the dry sweep line are written); `status: "running"` = go to the next PICK; `status: "stopped"` = stop and report (at `step: "resume"` also the owner's `choice`, or the `resume_requires_flag_non_interactive` stop; at `step: "resume"` / `"rebuild"` / `"pick"` the `coordinator_run` stop) | `running`: `--start pick`; `stopped` with `choice: "start_new"`: intake for a new run |

**Common fields:** `do`, `step` (the driver step that printed it — one of the driver's `case` arms: `resume`, `rebuild`, `resume-continue`, `pick`, `lane-guard`, `ceiling`, `meta-push`, `pending`, `reconcile`, `reconcile-status`, `trail-gate`, `trail-unstage`, `picked`, `run`, `run-result`, `run-record`, `rate-limit`, `drain`, `drain-result`, `superseded`, `awaiting-go`, `learning-emit`, `gate`, `validation`, `gate-eval`, `dismissed`, `decide`, `fix-now`, `park`, `sync`, `leftover`, `checkoff`, `terminate`), `run_id`, `item`, `pr`. The resume entry's instructions add `run_file` (the run every later call names).
- **`spawn` also carries:** `what` (above), `invocation` (`/autonomous run`, `owned drain`) or `drain_invocation` (`fix-now re-drain`), `then` (what to report back). `/autonomous run` adds `config_backup`; `owned drain` adds `head_sha` (the PR head read when the spawn was printed, or `null`); `fix-now re-drain` adds `agent`, `branch`, `contract` and `findings`.
- **`ask` also carries:** `gate` (the `docs/LANE_GATES.md` catalog code: `AUT-RESUME`, `AUT-PENDING`, `AUT-WAIVE`, `AUT-DISMISS`, `AUT-SUMMARY`, `AUT-LEFTOVER`), `question`, `header`, `options`, `cant_ask` and `questions` (≤4 entries, each `{question, header, options, option_notes?, draft?}`). The top-level `question`/`header`/`options` mirror `questions[0]`. `header` is the catalog code only for an `allowed` gate (`AUT-RESUME`, `AUT-SUMMARY`). It is `""` for a human-only gate (`AUT-PENDING`, `AUT-WAIVE`, `AUT-DISMISS`, `AUT-LEFTOVER`), never a code. `options` are the catalog labels (an `AUT-RESUME` answer may carry the ` (Recommended)` marker). `cant_ask` names the outcome the driver takes on `{"cant_ask": true}`: the same branch `--non-interactive` takes (`automate: resume_requires_flag_non_interactive stop (nothing written)` / `resume_ambiguous park`; the drafts stay undecided at PICK; `escalated (escalation_cause: validation_unrun)`; `pending_decisions recorded …`; `closeout_leftover park`). A summary draft is always asked in a call of its own.
- **`park` also carries:** `status: "paused"`, `pause_reason` (read back from `## Current`), `escalation_cause` when one is set, `pending_decisions` when this item produced drafts (a number, or the string `"unknown"`), and `message`.
- **`done` also carries:** `status` (`done` | `running` | `stopped`) and `remaining` (`done` / `running`), or `message` (`stopped`; at `step: "resume"` also `choice` — `start_new` | `archive` — or `stop: "resume_requires_flag_non_interactive"`, plus `run_file` and `closeout_others`, the start's record lines and leftover rows; at `step: "resume"` / `"rebuild"` / `"pick"` `stop: "coordinator_run"` with `parallel` — the run's `## Run Config` carries `- parallel: N`, a `--parallel` coordinator run, which continues through `skills/automate-loop/lanes.md`'s per-wave loop (single-lane mode for N = 1), never through the per-item PICK; printed before any lock or write, nothing written — not the run file, and on a fresh entry not the sidecar). `stopped` means the driver recorded what it could and nothing deterministic remains: `/autonomous` produced no PR (the pinned no-PR line is written; nothing to drain), or a drain ended without a terminal `REVIEW_HEAL_RESULT` while its PR does not read `merged` (nothing is written for the drain; the item stays `running` and the next start's RECONCILE decides). The run lock is released; the loop stops and reports.

**`--result` shapes.**
- **RUN report** (the `/autonomous run` spawn's answer — also for a failed run): `supervisor_result` (the verbatim `SUPERVISOR_RESULT` text) or `supervisor_result_file` (a path holding it; exclusive with the inline form), `session_id` (`.supervisor/state.md`'s `- session_id:`; read from that file when the report omits it), `run_note` (one line: the parenthetical of the `ran /autonomous → PR` line). The PR and branch are read from the `SUPERVISOR_RESULT` text's top-level `pr_url` / `branch`; optional `pr_url` / `branch` fields only fill a gap and must agree with it. A report with a PR must carry the text and a branch. Without a PR: `status_reason` (the `AUTONOMOUS_RUN` `status_reason` token, bare; `unknown` when omitted) and `no_pr_why` (required, one line). A malformed field — a multi-line value, a non-PR URL, a disagreeing `pr_url`, an unreadable file — exits 2 with nothing written. The driver then restores `.auto_review` (`config-restore`; `auto_review_original` was read with `config-orig <config> <backup>` right after the suppress), writes `<ts> auto_review restored (config-restore: original <true|false|absent>)`, `<ts> session_id <id> (<item>)`, `current-set … --pr <url> --branch <b>` BEFORE `<ts> ran /autonomous → PR <url>[ (<run_note>)]` (or `<ts> ran /autonomous — no PR: <status_reason> (<no_pr_why>)`), writes the text verbatim to `<run_id>.supervisor-result.md` and runs `sidecar-check` on it (only a `fail …` line is appended, as `<ts> sidecar-check: fail …`), then checks the rate-limit park and prints the owned-drain spawn.
- **DRAIN report** (the `owned drain` spawn's answer, and the `fix-now re-drain` spawn's): exactly one of `review_heal_result` (the verbatim terminal `REVIEW_HEAL_RESULT` text), `review_heal_result_file` (a path holding it) or `no_terminal_block: true` (the drain ended without one). The block's top-level `decision` must be `READY` or `ESCALATED`; its `termination_reason`, `rounds`, `fix_cycles`, `repeat_check_failure` and `unresolved_bot_feedback` are read from it. Optional: `head_sha` (the head the drain started on — else the head read when the spawn was printed, else `unknown`), `started_at` (ISO-8601 Z — else the time the spawn was printed), `ready_sha` (hex — GATE's `ready_sha`), `progress_notes` (≤ 20 one-line strings, each written `<ts> <note>` — e.g. `drain round 1: …`), `drain_note` (one line: the terminal line's parenthetical), and the drain report's `progress_note` / `items_processed` / `escalation_*` / `pr` under their own rules. A malformed field exits 2 with nothing written. The driver writes `<started_at> owned drain started — <invocation> @ <head>` (`owned drain started (fix-now re-drain) — …` for the re-drain; skipped when this drain's start line is already the last drain line), the notes, the terminal line — `<ts> drain <decision> (<drain_note>)`, or without a note the pinned `<ts> drain <decision> (<termination_reason>, <n> rounds, <k> fix cycles)`; a re-drain always writes the pinned `<ts> fix-now re-drain <decision> (<termination_reason>, <n> rounds, <k> fix cycles)` that `dismissed-cost` reads — then `owned_drain_started: <start ts> | owned_drain_result: <decision> | suppressed_default_dispatch: true` in `## Current`, after a re-drain `pending_decisions: <dismissed-pending> | fix_now_reentered: true` (when the line exists), the text verbatim to `<run_id>.review-heal-result.md` + its `sidecar-check`, then `learning-emit` (`--self-heal-rounds` from the supervisor-result sidecar's `heal_iterations`: N, `null` ⇒ 0, no line ⇒ omitted; the one `gh pr view … files` fetch, degraded to `[]`/0 on failure) and GATE with `drain_result` = the block's `decision`. `no_terminal_block` ⇒ `reconcile-item <pr>`: `merged` ⇒ `owned_drain_result: superseded_by_merge` (the pass's start kept), `<ts> drain superseded_by_merge — PR merged before a terminal REVIEW_HEAL_RESULT`, NO review-heal sidecar, NO learning-emit, NO GATE, `closeout <rf> <item> <pr> --session-id <sid>` through `closeout-classify` (leftovers ⇒ the leftover gate), then `## Status: paused` + `pause_reason: awaiting_go` + run-lock release and a `park`; any other verdict writes nothing and prints `done` `stopped`.
- **Drain report** (the tail's entry point, and the fix-now re-drain `spawn`'s legacy answer): `drain_result` (required, exactly `READY` or `ESCALATED`: `ESCALATED` routes to the escalated park, `READY` to the validation gate; any other value — `died`, `superseded_by_merge`, a lowercase or misspelt value — exits 2 with nothing written, never the READY path; `gate-eval` condition 1 stays the second line of defence), `termination_reason`, `ready_sha` (hex, 7–40), and for an `ESCALATED` drain `escalation_cause` (the enum above) / `escalation_check` / `escalation_run_id` / `escalation_attempt` (integers: an attempt 1–9 digits, a run id 1–20) / `escalation_sha` (hex). These default to the review-heal sidecar's `escalation_*` fields (a malformed sidecar value is dropped), and to `other` when it has none. Two optional fields: `items_processed` (a non-negative integer of 1–9 digits — a count `terminate` can compare; a count it cannot compare reads as over the limit, the `limit_reached` park; overrides the processed count `terminate` derives from the merged `- [x]` Queue rows) and **`progress_note`** (one line). A malformed field exits 2 with nothing written. One more optional field, **`pr`**, binds the report to its PR: a value other than `## Current`'s PR exits 2 with nothing written. A drain report starts a tail only while `## Current` reads `status: running`; after a terminal park a different report exits 2 with nothing written (the byte-identical one is a replay, below). The re-drain report answering a `spawn` replaces the first report entirely; the first report re-sent there (the same report key, carrying a `ready_sha` / `escalation_sha`) is a replay — the pending `spawn` re-prints and nothing is written. A tail's report outlives its tail as stale: re-sent while `## Current` names the next item (without a `pr` naming that item's PR) it exits 2 with nothing written, at a fresh entry and as a `spawn`'s answer alike. A report with no sha cannot be told from a replay and is taken (honest limit — `pr` binds it).
- **`progress_note`**: a model-authored free-text `## Progress` line, written as `<ts> <progress_note>` in place of the driver's own park line (e.g. `owned drain ESCALATED (pause_reason: escalated) — required check ci cannot execute (runner starvation); merge watcher armed`). It is the one channel for prose the driver cannot derive at a park. Because it is written at a line's start, a `progress_note` — and a DRAIN report's `progress_notes` entry — that begins (after leading blanks, compared case-insensitively) with a line the driver or a helper itself keys on — the driver's own lines and the `## Progress` readers' `^`-anchored prefixes (progress-append's `current_not_set` guard, validation-gate's waiver count, the dismissed-findings anchors, the `/lanes` step classifier and token line, `phase-timing.sh`, `read-token-ledger.sh`): `picked`, `parked`, `ran /autonomous`, `/autonomous done`, `owned drain started`, `drain READY`, `drain ESCALATED`, `drain superseded_by_merge`, `fix-now re-drain`, `re-drain`, `auto_review`, `session_id`, `rate-limited`, `rate-limit check:`, `validation-gate:`, `validation waived:`, `dismissed`, `owner decisions`, `sidecar-check:`, `gate-eval:`, `checked off`, `limit_reached`, `sweep (dry run)`, `closeout`, `fleet closeout:`, `auto-finalized`, `trail-pr`, `trail-gate`, `trail-unstage`, `lane park notify`, `converted`, `merged`, `supervisor:`, `launch-pad`, `launch pad`, `launchpad`, `finalize:`, `phase 4.5 iter`, `run started`, `run created`, `run-lock acquired`, `meta-entry`, `skipped AUT-QUEUE`, `run_lock_held`, `run_lock_degraded`, `refuse: live_lane`, `PARK: token_ceiling`, `PARK: ledger_unreadable`, `meta-push`, `reconcile-status:`, `current_rebuilt`, `cross-run closeout`, `drain_died`, `merge-watch noted` (the driver's `NS_RESERVED_PREFIXES`; `drain ` alone is not reserved — the `drain round N: …` notes are that prefix by design; `scripts/test-automate-next-step.sh` R12 fails when a reader's `^`-anchored prefix is missing from the list) — exits 2 with `next-step: --result: reserved_prefix — …` and nothing written: it would forge that record (a second owned drain, an owner's waiver); the same words later in the line are a note. at RUN and DRAIN the same role is played by `run_note`, `progress_notes` and `drain_note` (the model-authored parts of the recorded `ran /autonomous → PR <url> (…)`, `drain round N: …` and `drain READY (…)` lines) and by `no_pr_why`. Everything else the driver writes is a pinned line, byte for byte — at PICK / RECONCILE the helpers' own lines verbatim (`trail-gate: …`, `trail-unstage: …`, `validation-gate: …`, `reconcile-status: would stamp <file> (<status>)`, `closeout`'s and `current-rebuild`'s own appends) and `<ts> picked <item>`, `<ts> refuse: live_lane …`, `<ts> PARK: …`, `<ts> run_lock_held …`, `<ts> trail-pr: …` (a skip / abandon), `<ts> cross-run closeout …`, `<ts> meta-push-failed: …`, `<ts> drain_died — …`, `<ts> merge-watch noted: live pid=<p> watching <pr> — no second watcher armed` (once per live watcher of the in-flight PR at the open-PR park); at RUN / DRAIN `<ts> auto_review suppressed (backup <run_id>.config-backup.json) — running /autonomous --single-iteration`, `<ts> rate-limited — parking, resume once the window clears`, `<ts> rate-limit check: skipped — no session id` / `<ts> rate-limit check: skipped — no session log .supervisor/logs/<sid>.jsonl` and the lines named in the two bullets above; at the tail: `<ts> parked awaiting_merge <pr> — <n> dismissed decision(s) pending`, `<ts> gate-eval: MERGE`, `dismissed-drafts`' own summary line, `<ts> dismissed decisions asked after the park — <gate line>`, the decision-batch line, `<ts> closeout leftover: <run_id> <step> <detail>`, `<ts> checked off <item> — merged <pr>; remaining: <n>`, `<ts> limit_reached — <n> item(s) processed; remaining: <m>`, `<ts> sweep (dry run): <summary>`.
- **Answers** to an `ask`: `answers` holds one label per question, in order (`answer` for a single question). `note` is the free-text note: AUT-WAIVE's waiver words, passed verbatim to `validation-gate --waive`. A label that is not one of that question's options, or the wrong number of answers, exits 2 with nothing written.

**Idempotency.** The driver keeps the instruction it last printed, verbatim, in the gitignored sidecar `.supervisor/automate/<run_id>.next-step.json`, together with the step it waits on and the tail's context. A call with no `--result` while an instruction is pending re-prints it byte for byte and writes nothing. A replayed drain report (the same report for the same item and PR, sent again after a terminal `park` / `done`) also re-prints that instruction and writes nothing. `--session-id` is the loop's session id: SYNC's `closeout` re-enters the PICK's run lock with it, and the post-park lock windows acquire with it. `--non-interactive`, `--trust-unprotected`, `--mode`, `--session-id` and `--root` persist in the sidecar for the rest of the item's tail: a later call without them keeps them (a no-result retry of a failed step never turns interactive), an explicit one still applies, and the first call of each item's tail passes them again. The sidecar is bound to the item and PR its tail started for: when `## Current` names another item or PR (the owner left at a post-park ask, the PR merged, the next PICK set a new item running) its pending instruction, context and flags are discarded and the call is a fresh entry — a drain report starts the new item's tail at `gate`, anything else exits 2 with nothing written. Other state is read back from the run file: `## Current`, `## Run Config`, and the tail segment of `## Progress` after the last drain line (so a `validation-gate: none|ok|waived` line already there is not re-appended). `<run_id>.gate-ctx.json` is the ctx handed to `gate-eval`. It carries exactly the six loop-owned keys of §10's ctx shape, never a gate-owned key.

**One RUN, one owned drain per pass.** `--start run` while its `/autonomous` spawn is pending re-prints it; while any other instruction of the item's pass is open it exits 2 (`next-step: run_already_started — …`). A RUN or DRAIN report re-sent after the step it answered (the same item and PR, a byte-identical report) is a replay: it re-prints and writes nothing. A RUN report re-prints while the instruction its step printed — the owned-drain spawn, the rate-limit park, a no-PR `done` `stopped` — is still the pending one; the latest DRAIN report re-prints while an ask of its tail, or the tail's `park` / `done`, is pending. Any other report with nothing to answer exits 2 (a RUN report once the drain's report has moved the pass on, an earlier drain's report after the fix-now re-drain's). A request for another owned-drain spawn in the same pass — `--start drain` before the drain's report arrived, or after it — exits 2 with `next-step: drain_already_owned — …` on stderr, prints nothing, and leaves the run file and every sidecar byte-unchanged; a pass is the item, its PR and its last `picked` line, and the record is both the sidecar and the run file (a first-drain `owned drain started` line in the item's segment). The one sanctioned second drain is the fix-now re-drain, offered at most once per item (`fix_now_reentered`). `config-suppress`'s exit 2 on a malformed `.supervisor/config.json` exits 2 with `next-step: config_malformed — …` before the `/autonomous` spawn: no line, `config.json` byte-unchanged, no `<run_id>.config-backup.json`. `--start run` needs the loop's `--session-id`, because the rate-limit park at the end of RUN reads that session's log: without one it exits 2 with `next-step: session_id_missing — …`, a value that is not a session id with `session_id_malformed`, nothing written either way. A rate-limit check that still cannot read its log (no session id at the step, or no `.supervisor/logs/<sid>.jsonl`) writes the one pinned `rate-limit check: skipped — …` line and never reads as clean. An existing backup at `--start run` is a crash-stranded one (RECONCILE's crash-restore, `skills/automate-loop/` §4, restores it) and exits 2 with `config_backup_stranded`. The restore runs when the RUN report arrives and before the owned-drain spawn is printed, never at DRAIN. A retried step never appends one of its lines twice: each write it already made is recorded in the sidecar.

**Writers and failures.** The run file is written only through `automate-helpers.sh` `runfile-write` / `progress-append` / `current-set` / `current-escalation` / `queue-checkoff`, plus the helpers that write it themselves (`dismissed-decide`, `validation-gate --waive`, `closeout`, `closeout-classify --record`). A non-zero writer exit is surfaced: stderr names it, no instruction is printed, the exit code is non-zero (1, or the helper's own — `progress-append`'s 3), and the next call retries that step. Exit 2 means a usage error, a `--result` that does not answer what is pending, a malformed / out-of-state drain report, or a named refusal (`session_id_missing`, `pick_already_started`, `run_done`, `run_not_incomplete`, …) — nothing written. `current-set` runs BEFORE the `picked` line; the reverse order would trip `progress-append`'s exit 3 `current_not_set`, which is surfaced like any writer exit, never swallowed.

**Side effects and test seams.** The merge-watcher launch, the notify and `run-lock.sh` run through `NEXT_STEP_WATCH_CMD` / `NEXT_STEP_NOTIFY_CMD` / `NEXT_STEP_LOCK_CMD` (the defaults are the §6 detached `automate-merge-watch.sh` launch, which unsets the host session identity itself, a desktop notification or a lane's `lane-park-notify`, and `run-lock.sh`). Tests point them at recorders. The drain spawn's head read and learning-emit's one files fetch go through `gh` (`LOOMWRIGHT_GH_BIN` overrides it, as in every helper); tests stub it on `PATH`. Tests alone set `NEXT_STEP_FROM=<step>` / `NEXT_STEP_UNTIL=<step>` (start or stop at a step — a `--result` given with `NEXT_STEP_FROM` is read as the report that step consumes: a RUN report at `run-result` / `run-record` / `rate-limit`, a DRAIN report at `drain-result` / `superseded` / `learning-emit`, a drain report elsewhere) and `NEXT_STEP_CLOSEOUT_OUT=<file>` (closeout's output as fixed input — SYNC's and RECONCILE's). These seams let a golden case that begins or ends mid-loop run through the same steps.

**Shapes the driver reproduces from the recorded runs (honest notes).**
- A lane run's `dismissed-drafts` summary line carries a leading `<ts>`; a sequential run appends it verbatim. A lane is a checkout with `.supervisor/lane.json`, `lane-park`'s own criterion.
- An `--auto-merge` fail-closed park's line is `<ts> parked awaiting_merge <pr> — gate-eval PARK: <reason>`, with `; <n> dismissed decision(s) pending` appended only when drafts are pending. The `PARK:` line is not appended on its own.
- At a park-first READY park with no undecided draft, `park-ask-gate` is not called: there is nothing to ask.
- The default notifier is desktop-only, because no webhook gate type is defined for a sequential park.
- `sidecar-check: ok …` is never appended (the recorded runs' `ok` lines were the model's); only a `fail …` line is.
- The drain's start line is written when its DRAIN report arrives, stamped with the time the spawn was printed (or the report's `started_at`); the drain's free-text lines are stamped on arrival. A crash mid-drain therefore leaves no start line in `## Progress`. The sidecar's pending spawn (and its `drain_already_owned` record) is the evidence.
- The driver does not check a `REVIEW_HEAL_RESULT` / `SUPERVISOR_RESULT` text's `pr_url` against `## Current`'s PR. `gate-eval`'s condition-1 cross-check reads the review-heal sidecar back.
