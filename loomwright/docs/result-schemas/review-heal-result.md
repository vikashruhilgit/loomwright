## REVIEW_HEAL_RESULT

Produced by the standalone PR **review-and-heal** loop — emitted once at the end of the bounded review→fix→re-review cycle. The loop is the conceptual extraction of Supervisor **Phase 4.5** into a fresh, PR-URL-keyed session (no Supervisor job, no `.supervisor/state.md`). The **inline** `/review-pr` session has no worktree fan-out (it operates on the main thread's checkout); the **detached dispatched** until-mergeable drain runs in its own dispatcher-created sibling worktree (so it never shares a working tree with an inline Phase 4.5 self-heal). Its canonical names and field list are coined in `skills/review-heal/SKILL.md` (the single source of truth) and consumed verbatim here.

**Added in v14.16.0 (schema_version 1); extended to schema_version 2 in v14.30.0** for the opt-in `--until-mergeable` drain mode (which adds the `READY` decision + the drain/postmortem fields below). The block reports the *outcome of the loop*; it does **not** redefine review output. Each review iteration reuses the existing **`CODE_REVIEW_RESULT` schema (v3, `review_mode: diff_review`)** verbatim — the review-and-heal loop consumes `CODE_REVIEW_RESULT` and never re-coins it.

**Fix 7 (heal-only drain + earned fallback) required NO schema change here — stays `schema_version: 2`, no bump.** The drain becoming heal-only by default, and its one exception — the earned fallback, `no_review_lens_posted` (§"Earned Fallback Review", `skills/review-heal/SKILL.md`) — introduces no new `REVIEW_HEAL_RESULT` field. The fallback's one bounded `code-reviewer` diff review (when triggered) feeds its findings into the SAME round's existing §U3.5 Validate-Then-Fix counters (`findings_validated`, `findings_dismissed`, `issues_fixed`, `remaining_issues`) exactly like any other channel's `bot_findings` — no separate fix mechanism, no separate result field, no separate push path. `fallback_review_ran` is internal run-scoped loop state (a spawn-once guard), never emitted on the result block. **`CODE_REVIEW_RESULT` (v3) is unaffected by Fix 7** — the fallback's diff review IS a normal `review_mode: diff_review` CODE_REVIEW_RESULT emission, consumed verbatim exactly as every other review-and-heal iteration already does; no field, enum, or validation rule changed.

**red-team-hardening item 01 (untrusted-text envelope) required NO schema change here — stays `schema_version: 2`, no bump.** Adds ONE new OPTIONAL/additive field, `rejected_instruction_like` (int) — the count of `EXTERNAL_TEXT`-enveloped bodies that asked the agent to run/fetch/install/change permissions/act outside the PR branch and were therefore REJECTED before validate-then-fix ever saw them (`skills/review-heal/SKILL.md` §"Untrusted-Text Envelope"). Present only under `--until-mergeable` (the only mode that reads external channels at all); a block omitting it (a legacy artifact, or a default-loop v1 block, which never carries it) remains valid — same additive precedent as `channels_scanned`/`findings_validated`/etc. above.

**Schema versions (v1 still accepted):**
- **`schema_version: 1`** — the **default diff-only** review→fix→re-review loop (`/review-pr <pr-url>` **without** `--until-mergeable`). Seven fields; `decision` is exactly `PASS | ESCALATED`. **v1 is still accepted** for legacy artifacts and for every default-loop / auto-chained caller (this follows the same v1-accepted precedent as CODE_REVIEW_RESULT v2, WORKER_RESULT v1, and AUTONOMOUS_RUN v1 elsewhere in this file).
- **`schema_version: 2`** — emitted **only** under `--until-mergeable` (the opt-in drain loop, `skills/review-heal/SKILL.md` §"Until-Mergeable Mode"). Adds **`READY`** to the `decision` enum and the drain/postmortem fields documented below. Because `READY` and the drain fields appear **only** under `--until-mergeable`, every non-`--until-mergeable` caller — the default `/review-pr` loop, the plain-`/supervisor` completion-tail auto-dispatch, and the `/autonomous` EVALUATE step — continues to emit `schema_version: 1` with `decision` ∈ `{PASS, ESCALATED}` unchanged. **The all-channel drain and the drain-bounding-earned-checks change together add OPTIONAL/additive v2 fields — `channels_scanned`, `findings_validated`, `findings_dismissed`, `checks_waited`, `termination_reason`, `severity_floor`, `sub_floor_fixed`, `rejected_instruction_like` (red-team-hardening item 01), and — dismissed-findings-01 — `dismissed` — with NO schema_version bump beyond 2:** a v2 block that omits any of them (a legacy `--until-mergeable` artifact, or a default-loop v1 block, which never carries them) remains valid; consumers MUST treat each as "unspecified" when absent.

**Emission contexts (two senses of "fresh"):**
- **`/review-pr` runner** — `loomwright:review-pr-runner`, running as the main agent of its own fresh OS process (launched by `dispatch-pr-review.sh` from the plain-`/supervisor` completion tail) or inline on the main thread via `/review-pr <pr-url>`. Emits one `REVIEW_HEAL_RESULT` at exit.
- **`/autonomous` EVALUATE Task step** — the review-heal loop body runs as a Task-spawned step with fresh isolated context (NOT a nested `claude` process and NOT a `Task` on the `-runner` agent). The EVALUATE step parses the emitted `REVIEW_HEAL_RESULT` to decide its next action.

**Schema v1 (default diff-only loop):**

```yaml
REVIEW_HEAL_RESULT:
  schema_version: 1                    # integer, required — 1 for the default diff-only loop
  decision: enum [PASS, ESCALATED]     # required — exactly these two values (no FAIL in the result block)
  iterations: int                      # required — how many review→fix→re-review cycles ran
  issues_fixed: int                    # required — count of new+BLOCKING/HIGH issues addressed by fix workers
  remaining_issues: int                # required — new+BLOCKING/HIGH issues still open at exit
  pr_url: string                       # required — the PR this run operated on
  notified: bool                       # required — true if a NEEDS_HUMAN/escalation notification was attempted
```

**Schema v2 (opt-in `--until-mergeable` drain mode — adds `READY` + drain/postmortem fields):**

```yaml
REVIEW_HEAL_RESULT:
  schema_version: 2                    # integer, required — 2 ONLY under --until-mergeable
  decision: enum [PASS, ESCALATED, READY]   # READY added in v2; emitted ONLY under --until-mergeable
  iterations: int                      # required — review→fix→re-review cycles (default-loop sense; carried for back-compat)
  issues_fixed: int                    # required — count of new+BLOCKING/HIGH issues addressed by fix workers
  remaining_issues: int                # required — new+BLOCKING/HIGH issues still open at exit
  pr_url: string                       # required — the PR this run operated on
  notified: bool                       # required — true if a notification was attempted (escalation OR "ready to merge")
  # --- drain fields (v2; present only under --until-mergeable) ---
  rounds: int                          # drain rounds actually run (the --max-rounds-bounded outer loop; mechanized via scripts/drain-rounds.sh, read from its ledger at emit time — same ledger on both entry paths)
  max_rounds: int                      # the drain hard ceiling (default 5, the ONE authoritative home for this value is the `max_rounds` default in skills/review-heal/SKILL.md §"Step U4 — The bounded drain loop"; --max-rounds N overrides)
  fix_cycles: int                      # fix→push cycles run during the drain (postmortem-gate input)
  churn_rounds: int                    # consecutive rounds whose anti-churn fingerprint set did not shrink
  repeat_check_failure: bool           # a required check that was fixed re-failed in a later round (postmortem input)
  unresolved_bot_feedback: bool        # a bot-authored thread stayed unresolved after >=1 fix cycle (postmortem input)
  postmortem_churn_threshold: int      # the fix-cycle trigger bar in effect (default 2)
  postmortem_dispatched: bool          # informational — did the churn gate trip so the tail was REQUESTED? Emitted BEFORE dispatch, so it reports the gate/dispatch-request decision, NOT postmortem completion (the best-effort dispatcher may still no-op). NEVER a gate input (AC12)
  # --- all-channel drain fields (v2, OPTIONAL/ADDITIVE; present only under --until-mergeable) ---
  channels_scanned: [string]           # OPTIONAL — which review channels were read this run (e.g. reviews, latestReviews, reviewThreads, issue_comments, check_outputs). §"All-Channel Read"
  findings_validated: int              # OPTIONAL — count of bot findings CONFIRMED by §U3.5 Validate-Then-Fix (cases 2+3: auto-fixable + confirmed-but-not-auto-fixable)
  findings_dismissed: int              # OPTIONAL — count of bot findings validated as stale/invalid/already-addressed (§U3.5 case 4); does NOT block READY, not fixed
  checks_waited: [string]              # OPTIONAL — scoped checks the loop waited on to settle before the READY test (required + review-producing). §"Wait-For-Settled-Checks"
  # --- drain-bounding fields (v2, OPTIONAL/ADDITIVE; drain-bounding-earned-checks change) ---
  termination_reason: enum [converged, bound_hit, sub_floor_converged, ci_untrusted] | null   # OPTIONAL — WHY the drain terminated where it did. `converged`: a genuine empty-yield round (all channels re-scanned, nothing found). `bound_hit`: `--max-rounds` exhausted (ESCALATED). `sub_floor_converged`: a round whose entire FIXED yield was below `--severity-floor` terminated READY without a further all-channel re-scan (still ran the SHA-bound confirming required-check pass). `ci_untrusted` (ci-trust-probe-01): the only remaining READY-blockers were required checks classified `untrusted_infra` by `scripts/ci-run-probe.sh` (ESCALATED, never READY). Absent/null on other ESCALATED paths (fail-closed channel-unknown, human-judgment findings, unreadable round ledger) — NOT every exit sets this field.
  severity_floor: enum [BLOCKING, HIGH, MEDIUM, LOW]   # OPTIONAL — the `--severity-floor` value in effect this run (default HIGH). Termination-time only; never gates whether a finding was fixed.
  sub_floor_fixed: [object]            # OPTIONAL — present only when termination_reason == sub_floor_converged; the findings FIXED (never declined — reading B) in the final, un-re-scanned round.
  # --- untrusted-text field (v2, OPTIONAL/ADDITIVE; red-team-hardening item 01) ---
  rejected_instruction_like: int       # OPTIONAL — count of EXTERNAL_TEXT-enveloped bodies rejected as instruction-like (asked the agent to run/fetch/install/change permissions/act outside the PR branch) before validate-then-fix ever saw them. skills/review-heal/SKILL.md §"Untrusted-Text Envelope"
  # --- itemised dismissed findings (v2, OPTIONAL/ADDITIVE; dismissed-findings-01, harness-port/05) ---
  dismissed: [{finding: string, reason: string, source: string, severity?: string}]   # OPTIONAL — the ITEMISED §U3.5 case-4 dismissals (findings_dismissed above is the COUNT; this is the per-item detail). "Empty ⇒ absent": when zero findings were dismissed this run, this key is OMITTED from the wire block entirely — never emitted as `dismissed: []`. `finding` is a short description of the dismissed finding; `reason` is the validation-failure basis in free-text prose (stale / invalid / already-addressed — NOT a closed enum, unlike the self-heal-side `heal_dismissed.reason` below). `source` reuses the EXACT channel spellings from §"All-Channel Read" (`skills/review-heal/SKILL.md`): `reviews | reviewThreads | issue_comments | check_outputs` (the `reviews`/`latestReviews` §U1 channels both spell as `reviews` here — they are unioned into ONE `classify(...)` call over the SAME bot-findings shape, so `source` does not distinguish them) plus `code_reviewer` for a finding sourced from the Earned Fallback Review (§"Earned Fallback Review — `no_review_lens_posted`") lens. `severity` is OPTIONAL (additive, automate-followups/12, no schema_version bump): `BLOCKING | HIGH | MEDIUM | LOW | INFO`, present on a main-pass item ONLY when the finding stated one (never invented) and always on an Earned Fallback item (a `CODE_REVIEW_RESULT` issue carries it); absent ⇒ unspecified. `INFO` is main-pass only (the raw stated text read by `stated_severity(f)`) — an Earned Fallback item carries `CODE_REVIEW_RESULT`'s closed `BLOCKING | HIGH | MEDIUM | LOW`, which has no `INFO`. Transported off the result block via the marker-comment mechanism (`skills/review-heal/SKILL.md` §"Dismissed-findings marker comment") since `REVIEW_HEAL_RESULT` itself is not persisted anywhere `/pr-postmortem` can read it.
  # --- CI trust probe (v2, OPTIONAL/ADDITIVE; ci-trust-probe-01, harness-port/07) ---
  # --- rules gate (v2, OPTIONAL/ADDITIVE; automate-followups/07) ---
  rules_gate: enum [ok, none, fail, unresolved, unstamped, cmd_disabled, unreadable]   # OPTIONAL — the LAST round's `scripts/rules-gate-verdict.sh` verdict (skills/review-heal/SKILL.md §U4 + §"READY redefinition"). Absent ⇒ unspecified.
  # --- escalation cause (v2, OPTIONAL/ADDITIVE; automate-followups/31) ---
  escalation_cause: enum [check_pending, check_red_unrelated, check_red, findings, other]   # OPTIONAL — present ONLY on `decision: ESCALATED`: WHY the drain escalated. Check-driven sites copy `automate-helpers.sh escalation-cause`'s line; findings sites set `findings`; rules-gate / round-ledger / `ci_untrusted` sites set `other`.
  escalation_check: string | null      # OPTIONAL — with escalation_cause: the named check (check-driven causes), else null.
  escalation_run_id: string | null     # OPTIONAL — with escalation_cause: that check's workflow run id, else null.
  escalation_attempt: int | null       # OPTIONAL — with escalation_cause: that run's attempt, else null.
  escalation_sha: string | null        # OPTIONAL — with escalation_cause: the head sha classified, else null.
  checks_untrusted: [{check: string, reason: string, run_id: string | null}]   # OPTIONAL — required checks THIS ROUND'S `scripts/ci-run-probe.sh` classified `untrusted_infra` (narrow, evidence-based: zero steps / no runner ever assigned / a job conclusion of `startup_failure` — a REAL, DOCUMENTED GitHub Actions enum value, NEVER a free-text name/message match or a timestamp). "Empty ⇒ absent": when zero checks were classified untrusted_infra, this key is OMITTED entirely — never emitted as `checks_untrusted: []`. `check` is the required check's name; `reason` is the probe's own short reason slug (`zero_steps` \| `no_runner_assigned` \| `startup_failure`); `run_id` is the probed workflow run id, or `null` when unavailable. NEVER dispatched to a fix worker, NEVER counted toward `findings_validated`/`findings_dismissed` — an `untrusted_infra` required check still blocks READY exactly like any other red required check (skills/review-heal/SKILL.md §"READY redefinition"). Present ONLY alongside `termination_reason: ci_untrusted` on the round where it is the sole remaining blocker; may also appear (without forcing `ci_untrusted`) on an intermediate round where other findings/checks are still being fixed.
```

**Field notes:**

| Field | Type | Schema | Notes |
|---|---|---|---|
| `schema_version` | int | both | `1` for the default diff-only loop; `2` ONLY under `--until-mergeable`. |
| `decision` | enum | both | `PASS` or `ESCALATED` in v1. v2 adds **`READY`** (drain terminal state — required checks green AND no unresolved bot-authored threads). There is **no `FAIL`** in the result block: a reviewer `FAIL` is an internal loop signal that drives a fix iteration, becoming terminal only as `ESCALATED`. **`READY` is emitted ONLY under `--until-mergeable`** and is merge-identical to `PASS`/`ESCALATED` (terminal-stop-and-notify — **never merges**, AC6). |
| `iterations` | int | both | Number of review→fix→re-review cycles run. Default-loop bound is **3** (the `--heal-iterations` analogue). **Under `--until-mergeable` (v2): `iterations == rounds`** — the drain's bounded outer-loop counter (`while rounds < max_rounds`) IS the v1 `iterations` analogue, so this back-compat field carries the same value as `rounds`. (It is therefore distinct from `fix_cycles`, the fix→push count, which is `≤ rounds`.) |

**Outcome model:**
- `PASS` (v1/v2) → clean diff; loop done; `remaining_issues: 0`. The loop **NEVER merges the PR** (no-self-trust: an automated reviewer that also merges removes the human gate). PR is left open for a human to merge.
- `READY` (**v2 only, `--until-mergeable`**) → all **required** checks green AND no unresolved **bot-authored** review threads remain; the "ready to merge" notification fired (`notified: true`). Human approval, `reviewDecision: REVIEW_REQUIRED`, and human-authored unresolved threads are explicitly **NOT** readiness blockers — the loop never waits on a human (AC3). `READY` is terminal-stop-and-notify, **merge-identical to `PASS`/`ESCALATED`** — the PR is left open for a human (no `gh pr merge` is ever invoked, AC6). **Two `termination_reason` variants (drain-bounding-earned-checks change):** `converged` (a normal empty-yield round, every channel re-scanned) or `sub_floor_converged` (a round whose entire fixed yield was below `severity_floor` skipped only the all-channel re-scan, not the confirming required-check pass — see `sub_floor_fixed`/`severity_floor` above). Both are `decision: READY`; only `sub_floor_converged` is excluded from auto-merge eligibility (AC9).
- `ESCALATED` (v1/v2) → reviewer escalated (`NEEDS_HUMAN`) **or** the loop exhausted its bound (`max_heal_iterations` in v1; `max_rounds` in v2, **mechanized** via `scripts/drain-rounds.sh` — `termination_reason: bound_hit`) with issues remaining, **or** (v2) a fail-closed condition tripped (GraphQL review-thread query errored → thread-state unknown; required-check metadata unavailable without `--required-checks all-non-neutral`; an unreadable round ledger, AC5; **or** the AC11 SHA-bound confirming required-check pass found the pushed commit's required checks red/unreadable — a `sub_floor_converged` candidate that failed to confirm degrades here instead of ever claiming `READY`), **or** (v2, ci-trust-probe-01) the only remaining READY-blockers are required checks `scripts/ci-run-probe.sh` classified `untrusted_infra` (`termination_reason: ci_untrusted`, `checks_untrusted` names each one). Findings are posted to the PR via `gh pr comment`, notifications fired best-effort, PR left open. Never auto-fixes past escalation, never merges.

**External-state detection (v2, AC8):** under `--until-mergeable` the drain reads PR state each round via `gh pr view <pr-url> --json statusCheckRollup,reviews,latestReviews,reviewDecision,mergeable,mergeStateStatus`. Two derived signals need MORE than `--json` (there is **no** `--json reviewThreads` flag):
- **Unresolved review threads + author type** are GraphQL-only — `gh api graphql` querying `reviewThreads(first:100){ pageInfo{ hasNextPage } nodes{ isResolved, comments(first:1){ nodes{ author{ login __typename } } } } }`. A thread is a READY-blocker **only** when its first comment's author is a bot (`author.__typename == "Bot"` or `author.login` matching `*[bot]`, AC15); human/unknown-author threads are surfaced but never block. **Fail-safe (R1):** a GraphQL error → thread-state "unknown" → the loop **MUST NOT** claim READY → exits `ESCALATED`. **Truncation is fail-CLOSED too:** the query caps at 100 threads and is not paginated, so `reviewThreads.pageInfo.hasNextPage == true` (a >100-thread PR) is treated as unknown thread-state → `ESCALATED` (a truncated read must never become a false READY). Full pagination is a deliberate non-goal; escalating on the rare >100-thread PR keeps the fail-CLOSED contract consistent.
- **Which checks are required** comes from branch-protection metadata (`gh api repos/{owner}/{repo}/branches/{base}/protection/required_status_checks`, or GraphQL `baseRef.branchProtectionRule.requiredStatusCheckContexts`); READY gates on the discovered required contexts only (optional/non-required failing checks never block). **Fail CLOSED (AC14):** if required-check metadata is unavailable (insufficient permissions, no branch protection, API error) the loop MUST NOT claim READY — it exits `ESCALATED`, UNLESS `--required-checks all-non-neutral` is explicitly set (the only way to proceed without metadata; treats every non-`NEUTRAL`/`SKIPPED` check as blocking). `mergeStateStatus`/`mergeable` are corroborating only — never the sole READY/ESCALATED basis.

**Postmortem dispatch is read-only / append-only (v2, AC12):** the churn-gated postmortem tail runs **only after** the loop's `decision` is computed and `REVIEW_HEAL_RESULT` is emitted — it reads the decision as an input and can **NEVER** change it. `/pr-postmortem` is read-only on the analyzed repo and only **appends** one JSONL line to `.supervisor/postmortem/results.jsonl` (it mutates no repo file). The dispatcher (`scripts/dispatch-pr-postmortem.sh`) is fire-and-forget and `exit 0` on every path, so a dispatcher/gather/append failure leaves `REVIEW_HEAL_RESULT.decision` unchanged and the merge-ready result identical to a successful-postmortem run. `postmortem_dispatched` is **informational, never a gate input**.
