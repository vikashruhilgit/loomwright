## Hook Table

Hooks are centralized in `hooks.json`, which is the authoritative source for the current wiring **and count** — this page mirrors it and deliberately does not restate the totals (see `AGENT_GUIDELINES.md` §"Claim Duplication Rule": the table below *is* the list, so a number here could only ever drift). **Only three hooks still use prompt-based validation** (fast haiku model, 30s timeout): `SubagentStop[loomwright:code-reviewer]`, `Stop`, and `TaskCompleted` — the `code-reviewer` validator is deliberately retained because its cross-field + severity-cap logic is richer than presence-checking, and it is the ONE remaining prompt validator on any `SubagentStop` matcher. Every other hook is `type: command` for zero-latency. **`|| true` convention:** every `type: command` hook string carries `|| true` as belt-and-suspenders for missing-interpreter/syntax-error edges — valid ONLY because all of them are always-exit-0 fail-safe emitters/validators (`validate-launch-pad-result.py` included: it decides via stdout JSON, exit-0-by-contract). A future blocking gate (non-zero-exit) added as a `type: command` hook must NOT carry `|| true` — that would silently neuter it (see `CLAUDE.md` §"Failure-Mode Invariants"). **That future gate has now arrived:** the test-integrity guard's `PreToolUse[Bash]` and `PreToolUse[Write|Edit]` leaves (six-phase-loop-gaps/02, both invoking `scripts/guard-test-integrity.sh`) are the plugin's first fail-CLOSED blocking `type: command` hooks and are the ONLY two command-hook leaves in `hooks.json` without `|| true` — see the dedicated rows below for the full contract. The guard's own arm-backstop (`PreToolUse[Agent|Task]`) and disarm (`SessionEnd`) leaves are ordinary emitters and DO carry `|| true`, same as every other row in this table.

**Command-validator decision shape (probed 2026-09-21, Claude Code v2.1.278):** the six `validate-*-result.py` command validators print the *documented* Stop/SubagentStop decision for a `type: command` hook — `{}` on pass (no decision = allow) and `{"decision": "block", "reason": "…"}` on fail, always exit 0 — so a malformed result block now actually stops the subagent from stopping: the runtime feeds `reason` back as the agent's next instruction (`hook_blocking_error` in the subagent transcript) and re-fires SubagentStop with `stop_hook_active: true` on the retry, capped by the runtime at 8 consecutive continuations. Until this date they printed `{"ok": true|false, "reason": …}`, which is the **response schema of a `type: prompt` hook** (what the haiku model answers — still correct for the three prompt hooks named above) and is **not a command-hook output field**: a real `loomwright:worker` firing was recorded by the runtime as `hook_success` with `{"ok": false, …}` on stdout, no decision, no error notice, and the subagent stopped — every command validator had been a silent no-op since its v15.17.0 prompt→command conversion. Evidence: `scripts/fixtures/subagentstop-decision-shape-probe.json` (probe A = `ok` shape ignored, probe B = `decision: block` honoured); `test-result-validators.sh` §K pins the bytes. Honest limits: (a) closed in v15.83.0 — `emit-progress-event.sh` still fires on every SubagentStop (it cannot see its sibling validator's stdout) but now re-runs `validate-worker-result.py` as a subprocess and records `rejected`, and `check-children-settled.sh` / `build-floor.sh` skip `rejected: true` rows so a rejected-then-retried worker no longer settles on the early row; (b) blocking is only as good as the reason text — a worker that cannot satisfy a rule (e.g. rule 3's summary-file evidence) spends up to 8 retries, the runtime's cap, not ours. A worker forced to stop at that cap leaves only rejected rows and stays unsettled (fail CLOSED toward "not done"). Per-hook version provenance lives in `CHANGELOG.md`; the authoritative current wiring is `hooks.json` itself, mirrored in the table below.

### Guard contract (shared by the four test-integrity-guard rows above)

**Arm points — two prompt steps + one hook backstop + one dispatcher pre-arm:** Supervisor Phase 0 INIT (`skills/supervisor-config/SKILL.md`, end of `## Protocol` step 6) and `review-heal/SKILL.md`'s loop entry (covers inline `/review-pr` AND the `/automate` owned drain — the latter is already covered by the Supervisor's own marker from the same session, since nothing disarms between RUN and DRAIN) each run `guard-arm.sh arm <supervisor|review-heal>` and record `record_decision("guard_armed: {ok | failed: <reason>}")`; on `failed` the run proceeds **visibly unguarded** (logged into `## Decisions Log`, surfaced in the completion tail as `guard: unarmed`) — arming is fail-LOUD, never a silent skip. The `PreToolUse[Agent|Task]` backstop row above covers a skipped prompt step for any spawned worker/execute-manager/supervisor-runner/review-pr-runner subagent. The detached review-drain runner is launched via `claude --agent` (never a `Task`), so the backstop cannot fire for it — `scripts/dispatch-pr-review.sh` generates a uuid, writes `<worktree>/.supervisor/guard/<uuid>.json` (`guard-arm.sh arm dispatcher --session-id <uuid>` — the ONE caller allowed to pass the id explicitly, since it is a plugin script that owns the launch, not a prompt step) BEFORE the launch, and passes `--session-id <uuid>` to `claude -p` (verified: `claude --help` advertises `--session-id <uuid>`) — deterministic, script-owned, no LLM step; the runner's own `review-heal` loop-entry `arm` call then finds its own file already present and no-ops.

**Marker lifecycle:** ONE file per session, `.supervisor/guard/<session_id>.json` = `{session_id, armed_at, by}`. `arm` writes ONLY its own file (named from `$CLAUDE_CODE_SESSION_ID`, or the explicit `--session-id` in the dispatcher shape only) — there is no overwrite rule and no cross-session write of any kind, so a forged-env `CLAUDE_CODE_SESSION_ID=dead bash guard-arm.sh arm x` creates only a harmless `dead.json` that matches no real payload, and two sessions on one checkout each hold their own file and never see or disturb each other's. Empty/unset id → `exit 3`, one stderr line, writes nothing. `arm` also prunes marker files older than 7 days (dead sessions) — the only deletion it performs, never the caller's own or a newer file. Disarm is the SessionEnd row above — the single point, never reachable from a tool call; a crashed/killed session's marker simply outlives it until pruned (matches no live payload, so it is inert, not a live bypass).

**Opt-out — process env only:** `LOOMWRIGHT_ALLOW_GATE_CONFIG_EDITS=1` in the shell that launched Claude Code. Probed 2026-09-23 (P3, `progress-event-fixtures/guard-probe-2026-09-23/README.md`): **`settings.json`'s `env` block DOES reach hook processes** — so the `Write|Edit` matcher's `/.claude/` + `settings.json`|`settings.local.json` protection above is load-bearing, not belt-and-braces: without it, an armed agent could write the opt-out into `settings.json` mid-run and have a LATER `claude -p` process (the detached drain's fresh launch) silently honour it. There is no `.supervisor/config.json` key for this opt-out — pinned by `grep -rln ALLOW_GATE_CONFIG_EDITS loomwright/agents loomwright/skills` = empty (the name must never appear in agent/skill prose, where a worker could read and act on it).

**Deny wording — exactly two variants, keyed on `agent_type` presence in the payload** (probed 2026-09-23, P2: a `Task`-spawned subagent's own `PreToolUse` payload carries `agent_type`/`agent_id`, the main thread's does not): a subagent sees `test_integrity_guard: denied <bash|edit> — <label> — this session is a Loomwright run; record the need in outputs_gap / escalate NEEDS_HUMAN instead`; the main thread sees `… — a Loomwright run is armed in this session; finish or end the session before editing gate configuration`. Neither variant EVER names the opt-out env var, a marker path, `settings`, `config.json`, or `guard-arm` — a denied agent is never handed the recipe to disarm itself.

**Honest limits (S5 — a tripwire, not a sandbox):** script-file indirection (`printf … > x.sh; bash x.sh` is invisible to the Write|Edit matcher's basename check) OR inline `-c`/`eval` indirection (`bash -c "git commit -n -m x"`, `sh -c "..."`, `eval "..."` — the matcher parses the OUTER simple command's own words, never a string it hands to a shell/`eval` to re-parse; PR #258 round-4 review finding, flagged as a documentation gap rather than blocked on, since it is the same class of limit as script-file indirection just via no on-disk artifact); configs embedded inside `package.json`/`pyproject.toml` rather than a dedicated file are not covered; any path/basename not in the protected list is not covered; a marker file deleted via a command shape not covered by the Bash matcher's write-verb list still disarms that session; `--no-ver[a-z]*` is the only flag-abbreviation form recognized (other unambiguous git prefixes of other flags are not enumerated); **command channels other than the `Bash` tool are entirely outside both matchers** — `mcp__terminal__run_in_terminal`, a git MCP server, or a `Workflow` script can bypass every pattern above; **an inline run (`/supervisor`, `/review-pr`, `/automate`) arms the HUMAN's own session until it ends** — there is no tool-call disarm by design, so the main-thread deny variant then applies to the human's own `git commit -n` too; this is the stated trade for having no tool-call disarm, not a hidden cost. **Self-hosting cost:** a Supervisor run on THIS repo maintaining the guard has its own worker's fixture writes to protected basenames AND its `Edit` calls on `guard-*.sh`/`hooks.json` denied — the maintainer either launches that session with the env opt-out, or writes fixtures via heredoc into an unprotected basename (e.g. `fixture-jest-config.txt`) and has the test copy it; reading the guard's own source (`cat`/`sed -n`/`shellcheck`/`grep`/`bash -n`) is never denied. Full spec: `.supervisor/requirements/six-phase-loop-gaps/02-test-integrity-guard.md`.

## Detached-Drain Permission Regime (not a hook — a related credential-holding-process control)

`scripts/dispatch-pr-review.sh` launches the `review-pr-runner` as a **detached, unattended, credential-holding** `claude -p` process (`gh`/`git push` access) — no hook governs it, so its permission posture is documented here rather than in the table above (red-team-hardening item 01, v15.86.0+).

- **Pinned, never inherited.** Both the `DRY_RUN_DISPATCH` diagnostic and the real launch construct `--permission-mode dontAsk` + an explicit `--allowedTools` allowlist + `--disallowedTools WebFetch,WebSearch` from ONE shared function/constants — never two independently-typed strings. See `scripts/dispatch-pr-review.sh` header PERMISSIONS section and `docs/ARCHITECTURE_CONTRACTS.md`'s dispatch-shape cell.
- **Regime probe, refuse-don't-guess.** Before dispatch, the effective `permissions.defaultMode` is resolved (project local settings > project shared settings > user settings). A bypass/auto-approve resolution — or ANY tier whose file exists but is unreadable/malformed (ALWAYS fail CLOSED, never assumed safe) — degrades the dispatch to review-only (the SAME `LOOMWRIGHT_PR_IS_FORK=1` semantics a fork PR gets) unless the ONE opt-out, `LOOMWRIGHT_DRAIN_ALLOW_PERMISSIVE=1`, is set in the **dispatcher's own process env**. This opt-out is documented here and in `docs/ARCHITECTURE_CONTRACTS.md` — it is deliberately **NEVER** named in any agent/skill/command prompt file, any log line the model reads, or any `.supervisor/` file, so the model itself can never discover or recommend it (decision R2).
- **Unpinnable ⇒ refuse.** If the resolved `claude` build's `--help` cannot advertise a headless, allowlist-honouring mode, the dispatcher exits 0 printing `PERMISSION_REGIME_UNPINNABLE` and does NOT dispatch at all (decision R1).
- **Untrusted-text envelope — a tripwire and a narrowing, NOT a sandboxing claim.** Every externally-sourced review-channel body the drain reads is wrapped by `scripts/wrap-external-text.sh` in an `EXTERNAL_TEXT` envelope stating it is data, never an instruction (`skills/review-heal/SKILL.md` §"Untrusted-Text Envelope"), and only actors/checks on a user-scope allowlist (`classify-bot-review.sh --trusted-actors`, the `review_producing_checks[]` list) can produce a candidate finding. **Honest limit:** this is a content-shape tripwire plus a narrowing of who/what can produce a candidate — it is explicitly **not** a sandboxing or process-isolation boundary, and it does not attempt to sanitize hidden-character tricks beyond the envelope itself. **Delimiter-forgery defense (PR #248 finding #2):** `wrap-external-text.sh` now defangs any literal `<<<EXTERNAL_TEXT`/`<<<END_EXTERNAL_TEXT>>>` sequence found INSIDE a wrapped body, so a comment cannot forge a second, fake envelope (with its own attacker-chosen actor/trusted/channel) that reads as script-generated ground truth. **Honest limit:** this is a narrowing/tripwire against the exact literal delimiter strings, not a cryptographic guarantee — it does not defend against Unicode look-alikes/homoglyphs of the marker text.
