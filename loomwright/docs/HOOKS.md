## Hook Table

Hooks are centralized in `hooks.json`, which is the authoritative source for the current wiring **and count** — this page mirrors it and deliberately does not restate the totals (see `AGENT_GUIDELINES.md` §"Claim Duplication Rule": the table below *is* the list, so a number here could only ever drift). **Only one hook still uses prompt-based validation** (fast haiku model, 30s timeout): `TaskCompleted`. No `SubagentStop` matcher carries a prompt validator any more: the last one, `code-reviewer`, became the command script `validate-code-review-result.py` once a live probe (2026-09-27) showed its model never saw the block it was judging — see the code-reviewer row below. Every other hook is `type: command` for zero-latency. **`|| true` convention:** every `type: command` hook string carries `|| true` as belt-and-suspenders for missing-interpreter/syntax-error edges — valid ONLY because all of them are always-exit-0 fail-safe emitters/validators (`validate-launch-pad-result.py` included: it decides via stdout JSON, exit-0-by-contract). A future blocking gate (non-zero-exit) added as a `type: command` hook must NOT carry `|| true` — that would silently neuter it (see `CLAUDE.md` §"Failure-Mode Invariants"). **That future gate has now arrived:** the test-integrity guard's `PreToolUse[Bash]` and `PreToolUse[Write|Edit]` leaves (six-phase-loop-gaps/02, both invoking `scripts/guard-test-integrity.sh`) are the plugin's first fail-CLOSED blocking `type: command` hooks and carry no `|| true`; the finalize-publish guard's `PreToolUse[Bash]` leaf (`scripts/guard-finalize-publish.sh`, automate-followups/33) is the other fail-CLOSED leaf without it — see the dedicated rows below for each contract (`hooks.json` is the authority for which leaves those are). The guard's own arm-backstop (`PreToolUse[Agent|Task]`) and disarm (`SessionEnd`) leaves are ordinary emitters and DO carry `|| true`, same as every other row in this table.

**Command-validator decision shape (probed 2026-09-21, Claude Code v2.1.278):** the `validate-*-result.py` command validators print the *documented* Stop/SubagentStop decision for a `type: command` hook — `{}` on pass (no decision = allow) and `{"decision": "block", "reason": "…"}` on fail, always exit 0 — so a malformed result block now actually stops the subagent from stopping: the runtime feeds `reason` back as the agent's next instruction (`hook_blocking_error` in the subagent transcript) and re-fires SubagentStop with `stop_hook_active: true` on the retry, capped by the runtime at 8 consecutive continuations. Until this date they printed `{"ok": true|false, "reason": …}`, which is the **response schema of a `type: prompt` hook** (what the haiku model answers — still correct for the one prompt hook named above) and is **not a command-hook output field**: a real `loomwright:worker` firing was recorded by the runtime as `hook_success` with `{"ok": false, …}` on stdout, no decision, no error notice, and the subagent stopped — every command validator had been a silent no-op since its v15.17.0 prompt→command conversion. Evidence: `scripts/fixtures/subagentstop-decision-shape-probe.json` (probe A = `ok` shape ignored, probe B = `decision: block` honoured); `test-result-validators.sh` §K pins the bytes. Honest limits: (a) closed in v15.83.0 — `emit-progress-event.sh` still fires on every SubagentStop (it cannot see its sibling validator's stdout) but now re-runs `validate-worker-result.py` as a subprocess and records `rejected`, and `check-children-settled.sh` / `build-floor.sh` skip `rejected: true` rows so a rejected-then-retried worker no longer settles on the early row; (b) blocking is only as good as the reason text — a worker that cannot satisfy a rule (e.g. rule 3's summary-file evidence) spends up to 8 retries, the runtime's cap, not ours. A worker forced to stop at that cap leaves only rejected rows and stays unsettled (fail CLOSED toward "not done"). Per-hook version provenance lives in `CHANGELOG.md`; the authoritative current wiring is `hooks.json` itself, mirrored in the table below.

**Stop payload identity (probed 2026-09-27, Claude Code v2.1.283):** `Stop` fires at every main-thread turn end of every session, so a Stop hook must first decide whose turn is ending. The only reliable key is the payload's top-level `agent_type`: absent on a plain main thread, `loomwright:loomwright:code-reviewer` in a `claude --agent loomwright:code-reviewer` session. The payload also carries `background_tasks[]`, and each entry has its own `agent_type` and `status` (`running` while a background subagent works). That list describes the session's children, not the session. A `type: prompt` Stop hook sees the whole payload, so it judged a running background reviewer as the finishing session and blocked the main thread from yielding (observed 2026-09-27 during `/automate`). Fixture: `scripts/fixtures/stop-payload-shape-probe.json`.

**Result-text resolution — SubagentHandback (probed 2026-09-27):** current runtimes return a subagent's report through a `SubagentHandback` tool call. The full report, including its `*_RESULT` block, is that call's `input.message` in `agent_transcript_path`; the payload's `last_assistant_message` is only a short prose recap that typically NAMES the block without containing it. Every consumer that reads the result text therefore resolves it through one seam — `result_block_parser.resolve_payload_text` (every `validate-*-result.py` validator, launch-pad's and code-reviewer's included, and `emit-progress-event.sh`'s `result_block_present`), mirrored in jq by `send-webhook.sh` and in `send-telemetry-core.sh`: the inline text wins when it holds a real block HEADER line; otherwise the LAST `SubagentHandback` message wins if IT does; only the subagent-scoped `agent_transcript_path` is searched (the shared `transcript_path` is the parent's). A prose mention is not a header. Before this, a live `loomwright:worker` that had emitted a valid block was blocked with `missing WORKER_RESULT block` and re-prompted, the Supervisor webhook skipped every POST, and every worker row read `result_block_present: false`. Evidence and runnable fixture: `scripts/fixtures/subagentstop-handback-real-shape/`. This is why no `SubagentStop` matcher carries a `type: prompt` validator: its model judges the payload, not the transcript, so it never sees a handback-delivered block. In the same probe the code-reviewer prompt validator (since replaced by `validate-code-review-result.py`) rejected a valid handback-delivered block. The one remaining prompt hook, `TaskCompleted`, carries the same payload-only limit (and `Stop` stopped being one for exactly this reason; see "Stop payload identity").

## Host mode

A host that runs agent sessions in an owner's own repo (Loomwright Studio first) sets **`LOOMWRIGHT_HOST_MODE=1`**. The switch is on only when the value is exactly `1`; unset, or any other value, is off. With it on, no hook in `hooks.json` creates or modifies any path in the session's working tree, `.supervisor/` and the project-local settings file included. With it off, every hook behaves exactly as the rows above describe; those rows give the off-mode paths. Source requirement: `.supervisor/requirements/host-contract/02-host-mode-no-repo-writes.md`.

- **`LOOMWRIGHT_HOST_STATE_DIR`** is the optional destination. It counts only when it is an absolute path to an existing directory that is not inside any worktree of the repo, main or linked (judged by filesystem identity — `-ef` on each ancestor — so neither a symlink nor a case-variant spelling on a case-insensitive volume can point it back in). Unset, relative, missing, a file, or inside a worktree: treated as no state dir. Redirected state keeps the `.supervisor/` layout under it: `logs/<session>.jsonl`, `state.md`, `guard/<id>.json`, `logs/<id>.finalize-gate`.
- **No valid state dir — owner decision D1 (2026-10-09):** gate state goes to a per-user directory outside the repo, `${TMPDIR:-/tmp}/loomwright-host-<uid>/<repo-hash>/`, where `<repo-hash>` is the first 12 hex of the SHA-256 of the repo's absolute main-worktree path. `$TMPDIR` is that base only when it is absolute, an existing directory, and outside every worktree (by the same identity test); otherwise `/tmp` is. Because the root sits in a shared temp dir, the resolver creates both components itself (`umask 077`) and accepts each only as a real directory (not a symlink) owned by the current user, writable, and not group- or world-writable. Any other state makes the gate dir unresolvable: both guards then deny (`guard_unavailable`; `write-marker` refuses `gate_dir_unresolvable`) and every emitter skips.
- **Presence gate — no run, no state.** Off mode leaves a repo where the plugin is installed but never invoked untouched, because every emitter writes only into a `.supervisor/` that already exists. Host mode keeps the same rule for the D1 root: only the gate writers that start a run's state may create it — `guard-arm.sh` when it writes a marker (the `arm` step, or the `PreToolUse[Agent|Task]` backstop for a Loomwright spawn), `seed-run-owner.sh` when Context-Keeper's Write of the repo `state.md` names a live run (INIT writes it before it arms, and skipping the `.owner` seed would reopen the unknown-owner window), and `guard-finalize-publish.sh write-marker`. Every other caller resolves through `lw_gate_state_dir_existing`, which never creates: an existing, safe root is used; an existing root that fails the safety test is unresolvable, so the guards still deny; an absent root means no Loomwright run has created gate state for this repo yet, so the test-integrity guard is inert (no markers, as off mode with no `.supervisor/guard`), the finalize-publish guard still denies a publish while the repo `state.md` reads live (there is no marker), and every emitter skips. An armed session's marker lives in the root, so an armed session never reads "absent". When no entry named `loomwright-host-<uid>` exists under `$TMPDIR` or `/tmp`, a reader decides "absent" without running `git worktree list` or hashing; anything there, even a hostile entry, takes the full resolve. A valid `LOOMWRIGHT_HOST_STATE_DIR` exists by validation, so state-dir sessions are unchanged. "Gate state" means the guard markers, the finalize-gate marker, and the state those gates read: the `## Session` block of `state.md`, the plugin session log and its `.owner` seed. Every other hook write skips.
- **One resolver:** `scripts/host-mode.sh`, sourced by every hook script that writes. `lw_state_dir` resolves non-gate writes (the state dir, else skip), `lw_gate_state_dir` resolves gate state for the three gate writers (the state dir, else the D1 root, created if absent), `lw_gate_state_dir_existing` gives every reader and emitter the same answer without creating anything, and `lw_state_md_read` names the `state.md` every hook reads. A reader resolves through the same function as the writer of that state, and every caller follows one root rule: pass any worktree of the repo, and the resolver gives the same answer for all of them. `check-children-settled.sh` is not a hook, but it reads gate state, so under host mode it reads a repo-shaped `--log` (`.supervisor/logs/<id>.jsonl`, relative or under a worktree) from `<gate dir>/logs/<id>.jsonl` — resolving the gate dir against the real repo root git reports, never the prefix the log path suggests, so a valid state dir that is itself named `.supervisor` is honoured — except that an existing, readable `--log` outside every worktree of that repo is read as given (no host-mode writer puts one anywhere but the gate dir), and reports `unverifiable` when that dir cannot be resolved. When the D1 root does not exist yet it reads the log as absent, as off mode reads a missing log. The script's header is the contract; this section does not restate it.
- **Agent-written `state.md`:** host mode governs hooks only. Context-Keeper still creates the repo's `.supervisor/state.md` with the Write tool, and that repo copy decides which run is current: `lw_state_md_read` returns the gate-dir copy only when its `session_id` equals the repo copy's, or when the repo copy is absent. A gate copy left by an earlier run therefore never hides a newer repo seed. No hook writes the repo `state.md` under host mode; `build-state.sh` projects into the gate dir.
- **The fail-CLOSED gates keep enforcing.** The test-integrity guard reads its markers from `lw_gate_state_dir`, the same function `guard-arm.sh` writes them through, and its protected-path checks also cover the redirected guard dir and `host-mode.sh`, so an armed agent cannot disarm by editing either. The finalize-publish guard reads its marker and session log from the gate dir and treats the run as live when EITHER the repo `state.md` or the gate-dir copy reads `running`/`checkpoint`, taking the session id and branch from the copy that reads live (a finished copy never scopes the live run out of the gate). If `host-mode.sh` fails to load while the switch is on, both guards fail CLOSED (`guard_unavailable`), and every fail-SAFE emitter exits 0 without writing.

**Classification of every script `hooks.json` invokes**, plus the inline StopFailure leaf. `redirects`: the write goes to the resolved dir instead of the repo. `skips`: the write does not happen under host mode. `unaffected`: writes nothing in the repo in either mode. "(gate)" = gate state: the state dir, else the D1 root — written by an emitter only once that dir exists (`lw_gate_state_dir_existing`); only `guard-arm.sh`, `seed-run-owner.sh` and `write-marker` create it (`lw_gate_state_dir`). "(state dir)" = through `lw_state_dir`: the state dir, else skipped. `hooks.json` stays the authority for which leaves call which script.

**Honest limits:**

- **Hooks only.** Agent-authored writes still land in the repo: Context-Keeper's `state.md` seed, briefs, worker summaries, and any `session_end` row an agent appends itself. That agent-written `session_end` lands in the repo session log, which the host-mode projection (reading the gate-dir log) does not see.
- **The projected `## Session` block lives only in the gate dir.** Under host mode the repo `state.md` keeps Context-Keeper's seed values; a reader that opens the repo copy directly sees the seed, not the projection.
- **`/automate`'s rate-limit park does not see a host-mode stop failure.** `skills/automate-loop/SKILL.md` §6 (Rate-limit park) reads the repo `.supervisor/logs/failures.log`; under host mode the `STOP_FAILURE` line goes to the state dir, or nowhere under D1.
- **Without a state dir, non-gate observability is gone by design (D1):** `failures.log`, `notifications.log`, `telemetry.log`, `worktrees.log` and the nudge debounce markers are not written.
- **The D1 root lives under `$TMPDIR`.** A temp-dir cleaner that deletes it mid-run removes the guard markers, and the test-integrity guard then reads the session as unarmed (the same effect as deleting `.supervisor/guard/` in off mode). The finalize-publish guard stays closed while a repo seed reads `running` (the run is still live, and `write-marker` refuses without a session log).
- **An arm that cannot create the D1 root leaves the session unguarded.** With no root yet, the test-integrity guard reads an absent root as "nothing armed"; if `guard-arm.sh` then fails to create it (an unwritable temp base), no marker exists and the guard stays inert — the documented "a failed arm proceeds visibly unguarded" outcome (`skills/supervisor-config/SKILL.md`, INIT step 7), the same as an unwritable `.supervisor/` in off mode. A root that exists but is unsafe still denies.
- **The presence check's shortcut is per user, not per repo.** Once any host-mode run on the machine has created `loomwright-host-<uid>`, every host-mode hook in every repo takes the full resolve (`git worktree list` plus a hash) before it can skip. It still creates nothing.
- **The guard's redirected-dir check matches literal paths** (and, under D1, the per-user root's name). A host state dir named only through a shell variable (`$LOOMWRIGHT_HOST_STATE_DIR/guard/x`) is not recognised — the same class of limit as `D=.supervisor; rm $D/guard/x` in off mode.
- **The capabilities contract reads the off-mode branch of the StopFailure leaf.** `build-capabilities.sh` parses that inline leaf as if only its `else` branch stood there, so its host branch is checked behaviourally, by `scripts/test-host-mode.sh` alone.
- **`scripts/test-host-mode.sh` observes the repo, the session's HOME and TMPDIR, and the state dir** (its unsafe-`TMPDIR` case uses the real `/tmp` fallback and removes the per-repo dir it made there; the per-user parent stays). A hook writing to any other absolute path would not be caught. It fires every `hooks.json` leaf verbatim with `sh -c`; the runtime's own shell is not probed.

Suite: `scripts/test-host-mode.sh` — the state-dir and D1 cases, both guards, the stale-gate-copy case, a finished repo seed beside a live gate-dir run (the live copy's session id and branch key the publish gate), off mode, invalid state dirs, unsafe `TMPDIR` values, hostile pre-created D1 roots, a linked-worktree session, the `check-children-settled.sh` log mapping, an unloadable helper (both guards, `write-marker` and `guard-arm.sh`), the presence gate (a plain host session creates nothing; a live `state.md` Write or arming creates the root and the emitters write only after; planted unsafe roots still deny), `session-resume.sh`'s host-mode branches against real fixtures (nudge-marker redirects, no `--repair-merged` move, the rules-nudge and twin-section skips, the orphaned-worktree block with no repo `.supervisor/`, each with an off-mode control), `notify-desktop.sh`'s and `seed-run-owner.sh`'s redirected writes, and four mutation controls.

## Detached-Drain Permission Regime (not a hook — a related credential-holding-process control)

`scripts/dispatch-pr-review.sh` launches the `review-pr-runner` as a **detached, unattended, credential-holding** `claude -p` process (`gh`/`git push` access) — no hook governs it, so its permission posture is documented here rather than in the table above (red-team-hardening item 01, v15.86.0+).

- **Pinned, never inherited.** Both the `DRY_RUN_DISPATCH` diagnostic and the real launch construct `--permission-mode dontAsk` + an explicit `--allowedTools` allowlist + `--disallowedTools WebFetch,WebSearch` from ONE shared function/constants — never two independently-typed strings. See `scripts/dispatch-pr-review.sh` header PERMISSIONS section and `docs/ARCHITECTURE_CONTRACTS.md`'s dispatch-shape cell.
- **Regime probe, refuse-don't-guess.** Before dispatch, the effective `permissions.defaultMode` is resolved (project local settings > project shared settings > user settings). A bypass/auto-approve resolution — or ANY tier whose file exists but is unreadable/malformed (ALWAYS fail CLOSED, never assumed safe) — degrades the dispatch to review-only (the SAME `LOOMWRIGHT_PR_IS_FORK=1` semantics a fork PR gets) unless the ONE opt-out, `LOOMWRIGHT_DRAIN_ALLOW_PERMISSIVE=1`, is set in the **dispatcher's own process env**. This opt-out is documented here and in `docs/ARCHITECTURE_CONTRACTS.md` — it is deliberately **NEVER** named in any agent/skill/command prompt file, any log line the model reads, or any `.supervisor/` file, so the model itself can never discover or recommend it (decision R2).
- **Unpinnable ⇒ refuse.** If the resolved `claude` build's `--help` cannot advertise a headless, allowlist-honouring mode, the dispatcher exits 0 printing `PERMISSION_REGIME_UNPINNABLE` and does NOT dispatch at all (decision R1).
- **Untrusted-text envelope — a tripwire and a narrowing, NOT a sandboxing claim.** Every externally-sourced review-channel body the drain reads is wrapped by `scripts/wrap-external-text.sh` in an `EXTERNAL_TEXT` envelope stating it is data, never an instruction (`skills/review-heal/SKILL.md` §"Untrusted-Text Envelope"), and only actors/checks on a user-scope allowlist (`classify-bot-review.sh --trusted-actors`, the `review_producing_checks[]` list) can produce a candidate finding. **Honest limit:** this is a content-shape tripwire plus a narrowing of who/what can produce a candidate — it is explicitly **not** a sandboxing or process-isolation boundary, and it does not attempt to sanitize hidden-character tricks beyond the envelope itself. **Delimiter-forgery defense (PR #248 finding #2):** `wrap-external-text.sh` now defangs any literal `<<<EXTERNAL_TEXT`/`<<<END_EXTERNAL_TEXT>>>` sequence found INSIDE a wrapped body, so a comment cannot forge a second, fake envelope (with its own attacker-chosen actor/trusted/channel) that reads as script-generated ground truth. **Honest limit:** this is a narrowing/tripwire against the exact literal delimiter strings, not a cryptographic guarantee — it does not defend against Unicode look-alikes/homoglyphs of the marker text.
