## Common Pitfalls

### `/supervisor` or `/launch-pad` aborted with "Task/Agent tool unavailable"?
- Pre-11.1.1 name-collision trap: the slash command silently auto-delegated to a same-named registered subagent, which couldn't spawn its own children ([docs](https://code.claude.com/docs/en/sub-agents): *"Subagents cannot spawn other subagents"*).
- Fix in 11.1.1: registered agents are now `loomwright:supervisor-runner` and `loomwright:launch-pad-runner`. The slash commands are inline main-thread workflows; the `-runner` suffix lets `claude --agent loomwright:supervisor-runner` own a session without re-introducing auto-delegation.
- For an agent-owned session: `claude --agent …-runner`. Otherwise stay on the main thread via the slash command.

### `/supervisor` completed but skipped Phase 4.5 (or Phase 3 child agents)?
- **What this is:** inline main-thread execution misread as permission to stop orchestrating. "Don't delegate to `supervisor-runner`" does NOT mean "do everything yourself." Still spawn first-level children via Task — `orchestrator` (Phase 2), `execute-manager` or Single-Agent/Sequential-path worker (Phase 3), `code-reviewer` + fix loop (Phase 4.5).
- **Fix in 11.1.2:** Phase 4.5 completion-tail guard (`loomwright/agents/supervisor.md`) refuses a successful `SUPERVISOR_RESULT` when `skip_self_heal_requested=false` AND `phase45_review_invoked=false`. Run self-reports `status: failed`; job stays in `in-progress/`.
- **Recovery for pre-11.1.2 runs (operator workaround — unsupported, manual):**
  1. `/code-reviewer` has no first-class branch-vs-branch diff mode. Compute scope via `git diff --name-only origin/main...HEAD` and pass that file list to `/code-reviewer`, OR pipe `git diff origin/main...HEAD` into a manual review.
  2. Fix any new BLOCKING/HIGH issues; push to feature branch.
  3. Update `.supervisor/` state and the job file by hand. NOT supported — will become `/supervisor --recover-self-heal` in a follow-up PR.
- **Intentional skip:** re-run with `--skip-self-heal` (the guard accepts it as a recorded deliberate choice).

### Supervisor workflow interrupted?
State auto-saves to `.supervisor/state.md`. Resume with `/supervisor --continue task: BD-XX`. Check `.supervisor/history/` for completed sessions.
Resume is fail-closed (v15.3.0): `--continue` schema-validates the loaded state BEFORE consuming it (closed `phase`/`status` enums + branch-must-verify, per `skills/state-management/SKILL.md` §"Resume validation gate") and refuses with `error: "resume_state_invalid"` on any violation — inspect or delete the state file; there is no override flag.
**Schema-valid is NOT the same as true.** A state file can pass every schema check and still under-report reality: on 2026-07-27 all 5 subtasks were merged while `state.md` read `phase: ACQUIRE` / all `PENDING`, and `--continue` would have silently re-executed the whole job. Resume therefore also runs `scripts/reconcile-resume-state.sh`, which reconciles the `## Subtasks` rows against subtask + merge commits on the asserted branch and refuses with a **distinct** `error: "resume_state_stale"` (`UNKNOWN` fails closed too). Different error because the operator response differs — an *invalid* file is corrupt (delete it), a *stale* file is intact but behind, and the work it claims is pending already exists on the branch. **Root cause worth remembering: prompt-instructed bookkeeping is unreliable** (measured in this repo: 560 hook-written `token_ledger` events vs 6 agent-written `phase_transition` events across 11+ sessions), so the reconciler keys on commits — a byproduct of the work — never on anything an agent must remember to write. Do not patch a future gap here by adding another "write your state" instruction.

### Brief stuck in `.supervisor/jobs/in-progress/` after its PR already merged? (reconciler added in v15.39.0)
**Do NOT `/supervisor --continue` it.** The lifecycle move `in-progress/` → `done/` is completion-tail **step 2** and the originating-requirement stamp is **step 2.5** (`skills/self-heal-advisory/SKILL.md`) — both PROMPT-INSTRUCTED steps executed by the agent, not by code. Any failure that ends the agent's turn before the tail is reached strands the brief with its work already merged and shipped. Observed 2026-08-30 on PR #160: the Phase 4.5 reviewer failed 4× with a server error, the tail never ran, and the brief sat in `in-progress/` while v15.38.0 shipped from it.
**This cannot be fixed by hardening the tail** — an instruction cannot be made atomic against the agent dying before it is read — so the tail is deliberately unchanged and reconciliation is the repair. **This is the second such reconciler, not the first:** `stamp-requirement-status.sh` has closed out step 2.5 since 2026-08-04 by keying on a brief landing in `jobs/done/`. But it reads `jobs/done/` *exclusively*, so a stranded brief is invisible to it — the strand does not merely skip step 2, it structurally blocks the existing step-2.5 reconciler from firing at all. Repairing the move unblocks it; the two compose (this one never stamps a requirement, that one never moves a brief) and both run from the same SessionStart. Run `bash loomwright/scripts/reconcile-jobs.sh` to classify, then `--repair` to finish the move. It is **offline by construction** (never calls the forge CLI, because `session-resume.sh` runs it on every resume/clear/compact and, stranded-only, on every fresh startup) and it **never repairs an `unknown`** brief: a stranded brief carries no PR URL, since the `## Outcome` block that would carry one is precisely what did not get written. Evidence therefore comes from an automate run file that already recorded a reconciled merge, or a requirement already stamped done; a plain `/supervisor` run outside the automation engine may leave no evidence at all, and `unknown` means UNVERIFIED — not clean, and not stale.
**The pointer is NOT read literally, and the limit is named rather than guessed around.** Both reconcilers read the brief's `- **Source requirement:**` line through ONE shared extractor, `loomwright/scripts/brief-pointer.sh`. It tolerates every shape the real corpus carries: a bare repo-root-relative path; a path wrapped in backticks, single quotes or double quotes; a path followed by whitespace and a trailing annotation (parenthetical or prose); and the label written with any capitalisation, with leading whitespace, and with or without its leading `- `. The path is the pointer's **first whitespace-delimited token after delimiter stripping**. **The honest limit:** an annotation that is *not* whitespace-separated from the path — `…/05-archive-views.md(amended)` — is unreadable, because the first token then carries the annotation and the existence check refuses it. No brief in the corpus has that shape, and no heuristic guesses around it: an unreadable pointer is refused, never assumed. Before the extractor there were TWO divergent parsers, and measured 2026-09-10 over the three briefs then in `in-progress/`, a backticked pointer resolved in the stamper and not the reconciler while a backticked pointer with a trailing parenthetical resolved in neither — one of those briefs had shipped five days earlier and was stranded on a backtick.
**The probe used to make this worse.** `session-resume.sh` reported every in-progress file as "Supervisor was mid-run" and pointed at `/supervisor --continue`, re-emitting that for merged work every session until a human moved the file. It now separates **Stranded** (with the repair command) from **UNVERIFIED**, and suppresses the resume hint unless something is genuinely unverified.
**A fresh session is now told automatically (v15.64.0).** The reconciler used to fire only on `resume`/`clear`/`compact` — the sessions that already HAD context — while every fresh `startup` was silent, which is how the 2026-09-05 strand sat unnoticed for five days. The hook's dedicated startup arm now runs the same offline `reconcile-jobs.sh --porcelain` and emits one bounded `**Stranded brief:** <path> — evidence: …` line per `stranded_*` brief plus a `--repair` trailer, composed with the curation nudge into ONE envelope, 24h-debounced (`.supervisor/.stranded-nudge-shown`) and silenced by `LOOMWRIGHT_STRANDED_NUDGE=0|off|false|no`; when nothing is stranded the startup output is byte-for-byte what it was. **What is NOT surfaced on startup:** `unknown` briefs. The startup path is offline by construction (no forge call, ever), so a brief whose only evidence of shipping lives on the forge stays silent on a fresh session and appears only as UNVERIFIED on resume/clear/compact — run `bash loomwright/scripts/reconcile-jobs.sh` by hand when in doubt. Nothing else moved onto the startup path: Sections 1–5, the observability probe, the recovery hints and the house-rules nudge still never run there.
**Where the ONLINE repair now happens (v15.65.0): the engine's two seams, on evidence it already holds.** The `/automate` loop is the one caller that watched the merge — its `--auto-merge` gate merged the PR (`automate-loop` §6 step 5 SYNC), or its RESUME reconcile found an item parked `awaiting_merge` now merged (§6 step 1 RECONCILE). At both seams it calls `automate-helpers.sh brief-repair <item> <pr_url>`, which re-reads merge state (`gh pr view`, evidence-positive: only `MERGED` proceeds) and hands it to the same `reconcile-jobs.sh --repair` through the opt-in `--evidence <item>=<pr_url>` argument — one mover, scoped to that item, refusing an ambiguous match, `unknown` still never repaired, and the one output line appended to `## Progress` so the repair can be falsified. **What stays offline:** `session-resume.sh` is unchanged and still makes no forge call on any source; without `--evidence` the reconciler's behaviour and output are byte-for-byte what they were. **The honest limit:** only items the engine processed carry engine-held evidence. A `/supervisor` or `/autonomous` run **outside the engine** still has no online repair — its stranded brief is classified offline and remains a manual `reconcile-jobs.sh --repair`.
**Related, same family:** completion-tail step 2.5 stamped the requirement's status into a `- **Status:**` bullet while `automate-helpers.sh`'s `is_done()` reads only the `## Status:` heading — so a *successfully* closed-out requirement stayed re-enqueueable by `resolve-folder`/`resume-glob` forever. Fixed in v15.39.0 by moving the value onto the heading. It had never fired because step 2.5 had never once completed in this repo (zero close-out sentinels on disk), which is the tell: **a step that never runs cannot reveal that its output format is unreadable.**

### System Twin reads return nothing but `.supervisor/twin/contracts/` is full? (signal added in v15.40.0)
Run `bash loomwright/scripts/read-system-contract.sh` and read the `twin_store_status:` line: `dark` means contracts ARE stored and **every one failed provenance verification**, so the gate withheld all of them. That is NOT an empty store, and before v15.40.0 the two printed the same thing — which is how a 100% capability loss ran for two weeks with every gate green (2026-08-12 → 2026-09-01).
**Cause is almost always an out-of-band edit.** `.supervisor/twin/` is gitignored, so a tree-wide `sed`/rename/scrub over the working tree hits it without CI or review ever seeing the diff, and a body changed outside `write-system-contract.sh` has no matching hash in the ledger. Confirm by reversing the suspected substitution and re-hashing: if the reversed bodies match ledger `content_hash` values, that sweep is your culprit.
**Do NOT weaken the gate, and never `cat` the contract files to work around a drop** — the drop is the gate's verdict, not a malfunction (red-team W1: provenance alone is theater). Repair with `bash loomwright/scripts/reprovenance-twin-contracts.sh` (report first; `--confirm` to apply). It is human-gated on purpose: re-provenancing blesses the bytes currently on disk, so read them before confirming — on a genuinely poisoned store, confirming would launder the poison.
**`degraded` is the commoner and easier-to-miss case:** some contracts verify, some do not. A run whose touched subsystem is the dropped one gets nothing while the store looks mostly fine, so Phase 4.5 records `unverified` rather than `pass`/`skipped`.

### Orphaned worktrees after crash?
Since v15.66.0 the plugin records worktrees added through the Bash tool in a repo it has run in (gated on `.supervisor/` already existing) to `.supervisor/logs/worktrees.log`; `bash scripts/worktree-audit.sh report` (plugin-relative) lists the ones never seen removed that `git worktree list` still shows, and `session-resume.sh` surfaces the same list as `### Orphaned worktrees (advisory)` at session start — it reports, never removes; to keep a listed worktree and stop the advisory, run `bash scripts/worktree-audit.sh note removed <abs-path>` from the repo. Then: `git worktree list`; `git worktree remove ../project-BD-XXa`; `git branch -d feature/BD-XXa`. The detached until-mergeable review drain also creates a sibling worktree (`../{project}-review-{pr_hash}`, detached-HEAD at the PR head SHA) owned by `dispatch-pr-review.sh`'s `trap cleanup EXIT` wrapper, which removes it on the wrapper's normal/error exit. A **hard** kill (SIGKILL / power-loss) skips the trap, so that worktree can linger on disk — `git worktree prune` only reclaims an entry once its directory is *already gone*, and the durable per-PR marker blocks the same-PR re-dispatch whose pre-add cleanup would otherwise force-remove it. Remove a stray one manually — but run `bash scripts/worktree-salvage.sh <path>` first (plugin-relative, v15.67.0): it preserves uncommitted content under the primary checkout's `.supervisor/salvage/<name>-<ts>/` (the script's default destination; the drain's own sites pass the dispatching checkout's `.supervisor/` instead, beside the per-PR marker) and prints that path, or prints nothing when there is nothing to keep — then `git worktree remove --force ../{project}-review-{pr_hash}` (the leak is cosmetic — the marker preserves idempotency). The plugin's own removals (the drain's three `--force` sites and FINALIZE step 4) already run that salvage; a `--force` typed by hand does not.

### Two `.supervisor/` artifacts that look deletable and are not (retention policy added in v15.68.0)
`.supervisor/` grows without bound and nothing pruned it — but an age-based cleanup would destroy two things that look like garbage. **(1) The per-PR dispatch markers** in `review-dispatch/` and `postmortem-dispatch/` are idempotency guards durable *by design*: deleting one re-arms re-dispatch for that PR (the same-PR duplicate drain the marker exists to prevent), and a marker old enough to look stale is exactly the one still doing that job. **(2) Session logs** in `logs/*.jsonl` are the input `curation-status.sh` counts: `/dreaming`'s pending is the set complement of what it has consumed, `/insights`' pending is every signal log newer than `insights/dashboard.md` — so deleting old unconsumed logs does not shrink a directory, it lowers the number that tells you your recorded knowledge has gone stale, in the direction of "everything is fine". (A third — the five committed files under `memory/` and `postmortem/` — are the Twin's judgment and the least distinguishable from exhaust by age.) The policy that names every directory's verdict is `ARCHITECTURE_CONTRACTS.md` §"`.supervisor/` retention policy"; the tool that enforces it is `bash scripts/retention-sweep.sh` (plugin-relative) — **report-only by default**, `--delete` to act, only `logs/` (session logs whose id is absent from `curation-status.sh pending-ids`, plus the unread postmortem-dispatch transcripts) and `drain-rounds/` are ever swept, the tracked files are guarded twice (row verdict + `git ls-files`), and an unclassified directory is reported and skipped. It is wired into no hook; run it by hand, read the report first, and remember its first line: the data is gitignored and exists in exactly one place. **Why `drain-rounds/` was 737 files:** 732 were `{"rounds":0,…}` ledgers left by `test-drain-rounds.sh` §H, which called `drain-rounds.sh init` from the suite's own cwd — and that script writes its ledger relative to cwd — so every run from a checkout polluted that checkout's real `.supervisor/drain-rounds/`; since v15.68.0 §H runs through the suite's cwd-isolated helper and an end-of-suite pin turns any recurrence red.

### Detached review drain colliding with inline self-heal? (fixed in v14.42.0 — drain is now worktree-isolated)
**Do NOT write `.supervisor/config.json {"auto_review": false}` to suppress the until-mergeable drain for the self-heal race** — that practice is **retired** as of v14.42.0. The detached dispatched drain (`review-pr-runner`, launched by `dispatch-pr-review.sh`) now runs in its OWN sibling git worktree (detached-HEAD at the PR head SHA), so it no longer shares a working tree/index with the inline Phase 4.5 self-heal and cannot sweep its uncommitted edits — the collision the suppress kill-switch existed to dodge is gone. The `auto_review` flag **remains** as a legitimate general opt-out (turn the drain off entirely), but it is no longer the recommended fix for the concurrency hazard, and suppressing it for the race risks the exact silent-drop it used to cause (a suppressed drain with no safe restore = no dispatch; cf. PR #74). A markerless heal-outcome PR now surfaces in `/insights` under `## Missing-drain reconciliation` as the signal to investigate.

### `/autonomous` brief-save detection (fixed in v14.2.0 — `ls`-diff is now fallback-only)
**Fixed in v14.2.0.** The PLAN phase now reads `LAUNCH_PAD_RESULT.saved_brief_path` (emitted by Launch Pad Phase 7, validated by `scripts/validate-launch-pad-result.py`) as the **primary** brief-save signal — each Launch Pad invocation emits exactly one result block and the loop consults only the block from its own inlined call, so a concurrent `/launch-pad` can no longer be mistaken for this loop's save. The legacy `ls`-diff of `.supervisor/jobs/pending/` remains a **pre-v14.2.0 fallback** (used only when the result block is absent or fails validation); it keeps the original single-session-only constraint and still aborts the multi-file case with `status_reason="concurrent_session_detected"`. For pre-v14.2.0 plugins the safe operating rule remains: one autonomous / launch-pad invocation at a time per repo.

### `/autonomous --cheap` (supported since v15.2.0 — forwarded to the inlined `/supervisor`)
Since v15.2.0, `--cheap` **is forwarded**: `/autonomous` parses it at INIT and appends it to every inlined `/supervisor job:` invocation (EXECUTE step 1 §"Auto-forwarded flags"), and `/automate` passes it through to its inner `/autonomous` call — the full `/automate → /autonomous → /supervisor` chain carries the Sonnet cost profile. Note the `/automate` passthrough is NOT persisted in the run file's `## Run Config`, so re-pass it on each `--resume` / `/loop` tick. `--skip-preflight-sync` remains unforwarded. On pre-v15.2.0 plugins the flag was an inert no-op — there, run `/launch-pad` and `/supervisor --cheap` manually. See `commands/autonomous.md` "Parameters" → `--cheap interaction note` for details.
