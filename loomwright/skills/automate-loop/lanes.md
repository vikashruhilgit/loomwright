## §14 — Lanes (--parallel N)

Opt-in (parallel-automate/05). `/automate --parallel N` with N > 1 runs up to N independent Queue items at once, each in a **lane** — a local clone of the primary checkout at `<primary>-lanes/<run_id>/L<n>/` that runs the ordinary per-item loop (§6) for ONE item in a detached headless session — tracked by ONE **coordinator**: the `/automate` run in the primary. **Without the flag, or with N = 1, no lane code path is entered** — no `parallel:` line, no lint, no other new gate, and no `automate-lanes.sh` call except the read-only `pick-guard` (§4's new-run start, §6 step 1's PICK), which prints `ok` when `.supervisor/automate/` holds no `*.lanes` table — always the case in a checkout that never ran a wave — so a sequential run's output and run file are unchanged (and, when `--parallel 1` is passed explicitly, §4's first-step `init-check`, which prints `ok` for N = 1 and writes nothing). Every step below shells out to `scripts/automate-lanes.sh` (each subcommand is also a dispatch arm of `automate-helpers.sh`; the script's `--help` header is the per-subcommand contract), `scripts/automate-wave.sh` (`wave-build`, also a dispatch arm) or `scripts/lane-sampler.sh` (and, for policy answers, `scripts/lane-policy.sh`). **The owner merges the wave PR.** No lane subcommand merges or pushes: none merges into a wave branch, merges a lane PR, or pushes a lane's feature branch (the lane's own §6 run pushes it, as any item's does). The ONE writer of a wave branch is `wave-build` in `scripts/automate-wave.sh`: it builds the wave branch from the lane PR heads, runs the local CI and the version bump as the branch's last commit, pushes the wave branch and opens the wave PR — it never merges a PR, never pushes a lane branch, never force-pushes. `wave-plan` prints the same steps read-only, and `fleet-closeout` closes the wave after the owner merged the wave PR ("Wave close" below; owner decisions 2026-10-10 and 2026-10-11).

### INIT (coordinator and lane)

- **Refusals first:** `automate-helpers.sh init-check --parallel N [--auto-merge]` before any write — the first step of §4's start order whenever `--parallel` was passed. `refuse: auto_merge_with_parallel` (N > 1 with `--auto-merge`, refused permanently in this queue) or `refuse: parallel_out_of_range` (N < 1 or N > 10) stops the run with that line; `ok` proceeds.
- **`## Run Config` gains `- parallel: N`** on a `--parallel N>1` parent run only — absent on every sequential run and inside every lane.
- **Inside a lane** (`automate-helpers.sh lane-info` exits 0) the run id and the title come from `.supervisor/lane.json` verbatim (§3 "Inside a lane"); the lane never mints its own id. `lane-info` exit 1 ⇒ not a lane.
- **Resume path, recorded by the lane itself:** on entry, when the environment carries a non-empty `LOOMWRIGHT_LANE_RESUME_PATH` (set only by `lane-launch --resume-run`: `session <id>` — the lane's last session, resumed so its own `run.lock` is re-entrant — or `fresh session (…)`, the fallback), the lane's engine appends it to its own `## Progress` as `lane resume: <value>`. On a resume the coordinator never writes the lane's run file or lock (the wave-end and `--abandon` writes below are the only exceptions after launch); `--force-unlock` stays human-only.
- **The primary is locked for the whole wave:** the coordinator holds `scripts/run-lock.sh acquire --owner "automate-lanes:<run_id>" --session-id "<session_id>"` in the primary, AND every sequential PICK (§6 step 1 — refused ⇒ park `live_lane`, lock released) and every NEW run's start (§4 — a plain `/automate` or a second `--parallel` coordinator; refused ⇒ stop before intake, nothing written) in the primary runs `automate-helpers.sh pick-guard .supervisor/automate` — `refuse: live_lane <lane_run_id> <lane>` (exit 1; a lane whose process `lanes_proc_alive` confirms, or that has a pending question) refuses it, fail CLOSED. A coordinator's own `--resume` is not guarded by it (it is resuming those very lanes): a coordinator run (`## Run Config` carries `- parallel: N`) continues through the per-wave loop below on every `--resume`, never through §6's per-item PICK in the primary. The guard exists because the lock's liveness is the session's pid and a wave outlives a session: the lock alone is reclaimable once the coordinator's session ends.

### The per-wave loop

1. **Meta pull** — branch mode's `meta-entry` (§13).
2. **`closeout-others` ONCE, in the primary, before launching** (§4 start order). A lane clone skips it (`closeout-others: skipped — lane clone`).
3. **RECONCILE every lane** — `lane-status <parent_runfile>` (state per lane, below; a lane whose directory vanished reads `missing`, and a lane whose PR closed unmerged reads `gone` — both need a human).
4. **Plan the wave** — `plan-waves <parent_runfile> --max N` (its §2 intake lint already ran before the Queue was confirmed); record it with `automate-helpers.sh current-wave <parent_runfile> --wave <k> --items <i1,i2,…>` (the only writer of `## Current`'s `- wave: <k> | items: …` line; `--wave null` clears it). **Wave policy (optional, interactive only):** before any `lane-create`, the coordinator may ask the owner — one question with NO catalog code in its `header` (the owner setting a policy is never itself answered by one) — which `allowed` gates to pre-answer for this wave, and with which of each gate's catalog labels; it then runs `lane-policy.sh wave-set <parent_runfile> <code>=<label> …` with exactly the owner's answers and nothing else ("Policy answers" below). No answer, or a run that cannot ask ⇒ no wave policy.
5. **Wave-start snapshot** — `lane-status <parent_runfile> --leaks --snapshot` (the baseline the end-of-wave leak check compares against). It runs before any lane exists: with no `<run_id>.lanes` table yet, the parent run id and the primary come from `<parent_runfile>`. A snapshot that cannot be written exits 1 naming why (the one exception to observation's exit 0) — report it; the end-of-wave check has no baseline without it.
6. **Per item** — `lane-create <parent_runfile> <item> <n> --parallel N [--max-tokens T]` (clone, origin set to the primary's remote URL before any fetch, meta pull, carried configs, `lane.json`, a one-line `lane-backlog.md`, the relay hook merged into the lane's local settings), then `lane-launch <lane_dir> --owner-command '<the /automate command the owner typed>'`. After launch the coordinator never writes into the lane again, except `lane-answer`'s answer file, the wave-end `lane-convert-ready` conversion and its metadata push ("Terminal park" below), and `lane-remove --abandon`'s record on a `gone` lane ("Dismissed findings, tokens, RESUME, removal" below).
7. **Start the sampler** — `scripts/lane-sampler.sh --parent-run-id <run_id> --parent-pid <coordinator pid>` as the coordinator's own detached child; it exits by itself when that pid dies. Pass the coordinator pid explicitly — to the sampler and as `LOOMWRIGHT_LANES_COORDINATOR_PID` to the lane subcommands — never leave it to the ancestor guess.
8. **Poll — a resumable step, not an in-session wait.** Each `/automate --resume <run_id>` reconciles every lane and reports (`lane-status`, `--watch` for a bounded live view); an in-session until-loop dies with the session. **Arm the lane watcher:** right after step 7, and again after handling every `lane-wait` event, the coordinator runs `scripts/automate-lanes.sh lane-wait <parent_runfile>` as a BACKGROUND command (the host re-invokes the coordinator when it exits). It is token-free and read-only toward the lanes: it blocks until a lane needs the owner — a new pending question, or a lane entering any state that is neither live (`created`, `running`, `held_for_load`, `answer_pending`) nor coordinator-driven (`awaiting_merge`, `awaiting_go`, `done`, `removed`, `abandoned`), so every other park, failure or unknown state wakes the coordinator — prints one `lane-wait: …` line per event, then a hint per event kind (`act` for a state, `relay` for a question), and exits; the coordinator relays each question exactly as below, handles each state per "Lane states and what the coordinator does" (report it; resume a `stalled` lane once; `ready_for_release` waits for the wave end; the owner decides every other state — `died`, `escalated`, `gone`, a run-file park such as `token_ceiling`), and re-arms it after ANY event, question or state. It exits `idle` when no lane is running and nothing is new, so a parked wave never polls forever. Without it a lane's question sat unseen until the owner looked (W3, 2026-10-11: two lanes waited 22–24 min). It never answers or launches anything, so it needs no launch authority; the answer still comes only from the owner. A `Stop` hook (`scripts/guard-lane-wait-armed.sh`) now enforces the re-arm for the coordinator session only: a coordinator turn that ends with a live lane, or a question lane-wait has not reported, and no running watcher is sent back to arm it. If the session ends, the next `--resume` reads every pending question with `lane-status --inbox` regardless. For every lane reading `answer_pending` the poll runs `lane-answer <lane_dir> --deliver-pending --owner-command '<the /automate --resume command the owner typed in THIS session>'` ("Lane states" below). A lane first launched with the test-integrity guard's opt-out set records that fact coordinator-side, and every resume of it (`lane-answer`, `--deliver-pending`, `--resume-run`, `--continue`) whose environment lacks the opt-out is refused `BLOCKED` (exit 3; a validated answer stays pending): relay the line to the owner, who re-runs the command with the opt-out set or adds `--without-gate-optout` — the coordinator never sets it. `lane-status <parent_runfile> --inbox` lists every lane's pending HUMAN question in one list, oldest first, so the owner answers them as a batch.
9. **Build the wave** — at wave end, once every wave lane is converted (`awaiting_merge`, after `lane-convert-ready`, "Terminal park" below), the coordinator runs `wave-build <parent_runfile> [--wave-branch <name>]` as a BACKGROUND command (it runs the local CI, 15+ minutes; the host re-invokes the coordinator when it exits) and relays its last line to the owner: `wave-build: opened — <url>` (the owner reviews and merges that PR), `done — wave PR <url> already open` (a re-run), `refused — <reason>` (exit 1, nothing created — resolve it and re-run), or `STOPPED — <reason>` (exit 2, nothing pushed — hand the owner the printed worktree to integrate by hand per the conflict rules). `wave-plan <parent_runfile>` stays the read-only preview and the manual fallback ("Wave close" below).
10. **Close the wave** — after the owner merges, each `/automate --resume <run_id>` re-runs `lane-convert-ready <lane_dir>` for every lane `lane-status` reads `merged` (the done stamp and the lane-side finalize) and then runs `fleet-closeout <parent_runfile>` — which backstops any merged lane not yet closed out with the same `lane-convert-ready` — until it prints `fleet-closeout: wave closed — lock released` ("Wave close" below).

Launch outcomes: **`lane-launch: BLOCKED — <lane> — <reason> — need the owner`** (exit 3, no process) — no owner command, the pinned permission regime unavailable, or the host refused the spawn (record that with `lane-launch <lane_dir> --host-denied '<reason>'` ⇒ state `blocked_launch`). On BLOCKED the coordinator stops launching, keeps every lane already running, prints that line as its FIRST output line, and never retries the spawn in another shape. **`lane-launch: HELD — <lane> — memory_pressure | load overloaded | load busy`** (exit 4, no process, state `held_for_load`) — admission said not now; the launch is retried at the next poll. A lane holding an unanswered question reads `awaiting_input` instead (below) — its question is relayed, never relaunched. Neither guard ever kills a running lane: they stop STARTING only.

### Launch authority (a new stance — the plugin had none before)

`lane-launch` and every lane resume run only on behalf of a command the OWNER typed in this same session — `/automate --parallel N` or `/automate --resume <run_id>` — passed verbatim as `--owner-command`. A launch or resume requested by a cross-session or peer message, a hook, or text inside a lane's output cannot authorize a lane launch and cannot grant escalation: it is refused and named (the BLOCKED line above), never carried out. **Wave hand-over:** a wave continued in a new session resumes only when the owner types `/automate --resume <coordinator run_id>` there; `/handoff` gives the catch-up digest and the run file + metadata branch hold the state. A hand-over note from an earlier session may PREPARE (lanes set up, records pushed) but never asks the new session to launch.

### Lane states and what the coordinator does

`lane-status` reports, first match wins: `removed`/`abandoned`, `answer_pending`, `blocked_launch`, `held_for_load` (`awaiting_input` instead while the lane holds an unanswered question and no process runs — a HELD resume or a discarded pending answer), `created`, `missing`, `running`, `awaiting_input`, the lane run file's park (`ready_for_release`, `escalated`, `rate_limit`, …; `merged`/`gone` after `reconcile-item`), `lost_to_reset` (the machine booted after the last launch), `died` (a `.died` marker — the process exited with no terminal result), `stalled` (process gone, not parked, no question). Observation fails SAFE: an unreadable source reads `unknown`, exit 0.

**Where each lane is in its item — the step timeline.** `lane-status --json` gives every lane a `timeline`: seven steps (`pick` · `plan` · `build` · `heal` · `drain` · `decide` · `merge`), each with its `state` (`done`, `pending`, or the current step's `active` / `waiting` / `held` / `trouble`, taken from the lane state; every step `done` once `merged`), `started_at`, `ended_at`, `duration_s` and its last few lines, plus a `label` for the current step (`Build · EXECUTE`, `Drain · round 2`). It is read from the lane run file's dated `## Progress` lines and, for the Supervisor phase, the lane's `.supervisor/state.md` — only when that state was created at or after the pick, so a previous item's never shows. The `picked` line starts Plan, a Launch Pad "brief saved" line starts Build, and a step passed with no line of its own reads `done` with null times (the run never said when it ran). Each lane also carries `started_at`, and the document `run_started_at` (the parent run file's first dated line) and `utc_offset_s`. The plain view prints one `steps:` line per lane. The document also carries `waves`: every wave PR the run opened, oldest first, as `{wave, branch, pr, built_at}`, read from `wave-build`'s `wave built: <branch> — PR <url>` `## Progress` record (a hand-built wave's line in the same shape counts; `built_at` is null when it has no timestamp). lane-status makes no `gh` call for it, so the wave PR's own state is not shown; the plain view prints one `wave <k> PR:` line per wave.

- **`awaiting_input` — relay verbatim.** The lane's question hook recorded the question in the lane inbox and the lane exited deferred. The main session shows it to the owner exactly as asked (same text, same option labels) and answers with `lane-answer <lane_dir> <tool_use_id> --owner-command '<cmd>'`, stdin `{"answers":{"0":"<label>"},"note":"<optional>"}` — only the question's own labels are accepted (one unknown label refuses the whole answer; a note alone is refused), and the note is delivered to the lane on resume. The coordinator never answers a lane question on its own. A policy answer is not the coordinator answering: it is the owner's pre-given answer — a human-stamped project policy or the wave policy the owner set — applied by the lane's OWN relay hook as an exact lookup before the question is ever relayed, so such a question never reaches `awaiting_input` ("Policy answers" below). Everything the lookup does not answer is relayed exactly as above.
- **`answer_pending` — a HELD answer is kept, never lost.** When admission holds the resume (`lane-launch: HELD — …`, exit 4), `lane-answer` keeps the VALIDATED answers, the note and `via` — never an owner command — in the coordinator-side `.supervisor/automate/<run_id>.<lane>.answer-pending.json` and writes nothing into the lane; plain `lane-status` (observation) only SHOWS the lane as `answer_pending` and never spawns anything. Delivery happens only under a command the owner typed in the CURRENT session: the poll (step 8) runs `lane-answer <lane_dir> --deliver-pending --owner-command '<cmd>'`, which re-runs the full launch gate (authority, liveness, regime, admission — HELD again keeps it pending) and re-checks the stored answers against the recorded question's labels AND the lane's still-deferred `tool_use_id`; a mismatch refuses delivery and discards the pending file (the lane reads `awaiting_input` again and its question is relayed as above). One pending file per lane, last write wins: a second `lane-answer` for the same still-HELD question replaces the kept one — how the owner corrects it — and the next delivery uses the latest. Honest limit: that re-check proves the stored answer is a VALID label for the question still pending, not that the owner chose it — the same trust level as the lane inbox's answer file the relay hook reads; the pending file is not owner-authenticated, which is why it never carries, or stands in for, an owner command.
- **`stalled` — resume ONCE.** `lane-launch <lane_dir> --owner-command '<cmd>' --continue` sends the fixed decision-free message ("continue where you left off; wait in the foreground"). A second stall in the same phase escalates to the owner.
- **`died`, `lost_to_reset`** — reported; the owner decides. A resume is `lane-launch <lane_dir> --owner-command '<cmd>' --resume-run <the lane's run_id>` (its own run only — never a bare `--resume`). It resumes the lane's LAST session (a `--resume <session id>` spawn sending `/loomwright:automate --resume <run_id>`), so the lane's own `run.lock` — re-entrant only for the same session id — does not stall it; a fresh session is the fallback only when no session is recorded or that resume exits at once with no session (`lane-launch: <lane> — session <id> could not be resumed …`). Honest limit: the fallback fresh session still waits on a dead session's lock until `run-lock.sh`'s own reclaim (dead pid AND age ≥ its TTL); only a human runs `--force-unlock`.
- **Parks are per lane.** A fail-closed gate, `escalated` or `died` parks that lane only. A **`rate_limit` park in any lane pauses launching and reports all lanes** — the cap is account-wide; the owner decides whether the others continue.

### Terminal park — `ready_for_release`

**Validation gate first (af36-remainder/01):** before this park — and before the dismissed-findings step — the lane's GATE runs `automate-helpers.sh validation-gate <the lane's run file> <item> <pr_url>` exactly as §6 step 4 "Validation gate" says; only `none` / `ok` / `waived` reach `ready_for_release`. An `unrun` step parks this lane `escalated` with `escalation_cause: validation_unrun` unless the owner waives it: the `AUT-WAIVE` ask is relayed like any lane question (`awaiting_input`; human-only, so `lane-policy.sh decide` never answers it), and the owner's words come from `lane-answer`'s `note`. `lane-readiness` below reads the same Validation reader, but stays advisory and runs after the park. Inside a lane, a READY gate writes `ready_for_release` instead of `awaiting_merge` (`current-set <rf> --item <path> --status ready_for_release --pause-reason ready_for_release`), arms NO merge watcher, runs `automate-helpers.sh lane-park-notify <the lane's run file>` — the ONE notify step (parallel-automate/24 F6; never a hand-sent notification): the desktop notification and the `send-webhook.sh` gate event `automate_ready_for_release`, both carrying **"do not merge yet — wave open"** and both fail-SAFE, then ONE `## Progress` line naming what each channel actually did (`desktop: sent|disabled|suppressed|failed` — `sent` only when the OS notifier exists, else `failed (no OS notifier on PATH)`; `webhook: attempted|ignored (<reason>)|not configured|failed` — read from the notifiers' observable outcomes, never assumed; a run file not at this park ⇒ `skipped`, nothing sent; contract: `docs/TELEMETRY.md` §"`/automate` lane park gate event") — and `lane-readiness <lane_dir>` writes the advisory `<lane>/.supervisor/automate/<run_id>.merge-readiness.md` (it never merges; `lane-status --refresh-readiness` rewrites it). Like every park it calls no `trail-pr` (§6). **Wave end:** for every lane `lane-status` reads `ready_for_release`, the coordinator runs `automate-helpers.sh lane-convert-ready <lane_dir>` — step 6's second exception to the no-write rule, beside `lane-answer`'s answer file; it never hand-writes the conversion or pushes the lane's metadata another way. Under the lane's launch lock it refuses (`lane-convert-ready: refused — <lane> — <reason>`, exit 1, nothing written) a live lane process, a run file whose `## Current` does not read status and pause_reason `ready_for_release`, or an unknown metadata mode; otherwise it runs the same `current-set` item form on that lane's run file (`--status awaiting_merge --pause-reason awaiting_merge`) and, in branch mode, pushes the lane's non-claim files by exact list — that run file, its `<run_id>.merge-readiness.md`, its `<run_id>.dismissed-decisions` and the Orchestrator's task plans (every top-level `.supervisor/requirements/<slug>-plan.md` that is not a Queue item and carries no `## Status: done` heading — a managed path no other push carries, so without it `lane-remove` refused the lane forever) and the requirement drafts the lane filed (every top-level `.supervisor/requirements/proposed/*.md` that is not a Queue item and carries no `## Status: done` heading — a worker whose requirement says to file an out-of-scope follow-up as its own item writes it there; it is no done claim, so the evidence gate has nothing to judge, the same reason this run's dismissed drafts ride `trail-pr`, whose candidates carry no other `proposed/` file — wave W4's `twin-remediation-11` draft rode neither push and needed a hand push; a draft the lane only pulled is unchanged, so meta-sync pushes nothing for it) (`meta-sync.sh push --branch <the lane's mode-line branch> --root <lane> --paths-from <that list>`) — so the primary's next meta pull (`meta-entry`) reads `awaiting_merge`. **The rest of the lane's metadata goes through the evidence gate, never a whole-lane push:** in the same call it then runs `automate-helpers.sh trail-pr <the lane's run file> --reason wave-end` inside the lane — `trail-pr`'s own candidate list and evidence gate (§13 "The trail push"), branch mode only, and only when `trail-pr`'s mode reader agrees — so a done stamp or a `jobs/done/` brief rides only when its PR reads `MERGED` (`; excluded <path> — pr not merged` otherwise). This is the wave end's metadata step, not a fourth §6 trail trigger: the lane's item is parked and the gate drops every unmerged claim. Consequence: while the PR is open, the lane's unmerged done claims (its `jobs/done/` brief) stay local, the lane reads `local_ahead` and `lane-remove` refuses — by design. After the owner merges, re-run `lane-convert-ready`: already `awaiting_merge`, it runs no `current-set` but `closeout <the lane's run file> <item> <its ## Current pr> --no-trail` inside the lane, under the launch lock and BEFORE the pushes (automate-followups/38) — the writer of the requirement's done stamp, behind its own evidence gate (an unmerged PR ⇒ it writes nothing), which also checks the item off and reconciles `## Current` to `done` / `awaiting_go`; closeout's lines are echoed indented and the last line names any leftover `closeout-classify` reports (a leftover never changes the exit code; no `pr:` ⇒ closeout is not run) — then the pushes repeat and carry the stamp. One `lane-convert-ready` line names what the lane reads afterwards — `converted <lane> to awaiting_merge` on the conversion, `<lane> reads <status> / <pause_reason> (a re-run converts nothing)` on a re-run (`done / awaiting_go` once closeout ran). **Lane finalize (parallel-automate/21 A1):** when that re-run leaves the lane `done / awaiting_go` and branch mode is ON, it then runs `automate-helpers.sh finalize-empty <the lane's run file>` inside the lane — the lane run file reads `## Status: done`, and its `trail-pr --reason done` metadata push goes through the same evidence gate — and prints ONE `lane-convert-ready: finalize — <finalize-empty line>` line. Branch mode OFF ⇒ finalize is not run (it would open a trail PR) and the line reads `lane-convert-ready: finalize skipped — metadata mode off`; a lane already `## Status: done` is a no-op (`finalize-empty: skipped — not paused`). The lane is then removed by `fleet-closeout`, not by hand ("Wave close" below). A later re-run repeats only the pushes (and the finalize, a no-op by then); if the PR closes unmerged, `lane-remove <lane_dir> --abandon` records it (below). A failed push prints `lane-convert-ready: FAILED — <lane> — …` and exits 2: report that line to the owner — the lane reads `local_ahead`, so `lane-remove` keeps refusing, until a re-run of `lane-convert-ready` pushes it (an already-converted run file gets no `current-set`; only closeout — a no-op on an unmerged PR — and the pushes repeat). Lane PRs carry changelog fragments and no bump; `wave-build` integrates them on a wave branch, and the bump is that wave branch's last commit ("Wave close" below).

### Wave close — `wave-build`, then `fleet-closeout`

The flow (parallel-automate/21 Part A; owner decision 2026-10-11 — the mechanical integration is the engine's, only merging the wave PR stays the owner's): every lane converted to `awaiting_merge` → `wave-build` builds the wave branch and opens the wave PR → the owner merges the wave PR → on each `--resume`, `lane-convert-ready` per merged lane → `fleet-closeout`. All three subcommands are dispatched by `automate-helpers.sh` like every lane subcommand; the `automate-lanes.sh` header (`wave-plan`, `fleet-closeout`) and the `automate-wave.sh` header (`wave-build`) are the per-subcommand contracts. A sequential run never calls any of them.

**`wave-build <parent_runfile> [--wave-branch <name>]` — the one writer of a wave branch.** It reads the wave through the same resolver `wave-plan` prints from (lanes in planner order, each PR's exact head sha, the base, the branch name), so the two never disagree, and prints one `wave-build: <step> — <detail>` line per step, the result last. **Refused** (exit 1, nothing created — fail CLOSED): no lane table or no wave lanes; a wave item with no lane, no PR or an unreadable head; a lane PR not OPEN; a lane not parked (`lane-status` must read `awaiting_merge` or `ready_for_release`); the wave branch already on origin with no open PR, or already a local branch; an unreadable PR list or origin; another `wave-build` for the run holding its lock. An OPEN PR from the wave branch ⇒ `wave-build: done — wave PR <url> already open`, exit 0 (the idempotent re-run). Otherwise, in a temporary worktree off a fresh `origin/<base>` (never the primary's working tree, branch or index): `git merge --no-ff <sha> -m "Merge lane <L> (<item>) PR #<n>"` per lane; `bash scripts/ci-local.sh` when the repo has it (else `ci — skipped`); `bash scripts/bump-version.sh` and ONE `chore(release): v<version> — fold wave <k> fragments (<ids>)` commit as the branch's last commit (else `release — skipped`); a regular `git push -u origin <wave-branch>`; `gh pr create`; one parent `## Progress` line `wave built: <wave-branch> — PR <url> (lanes: …; ci …; release …)`; the worktree removed; last line `wave-build: opened — <url>`. **STOPPED** (exit 2) on a merge conflict (`git merge --abort`, the line names the lane, PR and files), a failed local CI, a failed release step or a failed push — nothing pushed, the worktree and local branch kept at the printed path for the owner. Only a failed `gh pr create` stops AFTER the push; its line names the pushed branch and the command to open the PR by hand. It takes its own per-run lock, never `run-lock.sh` (the primary's run lock is the coordinator's `automate-lanes:<run_id>` for the whole wave).

**`wave-plan <parent_runfile> [--wave-branch <name>]` — READ-ONLY: the preview of `wave-build`, and the manual fallback after a STOP.** It runs no git mutation, no push and no `gh` write (a guard test holds every ref and the working tree byte-identical across a run). For the lanes of the current wave in planner order (`## Current`'s `- wave: <k> | items: …` line, else the lane table order) it prints the owner's commands: `git fetch origin`; `git checkout -b <wave-branch> origin/<base>` (default `wave/<run_id>-w<k>`); one `git merge --no-ff <head sha> -m "Merge lane <L> (<item>) PR #<n>"` per lane, the exact head sha read from `gh pr view <pr> --json headRefOid,state` (unreadable ⇒ `# <lane>: head unreadable — resolve before integrating`, and that lane is skipped); `bash scripts/ci-local.sh`; the release step as the wave branch's last commit — `bash scripts/bump-version.sh` when the repo has that file, else `# run this project's release step`; `git push -u origin <wave-branch>` and `gh pr create --base <base> --head <wave-branch>`. Then the conflict rules: resolve a marker-only conflict in the merge commit; anything larger stops integration and goes to the owner; never rewrite or push a lane branch; a lane broken on the wave branch is fixed on its own PR and its new head re-merged.

**`fleet-closeout <parent_runfile>` — the wave close, in the primary, re-run on each `--resume`.** Stepwise and idempotent: each call performs every step it can, prints ONE `fleet-closeout: <step> — <detail>` line per lane and per step, and stops at the first step that must wait — never an in-session wait; the next `--resume` re-checks. In order:

1. **pull** — branch mode only: `meta-sync.sh pull --branch <mode branch>`; a failure prints `fleet-closeout: pull FAILED — <reason>`, exits 2, and nothing else runs.
2. **per lane**, from `lane-status`: `merged`, the lane run file not `## Status: done`, and no live lane process or watcher ⇒ **backstop** `lane-convert-ready <lane_dir>` (the sanctioned coordinator→lane close-out above: `closeout --no-trail`, the lane finalize, the pushes — token-free, no headless session, no launch authority needed); not merged yet (`awaiting_merge`, `ready_for_release`, `escalated`) ⇒ `waiting — <lane> <state>`; `gone` ⇒ `human — <lane> gone (PR closed unmerged): lane-remove <lane_dir> --abandon` (never auto-abandoned); a `.meta-push-failed` marker in the lane ⇒ `human — <lane> meta-push-failed: <reason>`.
3. **parent check-off** — for each lane whose run file reads `## Status: done` and whose item is still `- [ ]` in the parent `## Queue`: `queue-checkoff <parent_runfile> <item>` and one parent `## Progress` line `fleet closeout: <lane> <item> done (PR <url>)`.
4. **primary sync** — `git pull --ff-only` when the primary is on its base branch with no tracked modification; a refusal (the same set as `closeout`'s sync) is a `skipped — <reason>` line, never a reset.
5. **lane removal** — `lane-remove <lane_dir>` for each closed-out lane, never with `--stop`: a live watcher or lane process refuses, printed `waiting — <lane> <refusal>` and re-checked on the next call. An unpushed-metadata refusal names its paths (`metadata not pushed (local_ahead <n>) — paths: <path>, …`, "Removal" below), so the waiting line says which file to push — never a hand diff of `list-managed` against the metadata branch.
6. **after the last lane is removed** — `rmdir` the `<primary>-lanes/<run_id>/` directory only when empty, else `kept <dir> — contents: <names>` (salvage and `L<n>.*` logs are kept by design); `lane-status <parent_runfile> --leaks`, its first line appended to the parent `## Progress` as `fleet closeout leaks: <first line>`; `sweep: unavailable (automate-followups/22 not shipped)`; **main health** — the `ci` check conclusion of `origin/<base>` HEAD via `gh`: `failure` ⇒ `wave_paused: main_red after <sha>` appended to the parent `## Progress` and printed (no revert, no block); then, when the parent Queue has no `- [ ]` left, **the parent finalize** — under the still-held wave lock, exactly as §6 "Termination" ends a sequential run: ONE validated `runfile-write` that clears the `## Current` `- wave:` line (`current-wave --wave null`), writes `## Status: done` and `pause_reason: null` (`current-set --pause-reason null` on the staged copy), then the parent `## Progress` line `<ts> wave closed — Queue empty, run finalized`, `trail-pr <parent_runfile> --reason done` (its line printed and appended) and, branch mode OFF only, `trail-unstage <parent_runfile>`; one `fleet-closeout: finalize — <outcome>` line per step (a re-run on a `## Status: done` parent prints `finalize — skipped (already done)` and writes nothing; a refused write — or a run lock held by another owner; a free one is taken for the write — prints `finalize FAILED — <reason>`, leaves the run file unchanged and does not change the exit code) — and then, whatever the finalize printed, `run-lock.sh release --owner "automate-lanes:<run_id>"` and `fleet-closeout: wave closed — lock released`. A Queue item left for the next wave ⇒ no finalize and `lock kept — <n> Queue item(s) remain unchecked`.

Honest limits: a lane counts as merged only when its OWN PR reads `MERGED` (`reconcile-item`) — GitHub marks a lane PR merged when the wave PR is merged with a merge commit (its head is then an ancestor of the base; a squash merge does not); a lane PR the wave integration left open keeps reading `awaiting_merge`, and `fleet-closeout` waits on it. Neither `wave-build` nor `fleet-closeout` merges a PR or pushes a lane branch; the trusted-merge executor stays §10's alone (§11).

### Policy answers

A lane relays every question its engine asks. Most are decisions; a few are formalities the owner answers the same way every time. A **policy answer** is the owner's own answer to such a formality, given in advance and applied by an exact lookup — never a model judgement (parallel-automate/21 Part B).

- **Gate catalog — one authority.** Every engine ask is a gate with a stable code (at most 12 characters, the ask tool's `header` limit), its exact option labels and a policy, `allowed` or `human-only`. The ONE authoritative table is `scripts/lane-policy.sh catalog`; `docs/LANE_GATES.md` mirrors it (`test-lane-policy.sh` fails on drift). Read codes, labels and which gates are `allowed` there — this skill does not restate them. The engine asks each `allowed` gate with `header` = its code and the catalog's labels (a `(Recommended)` marker is allowed and stripped before comparison); a human-only gate is asked with no code; a question whose `header` is not a catalog code is ALWAYS the owner's.
- **Project policy — human-stamped.** `.agent/lane-policy.json` (tracked): `{"schema_version":1,"answers":{"<code>":"<label>",…}}`. It counts only while stamped through the EXISTING `rules-check.sh` stamp valve (`skills/rules/SKILL.md` §8 / §8.1 — there is no second valve), checked in the primary: a selected must-rule with id `lane-policy` exists (`rules-check.sh --list-selected`); that rule's `binds` array names `.agent/lane-policy.json` (read with `jq` as data — its check is never run here); the policy file is git-tracked; and `rules-check.sh --stamp-state` (read-only: executes nothing, never prompts, writes no stamp) prints `stamp<TAB>match`. Anything else ⇒ the whole project policy is ignored and reported (`lane-policy: project policy ignored — <reason>`), never partially applied. A rule that fits: id `lane-policy`, `enforcement: must`, a check that always passes on a valid file (for example `jq -e .schema_version .agent/lane-policy.json`), `binds: [".agent/lane-policy.json"]`. The stamp hashes the WHOLE selected must-rule set, so editing the policy file, this rule or any other must-rule turns project answers off until a human re-runs `/rules check --confirm` — fail closed by design. That confirm runs every must-check, and a stamped failing countable check blocks the merge gate (§10 condition 7), so keep this rule's check trivially true on a valid file.
- **Wave policy — owner-set.** `lane-policy.sh wave-set <parent_runfile> <code>=<label> …` writes `.supervisor/automate/<run_id>.wave-policy.json` and one parent `## Progress` line `wave policy: <code>=<label>, …`. It refuses (exit 1, nothing written) a code that is not `allowed` or a label that is not one of that code's catalog labels. The coordinator calls it ONLY with the owner's own answers to the wave-planning ask (per-wave loop step 4). Honest limit: the file is not owner-authenticated — the same trust level as `lane-answer`'s answer-pending file.
- **Resolve and carry.** `lane-create` runs `lane-policy.sh resolve <parent_runfile>` in the PRIMARY — the stamp is keyed per clone, so a lane cannot verify it — and writes the result into the lane's `lane.json` as `policy`: `{"policy_sha": …, "sources": […], "answers": {…}}`, the wave policy winning per code, only `allowed` codes with valid labels kept (anything else reported and dropped), or `"policy": null` when nothing is answered. No policy file and no wave policy ⇒ `null`, and the lane behaves exactly as before.
- **Decide and apply — the lane's OWN hook.** Before recording a question and deferring, the lane's `relay-hook` runs `lane-policy.sh decide` against `lane.json`'s `policy`. It answers only when EVERY question in the call has a catalog code whose policy is `allowed`, options whose labels (`(Recommended)` stripped) equal that code's catalog labels as a set, and a policy answer; otherwise it prints `human` — never a partial answer. On an answer the hook validates it exactly like an owner answer, writes the question file and an answer file marked `source: "policy"` with `policy_sha`, `gate`, `via: "policy"` and `at` (`docs/result-schemas/automate-run.md` §"Lane inbox answer file"), returns the same allow shape an owner answer gets (no defer, no resume), and appends one lane `## Progress` line `policy answer: <code> → <label> (policy_sha <first 12>)` (fail-SAFE: a failed append never blocks the answer). On `human` or any error the behaviour is the owner relay above, unchanged. The coordinator writes nothing into the lane for this — the lane's own hook writes the answer.
- **Visible and batched.** `lane-status <parent_runfile>` prints one `policy: <n> answered by policy[ since <first at>] — last <code> → <label> <at>` line per lane that has policy answers, or a header line `policy: none answered`. `lane-status <parent_runfile> --inbox` prints every lane's pending HUMAN questions (a question file with no answer file) in ONE list, oldest `asked_at` first: `<asked_at> <lane> <tool_use_id> <header> — <question>` plus its option labels.
- **Honest limits.** Removing the stamp turns policy answering off at the NEXT `lane-create`; a lane already created keeps the policy carried at its creation. `lane.json` is writable inside the lane (the lane's deny list is a tripwire, not a sandbox): the worst a tampered policy can do is answer an `allowed` gate with one of that gate's own labels, because codes are checked against the catalog at `wave-set`, at `resolve` and again at `decide`, and `decide` rejects a policy whose `policy_sha` does not match its answers.

### Dismissed findings, tokens, RESUME, removal

- **Dismissed findings across lanes:** `dismissed-pending` / `dismissed-decide` given the PARENT run file also include its lanes' drafts (`<parent>-L<n>--…--dismissed-*.md`); the `.supervisor/automate/*.dismissed-decisions` record is a meta-sync managed path, so decisions survive `lane-remove`.
- **Token split:** `--max-tokens T` on a parallel run is passed to `lane-create`, which records `floor(T / N)` in `lane.json` as that lane's own ceiling (enforced inside the lane as today, §6). The parent total is `read-token-ledger.sh` with `--root <lane>` repeated (summed into one line); `lane-status --tokens` prints per-lane and parent totals. No "checked between waves" claim — a one-wave run would never be checked. The totals are REAL since parallel-automate/24 F8 (before it every ledger line was a transcript-byte proxy and every TOTAL read 0, so no ceiling could trip — sequential runs included): `emit-token-ledger.sh` reads each subagent's own transcript usage, once per message id. Worker spend counts too: the `loomwright:worker` hook matcher runs the emitter (before the PR #435 fix-now it did not, so the usually-largest share never reached `--max-tokens`). `TOTAL` includes cache-read tokens (usually its largest part). Still NOT counted: the main thread's own tokens, CI-side `claude-review` spend, a `--parallel` coordinator's own run (it runs no `/autonomous`, so its run file names no session — `LEDGER_UNREADABLE=1` for the parent root alone is expected), and the output tokens of a message whose final transcript line is absent (its per-field max is counted — an under-count). Contract: `docs/ARCHITECTURE_CONTRACTS.md` §"Token ceiling".
- **RESUME:** in the primary, `resume-glob` skips every lane run file (a `<parent_run_id>-L<n>` run id in the title whose parent is engine-minted or has its run file beside it — a hand-made `nightly-L3` stays listed), so lanes never pollute the parent's resume; inside a lane clone it lists only that lane's own run. RECONCILE rebuilds lane belief from the lane run files + `gh` (`lane-status`); a vanished lane directory is `missing` and needs a human.
- **Removal:** `lane-remove <lane_dir> [--stop] [--abandon]` salvages first and refuses (fail CLOSED) on a live process, a live watcher, `awaiting_input`, unpushed metadata (read from `meta-sync.sh status --paths`; the refusal names up to five of the unpushed — or, on `conflict`, conflicting — paths, then `+<k> more`: `metadata not pushed (local_ahead 1) — paths: .supervisor/requirements/proposed/<name>.md`), a failure marker, and `gone` without `--abandon`. **`--abandon` on a lane `lane-status` reads `gone`** (its PR closed unmerged — the owner's decision) records it the way `reconcile-status --apply` records an `# abandoned:` Queue row, once no lane process runs: every done heading of the lane's requirement becomes `## Status: done_with_escalation — ABANDONED (- [x] <item>  # abandoned: PR closed unmerged — lane-remove --abandon)` (the evidence gate's one exemption), a `jobs/done/` brief pointing at it moves to `jobs/failed/`, and the lane's metadata is pushed exactly as at the wave end (`trail-pr --reason abandoned`) — so the lane is removable with no hand step and nothing pushed claims the unmerged work done. Its one parent `## Progress` line, `lane abandoned: <lane> (<run_id>) — state <the state lane-status reads>; salvage kept at <primary>-lanes/<run_id>/salvage/<name>`, carries no absolute path (no lane subcommand writes one into a run file). **Salvage and logs** stay at `<primary>-lanes/<run_id>/salvage/` and `<primary>-lanes/<run_id>/L<n>.stream.log` / `.stdin.json` / `.died`. End of wave: `lane-status <parent_runfile> --leaks` against the wave-start snapshot (run by `fleet-closeout` after the last lane is removed, "Wave close" above); its `lanes-dir` section excludes exactly those kept artifacts BY NAME (never a glob), so a clean wave reads `leaks: none` while a lane directory left behind, or any other file there, still reads as a leak. Its `merge-watch` section (header `## merge-watch v2`) lists `<pid> <pr_url>` per LIVE watcher read from the `*.merge-watch` markers of the primary and of every lane in the table — never a process-name match, which also caught any process merely naming the script (wave W3: `leaks: found — merge-watch` with no watcher running); a wave-start snapshot written before that format is not compared on that section (`merge-watch: not compared`, named on the first line), never a false `found`. Honest limit: a watcher with no marker is not listed.

### Fleet health

The sampler appends one line per interval to `.supervisor/automate/<run_id>.fleet.log` (CI-slot holders/waiters, load, swap, free memory, per-lane RSS); its memory guard writes the trip file `.supervisor/automate/<run_id>.memory-pressure` that holds every launch and resume, and it notifies once per crossing. `lane-status --resources` prints the latest sample and the peak. Lane test runs share the repo's CI slots (`run-self-tests.sh` takes a `ci-slot.sh` slot). Keep-awake is only SUGGESTED (macOS `caffeinate -i -w <coordinator pid>`); only `lane-status --keep-awake` starts it. `machine.keep_awake` reads macOS power assertions (`pmset -g assertions`), not only a `caffeinate` process: the Claude desktop app's "Keep computer awake while Claude works" hold counts as `held`, but it lasts only while a Code session works and headless lanes are not Code sessions, so `keep_awake_lasting` is true for a `caffeinate` holder alone, the suggestion stays until one holds, and `--keep-awake` still starts one when only the app holds (`keep_awake_holders` lists each holder; seconds-long macOS daemon assertions are listed as `other` and never make it `held`).
