## §9 — Two modes + READY / ESCALATED semantics

**`READY` = "ready, left open for a human" — NOTHING in the plugin merges.** `/review-pr` / `review-heal` and Supervisor Phase 4.5 all terminate at `READY`/`PASS` and leave the PR open; the merge is the engine's OWN step (GATE), which the driver runs — never merge by hand.

**Validation gate first, in both modes:** a `READY` drain reaches the safe-mode park or `gate-eval` only after `validation-gate` (the driver's `validation` step, §6 step 4 GATE) reads `none`, `ok` or `waived`; an `unrun` running-system Validation step the owner does not waive takes the `ESCALATED` park below with `escalation_cause: validation_unrun`. `gate-eval` does not run it itself.

- **Safe mode (default):** at the GATE, a `READY` drain that passed the validation gate parks `awaiting_merge` (`## Status: paused`; single-open-PR invariant), **park first, then ask**: `dismissed-drafts`, write the park state, arm the merge watcher, notify, `run-lock.sh release` (no `trail-pr` — the PR is unmerged), and only then `park-ask-gate` and the owner's decisions (fix-now only while the PR still reads `OPEN`, under a re-acquired run lock, at most one re-pass; otherwise a follow-up). Under `--non-interactive-fallback` nothing is asked and the drafts precede the park. A human merge makes the watcher run `closeout`; the next item waits for the owner's `--resume`. **Nothing is merged automatically.**
- **`--auto-merge` mode (opt-in, default OFF, gated):** at the GATE, `gh pr merge --squash` fires **only** when the trusted gate (§10) holds; otherwise fail **CLOSED** → park + notify — that `PARK: <reason>` park is `awaiting_merge` with the PR open, so it takes safe mode's park-first order: `dismissed-drafts`, the park state, the merge watcher, the notify and `run-lock.sh release` first, then `park-ask-gate` and the §6 "Dismissed-findings decision step (before the park)" decisions (after a `MERGE`, only its `dismissed-drafts` runs and the drafts wait for the next interactive PICK).

**`ESCALATED` never merges and PARKS the run** in BOTH modes — after the §6 "Dismissed-findings decision step (before the park)" runs (decide-then-park; park-first is for the READY park only): `## Status: paused`, `pause_reason: escalated`, notify, `current-escalation` from the drain's `REVIEW_HEAL_RESULT` `escalation_*` fields (§3) — or, for a validation-held `READY`, `--cause validation_unrun` — arm the merge watcher (a merge closes the item out; only a `check_pending`/`check_red_unrelated` cause gets one settle re-check, never `validation_unrun`), then `run-lock.sh release` — no `trail-pr`; it does **NOT** pick a new item. To proceed:

- **resolve the PR** (fix + merge, or close), **OR**
- **mark the item `skipped`/`abandoned`** in `## Queue` (§5), **OR**
- **for `validation_unrun` only:** paste the step's fenced output into the PR body — `--resume`'s RECONCILE re-runs `validation-gate` and, on `ok`/`waived`, writes the READY park (§6 step 1),

then `--resume`.

## §10 — Trusted auto-merge gate (7 conditions, fail CLOSED, SELF-RESOLVING)

> **Execute via the helper, not a re-implementation:** the driver's `gate-eval` step runs `automate-helpers.sh gate-eval <pr_url> <ctx.json> [--root <checkout>]` (§1.5) — the **single** implementation of this gate and the **only** code path that executes `gh pr merge --squash`. It prints `MERGE` (after merging) or `PARK: <reason>` and is self-tested for fail-closed behaviour on every condition. The conditions below are the SPEC `gate-eval` implements — read them to explain a park, never to re-run one. The full recipe and every park reason are `gate_eval()`'s header comment in `automate-helpers.sh`.

**SELF-RESOLVING.** The gate computes conditions 2–7 itself from live ground truth (`gh`, GraphQL, `classify-risk.sh`, `rules-gate-verdict.sh`, and two artifact-file reads); a caller cannot hand it a verdict for any of them.

**`ctx.json` — exactly the six keys only the drain/loop can know:** `drain_result` (`READY|ESCALATED`), `termination_reason`, `ready_sha`, `trust_unprotected`, `review_heal_result_path` and `supervisor_result_path` (the verbatim `REVIEW_HEAL_RESULT` / `SUPERVISOR_RESULT` artifacts). The driver writes it as `<run_id>.gate-ctx.json`; never write or edit it by hand.

**GATE-OWNED KEYS — REFUSED, NEVER TRUSTED.** A `ctx.json` carrying ANY of `high_risk`, `risk_reasons`, `head_sha`, `base`, `review_decision`, `unresolved_human_thread`, `protection_enforceable`, `checks_green`, `rubric_satisfied`, `rules_gate`, `rules_ok`, `rules_check` — whatever the value — parks `PARK: ctx_carries_gate_owned_key`, checked FIRST, before any condition.

`gh pr merge --squash` fires **ONLY** when **ALL SEVEN** conditions hold. If any fails or is **unreadable** ⇒ fail **CLOSED** → park (`pause_reason: awaiting_merge`/`escalated`) + notify. Two values are NOT automatic parks: a reviews-not-required `reviewDecision` (decided by cond 4) and an absent rubric (N/A, cond 5). This gate is the **only** sanctioned, EXECUTED `gh pr merge --squash` in the plugin (§11).

1. **Owned drain == `READY`, AND its `termination_reason` is NOT `sub_floor_converged`.** The owned inline drain (§7) returned `READY`; a `sub_floor_converged` `READY` (its last round skipped the all-channel bot-finding re-scan) parks like a non-`READY` result, and a missing/unreadable `termination_reason` parks. A `ci_untrusted` termination always pairs with `ESCALATED`, and the gate also parks it directly (defense in depth). `died` / `superseded_by_merge` never reach the gate; passed as `drain_result` they park `drain_not_ready`.
   - **Cross-checked against the artifact, never trusted as a bare assertion.** The gate parses `decision`/`termination_reason` from the `review_heal_result_path` artifact itself: missing/unreadable ⇒ `PARK: review_heal_result_unreadable`; disagreeing with the ctx ⇒ `PARK: drain_result_mismatch`.

2. **Head SHA still == the `READY` SHA AND base == `main`.** The gate re-reads `gh pr view <url> --json headRefOid,baseRefName,statusCheckRollup`; a moved head (the approved state is stale) or a non-`main` base ⇒ **do not merge**. `ready_sha` is the drain's claim, cross-checked against that live read.

3. **`reviewDecision` not blocking AND no unresolved thread from an actor outside the trusted-actor set.**
   - The gate's own `reviewDecision` read: `CHANGES_REQUESTED` / `REVIEW_REQUIRED` park; `null` (reviews not required — an unprotected or checks-only branch) is decided by **cond 4**; a failed read ⇒ `PARK: review_decision_unreadable`.
   - Threads are **GraphQL-only** (there is **no** `gh pr view --json reviewThreads` flag); the gate runs its own copy of `review-heal/SKILL.md` §"Step U1 — All-Channel Read" (b)'s query (minus the unused `body` field). An unresolved thread whose first comment's author is **NOT** in the user-scope trusted-actor set (the allowlist `classify-bot-review.sh --trusted-actors` and `wrap-external-text.sh` resolve; an absent file trusts nobody) ⇒ BLOCK — stricter than §U3's drain-time bot-vs-human split. `hasNextPage == true` or any GraphQL error ⇒ fail CLOSED.

4. **Enforceable branch protection (OR explicit `--trust-unprotected`).** The gate reads `gh api repos/<owner>/<repo>/branches/main/protection`: enforceable = `required_approving_review_count >= 1` OR required status checks; a **404** ⇒ unprotected; **ANY OTHER error** ⇒ `PARK: protection_unreadable`. Classic branch protection only (rulesets are out of scope in v1). A checks-only-protected branch may merge; a truly unprotected branch merges ONLY with `--trust-unprotected`. **Scope of the flag: `--trust-unprotected` overrides condition 4 ONLY** — it does not touch condition 6 (a high-risk diff parks with or without it), and there is no flag, config key, or project file that overrides condition 6.

5. **Required checks green AND rubric satisfied.**
   - Required checks: the required-context list from condition 4's protection payload (`review-heal/SKILL.md` §"Step U2 — Required-check discovery"), cross-referenced against condition 2's `statusCheckRollup` — all green, or none required (vacuously green).
   - **Rubric satisfied — a FILE READ, never a caller-asserted value.** The gate parses `rubric_score: N/M` from the `supervisor_result_path` artifact: `N == M` ⇒ satisfied; no such line ⇒ **N/A — NOT a blocker** (no `## Outcomes Rubric`); the file missing/unreadable ⇒ `PARK: supervisor_result_unreadable`.

6. **NOT a high-risk diff — the gate ITSELF invokes `classify-risk.sh`, NO override of any kind (owner decision R5).** It runs the plugin's `classify-risk.sh main <live head_sha> --root <checkout>` on the head condition 2 confirmed; no `ctx.json` input feeds it. The script is the ONE implementation of the heuristic, trusted-root instruction/config surfaces included (`classify-risk.sh --kind-table` prints the rules; `docs/RESULT_SCHEMAS.md` §SUPERVISOR_RESULT carries the one committed copy — not restated here). MERGE only on the JSON boolean `false`: `true`, `null` (unclassifiable), a missing key or ANY string — including `"false"` — park `PARK: high_risk_diff (<first 3 reasons; "; ">)`. **Nothing overrides this condition** — not `--trust-unprotected` (cond 4 only), not a config key, not an `exclude` list (`.agent/risk.json` has none; projects may only ADD surfaces, and the script reads it from the base ref `main`, never the PR head).

7. **No stamped, gate-countable `must`-rule check fails — the gate ITSELF invokes `rules-gate-verdict.sh`, NO override of any kind.** Evaluated AFTER cond 6, so every earlier PARK reason keeps its precedence. The gate runs the plugin's sibling `rules-gate-verdict.sh --root <checkout>`; no `ctx.json` input feeds it. The helper never runs a `check` itself (it delegates to `rules-check.sh`, the SOLE executor, `skills/rules/SKILL.md` §9) and prints ONE verdict JSON. `gate-eval` reads `.verdict` in the AFFIRMATIVE form: `ok` or `none` ⇒ holds; anything else PARKs with a NAMED reason:
   - **Checkout pin — evaluated FIRST, before the helper runs.** The verdict is trusted only for the bytes being merged: `<checkout>`'s HEAD must equal the live `headRefOid` condition 2 confirmed (a different, unreadable or non-checkout HEAD ⇒ `PARK: rules_gate_head_mismatch`), and the tree must be clean outside the two engine-owned paths `.supervisor/` and `.claude/agent-memory/` — a tracked or staged change, an untracked file not ignored by a committed `.gitignore` or the user's global ignore, an assume-unchanged / skip-worktree flag, a dirty or moved submodule, or a failing `git status` ⇒ `PARK: rules_gate_dirty_tree`. Both are fail-CLOSED with **no override**, and on either park the helper is not called.
   - **Fix hint for a `rules_gate_dirty_tree` park on a clean checkout:** commit an ignore line for the file or directory, or add it to your global ignore — `.git/info/exclude` is never honoured.
   - `fail` ⇒ `PARK: rules_check_failed (<up to 3 countable ids; "; ">)`.
   - `unresolved` ⇒ `PARK: rules_check_unresolved (<ids>)` — a truncated or forged replay can only ADD this blocker, never remove one.
   - `unstamped` ⇒ `PARK: rules_unstamped (<text>)`, the text chosen by the helper's optional `unstamped_reason` (message only — the park is keyed on the verdict). **D3's middle form:** it fires because ≥1 countable must-check exists now, OR because the countable id set DRIFTED from the one recorded at the last `/rules check --confirm` (a store whose must-checks are all advisory, and always were, answers `none` and does not park). A PR that edits a file a countable check `binds`, or changes WHICH rules count, lands HERE, so it cannot turn a failing bound check into a counted pass without a human re-running `/rules check --confirm` (`skills/rules/SKILL.md` §8.1).
   - `cmd_disabled` (`RULES_CHECK_NO_CMD=1` in the gate's environment) ⇒ `PARK: rules_cmd_disabled` — the gate cannot verify.
   - `unreadable`, helper absent/unreadable, non-zero exit, empty / non-JSON / non-object output, a missing / null / non-string `.verdict`, or any unrecognised verdict string ⇒ `PARK: rules_gate_unreadable`.
   Which must-checks count is decided by the rule's `binds` declaration and `rules-check.sh --list-gateable` (`skills/rules/SKILL.md` §8.1/§8.2 — not restated here); an advisory (non-countable) rule's pass/fail is reported, never counted. **Nothing overrides this condition** — not `--trust-unprotected` (cond 4 only), not a config key, not a project file.

On all seven holding: `gh pr merge --squash --match-head-commit <live head> <url>` — the SHA pin binds the merge to the exact head conditions 2, 6 and 7 were evaluated against, so a push landing between those reads and the merge is refused by GitHub and parks `merge_command_failed` instead of merging unchecked code. Then SYNC (`closeout … --no-trail`, whose sync fast-forwards `main`) so the next item branches fresh (§6 step 5).
