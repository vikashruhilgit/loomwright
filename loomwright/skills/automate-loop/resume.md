## §4 — RESUME = glob + reconcile (run-file is BELIEF; git/gh is TRUTH)

> **Execute via the helper, not a re-implementation:** glob with `automate-helpers.sh resume-glob <automate_dir> --finalize` (step 1) and reconcile each in-flight item's belief vs `gh` ground truth with `automate-helpers.sh reconcile-item <pr_url> <belief>` ⇒ `merged` / `awaiting_merge` / `gone` (§1.5). (`reconcile-item` resolves the `gh`-PR-state half; the complementary `git branch --contains <sha>` corroboration below is done by the loop.) The protocol below is the SPEC those subcommands implement.

**On every start** (including bare `/automate` and any `--resume`):

> **Branch mode (opt-in):** when `setup-memory.sh mode` reads `on`, `automate-helpers.sh meta-entry` runs FIRST — before step 1's glob — and a `failed` verdict aborts or parks `meta_unreachable`; see §13.

**Start order (automate-followups/32):** `init-check` (only when `--parallel` was passed) → `meta-entry` (branch mode) → **`closeout-others`** → `resume-glob --finalize` (step 1) → list / ask (step 4) → `pick-guard` (a NEW run only, before §2's intake). **Lane guards at start (parallel-automate/05, §14):** whenever `--parallel` was passed, `automate-helpers.sh init-check --parallel N [--auto-merge]` runs FIRST — before `meta-entry` and before any write — and `refuse: auto_merge_with_parallel`, `refuse: parallel_out_of_range` or (N = 1 only, branch mode off) `refuse: single_lane_requires_branch_mode` stops the start with that line, nothing written; without the flag it is not called. When step 4 resolves to a NEW run (no incomplete run exists, or the owner chose start new) — sequential, `--parallel N>1` or single-lane mode (`--parallel 1`, §14 "Single-lane mode") — `mkdir -p .supervisor/automate` (the run file needs it anyway) and then `automate-helpers.sh pick-guard .supervisor/automate` run before §2's intake: `ok` (exit 0 — always the answer when the directory holds no `*.lanes` table, i.e. in every checkout that never ran a wave) proceeds and writes nothing, so a sequential start is unchanged; `refuse: live_lane <lane_run_id> <lane>` (exit 1), or any other `refuse: …` line, stops the start with that line printed — no intake, no `/product-owner` run, no run file, so there is nothing to park. A `--resume` of an existing run is not guarded here: a sequential run is guarded at every PICK (§6 step 1, which parks `live_lane`), and a coordinator resuming its own wave must reach its own live lanes (§14). **Cross-run close-out first:** `automate-helpers.sh closeout-others .supervisor/automate [--record <runfile>]` (§1.5) closes out every OTHER run whose `## Current` names a not-`done` item whose PR reads `merged` — a paused run's merged item no longer waits for that run's own `--resume` (§8) — and runs BEFORE the PICK-time run lock is taken (each close-out takes its own `automate-closeout:<run_id>` lock, which a held `automate:<run_id>` PICK lock would refuse, so it never runs inside the per-item loop). Pass `--record <runfile>` when the target run is already known (`--resume <run_id>`); otherwise append each printed `closeout-others: record — <line>` with `progress-append` right after the run file is created or selected. The `leftover` rows it prints go through §6 step 1's close-out leftover gate before the first PICK; a `run_lock_held` row (that close-out met the run lock held by a LIVE process) does not — nothing is parked, and the next start retries it (§6 step 1). It runs before the finalize glob on purpose: a run whose last item it just closed out is then finalized by `resume-glob --finalize` in the same start. **Concurrency (lane guard, §14):** `run-lock.sh` is per checkout, so two lanes (separate clones) could once close out or finalize the SAME run file content each in its own clone. The lane seam now prevents it: inside a lane clone (a present `.supervisor/lane.json`) `closeout-others` prints `closeout-others: skipped — lane clone` and closes nothing, and `resume-glob --finalize` finalizes only the lane's own run — `finalize-empty` refuses every other run there (`skipped — lane clone (not this lane's run)`); the coordinator runs `closeout-others` ONCE in the primary before it launches a wave. In branch mode `meta-sync.sh push` still arbitrates any residual double push (`meta_sync: conflict <path>` ⇒ `meta-push FAILED`), never a silent overwrite.

1. **Glob** `.supervisor/automate/*.md` for **run files** — a `*.md` carrying the `# Automate Run:` title line anywhere in the file (`is_run_file`, a shape check, not a filename rule) — **NOT** marked `## Status: done`. The title line may differ from the exact form only by an optional leading UTF-8 BOM, 0–3 leading spaces (the CommonMark ATX-heading limit), letter case, and whitespace (any between `#` and `Automate`, at least one between `Automate` and `Run`, any before `:`) — exactly one `#`, so an H2 `## Automate Run:` line, a line indented 4+ spaces, or a tab-indented line (an indented code block quoting the title) is **not** a run file (listing a quoted example would re-create `resume_ambiguous`). `RUN_TITLE_ERE` in `automate-helpers.sh` implements this once for every `is_run_file` caller (`resume-glob`, the `runfile-write` / `progress-append` / `queue-checkoff` validators, `plan-waves`); `build-handoff.sh`'s title reader carries a mirrored copy. The §6 steps 2–3 result sidecars (`<run_id>.review-heal-result.md`, `<run_id>.supervisor-result.md`), transient or committed, are excluded: they have no `## Status:` line, so without the shape check each would read as an incomplete run and make resume ambiguous. **Finalize before listing:** the glob is `automate-helpers.sh resume-glob <automate_dir> --finalize`, which first runs `finalize-empty` (§1.5) on every candidate — a run whose Queue is fully resolved and whose `## Current` item `closeout` already marked `done` (`paused` + `awaiting_go` + `remaining` 0) is written `## Status: done` with its `--reason done` trail and is NOT listed — so a finished lane run is never offered as "incomplete" (before this, every finished single-item run stayed `paused`/`awaiting_go` and every later RESUME listed it). Every other run is listed exactly as before and is not touched; a run whose lock is held is not finalized and stays listed. **Branch mode OFF:** each finalized run opens or pushes its own `chore/<run_id>-trail-<n>` trail PR (one per run, idempotent, never merged by the engine), so finalizing N runs can open up to N trail PRs at once — accepted; §6 step 1's `trail-gate` counts only the CURRENT run's own trail PR, so these never park the current run, and `finalize-empty` un-stages each finalized run's trail paths from the primary index right after its trail (they would otherwise ride into the next item's commit and make `closeout`'s sync see a dirty index).
2. The run file is the loop's **belief**. **Repair an unset `## Current` first:** `automate-helpers.sh current-rebuild <runfile>` (§1.5; §3 "`## Current` moves only through `current-set`") — a no-op (`skipped — ## Current set`) whenever `## Current` names an item that is not `done`, or a `done` item that is the LAST `picked` line's item; a `done` item that differs from the last `picked` item is stale (the PICK after a close-out skipped its `current-set`) and is rebuilt. When it prints a `current_rebuilt: <item> pr <url|null> state <s>` line, the item was rebuilt as `status: running` with `pause_reason: null` (never a stale pause reason beside `running`) and the PR found ONLY on a `ran /autonomous` line after the last `picked` line (never a closeout / trail / `cross-run closeout` line, which carry other PRs' URLs), and it never claims `awaiting_merge`/READY/`escalated` and never triggers a close-out: the RESUME stops at step 4's **continue / start new / archive** ask with the rebuilt `## Current` shown (interactive), or — under `--non-interactive-fallback` — parks `resume_ambiguous`-style (one `## Progress` line naming the rebuilt item and its `state`, `current-set <rf> --pause-reason resume_ambiguous`, no automatic close-out). **Then reconcile each in-flight item against GROUND TRUTH before trusting a checkbox** — a crash between merge and check-off makes belief and reality disagree:
   - **PR merged?** `gh pr view <url> --json state,mergedAt` — a merged PR ⇒ the item is `- [x]` (merged) even if the file still shows it `- [ ]`/`awaiting_merge`; a merge found here is also the evidence §6 step 1's `closeout` call acts on (its `brief-repair` step, then local cleanup, stamp, check-off, trail), before the next item is picked. **A merge that superseded the owned drain (automate-followups/20):** when the `## Current` item's `## Progress` segment (after its last `picked` line) has an `owned drain started` line with no later line recording that drain's terminal decision (`READY`, `ESCALATED` or `superseded_by_merge`), the drain was stopped before a terminal `REVIEW_HEAL_RESULT` — so BEFORE that `closeout`, write the `owned_drain_*` line with `owned_drain_started` = that line's timestamp and `owned_drain_result: superseded_by_merge`, and append `<ts> drain superseded_by_merge — PR merged before a terminal REVIEW_HEAL_RESULT` (never `null`, never an omitted field — §6 step 3's driver step `superseded` is the same write from a live loop).
   - **PR open?** an `OPEN` PR ⇒ the item stays `awaiting_merge`; nothing re-checks it on a timer except the merge watcher armed at that park, which runs `closeout` when the PR merges — the next item is still picked only on the owner's explicit `--resume` (§8).
   - **PR closed-unmerged or vanished?** a `CLOSED` (never-merged) or otherwise gone PR ⇒ the item is `gone` — neither merged nor live. Treat it like an `escalated` park requiring human resolution (§9): the run stays paused until the human re-opens/redoes the work or marks the item `skipped`/`abandoned` in `## Queue` (§5). Never silently re-pick or auto-check a `gone` item.
   - **Branch landed?** `git log origin/main --oneline` / `git branch --contains <sha>` — verify the branch actually reached `main` (never assert "merged" from memory).
   - **Requirement stamped?** the requirement file's `## Status: done` stamp.
   - **No PR yet (`pr: null`, `pause_reason: rate_limit`)?** RUN failed before a PR ever existed (see §6 step 2's rate-limit park, the driver's `rate-limit` step), so there is nothing for `gh` to reconcile — this item is left exactly as parked (still `- [ ]`, still the `## Current` in-flight item) and falls straight through to step 4/6 below: resuming just re-picks it and retries RUN.
   - **A DETACHED drain died for this item's PR (`drain_died`, red-team-hardening item 04)?** Check `.supervisor/review-dispatch/*.died` for a marker whose `pr_url` field equals this item's `## Current` `pr:` URL. This is a SEPARATE fact from the `owned_drain_result` this loop's OWN inline `/review-pr --until-mergeable` drain records (§7, §6 step 3) — a `.died` marker only ever comes from the DETACHED `dispatch-pr-review.sh` dispatcher (Supervisor's step 5.5 or the `PostToolUse[Bash]` hook backstop), which this engine's owned drain never goes through. If a matching `.died` marker exists, treat it as `owned_drain_result: died` in `## Current` and `## Status: paused` / `pause_reason: drain_died` — **explicitly NEVER `awaiting_merge`**, because a died drain never reached a `READY`/`ESCALATED` verdict to park on in the normal sense; there is no `REVIEW_HEAL_RESULT` to trust either way, and the PR's true readiness is simply unknown. This check runs BEFORE the merged/open/closed reconcile above would otherwise re-pick or resume the item as if a normal drain outcome existed.
   - Reconcile each item, then rewrite `## Queue` checkboxes + `## Current` atomically (§3) so belief matches truth.
3. **RECONCILE also restores a crash-stranded config backup** (§7) — if `## Run Config`'s `config_backup` sidecar still exists on disk, the prior tick died with `.auto_review` suppressed; restore it (or delete `config.json` if originally absent) before proceeding.
4. **If an incomplete run exists**, `AskUserQuestion`: **continue / start new / archive** — gate `AUT-RESUME`: ask it with `header: "AUT-RESUME"` and exactly the options `Continue` · `Start new` · `Archive` (the catalog's labels, `loomwright/docs/LANE_GATES.md`; a `(Recommended)` marker is allowed). Any other header or wording is not a catalog gate, so no policy ever answers it.
   - **Cannot ask** (`--non-interactive-fallback`, or the ask tool is absent) with exactly ONE incomplete run and no `--resume`: **fail closed — no option is auto-picked.** `continue`, `start new` and `archive` are each the owner's choice, and `--resume [<run_id>]` is the explicit opt-in that already exists for `continue`. Ask nothing, PICK no item, resolve no source, create no run file, and write nothing to the incomplete run (no `current-set`, no `progress-append`); print `automate: resume_requires_flag_non_interactive <run_id>` with the hint to re-run with `--resume [<run_id>]` (or interactively, to start new / archive), and stop. The stop message also prints, verbatim, every `closeout-others` `record` line and every `leftover` row produced at start — no run file receives them on this path, so the printout is their only carrier; the leftovers reach the close-out leftover gate (§6 step 1) on the owner's next interactive `--resume`. **Bare and source-bearing starts take the same rule:** a `"<prompt>"` / `--folder` / `--backlog` source is NOT an implied `start new` while an incomplete run exists — no `/product-owner` run, no Queue, no second run file beside it. The only writes before this stop are the ground-truth start steps every start runs (`closeout-others`, the `resume-glob --finalize` glob, steps 2–3's reconcile), which no owner choice gates.
   - `--resume [<run_id>]` targets one explicitly; with the id omitted it targets the **most-recent incomplete** run.
   - Under **`--non-interactive-fallback`**, an **ambiguous** resume (more than one incomplete run and no explicit id) **fails closed**. In `AUTOMATE_RUN` this is persisted as **`pause_reason: resume_ambiguous`** in `## Current` (the run file has no `status_reason` field — that field is the inner `/autonomous` layer's `AUTONOMOUS_RUN`, which never sees this stop: RESUME runs before any `/autonomous` call, and `/autonomous` has no ambiguous-resume reason of its own). This stop prints the `closeout-others` `record` lines and `leftover` rows verbatim exactly like the one-incomplete-run stop above.
5. **Re-pass non-persisted passthrough flags.** `## Run Config` does NOT store `--notify` / `--non-interactive-fallback` / `--cheap` (§11), nor `--inline-phases` (kept for the current item only) — a resume or `/loop` tick that omits them silently reverts to defaults. This matters most for **`--cheap`**: omitting it reverts the remaining queue to the full-cost profile with cumulative dollar impact, so re-pass `--cheap` on **every** `/automate --resume` invocation and `/loop` tick of a cheap run.
6. **Resuming a `rate_limit` park.** This round-trips through the EXACT SAME RESUME flow above — no second reconcile code path, no second park vocabulary. The only difference from resuming `awaiting_merge` is *what* step 2 finds: an `awaiting_merge` item has a `pr` to reconcile against `gh`; a `rate_limit` item has `pr: null` and nothing to check (the "No PR yet" bullet above), so reconcile is a no-op for it. Either way, `continue` (step 4) re-enters the per-item loop at §6 step 1 RECONCILE and proceeds from there — for a `rate_limit` item that means falling straight through to §6 step 2 RUN, retrying the SAME item (the rate-limit window has presumably passed by the time a human or `/loop` resumes).
7. **RECONCILE also runs reconcile-status** — the `reconcile-status` dry-run pass (queue-hygiene/01) — **BEFORE step 4's PICK**: `automate-helpers.sh reconcile-status .supervisor/requirements` (no `--apply` — this is the engine's own RESUME reading ground truth back for requirement files OUTSIDE this run's own `## Queue`, the same "read it back, never infer it" posture as steps 1–2 above, kept dry-run because promoting a requirement's `## Status:` is a standing human-owned act, not an engine side-effect). For each `plan\t<file>\t…` row it prints, `automate-helpers.sh progress-append <runfile> "reconcile-status: would stamp <file> (<status>)"` — ONE `## Progress` line per row, appended before PICK runs. An `info\t…` row (a `brief-shipped` file with no merged-PR evidence; one with evidence prints a `plan` row like any other) is NOT progress-appended — it is advisory-only and never actionable from inside a run. Zero `plan` rows ⇒ no line, no-op. This step runs only after step 4 resolved to continue (an explicit `--resume` or an interactive pick); on step 4's can't-ask stops (`resume_requires_flag_non_interactive`, `resume_ambiguous`) it never runs, so nothing is appended to the incomplete run. This never writes to a requirement file itself; promoting the plan to a real stamp is `automate-helpers.sh reconcile-status .supervisor/requirements --apply`, run by a human (or a dedicated queue-hygiene pass), never by `/automate` itself.
8. **Pending dismissed-finding decisions (automate-followups/12).** `## Current`'s `pending_decisions: <n>` is BELIEF; the truth is the drafts on disk, read with `automate-helpers.sh dismissed-pending <runfile>` (this run's whole undecided set, every item's). RESUME never parks or blocks on it and it is never a `pause_reason`: an interactive resume asks the undecided set at §6 step 1 PICK (Follow-up / Drop only — the PICK-time ask there), before RECONCILE's `closeout`; a `--non-interactive-fallback` resume asks nothing and the count stays in `## Current`. A `fix_now_reentered: true` line means that item's one fix-now re-pass already ran.

## §5 — Skipped / abandoned items

An item the human (or the loop) abandons is written in `## Queue` as:

```md
- [x] <path>  # skipped: <reason>
- [x] <path>  # abandoned: <reason>
```

- **Checked-off ⇒ never re-picked** ("next unchecked item" skips it). The reason is ALSO logged in `## Progress`.
- **`remaining` counts only `- [ ]` items**, so a skipped/abandoned item does **not** block `## Status: done`.
- This is the **documented way to unblock an `escalated`-parked run without merging** (§9): mark the parked item `skipped`/`abandoned`, then `--resume`.
- **A skip/abandon check-off runs `trail-pr`** (`--reason skipped`/`--reason abandoned`) — trigger (c) of "Trail PR after merge and at run end": at §6 step 6 when the loop writes it, at RECONCILE when a human wrote it. The item's requirement rides only when it carries no done stamp or its PR merged (the evidence gate there), so an abandoned escalated item never lands a done claim.
