# Automate Loop Skill

The **single source of truth** for the `/automate` generic automation engine — the protocol that walks **arbitrary work from any starting point** through to a reviewed PR (and, opt-in, a trusted merge). This skill is the **authority**; the `/automate` command body (`${CLAUDE_PLUGIN_ROOT}/commands/automate.md`), the `AUTOMATE_RUN` run-file layout in `docs/RESULT_SCHEMAS.md`, and the helper scripts under `scripts/` all **reference** the names and contracts coined here and must not re-coin or rename them.

> This is a **reference contract** skill (markdown prose, NOT executable code), in the same spirit as `skills/review-heal/SKILL.md` and `skills/autonomous-loop/SKILL.md`. There is **no `-runner` agent** — `/automate` is inline-only (agents stay 14).

---

## §1 — Purpose & Layering

The plugin can drive **one** requirement deep (`/autonomous`), but nothing walks **arbitrary** work from any starting point. `/automate` is the outermost loop. The layering is strictly nested:

```
/autonomous (one requirement)  ⊂  per-item loop  ⊂  /automate (source → Queue → loop)
```

- **`/autonomous`** runs one requirement end-to-end to a PR (Launch Pad → Supervisor, with Phase 4.5 self-heal + Rubric Grader). The engine drives it `--single-iteration`.
- **The per-item loop** wraps a single `/autonomous` run with an OWNED until-mergeable drain, a trusted-merge-or-park gate, and a `main` re-sync — see §6.
- **`/automate`** resolves a SOURCE into a `## Queue` once, materializes ONE run file, and drives each Queue item through the per-item loop.

The per-item engine is **source-agnostic** — only the *intake* differs, and intake is just "convert the source into the run file's Queue, once" (§2). It is **NOT a pluggable adapter framework**. **`/backlog` is NOT a separate command** — a folder or a backlog-doc is simply one *kind* of source.

### Non-goals (v1)

- Sources beyond **prompt / folder / backlog-doc** (issues, Beads `bd ready`, Jira are additive later — each just populates the Queue, no framework).
- A `-runner` agent (inline-only; agent count stays 14).
- QA-in-loop.
- Parallel / multi-item execution.
- **Multiple concurrent open PRs** — BOTH modes keep a **single-open-PR invariant** (§8); `escalated` parks the run, it never opens a second PR.
- A separate registry / manifest / `progress.jsonl` / dashboard file — the **single run file is enough** (§3).

The scriptable, security-critical steps of this protocol are **NOT re-implemented in prose each run** — the inline `/automate` loop **executes them by shelling out to a single self-tested helper**:

```
bash "${CLAUDE_PLUGIN_ROOT}/scripts/automate-helpers.sh <subcommand> [args…]"
```

so **the tested code IS the executed code** (one implementation, guarded by `scripts/test-automate-helpers.sh`). **The SKILL section prose is the SPEC each subcommand implements — single source of truth; the helper conforms to it, never the reverse.** When a contract changes, change the prose here first, then make the helper conform.

## §2 — Intake: any source → the Queue (convert once, NO adapter framework)

Exactly **one** source is resolved per run. Resolution produces the **FULL** ordered list of items, which is written to `## Queue` and **shown to the user for confirmation before processing** (a prompt that explodes into 40 files never runs silently). Under `--non-interactive-fallback` the confirmation prompt is skipped and the `--limit` cap is enforced without asking.

### Prompt source — `/automate "X"`

- Runs **`/product-owner`** on the prompt text. This is a **REUSE**, not a new code path: Product Owner already writes `.supervisor/requirements/*.md` story files (and, in Beads-absent mode, an optional `_BACKLOG.md`).
- The **generated file paths become the `## Queue`** (in PO's emitted order; if PO also wrote a `_BACKLOG.md`, prefer its documented dependency order per the backlog-doc rules below).
- **1 generated file ⇒ single-item run; N files ⇒ loop.**
- **Bare `/automate`** (no prompt, no source flag): **attempt RESUME first** (§4); if no incomplete run exists, `AskUserQuestion` *"What do you want to automate?"* and then proceed as a prompt source.
- **0 generated files ⇒ report + stop** (never wedge) — the run file records `## Status: done`, `remaining: 0` with a `## Progress` note that the prompt produced no items.

### Folder source — `/automate --folder <dir>`

- Enqueues **every `.md` in `<dir>`** as a Queue item, **skipping any already marked `## Status: done`** (read each file's `## Status:` stamp; a done file is excluded from the Queue, not enqueued-then-checked).
- Order = directory order unless a sibling `_BACKLOG.md` documents a build order (then defer to backlog-doc ordering).

**Two independent not-ready skips exist for the folder / backlog-dir-fallback sources (harness-port/02):** (1) the pre-existing `proposed/` **subfolder** convention — `"$dir"/*.md` does not recurse, so a file kept inside a `proposed/` subfolder (as `/propose` writes, and `commands/propose.md` documents) is simply never scanned; and (2) a `## Status:` heading stamp of `proposed|parked` on a file that IS scanned — this file is read, its stamp checked (`is_not_ready()` in `automate-helpers.sh`), and it is then skipped (excluded from the Queue), the same way a `## Status: done` file is excluded. Either way, a skipped file is **not checked off** in `## Queue` and does **not** count toward the run's own `## Status: done` — it simply never entered the Queue in the first place. (Run-file resume semantics — `resume-glob` over `.supervisor/automate/*.md`, whose `## Status:` vocabulary is `running|paused|done` — are untouched by this `proposed|parked` stamp; see §4.)

### Backlog-doc source — `/automate --backlog <_BACKLOG.md>`

- Enqueues in the doc's **documented dependency order** — the doc's build order plus `## Status: done` / ✅ markers are treated as **ground truth** (done items excluded).
- **"Done" is read from two places, and either one excludes the line:** (1) the checklist line itself — `- [x]`, a ✅, or an inline `# Status: done`; (2) **the file the line names** — when it resolves to a regular `*.md` file whose own `## Status:` heading is `done`/`done_with_escalation` (`is_done`, the SAME predicate as the folder source and the dir fallback). (2) is the evidence-gated truth: it is the stamp `closeout` writes after reading the PR `MERGED` (§6 "Post-merge close-out"), and the stamp `trail-pr`'s evidence gate polices. The path is tried as written (relative to the caller's cwd — the repo root, where the loop runs), then relative to the backlog doc's directory; a path that resolves to nothing, to a non-`*.md`, or to a non-regular file is NOT read and the line stays queued (fail toward listing — the full Queue is shown for confirmation before processing, §2 `--limit`; a silently hidden item is the worse failure). Only `is_done` applies on this path: the `proposed|parked` not-ready stamp is still honoured on the dir fallback only (a checklist line is a human's explicit inclusion decision for a not-yet-ready item, but no one includes merged work on purpose).
- **The engine never ticks the backlog doc.** `_BACKLOG.md` is human-owned; `closeout` stamps the requirement file and checks off the RUN file's `## Queue`, and does not edit the backlog checklist. Why: a ticked line would be a second, ungated done claim — `trail-pr`'s evidence gate and retraction (§6 "Trail PR after merge and at run end") police the requirement file's stamp, nothing polices a checklist tick, and a tick written for work whose PR is later reverted or retracted would hide it from every future `--backlog` run. Since (2) above makes the stamp sufficient, the tick would add a writer without adding truth. Ticking the doc stays a human (or `reconcile-status`-style, owner-run) act.
- **`_BACKLOG.md`-absent fallback:** if the passed path does not exist (or has no documented order), fall back to `## Status:`-stamp ordering over the directory the path points into; if there are no stampable items, the Queue is empty ⇒ `remaining: 0`.

### `--limit N` — caps PROCESSED items, NOT Queue size

- The run file's `## Queue` **always holds the FULL resolved list**. `--limit N` (recorded in `## Run Config`, **default 5** — "pull 5–10 and start") caps how many items are **completed** this run.
- After **N items are processed** with items still unchecked ⇒ `## Status: paused`, `pause_reason: limit_reached`, report `remaining: <unchecked count>`. Raise `limit` or `--resume` to continue.
- The **full resolved Queue (count + ordered items) is shown to the user for confirmation before processing.** Under `--non-interactive-fallback` the cap is enforced without the prompt.

## §3 — The single run file (`.supervisor/automate/<run_id>.md`)

**The single-file principle (this design's core):** there is **no manifest, no registry, no `progress.jsonl`, no dashboard file**. ONE markdown run file holds everything — it IS the manifest, registry, progress log, and dashboard. **"Find prior runs" = glob `.supervisor/automate/*.md` for run files — those carrying the `# Automate Run:` title line (`is_run_file`) — not marked `## Status: done`** (§4). The only other artifacts are sidecars, never runs: a *transient* config-backup sidecar that exists only during a tick (§7), and the two per-run result sidecars `<run_id>.supervisor-result.md` / `<run_id>.review-heal-result.md` written verbatim at §6 steps 2–3 (overwritten per item; they carry no `# Automate Run:` title, so RESUME never lists them).

### Run-file template (reproduce exactly)

```md
# Automate Run: <title>
## Status: running          # running | paused | done   (paused = stopped, work remains; done only when the Queue is fully resolved)
## Source
- <user prompt text | folder <dir> | backlog <_BACKLOG.md> | ...>
## Run Config
- mode: safe|auto-merge | limit: 5 | trust_unprotected: false
- auto_review_original: <true|false|absent> | config_backup: <run_id>.config-backup.json
- max_tokens: <N|absent>          # red-team-hardening/06 — ONLY present when --max-tokens was passed; opt-in, PERSISTED (unlike --cheap/--notify) so a bare --resume still enforces it
## Queue                    # `- [ ]` queued · `- [x]` done (merged) · `- [x] … # skipped|abandoned:` excluded; order = processing order
- [ ] <requirement path or generated file>
- [x] <... merged ...>
- [x] <... path ...>  # skipped: <reason>     # checked-off so "next unchecked" never re-picks it; reason also in ## Progress
## Current
- item: <path> | status: running|awaiting_merge|escalated|failed|rate_limit|drain_died|done | pr: <url> | branch: <name>
- pause_reason: awaiting_merge|awaiting_go|escalated|limit_reached|resume_ambiguous|rate_limit|drain_died|token_ceiling|run_lock_held|meta_unreachable|trail_pr_open|null
- owned_drain_started: <ts> | owned_drain_result: READY|ESCALATED|died | suppressed_default_dispatch: true (`READY`'s `termination_reason` — `converged` or `sub_floor_converged`, mechanized bound via `scripts/drain-rounds.sh` — is read straight through from `REVIEW_HEAL_RESULT`; `sub_floor_converged` is NOT merge-eligible, §10 cond 1. `died` — red-team-hardening item 04 — is NOT a `REVIEW_HEAL_RESULT` decision at all; it means a DETACHED `dispatch-pr-review.sh` drain for this item's PR exited without ever producing one, discovered via a `.supervisor/review-dispatch/<hash>.died` marker at RECONCILE, §4 — see that section for the full contract)
- pending_decisions: <n> | fix_now_reentered: <true|false>     # automate-followups/12 — present ONLY when this item produced dismissed-finding drafts (§6 "Dismissed-findings decision step (before the park)")
## Progress                 # APPEND-ONLY (never rewritten)
- <ts> picked <item>
- <ts> session_id <id> (<item>)     # red-team-hardening/06 — the Supervisor session RUN just used; read-token-ledger.sh --run-id sums every session_id line in this file
- <ts> ran /autonomous → PR <url>
- <ts> drain READY → awaiting_merge
```

### Item lifecycle

```
queued (- [ ]) → running → rate_limit (parks, no PR yet) | pr-open → awaiting_merge → merged (- [x]) | escalated (parks) | failed | skipped
```

### `## Status` semantics

- **`running`** — the loop is actively processing (or is the freshly-created run).
- **`paused`** — stopped with work remaining; always paired with a `pause_reason` (`awaiting_merge` | `awaiting_go` | `escalated` | `limit_reached` | `resume_ambiguous` | `rate_limit` | `drain_died` | `token_ceiling` | `run_lock_held` | `meta_unreachable` — branch mode's `meta-entry` failed on a `--resume` of an existing run, §13).
- **After a close-out — `paused` + `awaiting_go`.** Once `closeout` has closed out the `## Current` item (its PR merged; §6 "Post-merge close-out"), nothing is in flight and nothing blocks the run, but the next item still waits for the owner's explicit go (`/automate --resume`; `closeout` never picks). That state reads: `## Status: paused` (unchanged — the run is stopped, and `done` is reserved for the Queue-resolved termination with its `--reason done` trail, which `closeout` never writes, even when it checked off the last item), `## Current` item `status: done`, `pause_reason: awaiting_go`. `null` is NOT used here: `null` means "not paused" (`running`/`done`), and a `paused` run with `pause_reason: null` would break the pairing rule above. When `closeout` runs inside a live loop (RECONCILE, `## Status: running`), it writes `pause_reason: null` instead — the loop is running and its PICK goes on. A `--resume` of an `awaiting_go` run needs no reconcile for that item (it is `- [x]` and `done`); it falls straight through to PICK.
- **`done`** — set **only** when the Queue is **fully resolved** (no `- [ ]` items remain), i.e. `remaining: 0`. `remaining` is **COMPUTED/REPORTED** (the count of `- [ ]` Queue items, via `automate-helpers.sh remaining`) — it is **NOT a persisted run-file field**; the template stores no `remaining:` line.

### Crash-safety contract (HIGH-risk mitigation — run-file is the ONLY copy of resume state)

> **Execute via the helper, not a re-implementation:** the run-file mutations are done by shelling out — `automate-helpers.sh runfile-write <runfile>` (full atomic write, content on stdin), `automate-helpers.sh progress-append <runfile> <line>` (append-only `## Progress`), `automate-helpers.sh queue-checkoff <runfile> <item> [reason] [mark]` (flip `- [ ]` → `- [x]`; `mark` = `skipped` (default) or `abandoned`, §5), and `automate-helpers.sh remaining <runfile>` (COMPUTED `- [ ]` count) (§1.5). The contract below is the SPEC those subcommands implement.

- **Atomic write (temp + rename):** every run-file update is written to a temp file and `mv`-renamed into place. A crash mid-write never leaves a half-written file — the prior intact version remains.
- **Validate before rename (fail CLOSED on the payload):** temp+rename protects against a crash *mid-write*, but it installs whatever the temp file holds — and the engine builds rewrites as `<generator> "$RF" | automate-helpers.sh runfile-write "$RF"`, where a generator that errors (BSD awk rejecting a newline in a `-v` value, an unescaped delimiter in a `sed`, a failed redirect) prints nothing and the helper cannot see its exit status. So `runfile-write` stages stdin to the temp file and validates it **before** the `mv`; any failure is exit 1 with the temp file removed and the run file **byte-unchanged**. It refuses when the staged content: (1) is empty; (2) lacks the `# Automate Run:` title line (`is_run_file` — without it `resume-glob` stops listing the run); (3) lacks a `## Status:` line (without it `is_done` can never fire and RESUME cannot tell `running`/`paused`/`done`); (4) lacks a `## Queue` heading (without it `remaining` computes `0` and the run looks finished); or (5) — when the file being replaced is already a run file — does not begin its `## Progress` block with the existing `## Progress` block line-for-line (the APPEND-ONLY rule below, enforced: a truncated generator keeps the header sections and silently drops the tail). A shrinking line count is deliberately **not** a refusal reason (unlike `/verify`'s `queue-write`): `## Current` legitimately loses lines (e.g. `pending_decisions:` disappears when the next item is picked). `progress-append` and `queue-checkoff` validate the same way: both refuse a target that is not a run file (no `# Automate Run:` title) instead of fabricating structure on it, and both put their own output through the same pre-rename check. **Recovery is a human act:** a refusal leaves the prior run file in place; never "fix" a refusal by writing the file another way.
- **`## Progress` is APPEND-ONLY** — it is **never rewritten**. New lines are appended; existing lines are immutable.
- **Rewrites are confined** to `## Queue` checkboxes and the `## Current` block. `## Status`/`## Source`/`## Run Config` change rarely and atomically; `## Progress` only grows.
- **Optional secondary breadcrumb:** ONE terminal line per run **appended** to the existing `.supervisor/logs/<run_id>.jsonl` (the shared session-log convention) for trend tooling — **never the source of truth**.

## §4 — RESUME = glob + reconcile (run-file is BELIEF; git/gh is TRUTH)

> **Execute via the helper, not a re-implementation:** glob with `automate-helpers.sh resume-glob <automate_dir>` and reconcile each in-flight item's belief vs `gh` ground truth with `automate-helpers.sh reconcile-item <pr_url> <belief>` ⇒ `merged` / `awaiting_merge` / `gone` (§1.5). (`reconcile-item` resolves the `gh`-PR-state half; the complementary `git branch --contains <sha>` corroboration below is done by the loop.) The protocol below is the SPEC those subcommands implement.

**On every start** (including bare `/automate` and any `--resume`):

> **Branch mode (opt-in):** when `setup-memory.sh mode` reads `on`, `automate-helpers.sh meta-entry` runs FIRST — before step 1's glob — and a `failed` verdict aborts or parks `meta_unreachable`; see §13.

1. **Glob** `.supervisor/automate/*.md` for **run files** — a `*.md` carrying the `# Automate Run:` title line anywhere in the file (`is_run_file`, a shape check, not a filename rule) — **NOT** marked `## Status: done`. The §6 steps 2–3 result sidecars (`<run_id>.review-heal-result.md`, `<run_id>.supervisor-result.md`), transient or committed, are excluded: they have no `## Status:` line, so without the shape check each would read as an incomplete run and make resume ambiguous.
2. The run file is the loop's **belief**. **Reconcile each in-flight item against GROUND TRUTH before trusting a checkbox** — a crash between merge and check-off makes belief and reality disagree:
   - **PR merged?** `gh pr view <url> --json state,mergedAt` — a merged PR ⇒ the item is `- [x]` (merged) even if the file still shows it `- [ ]`/`awaiting_merge`; a merge found here is also the evidence §6 step 1's `closeout` call acts on (its `brief-repair` step, then local cleanup, stamp, check-off, trail), before the next item is picked.
   - **PR open?** an `OPEN` PR ⇒ the item stays `awaiting_merge`; nothing re-checks it on a timer except the merge watcher armed at that park, which runs `closeout` when the PR merges — the next item is still picked only on the owner's explicit `--resume` (§8).
   - **PR closed-unmerged or vanished?** a `CLOSED` (never-merged) or otherwise gone PR ⇒ the item is `gone` — neither merged nor live. Treat it like an `escalated` park requiring human resolution (§9): the run stays paused until the human re-opens/redoes the work or marks the item `skipped`/`abandoned` in `## Queue` (§5). Never silently re-pick or auto-check a `gone` item.
   - **Branch landed?** `git log origin/main --oneline` / `git branch --contains <sha>` — verify the branch actually reached `main` (never assert "merged" from memory).
   - **Requirement stamped?** the requirement file's `## Status: done` stamp.
   - **No PR yet (`pr: null`, `pause_reason: rate_limit`)?** RUN failed before a PR ever existed (see "Rate-limit park" under §6 below), so there is nothing for `gh` to reconcile — this item is left exactly as parked (still `- [ ]`, still the `## Current` in-flight item) and falls straight through to step 4/6 below: resuming just re-picks it and retries RUN.
   - **A DETACHED drain died for this item's PR (`drain_died`, red-team-hardening item 04)?** Check `.supervisor/review-dispatch/*.died` for a marker whose `pr_url` field equals this item's `## Current` `pr:` URL. This is a SEPARATE fact from the `owned_drain_result` this loop's OWN inline `/review-pr --until-mergeable` drain records (§7, §6 step 3) — a `.died` marker only ever comes from the DETACHED `dispatch-pr-review.sh` dispatcher (Supervisor's step 5.5 or the `PostToolUse[Bash]` hook backstop), which this engine's owned drain never goes through. If a matching `.died` marker exists, treat it as `owned_drain_result: died` in `## Current` and `## Status: paused` / `pause_reason: drain_died` — **explicitly NEVER `awaiting_merge`**, because a died drain never reached a `READY`/`ESCALATED` verdict to park on in the normal sense; there is no `REVIEW_HEAL_RESULT` to trust either way, and the PR's true readiness is simply unknown. This check runs BEFORE the merged/open/closed reconcile above would otherwise re-pick or resume the item as if a normal drain outcome existed.
   - Reconcile each item, then rewrite `## Queue` checkboxes + `## Current` atomically (§3) so belief matches truth.
3. **RECONCILE also restores a crash-stranded config backup** (§7) — if `## Run Config`'s `config_backup` sidecar still exists on disk, the prior tick died with `.auto_review` suppressed; restore it (or delete `config.json` if originally absent) before proceeding.
4. **If an incomplete run exists**, `AskUserQuestion`: **continue / start new / archive**.
   - `--resume [<run_id>]` targets one explicitly; with the id omitted it targets the **most-recent incomplete** run.
   - Under **`--non-interactive-fallback`**, an **ambiguous** resume (more than one incomplete run and no explicit id) **fails closed**. In `AUTOMATE_RUN` this is persisted as **`pause_reason: resume_ambiguous`** in `## Current` (the run file has no `status_reason` field — that identifier belongs to the inner `/autonomous` layer's `AUTONOMOUS_RUN`, which surfaces it as `status_reason: "resume_ambiguous_non_interactive"` when the loop forwards the fallback).
5. **Re-pass non-persisted passthrough flags.** `## Run Config` does NOT store `--notify` / `--non-interactive-fallback` / `--cheap` (§11) — a resume or `/loop` tick that omits them silently reverts to defaults. This matters most for **`--cheap`**: omitting it reverts the remaining queue to the full-cost profile with cumulative dollar impact, so re-pass `--cheap` on **every** `/automate --resume` invocation and `/loop` tick of a cheap run.
6. **Resuming a `rate_limit` park.** This round-trips through the EXACT SAME RESUME flow above — no second reconcile code path, no second park vocabulary. The only difference from resuming `awaiting_merge` is *what* step 2 finds: an `awaiting_merge` item has a `pr` to reconcile against `gh`; a `rate_limit` item has `pr: null` and nothing to check (the "No PR yet" bullet above), so reconcile is a no-op for it. Either way, `continue` (step 4) re-enters the per-item loop at §6 step 1 RECONCILE and proceeds from there — for a `rate_limit` item that means falling straight through to §6 step 2 RUN, retrying the SAME item (the rate-limit window has presumably passed by the time a human or `/loop` resumes).
7. **RECONCILE also runs reconcile-status** — the `reconcile-status` dry-run pass (queue-hygiene/01) — **BEFORE step 4's PICK**: `automate-helpers.sh reconcile-status .supervisor/requirements` (no `--apply` — this is the engine's own RESUME reading ground truth back for requirement files OUTSIDE this run's own `## Queue`, the same "read it back, never infer it" posture as steps 1–2 above, kept dry-run because promoting a requirement's `## Status:` is a standing human-owned act, not an engine side-effect). For each `plan\t<file>\t…` row it prints, `automate-helpers.sh progress-append <runfile> "reconcile-status: would stamp <file> (<status>)"` — ONE `## Progress` line per row, appended before PICK runs. An `info\t…` (brief-shipped) row is NOT progress-appended — it is advisory-only and never actionable from inside a run. Zero `plan` rows ⇒ no line, no-op. This never writes to a requirement file itself; promoting the plan to a real stamp is `automate-helpers.sh reconcile-status .supervisor/requirements --apply`, run by a human (or a dedicated queue-hygiene pass), never by `/automate` itself.
8. **Pending dismissed-finding decisions (automate-followups/12).** `## Current`'s `pending_decisions: <n>` is BELIEF; the truth is the drafts on disk, read with `automate-helpers.sh dismissed-pending <runfile>` (this run's whole undecided set, every item's). RESUME never parks or blocks on it and it is never a `pause_reason`: an interactive resume asks the undecided set at §6 step 1 PICK (Follow-up / Drop only — the PICK-time ask there), before RECONCILE's `closeout`; a `--non-interactive-fallback` resume asks nothing and the count stays in `## Current`. A `fix_now_reentered: true` line means that item's one fix-now re-pass already ran.

## §5 — Skipped / abandoned items

An item the human (or the loop) abandons is written in `## Queue` as:

```md
- [x] <path>  # skipped: <reason>
- [x] <path>  # abandoned: <reason>
```

- **Checked-off ⇒ never re-picked** ("next unchecked item" skips it). The reason is ALSO logged in `## Progress`.
- **`remaining` counts only `- [ ]` items**, so a skipped/abandoned item does **not** block `## Status: done`.
- This is the **documented way to unblock an `escalated`-parked run without merging** (§9): mark the parked item `skipped`/`abandoned`, then `--resume`.
- **A skip/abandon check-off runs `trail-pr`** (`--reason skipped`/`--reason abandoned`) — trigger (c) of "Trail PR after merge and at run end": at §6 step 6 when the loop writes it, at RECONCILE when a human wrote it. The item's requirement rides only when it carries no done stamp or its PR merged (the evidence gate there), so an abandoned escalated item never lands a done claim.

## §6 — The per-item loop

For each `- [ ]` Queue item (top-down, single-open-PR invariant permitting — §8):

1. **RECONCILE** — re-check ground truth for any in-flight item before picking (§4); never pick a new item while one has an open unmerged PR (§8). When `reconcile-item` returns `merged` for an item previously parked `awaiting_merge` (or `escalated`), the loop runs `automate-helpers.sh closeout <runfile> <item> <pr_url> --session-id <this loop's session id>` BEFORE any PICK — the `--session-id` makes closeout's own run-lock acquire RE-ENTER the `automate:<run_id>` lock this PICK already holds (it subsumes the `brief-repair` call that used to sit here; closeout's step 2 is that call). Advisory, fail-SAFE: closeout appends its own `## Progress` lines and its result never changes the reconcile verdict (see "Post-merge close-out" below). A live `<run_id>.merge-watch` marker for the in-flight PR is noted with one `progress-append` line instead of arming a second watcher. When RECONCILE instead finds the parked `## Current` item checked off `# skipped:`/`# abandoned:` by a human (§5's unblock path), it runs `automate-helpers.sh trail-pr <runfile> --reason skipped|abandoned` and appends its line, BEFORE PICK (trigger (c) of "Trail PR after merge and at run end"; idempotent — a re-run is the no-diff skip).

   **PICK-time trail gate (after RECONCILE, its `closeout` and any skip/abandon `trail-pr`; BEFORE the trail un-stage below).** `automate-helpers.sh trail-gate <runfile>`, its line appended to `## Progress`. The single-open-PR invariant counts this run's own trail PR (§8): `PARK — …` (an open `chore/<run_id>-trail-<n>` PR, or its state unreadable — fail CLOSED) parks the run here — `## Status: paused`, `pause_reason: trail_pr_open`, `## Current`'s other lines unchanged, then `run-lock.sh release`; no `trail-pr` at this park ("Trail PR after merge and at run end"). The owner merges (or closes) the named PR, then `--resume`. `clear — …` proceeds: the gate has already synced the primary onto the base branch with `closeout`'s own sync, which re-stages the recorded trail blobs that landed (`<run_id>.trail-staged`) before its `git pull --ff-only`, so the merged trail fast-forwards and the next item branches off a base that carries it; the un-stage below then drops whatever did not land. Before this gate nothing synced at PICK, and a hand pull after the un-stage refused (run `automate-2026-10-01-142337` item 02 re-staged the blobs by hand with `git update-index --cacheinfo`). A `sync skipped — <reason>` answer (the primary on another branch, uncommitted changes outside the trail paths, a refused pull) is reported and never parks — the sync is checkout housekeeping, exactly as in `closeout`; RUN then proceeds from the primary as it is, which is what every PICK did before this gate.

   **PICK-time trail un-stage (after RECONCILE, its `closeout` and the trail gate, BEFORE RUN).** `automate-helpers.sh trail-unstage <runfile>`, its line appended to `## Progress`. Every `trail-pr` (`closeout`'s own trail, a skip/abandon check-off, or run end) leaves this run's trail paths STAGED in the primary index (the checkout contract, "Trail PR after merge and at run end") — `closeout`'s trail runs after its sync, with the primary on `main`, which is exactly where the next item branches; `git checkout -b` carries those entries onto the next item's branch, and a plain `git commit` there commits the whole index — so without this step the next item's PR would carry the run's trail files. Fail-SAFE, advisory: it never gates the pick.

   **PICK-time run-lock acquire (red-team-hardening/06 — BEFORE anything else at PICK, including RECONCILE above).** The very first action of every PICK is `scripts/run-lock.sh acquire --owner "automate:<run_id>" --session-id "<session_id>"` (see §1.5's `run-lock.sh` row for the full path convention) — a lock already held by another run/process in this checkout PARKS the run immediately (`## Status: paused`, `pause_reason: run_lock_held`, one `## Progress` line naming the `run_lock_held owner=<label> pid=<pid> age=<s>` output) and the loop stops WITHOUT touching `## Queue`/`## Current`/`.auto_review` — it never proceeds silently. On success the lock is held for the rest of this item's loop and released at CHECK OFF (step 6) or any park below (step 2's rate-limit park, DRAIN's `drain_died`, or GATE's `awaiting_merge`/`escalated`) — see §11 for the human-only `--force-unlock` escape hatch on a stranded lock.

   **PICK-time token-ceiling check (red-team-hardening/06 — when `--max-tokens N` was passed).** Immediately after the lock acquire succeeds, and BEFORE RECONCILE above: `automate-helpers.sh ceiling-check <runfile> <N>`. A `PARK: token_ceiling …` or `PARK: ledger_unreadable` answer PARKs the run right here — `## Status: paused`, `pause_reason: token_ceiling`, one `## Progress` line — then `run-lock.sh release` for the lock just acquired (never left held on a park). No `trail-pr` at this park ("Trail PR after merge and at run end"). An `OK …` answer proceeds to RECONCILE as normal. Skipped entirely (no check, no `## Run Config` field) when `--max-tokens` was not passed — opt-in, byte-for-byte unchanged behavior otherwise.

   **PICK-time pending-decisions ask (automate-followups/12 — after the lock acquire and the ceiling check, BEFORE RECONCILE's `closeout`).** Interactive runs only: `automate-helpers.sh dismissed-pending <runfile>`; a non-zero count OR `unknown` ⇒ `AskUserQuestion` over this run's undecided drafts (≤4 questions per call, one per draft) with the options **Follow-up (keep draft)** / **Drop** ONLY — fix-now is offered only at the park (§6 "Dismissed-findings decision step (before the park)" step 2, before the merge watcher is armed), never at PICK, so no fix push can race an armed watcher or a human merge. Each answer ⇒ `automate-helpers.sh dismissed-decide <runfile> <draft_path> follow-up|drop` (its one `## Progress` line is the record). It needs no merge evidence, only the undecided set, which is why it runs before `closeout`: the `closeout` trail then carries decided drafts, not undecided ones. The ask writes nothing else — no park-state rewrite, no `fix_now_reentered` change. Under `--non-interactive-fallback` it never runs and never blocks; the count stays in `## Current`.
2. **RUN** — set `.supervisor/config.json {"auto_review": false}` (the suppress contract, §7) **then** run `/autonomous --single-iteration --requirement <path>`, appending `--cheap` when it was passed to `/automate` (pure passthrough, v15.2.0+ — the engine never interprets the flag itself and does NOT store it in `## Run Config`; the inner `/autonomous` forwards it on to `/supervisor`, §11) and appending `--max-tokens N` when it was passed to `/automate` (red-team-hardening/06 — UNLIKE `--cheap`, this one IS recorded in `## Run Config` as `max_tokens: N` so a bare `--resume` still enforces it; the inner `/autonomous` forwards it on to `/supervisor` exactly like `--cheap`, §11). The suppress MUST wrap the RUN phase: both default dispatches fire *during* `/autonomous` (Supervisor step 5.5 + the `PostToolUse[Bash]` `gh pr create` hook), so toggling at DRAIN is too late. Capture the emitted `SUPERVISOR_RESULT` (status, `pr_url`, `branch`, `rubric_score`, `heal_decision`, `heal_iterations`) and **write its raw text VERBATIM to `.supervisor/automate/<run_id>.supervisor-result.md`** (transient, overwritten per item, same convention as the DRAIN-step artifact below) — this is the file `gate-eval`'s condition-5 rubric check (§10) parses a `rubric_score: N/M` line from itself; the gate never trusts a caller-asserted rubric verdict. **Restore `.auto_review` in a finally-style cleanup immediately after `/autonomous` returns *or fails* — i.e. BEFORE the owned DRAIN below** (§7). The owned drain is inline and NOT gated by `.auto_review`, so restoring before it both keeps the suppression window tight and is safe. **Then, before proceeding to step 3 DRAIN, check for a rate-limit park** — see "Rate-limit park" below; a parked item stops the run right here and never reaches DRAIN/GATE.

   **Session-id recording for the token ledger (red-team-hardening/06).** Immediately after `/autonomous` returns (successfully or not), read `.supervisor/state.md`'s `- session_id:` field — the Supervisor session this RUN invocation just used — and `automate-helpers.sh progress-append <runfile> "session_id <id> (<item>)"`. This is what lets `read-token-ledger.sh --run-id <runfile>` (§1.5) find every session's ledger for this run, including for `--max-tokens` runs that never set a ceiling this time but might on a future `--resume`. Recorded UNCONDITIONALLY (not gated on `--max-tokens` being set) so a later `--max-tokens`-bearing `--resume` of an UN-ceilinged run still has a complete session-id trail to sum.
3. **DRAIN** — own **exactly ONE** inline `/review-pr --until-mergeable --no-auto-postmortem` on the PR per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent); §6 "Dismissed-findings decision step (before the park)" (§7). Read its terminal `REVIEW_HEAL_RESULT` synchronously; record `owned_drain_started` / `owned_drain_result` / `suppressed_default_dispatch: true` in `## Current`. **Also write the terminal `REVIEW_HEAL_RESULT` block's raw text VERBATIM to `.supervisor/automate/<run_id>.review-heal-result.md`** (transient, overwritten per item — same convention as the `<run_id>.config-backup.json` sidecar, §7) — this is the artifact `gate-eval`'s condition-1 cross-check (§10) reads back and compares against the loop's own `drain_result`/`termination_reason` claim, so the drain's self-report can never merge on a bare, uncorroborated assertion. **Then, at the END of DRAIN (BEFORE step 4 GATE), emit the engine-native learning line** — see "Learning-emit at end-of-DRAIN" below. This runs for EVERY item that produced a PR (merged OR parked); emitting here (not at step 6 CHECK OFF) covers parked items, which stop at the GATE and never reach CHECK OFF.
4. **GATE** — apply the per-mode decision (§9): safe mode parks `awaiting_merge`; `--auto-merge` runs the trusted-merge gate (conditions enumerated in §10), which is now **SELF-RESOLVING** (red-team-hardening item 03) — the gate itself re-derives every condition from 2 on from live `gh`/GraphQL/`classify-risk.sh`/`rules-gate-verdict.sh` reads rather than trusting loop-supplied values; the loop's `ctx.json` shrinks to exactly `{drain_result, termination_reason, ready_sha, trust_unprotected, review_heal_result_path, supervisor_result_path}` (§10). `ESCALATED` always parks (§9). **Before ANY park that leaves this item's PR open** — safe-mode `awaiting_merge`, a fail-closed `--auto-merge` park, `escalated` — run the §6 "Dismissed-findings decision step (before the park)" FIRST: the owner's decisions (and a fix-now re-pass) come before the park state is written, the merge watcher is armed and the run-lock is released. After a `--auto-merge` `MERGE` (no park), run only that step's `dismissed-drafts` and record `pending_decisions` — nothing is asked there; the next interactive PICK asks.
5. **SYNC** — after a successful merge (auto-merge mode), `git checkout main && git pull` so the next item branches off **fresh `main`** (no stale-base / PR-tower). After `gate-eval` printed `MERGE`, call `automate-helpers.sh brief-repair <item> <pr_url>` (before the `git pull`; order is immaterial, the brief is gitignored) and append its line to `## Progress`.
6. **CHECK OFF + PROGRESS** — mark the item `- [x]` in `## Queue` and **append** a `## Progress` line, via **one atomic write** (§3). Report `remaining: N` (count of `- [ ]` items). When THIS check-off is a `# skipped:`/`# abandoned:` one, and when it resolves the Queue (`## Status: done`), the loop runs `automate-helpers.sh trail-pr` FIRST and only then `run-lock.sh release`; no park path runs it (the trigger list and contract live in "Trail PR after merge and at run end" below). **Release the run-lock** (red-team-hardening/06) — `run-lock.sh release --owner "automate:<run_id>"` — as the LAST action of this step, whether the item just merged or was checked off `skipped`/`abandoned`. The SAME release fires on every OTHER path this item's loop can stop on (rate-limit park, `drain_died`, `awaiting_merge`/`escalated` GATE parks, `limit_reached` termination) — the lock is held for at most one item's worth of loop, NEVER carried across a park that stops the whole run, so a human resuming a parked `/automate` run is never blocked by its own prior lock.

### Rate-limit park (end of RUN, before DRAIN)

Immediately after step 2 RUN captures `SUPERVISOR_RESULT` and restores `.auto_review`, and **before** proceeding to step 3 DRAIN, the loop checks its own session's JSONL log — `.supervisor/logs/{session_id}.jsonl`, the SAME file `scripts/emit-lifecycle.sh` appends to (`docs/RESULT_SCHEMAS.md` §"`agent_lifecycle` JSONL event records") — for an `agent_lifecycle` row with `state: "failed"`, `agent_scope: "main"` (no `agent_id` — for `/automate` the main thread IS this loop, so a main-scope failure is the loop's own turn dying, matching the source requirement's honest limit that every observed rate-limit `StopFailure` in this repo has been main-thread), and `reason: "rate_limit"`, timestamped AFTER this item's own `## Progress` "picked" line (never a stale hit carried over from an earlier item in the same run file). **No new script is needed for this read** — the loop reads its own session log directly, exactly the way it already reads its own `## Progress` lines; there is no PR yet at this point for a `gh`-keyed helper like `reconcile-item` to key on.

- **Classified hit (`reason: "rate_limit"`):** park immediately, following the EXISTING park shape exactly (never a new `status: parked` placeholder) — `## Current` gets `status: rate_limit` AND `pause_reason: rate_limit` (item-level `status` mirrors `pause_reason`, the same way `awaiting_merge`/`escalated` already do), `## Status: paused`, one `## Progress` line naming the rate-limit fact (e.g. `<ts> rate-limited — parking, resume once the window clears`), then `run-lock.sh release` (no `trail-pr` — "Trail PR after merge and at run end"), and the run **STOPS (exit 0)**. It does NOT proceed to DRAIN/GATE and does NOT retry RUN into the same wall.
- **Unknown hit with a `429` hint (fallback, `reason: "unknown"`):** the `agent_lifecycle` row itself carries no message text, so before falling through to today's unchanged handling, check the sibling `STOP_FAILURE` line in `.supervisor/logs/failures.log` for the SAME session (matched by `session_id`, the line closest-preceding the `agent_lifecycle` row's own `ts`) and read its `last_assistant_message` field for a `429` substring. A hit there records a SEPARATE `reason_hint: rate_limit` line in `## Current` — additive, **never** written into `reason` (the `agent_lifecycle` row stays `"unknown"`, untouched) and **never** promoted into `status`/`pause_reason` as if it were a classified certainty — **and** the item still parks the SAME way a classified `rate_limit` would (`status: rate_limit`, `pause_reason: rate_limit`, same `## Progress`/stop behavior above): a hint is enough to stop retrying into a wall, not enough to relabel the underlying fact as certain.
- **Every other classified reason — UNCHANGED.** `server_error` / `authentication_failed` / `model_not_found`, or `unknown` with no `429` hint, take today's existing failure/error path exactly as before (whatever `SUPERVISOR_RESULT`'s own failure status already drives, and the `/autonomous` correctness gates that bubble up per §11). This item adds exactly ONE new branch; it does not restructure any other reason's handling.

### Termination (two exits)

- **Queue fully resolved** (no `- [ ]` left) ⇒ `## Status: done`, `remaining: 0`, the `/loop` driver stops.
- **`limit` items processed** with the queue NOT empty ⇒ `## Status: paused`, `pause_reason: limit_reached`, `remaining: <unchecked count>`, loop stops.

On the **`## Status: done`** exit ONLY, the loop runs `trail-pr --reason done` and only then `run-lock.sh release`; the `limit_reached` exit is a park and releases the lock without a trail — see "Trail PR after merge and at run end".

(A park on `awaiting_merge`, `escalated` — §8/§9 — or `rate_limit` — the "Rate-limit park" subsection above — or `drain_died` — §4 RECONCILE, a DETACHED drain that exited without a result, red-team-hardening item 04 — or `trail_pr_open` — §6 step 1's trail gate, §8 — also stops the loop with the corresponding `pause_reason`.)

All `/autonomous` correctness gates still bubble up (NO-GO, Plan Review FAIL×3, adjudication, rubric gate); `--notify`, `--non-interactive-fallback`, and `--cheap` pass through to the inner `/autonomous` (§11).

### Learning-emit at end-of-DRAIN (engine-native ground-truth signal)

At the END of §6 step 3 (DRAIN), AFTER reading the terminal `REVIEW_HEAL_RESULT` and BEFORE step 4 (GATE), append **ONE** ground-truth learning line per processed PR (merged OR parked). This replaces the GitHub-blind `/pr-postmortem` for automate'd PRs: the engine already holds the real churn, so it builds an honest line instead of reading a false `review_rounds: 0` off GitHub.

> **Execute via the helper, not a re-implementation (reference-don't-restate, to avoid mirror drift):** call `automate-helpers.sh learning-emit` (§1.5). The helper owns all the record-building logic (the `effective_review_rounds` rule, the `categories[]` zero-rule, `self_heal_misses` derivation, idempotency-skip, jq-only injection-safe construction, always-exit-0). Do NOT restate that logic here — the authoritative field mapping lives in `docs/RESULT_SCHEMAS.md` POSTMORTEM_RESULT §"`source: \"automate_drain\"` variant".

- **Inputs the engine already holds:** from the step-3 `REVIEW_HEAL_RESULT` read `fix_cycles`, `repeat_check_failure`, `unresolved_bot_feedback`, and `decision` (the drain result `READY|ESCALATED`); from the step-2 `SUPERVISOR_RESULT` read `pr_url`, `branch` (and `heal_decision`/`rubric_score` for the summary). **Derive `repo` (`owner/repo`) and `number` from `pr_url`** (parse `…/<owner>/<repo>/pull/<n>`) — `SUPERVISOR_RESULT` does not carry them as bare fields, and a correct `--repo` is **load-bearing for visibility** (next bullet).
  - **`heal_iterations` → `--self-heal-rounds`** (the Phase 4.5 self-heal churn the PR absorbed before the drain — without it a PR healed in self-heal and drained with 0 fix cycles records a false-0). Read `heal_iterations` from the verbatim `.supervisor/automate/<run_id>.supervisor-result.md` written at step 2 — it is the **OBSERVED** count, **never** the configured `/supervisor --heal-iterations` maximum bound. `heal_iterations: N` ⇒ pass `--self-heal-rounds N`; `heal_iterations: null` (the heal loop did not run) ⇒ pass `--self-heal-rounds 0`; **no `heal_iterations:` line at all** (e.g. a main-thread reconstruction of a resumed item) ⇒ **OMIT the flag** — never fabricate a count. The helper owns the resulting `self_heal_rounds` field and `self_heal_churn` category (field mapping: `docs/RESULT_SCHEMAS.md` POSTMORTEM_RESULT §"`source: \"automate_drain\"` variant").
  - **`--item` is the FULL Queue path** (the `## Queue` entry verbatim, e.g. `.supervisor/requirements/<folder>/<NN-slug>.md`), never a short key — the PR #267 line was emitted with a short `twin-loop/08-…md` item, so its `automate_key` diverged from every sibling line's (and from the key a re-entry passing the full path would compute).
- **The ONE added fetch** (the only data not already in hand): a single `gh pr view "<pr_url>" --json files,additions,deletions,changedFiles`, where `changed_paths = [.files[].path]`. On ANY fetch failure, degrade to `--changed-paths-json '[]'` and `--additions 0 --deletions 0 --changed-files 0` (integers, never `null`) — the line is still emitted, just invisible to `read-postmortem.sh` (**and correctable — see the degraded-emit bullet below**).
- **A degraded emit is INVISIBLE but no longer PERMANENT (second half of the same trap as `--repo`).** A line emitted with `changed_paths: []` — because the fetch above failed, or because the caller omitted the fetch args entirely — can never overlap a queried path, so `read-postmortem.sh` can never return it. The `--repo` bullet above covers one half of that silent-invisibility trap; this is the other half. Historically it was also *permanent*: the `automate_key` was keyed on `run_id`+item+`pr_url`+`source` alone, so the degraded line poisoned the key and **every** later emit carrying the real data was silently skipped (observed 2026-08-06 on PR #126). The key now carries a `complete`\|`degraded` discriminator, so **a degraded line does NOT block a later complete one** — re-running `learning-emit` for the same run/item/PR with the fetch data appends the corrective line, and the inert degraded line is left in place (append-only; `curate-postmortem.sh` remains the sole curator writer). The helper still writes **at most one complete line** per run/item/pr/source, and a degraded retry *after* a complete line is skipped, so the correction cannot run backwards or duplicate. **Prefer passing real fetch data on the first call** — the correction is a safety net, not a licence to skip the fetch.
- **Visibility is gated by BOTH `changed_paths` AND `repo` (load-bearing — pass a real `--repo`).** `read-postmortem.sh` returns a corpus line as a prior-churn hit only when its `changed_paths` overlaps the queried paths **AND** (when the current repo is determinable) its `repo` matches the reader's repo case-insensitively (`read-postmortem.sh:159` [pins: `changed_paths overlap the query set`]). The helper defaults `repo` to `""` (emitted as `repo: ""`, **not** `null`), which the reader filters out whenever its own repo resolves — so an empty `--repo` produces a **silently-invisible** line, exactly the failure this feature exists to prevent. Always pass `--repo <owner/repo>` (derived above). Also pass `--plugin-version` (from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`) so engine-native lines carry the real version, not `"unknown"`.
- **Idempotency:** pass `--run-id <run_id> --item <item> --pr-url <pr_url> --source automate_drain` so the helper's `automate_key` skip yields exactly ONE line across a crash between emit and check-off, or a `--resume` re-entry. The key is **degradation-aware** (previous bullet): exactly-once holds per (run/item/pr/source, `complete`\|`degraded`) state, which is what lets a re-entry that *recovers* the fetch data correct an earlier degraded line while a plain re-entry still writes nothing.
- **Ledger:** `.supervisor/postmortem/results.jsonl` (the same unified corpus `/pr-postmortem` appends to; the `source` field discriminates the two).
- **Advisory / fail-SAFE — NEVER gating.** `learning-emit` ALWAYS exits 0; the loop **ignores its exit status entirely**. A `learning-emit` failure (jq absent, unwritable ledger, fetch fail, bad arg) NEVER changes `owned_drain_result`, the step-4 GATE / merge-or-park decision, `## Status`, `## Current`, or any inner `/autonomous` gate — exactly like the `postmortem_dispatched`-is-informational invariant.
- *(Optional, advisory)* the `AUTOMATE_RUN` summary MAY carry a `learning_lines_emitted` counter; skip it if it adds risk.

### Brief-repair at RECONCILE and SYNC (merge-evidenced lifecycle repair)

The engine is the one caller that holds ONLINE evidence that a Queue item's PR merged — it merged it (step 5 SYNC), or its RESUME reconcile just found an item parked `awaiting_merge` now merged (step 1 RECONCILE). At both seams `automate-helpers.sh brief-repair <item> <pr_url>` (§1.5) runs — at RECONCILE as step 2 of `closeout` (which appends its line to `## Progress`), at SYNC called by the loop directly — and its single output line lands in `## Progress` verbatim, so a reader can falsify the repair from the run file. The helper re-reads merge state from the forge (evidence-POSITIVE: only `MERGED` proceeds; an unreadable or non-merged answer is a `skipped`, never a repair) and hands the evidence to the sibling `reconcile-jobs.sh --repair --evidence <item>=<pr_url>`, which stays the ONE mover: the repair is scoped to that item's brief, an ambiguous match (two in-progress briefs with the same pointer) repairs nothing, and `unknown` is still never repaired. The `--evidence` key is compared EXACTLY against the brief's `- **Source requirement:**` token — a Queue item spelled `./…` or as an absolute path (`--folder /abs/dir`) never matches Launch Pad's repo-root-relative pointer and lands on a `skipped` line.

- **Advisory / fail-SAFE — NEVER gating.** `brief-repair` ALWAYS exits 0; the loop **ignores its exit status entirely**. A `brief-repair` failure (gh absent or erroring, unparseable output, brief unreadable, reconciler absent, no matching brief, malformed arguments, ambiguous match) NEVER changes `owned_drain_result`, the step-4 GATE / merge-or-park decision, `## Status`, `## Current`, or any inner `/autonomous` gate — exactly like `learning-emit`. It never reads or writes the run file, never touches `## Queue`/`## Current`, and never calls `gh pr merge` (the sole executor stays `gate-eval`, §11).
- **Idempotent.** A second call for the same item finds no in-progress brief and prints `skipped — no in-progress brief matches …`; the moved brief is never re-stamped.
- **Honest limit.** Only items the engine processed have engine-held evidence. A `/supervisor` or `/autonomous` run **outside the engine** still has no online repair: its stranded brief is classified offline by `session-resume.sh` (unchanged — still no forge call) and remains a manual `reconcile-jobs.sh --repair` (or a SessionStart classification), exactly as before.

### Dismissed-findings decision step (before the park)

Dismissed review findings (Phase 4.5's `SUPERVISOR_RESULT.heal_dismissed[]`, the owned drain's `REVIEW_HEAL_RESULT.dismissed[]`) used to be write-only: one `<!-- loomwright:dismissed round=<n> -->` PR comment, then the merge took them with it. This step turns each one into a propose-only draft in `.supervisor/requirements/proposed/` and — interactively — an owner decision. Mechanics live in `automate-helpers.sh dismissed-drafts` / `dismissed-decide` / `dismissed-pending` (§1.5; implemented in `scripts/automate-dismissed.sh`, self-tested by `scripts/test-automate-dismissed.sh`). Finding text is DATA only: every finding line is written `> `-quoted inside a fence longer than any backtick run in it (so no finding line can start a column-0 `#`, `## Status:` or `- **…:**` that a line-anchored scanner would read), never executed; a fix-now finding reaches the fix worker only inside the EXTERNAL_TEXT envelope.

**The threshold (the ONE rule — the script's header mirrors it).** After deduping on (origin, source, whitespace-normalized finding) — both accumulators append per iteration/round, so a re-reported finding yields ONE draft per origin — a dismissed item gets its OWN draft when ANY of: `severity` ∈ {BLOCKING, HIGH, MEDIUM}; `reason == pre_existing` (any severity); `severity` absent (or not one of BLOCKING/HIGH/MEDIUM/LOW/INFO, read as absent) and `reason != nit` — fail TOWARD tracking. Everything else (`severity` LOW/INFO, or `reason == nit`, and not `pre_existing`) is listed in a summary draft (one undecided summary per item; a finding first seen after that summary was decided opens the next slot, `…-summary-<N>.md`). Zero items ⇒ no files. Severity wins over `nit`: a MEDIUM nit gets its own draft. The `nit`/`pre_existing` vocabulary exists only on Phase 4.5 items; the drain's `reason` is free text, so every drain dismissal without a stated severity gets its own draft (deliberate; a noise risk to revisit after the first real run).

**Order — for every GATE outcome that parks with an open PR (`awaiting_merge` in safe mode, a fail-closed `--auto-merge` park, `escalated`):**

1. `automate-helpers.sh dismissed-drafts <runfile> <item> <pr_url>` (add `--after-fix-now` ONLY on the run that follows this item's fix-now re-pass, i.e. once `fix_now_reentered: true`); `progress-append` its summary line. A missing sidecar is not an error (that loop dismissed nothing or did not run).
2. **Interactive** ⇒ `AskUserQuestion`, batched ≤4 questions per call: ONE question per per-finding draft, options **Follow-up (keep draft)** (recommended, first) · **Fix now on this PR** · **Drop**; plus ONE question per summary draft (**Keep summary** ⇒ `follow-up` / **Drop summary** ⇒ `drop`). An `unreadable <path>` line is shown in the question text as a warning, never silently skipped. Each answer ⇒ `automate-helpers.sh dismissed-decide <runfile> <draft_path> follow-up|fix-now|drop` (follow-up keeps the file with its `- **Decision:**` line rewritten; drop and fix-now delete it — for fix-now the `## Progress` line and the PR's fix commit are its record).
3. **Any `fix-now` answer ⇒ ONE full re-pass of DRAIN → GATE.** Spawn ONE `general-purpose` fix worker on the PR branch under review-heal's existing fix-worker spawn contract (`skills/review-heal/SKILL.md` §U3.5 — not restated here), the selected findings passed as quoted data inside the EXTERNAL_TEXT envelope; then a complete §6 step 3 DRAIN (the owned `/review-pr --until-mergeable --no-auto-postmortem`; the `<run_id>.review-heal-result.md` sidecar is rewritten; `owned_drain_started` / `owned_drain_result` in `## Current` become the re-drain's) and set `fix_now_reentered: true`; then §6 step 4 GATE re-evaluated from the NEW drain result — under `--auto-merge` a fresh `gate-eval` (new `ready_sha`, new `termination_reason`), and a re-drain `ESCALATED` turns the park into `escalated` (so no merge watcher is armed); then this step again from 1 with `--after-fix-now` on the new sidecars. Content-addressed names plus per-finding decisions mean an already-decided finding is never re-asked — even when the re-drain re-dismisses it at a severity that moves it between its own draft and a summary (the decision follows the finding, §1.5 `dismissed-drafts`). **Fix-now is offered at most ONCE per item:** with `fix_now_reentered: true` the options are Follow-up / Drop only. **Re-dismissed fix-now finding:** a drain-origin draft whose ledger row reads `fix-now` and that the re-drain dismissed again (the fix did not take) is re-written `- **Decision:** undecided (fix-now unconfirmed)` (ledger row `fix-now-unconfirmed`) and asked again with Follow-up / Drop — never silently suppressed. This is drain-origin ONLY: `<run_id>.supervisor-result.md` is written once per item and never rewritten by the re-pass, so a Phase 4.5-origin fix-now name stays suppressed (its static sidecar can neither confirm nor refute the fix). Without `--after-fix-now` (e.g. a crash after `dismissed-decide … fix-now` and before the re-drain, then a resume re-running this step on the OLD sidecar) a fix-now name stays suppressed too — it is never marked unconfirmed when no re-drain ran.
4. Only then write the park state — the verdict of the LAST GATE pass — with `pending_decisions: <n>` (the `dismissed-pending` count) and `fix_now_reentered: <true|false>` on `## Current` whenever this item produced drafts; then §9's park tail (merge-watcher arming on `awaiting_merge`, `run-lock.sh release`), unchanged otherwise.

**Under `--non-interactive-fallback`** step 2 asks nothing and step 3 never runs: the drafts stay `undecided` and `## Current` carries `pending_decisions: <n>`. **After a successful `--auto-merge` `MERGE`** (no park, including a MERGE reached on the fix-now re-pass) only step 1 runs; the drafts stay `undecided` with `pending_decisions: <n>`. In both cases the next interactive PICK asks (§6 step 1 "PICK-time pending-decisions ask", Follow-up / Drop only). `pause_reason` gains no value.

**Trail and retraction.** This run's drafts still on disk are `trail-pr` candidates and ride the item's post-merge trail PR ("Trail PR after merge and at run end"); a dropped / fix-now draft is deleted and so is no longer a candidate. Because an UNDECIDED draft can ride a pushed trail commit (non-interactive, after an `--auto-merge` MERGE, or when the merge watcher's `closeout` runs before the owner decides), `trail-pr` retracts a later-dropped one from a REUSED trail branch (details there).

**Honest limits.** `drain-rounds.sh init` resets the per-PR round ledger, so the real bound on one item is 2 × `--max-rounds` drain rounds. `learning-emit` writes at most one complete line per run/item/PR/source, so the engine-native learning line reflects the FIRST drain only. A trail PR ALREADY merged to `main` that carried an undecided-then-dropped draft is `main`'s content — the owner deletes it by hand (the park-time and PICK-time asks make that window rare). An undecided summary that lists an entry absent from the current sidecars (both missing or unreadable, or a rewritten sidecar that no longer dismisses it) is never retired — the draft may be that finding's only record — so it stays and is asked about even when its other entries moved to their own drafts (fails toward asking, at the cost of such a finding being listed twice); but when that slot is REWRITTEN because other current entries belong in it, the rewrite holds the current undecided set only, so a vanished entry is not carried over.

### Trail PR after merge and at run end

> **Branch mode (opt-in):** with the mode on, `trail-pr` pushes to the metadata branch through `meta-sync.sh` instead of opening a PR — same triggers, same evidence gate, loud on failure; see §13.

Nothing else commits the tracked `.supervisor` trail (the run file, its result sidecars, the Queue's requirement files, their done/failed briefs, this run's ledger lines), so the engine commits it itself as ONE PR: `automate-helpers.sh trail-pr <runfile> --reason <closeout|done|skipped|abandoned>` (§1.5; implemented in `scripts/automate-trail.sh`, self-tested by `scripts/test-automate-trail.sh`).

- **When — this is the ONE authoritative trigger list (and the ONE park-path list).** Exactly three triggers, each after the evidence that the work it records is final: **(a)** inside `closeout`, after its evidence gate read the item's PR `MERGED` and after its sync, stamp and check-off (`--reason closeout`; closeout prints the line, "Post-merge close-out" below); **(b)** at the `## Status: done` termination — the Queue fully resolved — after that state is written and BEFORE `run-lock.sh release` (`--reason done`); **(c)** when an item is checked off `# skipped:`/`# abandoned:` — by the loop at §6 step 6 (before that step's lock release), or found so marked by a human at RECONCILE (§5's unblock path; before PICK) — (`--reason skipped` / `--reason abandoned`). At (b) and (c) its one output line is appended with `progress-append`. **No park calls it:** `awaiting_merge`, `escalated`, `rate_limit`, `drain_died`, `token_ceiling`, `trail_pr_open`, `limit_reached` write the park state and release the run-lock directly (`run_lock_held`, `resume_ambiguous` and `meta_unreachable` never held the lock). Why: at a park the item's PR is unmerged, yet Phase 4.5's completion tail has already stamped its requirement `## Status: done`/`done_with_escalation`; a park-time trail PR carried that stamp to `main` ahead of the feature PR, so an owner who merged the trail PR and then closed or reworked the feature PR left `main` saying the item was done — and `is_done` keeps `resolve-folder`/`reconcile-status` from ever re-queueing it (two PRs per item, with an ordering trap). A parked item's trail lands with its `closeout` (or a skip/abandon, or the run end) instead. Honest limit: under `--auto-merge` a gate-merged item never passes through `closeout` (step 5 SYNC runs `brief-repair` + pull), so its trail rides the next `closeout`, skip/abandon check-off or run end — a run that parks for good after auto-merged items leaves their trail uncommitted until one of those fires (`/automate --resume`, or a hand `trail-pr --reason done`).
- **Paths — explicit, never `git add -A`/`.`:** the run file; `<run_id>.review-heal-result.md` / `<run_id>.supervisor-result.md` only when `sidecar-check` says `ok` (a `fail` sidecar is excluded and named in the output line); every `## Queue` item that is a requirement file (`.supervisor/requirements/**.md` only — a Queue item naming any other path, e.g. a source file, is never committed, so its local WIP cannot ride into the trail PR); every `.supervisor/jobs/done|failed/*.md` brief whose `- **Source requirement:**` token equals a Queue item; `.supervisor/postmortem/results.jsonl` as the trail base's copy plus ONLY this run's lines (`automate_key` prefixed by `<run_id>`, or `run_id`), never the whole local file; and this run's dismissed-finding drafts still on disk, `.supervisor/requirements/proposed/<run_id>--*--dismissed-*.md` ("Dismissed-findings decision step (before the park)") — requirement files carrying no done heading (every finding line is `> `-quoted), so the evidence gate below never calls `gh` for them. A path `git check-ignore` reports ignored is dropped (that is how the ledger's repo-allowlist gate is honoured), and so is a path identical to the trail base.
- **Evidence-gated stamps (defense in depth — in the script, not only this prose).** A done claim rides only for merged work. **Requirements** are judged by `is_done`'s own predicate (any `^## Status: done|done_with_escalation` heading, with or without the `<!-- loomwright:requirement-closeout -->` sentinel): every `- **PR:**` in each such heading's block must read `merged` via `reconcile-item` (one `gh pr view --json state,mergedAt` per distinct URL; the value's first `https?://…/pull/<n>` token, stopping at whitespace and markdown link punctuation `[]()<>`, is what is read, so an annotated `<url> (merged by …)`, a `[<url>](<url>)` link or `<url>` works). A done heading naming no parseable PR fails closed. The ONE exemption is the exact heading `reconcile-status --apply` writes for an owner's `# abandoned:` Queue row — `## Status: done_with_escalation — ABANDONED (- [x] <path>  # abandoned: <reason>)`, em dash byte-exact — an owner decision that rides untouched; any other heading that merely contains "ABANDONED" (`done — not ABANDONED`, `done <!-- ABANDONED -->`) is a done claim like any other. **`done/` briefs** follow the same rule on their Outcome section (an `## Outcome` / `### Outcome` heading followed by whitespace, a colon or end of line — `## Outcome — ESCALATED`, `## Outcome:` — never `## Outcomes Rubric`, `##Outcome` or `## Outcome-ish`); an Outcome section naming no PR fails closed. OPEN, CLOSED, unreadable (`gh` failing — `reconcile-item` fails closed) or unparseable ⇒ the path is EXCLUDED and named (`; excluded <path> — pr not merged`). A requirement with no done heading, and a brief with no Outcome section, are unaffected (no `gh` call). The same rule covers skipped/abandoned items. **Retroactive over a reused trail branch:** when `trail-pr` reuses an open (or orphaned) `chore/<run_id>-trail-<n>` whose tip already carries a failing done claim for an excluded path — e.g. a v15.114.0/.1 park-time trail — that path — any gate-excluded path whose tip blob differs from `origin/<default>`'s CURRENT blob and itself fails the gate (so a path `main` changed after the fork also counts, harmlessly) — is put back to `origin/<default>`'s version in the new commit (removed when `main` lacks it) and named `; retracted <path>`; the retracted blob is dropped from the primary index if an earlier `trail-pr` staged it, and the checkout contract never stages a gate-excluded path. So neither a wrong-moment caller nor an older trail PR still open leaves a done claim for unmerged work at the trail tip. Honest limits: a done claim an older trail PR already MERGED to `main` is `main`'s content and is not retracted here (`reconcile-status`, run by a human, is the tool for that). The gate fails CLOSED on a transient `gh pr view` failure, so such a blip excludes — and, on a reused trail branch, RETRACTS — a legitimate MERGED stamp from the open trail PR; the next `trail-pr` restores it, but nothing restores it after the run-end (`--reason done`) trail, where the owner re-runs `trail-pr` by hand. This is deliberate: a missed done stamp is recoverable (`reconcile-status` finds merged work), a false one is not.
- **Dropped-draft retraction (a separate `git rm`, beside the evidence-gate retraction).** Only on a REUSED open (or orphaned) `chore/<run_id>-trail-<n>` branch whose tip differs from `origin/<default>`: a path matching this run's draft glob that the branch TIP carries (or `<run_id>.trail-staged` records), that is ABSENT on disk, and whose `<run_id>.dismissed-decisions` last row reads `drop`, `fix-now` or `moved` (an undecided draft retired because its finding moved to the other bucket — it rides in its new draft) is `git rm`'d in the trail worktree, dropped from the primary index if staged, and named `; retracted <path>` (PR body: `retracted (dismissed draft dropped)`, distinct from `retracted (done claim for unmerged work)`). An absent draft with NO such ledger row is left alone (never guess); never on a fresh branch cut from `origin/<default>`, and never for a draft whose blob `origin/<default>` already carries — that is `main`'s content, the owner's hand delete.
- **Branch + idempotency:** this run's trail PRs are found with `gh pr list --state all --search head:chore/<run_id>-trail` and filtered locally to `chore/<run_id>-trail-<n>`. An OPEN one is re-used — its branch is the base and the new commit is pushed fast-forward to it (`pushed <url>`). Otherwise `n` = the highest existing `n` + 1, based on fresh `origin/<default branch>`; a remote branch of that name without a PR (a crash between push and PR-open) is used as the base and its PR opened. Nothing differs from the base ⇒ `skipped — trail already up to date` (no commit, no PR). Never a force push.
- **Mechanics:** `git fetch origin`, a detached `git worktree add` in a `mktemp -d` directory, copy each path from the primary checkout by explicit path (gitignored scratch does not exist in a fresh worktree), `git add -- <paths>`, commit `chore(supervisor): <run_id> trail (<reason>)`, `git push origin HEAD:refs/heads/<branch>`, `gh pr create` (title + a body naming the run, the reason and the path list) or re-use; the worktree is salvaged (`worktree-salvage.sh`) and removed in a trap.
- **Checkout contract (proved by a fixture, not assumed).** A plain `git pull` refuses to overwrite untracked or modified local copies of the paths the merged trail PR brings in. So after a successful push — and on the no-diff `trail already up to date` skip against an open trail PR — `trail-pr` sets the primary checkout's INDEX entry of EVERY path the trail branch changes (every push on it, not only the latest delta) to that path's blob at the trail-branch TIP (`git update-index --cacheinfo`, never the working copy) and leaves the working copies alone. When the owner merges the trail PR, a plain `git checkout main && git pull` fast-forwards (index == incoming blob), and the bytes that differ BY DESIGN — Progress lines the live run file gained after the push, other runs' ledger lines — stay as ordinary unstaged local modifications. No `git reset`, no stash, no byte discarded. Those staged entries ride along in ANY commit made from the primary index — `git checkout -b` carries them and a plain `git commit -m` (the commit-skill shape; the Supervisor Single-Agent Path commits in the primary) commits the whole index, even after an explicit `git add <file>`. So the engine drops them at PICK, before the next commit-producing phase (`trail-unstage`, §6 step 1), and `trail-pr` records every blob it stages in the gitignored `.supervisor/automate/<run_id>.trail-staged`; `closeout`'s sync re-stages, immediately before its `git pull --ff-only`, each recorded blob that the fetched `origin/main` now carries at that path (index only — bytes this run itself committed and that have landed), so the post-merge pull keeps fast-forwarding after an un-stage. The next `trail-pr` (the next `closeout`, skip/abandon check-off or run end) re-stages every path its reused trail PR carries, including those an earlier PICK dropped, so the owner's hand pull after merging that PR fast-forwards too; `trail-unstage` clears the union of the `.trail-staged` record and the current trail candidates. Honest limits: between a PICK and the next `trail-pr`, a HAND-run `git pull` over a merged trail PR refuses (closeout's sync does not; since `trail-gate`, no trail PR of this run is open across a PICK — the gate parks on one and syncs over a merged one before the un-stage — so this needs a trail PR merged outside that window); a trail PR closed unmerged leaves its entries staged until the next PICK's `trail-unstage`; **the trail branch is never rebased** — once `origin/main` moves the postmortem ledger (another run's trail PR, a postmortem line) after this run's trail branch was cut, a later pushed/no-diff re-trail stages the trail-TIP ledger blob, which lacks main's new line, so the trail PR conflicts at the ledger's EOF and both a hand pull and `closeout`'s sync refuse (fail-safe: no reset, no byte lost) until the owner resolves that trail PR by hand. When `closeout`'s `git pull --ff-only` refuses, the entries it re-staged are put back to their prior index state, so a refused sync leaves the index as it found it. `closeout`'s sync treats these trail paths as trail paths, not as uncommitted changes. **Re-examined for trail-after-merge (v15.114.2) — by fixture, every piece is still load-bearing, none removed:** `closeout`'s own trail runs after its sync, with the primary on `main`, and still stages into the primary index, so the next PICK — which branches off that `main` — still needs `trail-unstage` (without it the next item's plain commit sweeps the trail paths); the owner's hand `git pull` after merging `closeout`'s trail PR refuses without the staged tip blobs (the run file is untracked on `main` until that PR lands); and the NEXT `closeout`'s sync, after a PICK dropped those entries, refuses without the `.trail-staged` re-stage (`scripts/test-automate-trail.sh` leg D3, each with a control that turns red).
- **Output:** exactly ONE line — `trail-pr: opened <url>` / `trail-pr: pushed <url>` / `trail-pr: skipped — <reason>` — with any sidecar or evidence-gate exclusion appended to that same line as `; excluded <path> — <reason>`, and any retraction as `; retracted <path>`.
- **Advisory / fail-SAFE — NEVER gating.** Always exit 0; the loop ignores its exit status. A trail failure (gh absent or failing, fetch/push refused, nothing to commit) never blocks a close-out, a check-off or the run end, never changes a gate decision, `## Status` or `## Current`. `trail-pr` never calls `run-lock.sh`, never merges (the sole merge executor stays `gate-eval`, §11), and never force-pushes.

### Post-merge close-out (`closeout` + the merge watcher)

When the owner merges a parked item's PR, ONE deterministic script closes it out: `automate-helpers.sh closeout <runfile> <item> <pr_url> [--session-id <sid>]` (§1.5; implemented in `scripts/automate-trail.sh`, self-tested by `scripts/test-automate-trail.sh`). Two callers, never the next PICK: `--resume` RECONCILE (§6 step 1, with `--session-id`) and the merge watcher (below, without it). It never merges anything and never picks the next Queue item — the owner's explicit go still starts the next item (the run file then reads `paused` / `awaiting_go`, §3). It does not tick `_BACKLOG.md` either (§2 "The engine never ticks the backlog doc") — the requirement stamp it writes is what `resolve-backlog` reads.

- **Guards:** missing run file ⇒ `closeout: skipped — run file not found`; `gh` absent or `gh auth status` failing ⇒ `closeout: skipped — gh unavailable`. Then the evidence gate: `reconcile-item <pr_url>` must say `merged`, else ONE `closeout: skipped — pr not merged (<state>)` line and nothing else runs.
- **Steps (execution order):** brief repair (the `brief-repair` line, passed through) → run-lock acquire → **3a** each linked worktree on the PR's `headRefName` (never the primary) whose HEAD == the PR's `headRefOid` (the same squash-safe tip check as 3b — a same-named branch at another tip is kept and named, never salvaged or removed, because `git worktree remove` deletes GITIGNORED content that `worktree-salvage.sh` skips by design): `worktree-salvage.sh`, then `git worktree remove` only when it is clean after salvage — a still-dirty worktree is kept and named → **4 sync**: refused when a TRACKED path outside the trail paths (the same set `trail-pr` commits, including the entries it staged) is modified, or the primary is on neither `main` nor the PR head; else `git checkout main` + `git pull --ff-only` — a refusal is a `skipped` line, never a reset → **3b** the local head branch: `git branch -D` ONLY when its tip == the PR's `headRefOid` (one `gh pr view --json headRefName,headRefOid`); squash merges make ancestry useless, so `-d` and "0 commits outside origin/main" are never used; a checked-out branch is kept → **stamp** the requirement with the PASS-shape footer of `skills/self-heal-advisory/SKILL.md`'s completion tail (sentinel + `## Status: done` + Completed/Brief/PR, the Brief being the newest `.supervisor/jobs/done/` brief whose `- **Source requirement:**` equals the item; none ⇒ `skipped — no done brief`; sentinel already present ⇒ `skipped — already stamped`) → **check off** with `queue-checkoff <runfile> <item>` (NO reason argument — a reason writes the excluded `# skipped:` form) → **reconcile `## Current`**: ONLY when `## Current`'s `- item:` line names THIS item AND its `pr:` equals THIS `pr_url` (both compared exactly, after the same `./` strip the item gets), rewrite that line's `status:` to `done` and the `- pause_reason:` line to `awaiting_go` when `## Status: paused` (`null` otherwise — §3 "After a close-out"), through `runfile-write` (the validated atomic write, §3), every other line byte-unchanged; a `## Current` naming a different item or PR (a watcher firing after a later item was picked) is NEVER touched (`skipped — ## Current is <item> (<pr>), not this item/PR`), nor is `## Current` touched unless the Queue reads `- [x] <item>` (a failed check-off leaves it as is), and one already reading `status: done` with the target `pause_reason` is `skipped — ## Current already done`; `## Status` is never rewritten → `progress-append` one line per step, ONLY when an item step changed something (`removed`/`stamped`/`checked`/`reconciled`, or a non-skip brief repair) — a `synced` line alone never appends → **trail** via `automate-helpers.sh trail-pr <runfile> --reason closeout` → release. The check-off runs before the trail so the trail PR records the closed-out item; the trail line is printed but not appended to `## Progress` (that append would leave the run file one line ahead of the trail, and every re-run would push again).
- **Output:** one line per step — `closeout: removed|synced|stamped|checked|reconciled|skipped — <detail>`, plus the passed-through `brief-repair:` and `trail-pr:` lines. **Idempotent:** a second run prints only `skipped — …` item lines (the trail reads `skipped — trail already up to date`) and leaves the run file byte-identical. Its sync may still print `synced — main at <sha>` — `main` moved since the first run, most often because the owner merged that run's own trail PR — and that line never appends to `## Progress` by itself: a sync is checkout housekeeping, not close-out progress, and counting it made every re-run after a trail merge append its skip lines and open a fresh trail PR holding only them (run `automate-2026-10-01-142337`, trail PR #330). **Always exit 0.**
- **Concurrency:** steps 3–7 run under `run-lock.sh acquire --owner automate-closeout:<run_id>` (plus `--session-id <sid>` when given, which RE-ENTERS the PICK's `automate:<run_id>` lock — outer owner unchanged). Release is `run-lock.sh release --owner automate-closeout:<run_id>` ONLY, in a trap — never `--session-id`, which would release the outer PICK lock mid-RECONCILE. A held, non-re-enterable lock ⇒ one `closeout: skipped — run lock held by <owner>` line for steps 3–7.
- **The merge watcher — `scripts/automate-merge-watch.sh <runfile> <item> <pr_url>`.** Armed ONLY at §9's safe-mode `awaiting_merge` park, after the park state is written and before `run-lock.sh release`; an `escalated` park arms none. Launched detached, pure bash, no Claude session, no tokens: `env -u CLAUDE_PID -u CLAUDECODE nohup bash <plugin root>/scripts/automate-merge-watch.sh <runfile> <item> <pr_url> </dev/null >.supervisor/automate/<run_id>.merge-watch.log 2>&1 &` (not `setsid`, absent on stock macOS). It polls `gh pr view <url> --json state` every `LOOMWRIGHT_MERGE_WATCH_INTERVAL` seconds (default 60; a `gh` error doubles the wait up to 15 min, reset on success). `MERGED` ⇒ `closeout` (no `--session-id`); a TRANSIENT guard skip — `skipped — run lock held`, `skipped — gh unavailable`, `skipped — pr not merged (…)` (the forge disagreeing with the watcher's own `MERGED` read is a blip), or no output at all — is retried on a later poll (backoff doubling to 15 min) within the lifetime cap; any OTHER lone guard skip (`run file not found`, `not a git checkout`, …) is terminal: one `## Progress` line + a notify naming the skip, exit, never the success notify. Only a closeout that got past its guards gets the success notify (`notify-desktop.sh` + `send-webhook.sh`, both fail-safe), exit. `CLOSED` ⇒ one `gone` `## Progress` line + notify, exit, no cleanup (§4's `gone` rules stand). Lifetime cap `LOOMWRIGHT_MERGE_WATCH_MAX_SECONDS` (default 72h) ⇒ one `## Progress` line, exit; when the watcher HAS read `MERGED` but `closeout` kept returning a transient skip until the cap, that line and a failure-style notify both say the PR is merged and name the last skip reason (`/automate --resume` closes it out).
- **Single instance per run:** marker `.supervisor/automate/<run_id>.merge-watch` (TSV `pid`/`pr_url`/`started`, gitignored because it is not `*.md`). A live marker pid counts only when `ps -ww -p <pid> -o command=` shows an `automate-merge-watch.sh` process carrying the marker's `pr_url` — a recycled pid is never signalled, the marker is reclaimed as stale. Same `pr_url` ⇒ `merge-watch: already running pid=<p>`, exit. A DIFFERENT `pr_url` (the run parked a later item) ⇒ the old watcher is replaced: TERM (its sleeps are interruptible, its trap removes its marker), KILL only if it is still alive after 60s, one `## Progress` line naming the PR that is no longer watched (`/automate --resume` closes it out after it merges), then the new watcher starts. `ps` unavailable ⇒ not verifiable ⇒ `already running`. A dead pid is reclaimed; the marker is removed on every exit, and a launch removes only the marker it inspected.
- **Why `CLAUDE_PID`/`CLAUDECODE` are unset (the launcher and the watcher itself both do it):** with them set, `run-lock.sh` would record the launching Claude session as the holder of closeout's lock, and a closeout that died without its trap would leave a lock nobody can reclaim while that session lives. Unset, the lock meta records `pid_source ppid` — the closeout process — so a crashed closeout's lock is reclaimable (dead pid + the 1800s TTL).
- **Rejected alternative:** an in-session `Monitor` until-loop dies with the session and is not verified headless.
- **Honest limit:** nothing surfaces a live watcher at SessionStart; the marker and the lifetime cap bound it.

## §7 — Single drain (no double-dispatch) + the config-toggle contract

`/autonomous` already triggers Supervisor's **default detached until-mergeable drain** (Phase 4.5 step 5.5 **and** the `PostToolUse[Bash]` `gh pr create` hook backstop). If the engine *also* drains, two until-mergeable loops race the branch (HIGH risk). The engine therefore **suppresses the default dispatch and owns exactly ONE inline drain per pass** — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent) (§6 "Dismissed-findings decision step (before the park)").

### Suppress window (wrap the RUN phase)

- Set `.supervisor/config.json {"auto_review": false}` **BEFORE** invoking `/autonomous` and restore it in a **finally-style cleanup** immediately after `/autonomous` returns *or fails* — i.e. **BEFORE the engine's own inline `/review-pr --until-mergeable` drain** (§6 step 3). Both default dispatches fire *during* `/autonomous`, so setting it at DRAIN is too late; the owned drain is inline and not gated by `.auto_review`, so restoring before it is correct and keeps the suppression window tight.

### Config-toggle contract (byte-for-byte; absent-delete; malformed-abort)

> **Execute via the helper, not a re-implementation:** suppress with `automate-helpers.sh config-suppress <config_path> <backup_path>`, restore with `automate-helpers.sh config-restore <config_path> <backup_path>`, and read the original with `automate-helpers.sh config-orig <config_path> [<backup_path>]` (§1.5) — **pass the backup path whenever suppress has already run** (next bullet). The prose below is the SPEC those subcommands implement.

- **Backup:** byte-for-byte copy the existing `.supervisor/config.json` to a **transient** `<run_id>.config-backup.json`. Record its path + the original `.auto_review` value in `## Run Config` (`auto_review_original: <true|false|absent>`, `config_backup: <run_id>.config-backup.json`). **Record absence** (`auto_review_original: absent`) if there was no prior config.
- **Read the original from the BACKUP once suppress has run (call-order hazard).** The sequence above is backup → suppress → record, so the value is read *after* the live `config.json` has already been rewritten to `auto_review: false` — at that point the live file reports `false` for EVERY original, and only the byte-for-byte backup (or its `__ABSENT__` marker) still holds the truth. **`config-orig <config_path> <backup_path>` prefers the backup when it exists and falls back to the live config when it does not**, so it returns the true original in either call order; a corrupted backup ABORTS (exit 2) rather than fabricate a value. Calling the one-arg form after suppress records a WRONG original — observed 2026-09-04 on a real run, where a config with no `auto_review` key was recorded as `false` instead of `absent`. This matters because RECONCILE (§4 step 3) is the consumer of that recorded value; the *restore* path itself is unaffected (it is byte-for-byte from the backup and never consults `config-orig`). Guarded by `scripts/test-automate-helpers.sh` §A7. A backup path that is **given but missing** falls back to the live config rather than aborting — missing is the normal state of a correct *pre*-suppress call, so aborting on it would re-introduce call-order dependence in the other direction (a *malformed* backup still aborts; it can never be legitimate). **The caller must therefore record `auto_review_original` before the backup is deleted** — a backup lost after suppress puts the reader back on the live config and back on the wrong answer. Both arms pinned in test §A7f.
- **Restore:** overwrite `config.json` from the backup **OR delete `config.json` if it was originally absent** — **never leave a partial `config.json` shadowing the legacy `notify-config.json`** (the new path wins when both exist, so a stray empty `config.json` would mask `notify-config.json`).
- **Malformed pre-existing config ⇒ ABORT.** If the existing `config.json` is not parseable JSON, do not blindly overwrite it — abort the tick (the user has a hand-edited config we must not clobber).
- **Crash-restore:** RECONCILE (§4) restores a crash-stranded backup on the next start.
- On clean restore, **delete** the transient backup sidecar.

### Own ONE inline drain

After suppression, DRAIN owns **exactly ONE** inline `/review-pr --until-mergeable --no-auto-postmortem` per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent); the re-drain runs only after the first drain returned and its result was read, and is itself one inline drain under the same `.auto_review` contract (the standalone review-and-heal drain — authority is `skills/review-heal/SKILL.md` §"Until-Mergeable Mode"). The **`--no-auto-postmortem`** flag suppresses the owned drain's churn-gated Postmortem Dispatch Tail: inside `/automate` the engine emits its OWN honest engine-native learning line (§6 step 3 "Learning-emit at end-of-DRAIN"), so the owned drain must NOT also append a GitHub-blind false-0 postmortem line for the same PR — one honest line, not honest + false-0. (Outside `/automate`, a standalone `/review-pr --until-mergeable` keeps its Postmortem Dispatch Tail unchanged.) Its **terminal `REVIEW_HEAL_RESULT` is read synchronously** and written to `## Current`:

- `owned_drain_started: <ts>`
- `owned_drain_result: READY | ESCALATED`  (the `--until-mergeable` terminal decision — `READY` is "ready, left open for a human"; it **never merges**. `READY`'s bound is now **mechanized** via `scripts/drain-rounds.sh`, the same shared ledger both `/review-pr` entry paths call — `review-heal/SKILL.md` §U4 — and `READY` carries a `termination_reason` of `converged` or `sub_floor_converged`; ONLY `sub_floor_converged` is excluded from the §10 trusted-merge gate, condition 1, below)
- `suppressed_default_dispatch: true`

**Verifiable** via those `## Current` fields **plus the absence of any detached `dispatch-pr-review.sh` artifact for the PR** (no `.supervisor/review-dispatch/` marker for the PR URL, no `pgrep -lf review-pr-runner` for it).

## §8 — Single-open-PR invariant (BOTH modes)

**While ANY item has an OPEN unmerged PR — status `awaiting_merge` OR `escalated` — or this run's own trail PR is open, the loop MUST NOT PICK a new item.** At most ONE open PR exists at any time, the engine's trail PR included.

- **`awaiting_merge`:** the run is stopped (`paused` also stops a `/loop` driver, §12), so nothing re-checks the PR on its own except the **merge watcher** armed at the park (§6 "Post-merge close-out"): when a human merges, it runs `closeout` (cleanup, `main` sync, stamp, check-off, trail) and notifies. An `/automate --resume` RECONCILE runs the same `closeout` if the watcher has not. Either way **the owner's explicit go is still required before the next item is picked**; it then branches off **fresh `main`**. (`--auto-merge` skips this park by merging at the gate — §10 — but still parks on `escalated`.)
- **`escalated`:** the run stays **paused** (`## Status: paused`, `pause_reason: escalated`) until a human resolves it (§9). An escalated PR is open + unresolved; stacking a second PR would violate this invariant.
- **This run's trail PR (`trail_pr_open`).** `closeout` opens the trail PR right after the item's merge (§6 "Trail PR after merge and at run end"); if the owner gives the next go first and merges the trail PR while the next item's PR is open, that merge moves the base under it. With `strict` required status checks (classic protection's "Require branches to be up to date before merging") the item PR then reads `mergeStateStatus: BEHIND` and cannot merge until someone merges the base into it (run `automate-2026-10-01-142337`: trail PR #345 under PR #347). So the PICK-time trail gate (`automate-helpers.sh trail-gate`, §6 step 1) parks `pause_reason: trail_pr_open` while a `chore/<run_id>-trail-<n>` PR is open — or its state cannot be read (fail CLOSED) — and, once none is, syncs the primary over the merged trail before the next branch is cut. The owner's go then means "merge the trail PR, then `--resume`", which is the close-out order the owner already asked for. Options considered — this gate is (b)'s first form, PICK refuses while the trail PR is open:
  - **(a) Refresh a READY-but-BEHIND PR by a regular merge of `origin/main` plus one confirming required-check pass — rejected.** Not the drain's job: `review-heal` §U4's READY is defined over review signals and required checks, `mergeStateStatus` is corroborating-only and never the basis of a READY/ESCALATED verdict (`review-heal` §"Until-Mergeable Mode", "Corroborating-only fields"), the drain pushes only fixes for validated findings, and `/review-pr` also runs on PRs outside this engine, where merging the base into the head branch is the repository owner's policy call. As an engine step at GATE it would cover only a base that moved before the park — in safe mode the trail lands after the park, while the PR waits for the human merge the engine never sees — and under `--auto-merge` the merge commit is a new head the drain never verified, so `gate-eval`'s `head_sha_moved` (§10) would have to accept a `ready_sha` the drain did not produce: a weaker condition 2, an owner decision rather than a fix.
  - **(b)'s second form, hold the trail until run end — rejected.** `closeout`'s trail exists so a merged item's stamp, run file and drafts reach `main` per item, before the next one starts (trail-after-merge, v15.114.2); holding it would leave every stamp off `main` for a run that parks for good, and the run-end trail PR would carry the whole run at once.
  - **(c) Exempt `.supervisor/**`-only changes from the up-to-date requirement — not possible.** Classic branch protection's `required_status_checks.strict` is one boolean per protected branch with no path filter, and a ruleset's "require branches to be up to date" (`strict_required_status_checks_policy`) has none either: any commit on the base makes every open PR `BEHIND`, whatever paths it touched.
  - **Honest limits.** The gate covers this run's trail PR only: another merge to the base while an item's PR is open (a hand-merged PR, another run's trail PR) still leaves it `BEHIND` under `strict` — the owner updates the branch (GitHub's "Update branch" button, or a hand merge of the base), and under `--auto-merge` the gate's `gh pr merge --squash` fails and parks `merge_command_failed`. Under `--auto-merge` a skip/abandon check-off opens a trail PR mid-run, so an unattended run parks `trail_pr_open` at the next PICK until the owner merges it.

## §9 — Two modes + READY / ESCALATED semantics

**`READY` = "ready, left open for a human" — NOTHING in the plugin merges.** `/review-pr` / `review-heal` and Supervisor Phase 4.5 all terminate at `READY`/`PASS` and leave the PR open. But without a merge the engine would **stale-base** the next item or build a **PR tower**, so the merge is the engine's OWN step:

- **Safe mode (default):** at the GATE, a `READY` drain ⇒ `## Current` status `awaiting_merge`, `## Status: paused`, `pause_reason: awaiting_merge`. The loop parks (single-open-PR invariant): run the §6 "Dismissed-findings decision step (before the park)" FIRST (owner decisions, and at most one fix-now re-pass, before the park state is written), then write the park state, arm the merge watcher (`automate-merge-watch.sh`, detached — §6 "Post-merge close-out"), then `run-lock.sh release` — no `trail-pr` here: the PR is unmerged ("Trail PR after merge and at run end"). When a human merges, the watcher runs `closeout`, whose own trail commits the item's trail; the next item waits for the owner's `--resume`. **Nothing is merged automatically.**
- **`--auto-merge` mode (opt-in, default OFF, gated):** at the GATE, `gh pr merge --squash` fires **only** when the trusted gate (§10) holds; otherwise fail **CLOSED** → park + notify, with the §6 "Dismissed-findings decision step (before the park)" run before that park is written (after a `MERGE`, only its `dismissed-drafts` runs and the drafts wait for the next interactive PICK).

**`ESCALATED` never merges and PARKS the run** in BOTH modes — after the §6 "Dismissed-findings decision step (before the park)" runs: `## Status: paused`, `pause_reason: escalated`, notify (best-effort desktop + webhook), then `run-lock.sh release` — no `trail-pr` ("Trail PR after merge and at run end"); it does **NOT** pick a new item. To proceed:

- **resolve the PR** (fix + merge, or close), **OR**
- **mark the item `skipped`/`abandoned`** in `## Queue` (§5),

then `--resume`.

## §10 — Trusted auto-merge gate (7 conditions, fail CLOSED, SELF-RESOLVING)

> **Execute via the helper, not a re-implementation:** the loop hands `automate-helpers.sh gate-eval <pr_url> <ctx.json> [--root <checkout>]` (§1.5) — the **single** implementation of this gate and the **only** code path that executes `gh pr merge --squash` — a SHRUNK `ctx.json` carrying only what the loop alone knows. It prints `MERGE` (after merging) or `PARK: <reason>` and is self-tested for fail-closed behaviour on every condition. The conditions below are the SPEC `gate-eval` implements.

**SELF-RESOLVING (red-team-hardening item 03).** Before this hardening, every condition below validated only the SHAPE of a value the model-authored loop wrote into `ctx.json` (`has()` + `type == "boolean"`, exact-string checks) — none of them re-derived the value from reality, so a `ctx.json` claiming `"high_risk": false` with no `classify-risk.sh` run at all would merge a genuinely high-risk diff. **The gate now computes every condition it can from LIVE ground truth itself** (`gh`, GraphQL, `classify-risk.sh`, and two artifact-file reads) — a caller can no longer hand the gate a fabricated verdict for any of conditions 2 through 7.

**`ctx.json` shape — SHRUNK to exactly what only the drain/loop can know:**

```json
{
  "drain_result": "READY|ESCALATED",
  "termination_reason": "converged|bound_hit|sub_floor_converged|ci_untrusted",
  "ready_sha": "<sha>",
  "trust_unprotected": true|false,
  "review_heal_result_path": "<path to the verbatim REVIEW_HEAL_RESULT artifact>",
  "supervisor_result_path": "<path to the verbatim SUPERVISOR_RESULT artifact>"
}
```

**GATE-OWNED KEYS — REFUSED, NEVER TRUSTED.** Every other former key now names a condition the gate computes itself: `high_risk`, `risk_reasons`, `head_sha`, `base`, `review_decision`, `unresolved_human_thread`, `protection_enforceable`, `checks_green`, `rubric_satisfied`, and — condition 7 (rule-enforcement-at-review-and-merge) — `rules_gate`, `rules_ok`, `rules_check`. **If a `ctx.json` carries ANY of these keys — regardless of the value — the gate PARKs with `PARK: ctx_carries_gate_owned_key` before evaluating anything else.** A caller attempting to hand the gate a pre-computed verdict for a gate-owned condition is refused outright, never silently accepted. This is checked FIRST, ahead of every condition below.

`gh pr merge --squash` fires **ONLY** when **ALL SEVEN** conditions hold. If any fails or is **unreadable** ⇒ fail **CLOSED** → park (`pause_reason: awaiting_merge`/`escalated`) + notify. (Two values are NOT automatic parks — they have explicit per-condition semantics below: a **reviews-not-required `reviewDecision`** is deferred to cond 4, and an **absent rubric** is N/A — see cond 3 and cond 5.) This gate — implemented in `automate-helpers.sh gate-eval` — is the **only** sanctioned, EXECUTED `gh pr merge --squash` in the plugin (§11).

1. **Owned drain == `READY`, AND its `termination_reason` is NOT `sub_floor_converged`.** The engine's own inline `/review-pr --until-mergeable` (§7) returned `READY` (not `ESCALATED`). **A `sub_floor_converged` READY is NOT auto-merge-eligible** (AC9, drain-bounding-earned-checks): its final round skipped the all-channel bot-finding re-scan (`review-heal/SKILL.md` §"Termination-only severity floor"), so it must PARK exactly like a non-`READY` drain result. `automate-helpers.sh gate-eval` reads `termination_reason` with the same explicit `has()`/`!= null` fail-CLOSED form as cond 3's `unresolved_human_thread` — missing/unreadable ⇒ PARK, never a silent merge. **`termination_reason: ci_untrusted` (ci-trust-probe-01):** a `ci_untrusted` termination always pairs with `drain_result: ESCALATED`, never `READY` (`scripts/ci-run-probe.sh` classifying a required check `untrusted_infra` still blocks READY, `review-heal/SKILL.md` §"READY redefinition"), so a well-formed ctx already fails CLOSED through this SAME condition's `drain_result != "READY"` check. `gate_eval()` (`automate-helpers.sh`) ALSO carries a separate, deliberate defense-in-depth PARK for this value specifically (its condition 1c, immediately after the `sub_floor_converged` check) — mirroring that guard's shape — so a hypothetically-corrupted ctx claiming `drain_result: READY` alongside `termination_reason: ci_untrusted` still cannot merge.
   - **Cross-checked against the artifact, never trusted as a bare assertion.** The gate ALSO reads `ctx.json`'s `review_heal_result_path` — the file the DRAIN step (§6) wrote the terminal `REVIEW_HEAL_RESULT` block to VERBATIM — and parses that file's OWN `decision`/`termination_reason` fields (a bounded grep/awk extraction; `result_block_parser.py` is a library with no CLI). The ctx's `drain_result`/`termination_reason` MUST match what the artifact actually says, or the gate PARKs (`PARK: review_heal_result_unreadable` if the file is missing/unreadable, `PARK: drain_result_mismatch` if the two disagree). The drain's self-report about its own outcome is corroborated against the artifact it actually produced, never trusted blind.

2. **Head SHA still == the `READY` SHA AND base == `main`.** The gate itself re-reads `gh pr view <url> --json headRefOid,baseRefName,statusCheckRollup`; if the live head moved since the drain declared `READY` (a new commit landed), or the base is not `main`, **do not merge** (the approved state is stale). `ready_sha` stays a ctx input (the drain's claim) — but it is now CROSS-CHECKED against the live read, never trusted alone.

3. **`reviewDecision` not blocking AND no unresolved thread from an actor outside the trusted-actor set.**
   - The gate reads `gh pr view <url> --json reviewDecision` ITSELF (a separate call from condition 2's, so a reviewDecision-specific read failure PARKs on its own reason rather than being masked by condition 2's) ⇒ **NOT** in `{CHANGES_REQUESTED, REVIEW_REQUIRED}` (those park). A **`null` `reviewDecision` means the branch does not require approving reviews** (an unprotected branch, or **checks-only protection**) — this is **NOT** a cond-3 blocker; whether such a branch may merge is decided by **cond 4** (enforceable protection OR `--trust-unprotected`). Only a **genuinely unreadable** read (the `gh` call failed) parks here (fail closed) as `PARK: review_decision_unreadable`.
   - **No unresolved thread from an actor outside the trusted-actor set.** Threads are **GraphQL-only** (there is **no** `gh pr view --json reviewThreads` flag — see `review-heal/SKILL.md` §"Step U1 — All-Channel Read" GraphQL block, and its Anti-Pattern "Inventing a `gh pr view --json reviewThreads` flag"). The gate runs the query itself, VERBATIM from `review-heal/SKILL.md` §"Step U1" (b) (never re-derived):
     ```
     gh api graphql -f query='
       query($owner:String!,$repo:String!,$number:Int!){
         repository(owner:$owner,name:$repo){
           pullRequest(number:$number){
             reviewThreads(first:100){
               pageInfo{ hasNextPage }
               nodes{ isResolved comments(first:1){ nodes{ author{ login __typename } } } }
             }
           }
         }
       }' -F owner=<owner> -F repo=<repo> -F number=<number>
     ```
     For each `isResolved == false` thread, the gate checks the first comment's author login against the **trusted-actor set** (`${HOME}/.claude/loomwright/trusted-actors.json`, red-team-hardening item 01 — the SAME user-scope allowlist `classify-bot-review.sh --trusted-actors` and `wrap-external-text.sh` resolve): an actor **NOT** in the set ⇒ BLOCK. This is a stricter, merge-time-only rule than §U3's drain-readiness bot-vs-human split (which lets ANY bot-authored thread through) — the FINAL merge gate trusts only the explicitly-named allowlist, not a login-shape heuristic. `hasNextPage == true` (truncated >100 threads) or ANY GraphQL read error ⇒ fail CLOSED (treated as a blocking thread) — same "absent file ⇒ nobody trusted" resolution as `wrap-external-text.sh`, no `bot_author_re` fallback here.

4. **Enforceable branch protection (OR explicit `--trust-unprotected`).** The gate itself calls `gh api repos/<owner>/<repo>/branches/main/protection` ⇒ protection is **enforceable** when `required_approving_review_count >= 1` **OR** there are required status checks. A **404** ⇒ genuinely unprotected (`false`); **ANY OTHER error** ⇒ `PARK: protection_unreadable` (never silently treated as either protected or unprotected). **GitHub rulesets are out of scope in v1** (only classic branch protection is read). This condition is what actually decides a **reviews-not-required** branch (cond 3 `null`/"none"): a **checks-only-protected** branch (required status checks, `required_approving_review_count == 0`) is enforceable and may merge; a **truly unprotected** branch merges ONLY with `--trust-unprotected`. **Scope of the flag: `--trust-unprotected` overrides condition 4 ONLY** — it does not touch condition 6 (a high-risk diff parks with or without it), and there is no flag, config key, or project file that overrides condition 6. `trust_unprotected` stays a ctx input — it is a legitimate operator flag, not a fact the gate can observe.

5. **Required checks green AND rubric satisfied.**
   - Required checks: the gate discovers the required-context list from the SAME branch-protection payload condition 4 already fetched (the discovery recipe is `review-heal/SKILL.md` §"Step U2 — Required-check discovery") and cross-references it against `statusCheckRollup` from condition 2's combined read — all green, or there are no required contexts (vacuously green).
   - **Rubric satisfied — now a FILE READ, never a caller-asserted value.** `ctx.json`'s `supervisor_result_path` names the file the RUN step (§6) wrote the terminal `SUPERVISOR_RESULT` block to VERBATIM; the gate parses a `rubric_score: N/M` line from that file ITSELF. `N == M` ⇒ satisfied; no such line ⇒ **N/A — NOT a blocker** (the item had no `## Outcomes Rubric`); the file missing/unreadable ⇒ `PARK: supervisor_result_unreadable`.

6. **NOT a high-risk diff — the gate ITSELF invokes `classify-risk.sh`, NO override of any kind (owner decision R5).** The gate runs `"$(dirname "$0")/classify-risk.sh" main <live head_sha> --root <checkout>` (the plugin's `scripts/classify-risk.sh`) on the **live head SHA condition 2 just confirmed** and reads `.high_risk`/`.reasons` from its own output — **no `ctx.json` input feeds this condition any more** (`high_risk`/`risk_reasons` are gate-owned keys, refused if present — see above). The script is the ONE implementation of the high-risk heuristic (branches a/b/c — security/financial/migration surfaces, workflow/orchestration surfaces, sheer size — plus the add-only `.agent/risk.json` project extension; `classify-risk.sh --kind-table` prints the rules and `docs/RESULT_SCHEMAS.md` §SUPERVISOR_RESULT carries the one committed copy — not restated here). `gate-eval` reads `high_risk` in EXACTLY cond 3's fail-CLOSED shape (`has()` + `type == "boolean"`, MERGE only on the JSON boolean `false`): `true`, `null` (unclassifiable — bad ref, git or jq failure), a missing key, or ANY string — including `"false"` — all park as `PARK: high_risk_diff (<first 3 reasons; "; ">)`. **Nothing overrides this condition** — not `--trust-unprotected` (cond 4 only), not a config key, not an `exclude` list (`.agent/risk.json` has none; projects may only ADD surfaces).
   - **Honest limit:** the heuristic is pattern-based, not semantic — a comment containing `token` trips it, and in an agent-orchestration repo nearly every PR touches `agents/`/`commands/`/`skills/`, so nearly every PR parks here by construction. That is the intent: high-risk stays behind a human.

7. **No stamped, gate-countable `must`-rule check fails — the gate ITSELF invokes `rules-gate-verdict.sh`, NO override of any kind (automate-followups/07, owner decisions D1–D4, 2026-09-28).** Evaluated AFTER cond 6, so every earlier PARK reason keeps its precedence. The gate runs `"$(dirname "$0")/rules-gate-verdict.sh" --root <checkout>` (the plugin's `scripts/rules-gate-verdict.sh`, resolved as a sibling exactly like cond 6's `classify-risk.sh`) on the checkout the drain declared `READY` in — **no `ctx.json` input feeds this condition** (`rules_gate`/`rules_ok`/`rules_check` are gate-owned keys, refused if present — see above). The helper never runs a `check` itself: it DELEGATES to `rules-check.sh` (`--list-selected`, `--list-gateable`, `--gate-state`, then one `--if-stamped` replay — `rules-check.sh` stays the SOLE executor of a rule `check`, `skills/rules/SKILL.md` §9) and prints ONE verdict JSON, always exit 0. `gate-eval` reads `.verdict` with an explicit `has()` + `type == "string"` check and computes `rules_ok` in the AFFIRMATIVE form (never a `= "false"` test): `ok` ⇒ holds; `none` ⇒ holds (nothing countable to verify — the cond-5 absent-rubric N/A precedent); anything else PARKs with a NAMED reason:
   - `fail` ⇒ `PARK: rules_check_failed (<up to 3 countable ids; "; ">)`.
   - `unresolved` ⇒ `PARK: rules_check_unresolved (<ids>)` — a truncated or forged replay (a pre-printed `[PASS]`, a forged `[SKIP] all (unstamped)` beside a `[RUN ]` line, a forged trailer) can only ADD this blocker, never remove one.
   - `unstamped` ⇒ `PARK: rules_unstamped (<text>)`, the text chosen by the helper's optional `unstamped_reason` (message only — the park is keyed on the verdict, so a missing or unknown reason still parks): `countable_set_drift` ⇒ `countable rule set changed since the last /rules check --confirm on this machine` (no count: drift can EMPTY the live countable set, and "0 … never confirmed" would read as nothing to confirm), `legacy_stamp` ⇒ `the stamp predates the recorded countable rule set; re-run /rules check --confirm on this machine`, and `never_confirmed` / missing / unknown ⇒ `<n> countable must-check(s) never confirmed on this machine` — **D3's middle form:** this fires because ≥1 countable must-check exists now, OR because the countable id set DRIFTED from the one recorded at the last `/rules check --confirm` (a store whose must-checks are all advisory, and always were, answers `none` and does not park). A PR that edits a file a countable check `binds` moves the stamp hash, and a PR that changes WHICH rules count (drops or breaks `binds`, `chmod +x` on a read file, demotes or removes a countable rule) moves the recorded countable set — both land HERE, so the edit cannot turn a failing bound check into a counted pass without a human re-running `/rules check --confirm` (`skills/rules/SKILL.md` §8.1). A `.agent/rules/*.json` file that is not a parseable JSON array is `unreadable`, never `none`.
   - `cmd_disabled` (`RULES_CHECK_NO_CMD=1` in the gate's environment) ⇒ `PARK: rules_cmd_disabled` — the gate cannot verify, same fail-closed posture as `unstamped`.
   - `unreadable`, helper absent/unreadable, non-zero exit, empty / non-JSON / non-object output, a missing / null / non-string `.verdict`, or any unrecognised verdict string ⇒ `PARK: rules_gate_unreadable`.
   Which must-checks count is decided by the rule's `binds` declaration and `rules-check.sh --list-gateable` (`skills/rules/SKILL.md` §8.1/§8.2 — not restated here); an advisory (non-countable) rule's pass/fail is reported, never counted. **Nothing overrides this condition** — not `--trust-unprotected` (cond 4 only), not a config key, not a project file.
   - **Honest limit (dormancy):** on a READABLE store with no countable `must` rule (this repo's own store today) the verdict is `none` and the condition always holds — the gate has teeth only once a human declares `binds` on a checkable `must` rule and confirms it with `/rules check --confirm`. `none` needs that readable store: a non-parseable store is `unreadable` and a recorded stamp whose live countable set has drifted to empty is `unstamped` (`countable_set_drift`) — both park (the `unstamped` / `unreadable` bullets above). A LEGACY stamp (one predating the recorded countable set) with an empty live countable set is NOT drift: it reads `none` and the condition holds (the `rules-gate-verdict.sh` header, THE COUNTABLE-SET BINDING).

On all seven holding: `gh pr merge --squash <url>`. Then SYNC (`git checkout main && git pull`) so the next item branches fresh (§6).

```
/automate ... --cheap                        # passthrough to inner /autonomous (Sonnet cost profile → /supervisor; not persisted — re-pass on --resume)
/automate ... --max-tokens N                 # opt-in spend ceiling (red-team-hardening/06) — PARKS before PICK on breach; PERSISTED in ## Run Config (unlike --cheap/--notify)
```

### `/loop` driver (namespaced form required headless)

The engine is designed to be driven continuously by Claude's `/loop`. Use the **namespaced** form (bare `/automate` is "Unknown command" under detached `claude -p`):

```
/loop /loomwright:automate [...]
```

`/loop` re-invokes `/automate` each tick; the run file's `## Status` is the stop signal — `done` (Queue fully resolved) or `paused` (limit / awaiting_merge / escalated) both stop the driver.

## §13 — Branch mode (opt-in, default OFF)

A repo that opts in keeps its run history — `.supervisor/requirements/`, `jobs/done|failed/`, `automate/*.md`, the findings ledger — on the metadata branch that `scripts/meta-sync.sh` syncs (`docs/ARCHITECTURE_CONTRACTS.md` §"Metadata branch") instead of committing it to the default branch through a trail PR. A repo that has not opted in takes every other section of this skill byte-for-byte; nothing below runs.

- **The switch and its ONE reader.** `/setup memory` writes the mode: `setup-memory.sh apply --branch-mode <branch>` (suggested value `loomwright-meta`, meta-sync's own default) rewrites the managed `.gitignore` block without the run-history re-includes and records ONE tracked comment line inside the sentinels, `# loomwright-meta-branch: <branch>`; `--branch-mode off` restores the default block; a plain `apply` preserves the line; `remove` deletes it with the block. `setup-memory.sh mode` prints exactly one line — `off` | `on <branch>` | `unknown <reason>` — and every caller below uses it; nothing else parses the block. Switching never untracks already-committed run history (a separate operator step).
- **`meta-entry` FIRST, on every entry.** Before §4's glob, before any run file is created, before the PICK run-lock acquire, run `automate-helpers.sh meta-entry`. It reads the mode itself (no caller input can assert it) and prints one line: `meta-entry: off` ⇒ proceed exactly as today; `meta-entry: pulled <branch>` ⇒ run history is current, proceed; `meta-entry: failed — <reason>` (meta-sync's own `no_remote_branch` / `conflict <path>` / fetch-failure text, or `mode unknown (<reason>)`) ⇒ **no run file targeted** (a new run, or bare `/automate` / `--resume` with no matching LOCAL run file) — **ABORT** with the message and create nothing (a park would create a run file and make the next resume ambiguous); **an existing local run file targeted by `--resume <id>`** — park it: `## Status: paused`, `pause_reason: meta_unreachable`, one `## Progress` line naming the reason (a conflict names its path). Never fall through to an empty `resume-glob`: with run history absent every reader answers empty with exit 0, and a second run would start beside a paused one (silent amnesia).
- **The trail push (replaces §6's trail PR).** `trail-pr` keeps its three triggers but, with the mode on, opens NO PR and creates no trail worktree: it builds the list from the same candidates and the same evidence gate (a done claim rides only for MERGED work; an excluded path is named `; excluded <path> — pr not merged`) — EXCEPT the `git check-ignore` drop, skipped here because every run-history path is ignored in branch mode — and runs `meta-sync.sh push --branch <branch> --paths-from <list> --message "chore(supervisor): <run_id> trail (<reason>)"`. One line: `trail-pr: meta-pushed <branch>` | `trail-pr: skipped — meta no_changes` | `trail-pr: meta-push FAILED — <reason>`, `; excluded …` appended. **Ledger:** `.supervisor/postmortem/results.jsonl` is listed as a whole file (meta-sync line-unions it; its scrub rule (a) refuses a foreign `.repo` — which fails the WHOLE push, not just the ledger). **Dropped drafts:** this run's dismissed drafts absent on disk whose `<run_id>.dismissed-decisions` last row reads `drop` / `fix-now` / `moved` are listed too, so meta-sync deletes them on the branch. `trail-unstage` prints `trail-unstage: skipped — branch mode`; `closeout` skips the `.trail-staged` re-stage; no `.trail-staged` record is written.
- **Push failures are loud.** A non-zero `meta-sync.sh push` (conflict, `no_remote_branch`, fetch failure, exhausted retries, `tree_guard`, `locked`, a scrub hit) or a mode reading `unknown` ⇒ `trail-pr` appends ONE `## Progress` line `meta-push FAILED: <reason>` to the run file itself (so `closeout` and the merge watcher record it too), fires the fail-safe notify pair, and writes the gitignored marker `.supervisor/automate/<run_id>.meta-push-failed` (UTC timestamp + reason; a scrub hit's full `meta_sync: scrub <path>: <rule>` list follows). The next successful push removes it. **PICK report:** before picking, run `automate-helpers.sh meta-push-failed <runfile>`; a non-empty answer is reported to the owner and appended to `## Progress` — a report, not a block.
- **SessionStart hint (no network).** When the mode is on and `<gitdir>/meta-base` does not exist, `session-resume.sh` adds one line: run history is on branch `<branch>` and has not been pulled — run `meta-sync.sh pull`. It never calls `meta-sync.sh status` (that fetches).
- **Honest limits.** (1) A manual whole-set `meta-sync.sh push` bypasses the evidence gate — only `trail-pr` applies it. (2) A done claim already on the branch for work later reverted stays there — no retroactive retraction on this path; `reconcile-status` is the tool. (3) `meta-entry`'s pull needs the network, so an offline machine in branch mode cannot start or resume a run — deliberate; the alternative is silent amnesia. (4) The SessionStart hint reads only `meta-base` presence, so a stale-but-once-synced clone gets no hint (the entry pull covers it). (5) `meta-sync.sh push` plans over the WHOLE managed set even under `--paths-from`, so a conflict on ANY managed path — not only this run's — blocks this run's trail push until a human resolves it (loud, per above).

## Anti-Patterns

- **Building an adapter framework for sources.** Intake is "convert the source into the Queue, once" (§2) — three concrete resolvers (prompt/folder/backlog-doc), not a pluggable plugin system.
- **Creating a manifest / registry / `progress.jsonl` / dashboard file.** The ONE run file is the only persistent tracking artifact (§3); everything else is a sidecar — the transient config-backup (§7), the §6 result sidecars (`<run_id>.review-heal-result.md` / `<run_id>.supervisor-result.md`), and the gitignored §6 trail/watcher files — the `<run_id>.trail-staged` record, the `<run_id>.merge-watch` marker and the `<run_id>.merge-watch.log` ("Trail PR after merge and at run end", "Post-merge close-out"), and the `<run_id>.dismissed-decisions` ledger ("Dismissed-findings decision step (before the park)").
- **Rewriting `## Progress`.** It is append-only (§3) — rewriting it loses crash-recovery breadcrumbs.
- **Non-atomic run-file writes.** A crash mid-write would lose the ONLY copy of resume state — always temp + rename (§3).
- **Feeding `runfile-write` from a generator that can fail silently — or routing around its refusal.** Never pass a multi-line value through `awk -v` (BSD awk dies "newline in string" and prints nothing; pass it through the environment and read `ENVIRON[...]`, as `progress-append` does), never pipe an unescaped-delimiter `sed` into it, and prefer `progress-append` / `queue-checkoff` over a whole-file rewrite. A `[runfile_write_refused]` exit means the payload was bad and the run file is intact — fix the generator and retry; never write the file another way (§3 "Validate before rename").
- **Trusting a checkbox without reconciling.** The run file is *belief*; reconcile vs `gh`/`git`/`## Status: done` before trusting it (§4). A crash between merge and check-off makes them disagree.
- **Asserting "merged"/"on main" from memory.** Always verify via `gh pr view --json state,mergedAt` / `git branch --contains` (§4) — this is the stale-branch incident discipline.
- **Double until-mergeable drain.** Suppress `.auto_review` around the RUN phase and own exactly ONE inline drain per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent) (§7); never let `/autonomous`'s detached drain race the engine's.
- **Parking with dismissed findings nobody decided on.** In an interactive run the §6 "Dismissed-findings decision step (before the park)" asks fix-now / follow-up / drop per drafted finding BEFORE the park is written and the merge watcher is armed; offering fix-now at PICK (where it could race an armed watcher or a human merge), or a second time for the same item, is the anti-pattern.
- **Toggling `.auto_review` at DRAIN instead of around RUN.** Both default dispatches fire *during* `/autonomous` — DRAIN is too late (§7).
- **Leaving a partial `config.json` on restore.** Restore byte-for-byte OR delete-if-originally-absent; a stray empty `config.json` shadows the legacy `notify-config.json` (§7).
- **Overwriting a malformed pre-existing `config.json`.** Abort the tick instead — never clobber a hand-edited config (§7).
- **Picking a new item while a PR is open.** Single-open-PR invariant — `awaiting_merge`, `escalated` and this run's own open trail PR (`trail_pr_open`) all block PICK (§8).
- **Retrying RUN into a rate-limit wall, or misreporting it as a dead worker.** A `reason: "rate_limit"` (or an `"unknown"` reason with a `429` hint) on the loop's OWN `agent_lifecycle: failed` row parks the item (`status`/`pause_reason: rate_limit`) and stops — it never re-invokes `/autonomous` for the same item in the same tick (§6 "Rate-limit park").
- **Promoting a `429` text hint into the classified `reason`.** The string-table fallback only ever writes a SEPARATE `reason_hint: rate_limit` field; the underlying `agent_lifecycle` row's `reason` stays whatever was actually classified (§6 "Rate-limit park").
- **Merging on bare `READY`.** `READY` ignores `REVIEW_REQUIRED`, human threads and diff risk; `--auto-merge` must pass EVERY condition of the trusted gate (§10) — fail CLOSED otherwise.
- **Reusing the Supervisor's `risk_classification` at the gate, or inventing an override for condition 6.** The loop re-runs `classify-risk.sh` on the SHA it judges (§10 cond 6); `--trust-unprotected` is cond 4 only; `.agent/risk.json` has no `exclude` key and no flag/config key lowers a classification.
- **Inventing a `gh pr view --json reviewThreads` flag.** Unresolved threads + author type are GraphQL-only (§10 cond. 3; `review-heal/SKILL.md` §"Step U1 — All-Channel Read").
- **Gating rubric on the autonomous EVALUATE loop.** Single-iteration short-circuits EVALUATE; read the rubric from `SUPERVISOR_RESULT.rubric_score` (Phase 4.5 Rubric Grader), which runs under single-iteration (§10 cond. 5).
- **Stacking a second PR on `escalated`.** An escalated PR parks the run; resolve it or mark the item `skipped`/`abandoned`, then `--resume` (§5/§9).
- **Running two `/automate` loops in one repo.** The `.auto_review:false` window is repo-global; single-run-per-repo — ENFORCED by `run-lock.sh` at PICK, not merely documented (§6 step 1 / §11).
- **Committing a done stamp for unmerged work.** Phase 4.5 stamps the requirement `## Status: done`/`done_with_escalation` before any merge; a trail PR that carries it ahead of the feature PR makes `main` claim the item is done (and `is_done` never re-queues it) even if the feature PR is then closed or reworked. Trail only after merge, at a skip/abandon check-off, or at run end — never at a park — and let `trail-pr`'s evidence gate exclude a stamp whose PR is not merged (§6 "Trail PR after merge and at run end").
- **Letting the engine merge anywhere but the §10 gate.** `gh pr merge --squash` lives ONLY in the `--auto-merge` gate; `review-heal`/Supervisor Phase 4.5 never merge (§11).

## Quality Gates

- Exactly **one** source resolved per run; the FULL resolved Queue is materialized in `## Queue` and human-confirmed before processing (skipped under `--non-interactive-fallback`).
- `--limit N` caps **PROCESSED** items (default 5), never Queue size; the run file always stores the full list.
- Exactly ONE `.supervisor/automate/<run_id>.md` per run — NO `manifest.json` / `runs.jsonl` / `progress.jsonl` / dashboard created.
- Run-file writes are atomic (temp + rename); `## Progress` is append-only; rewrites confined to `## Queue` + `## Current`.
- RESUME globs run files (`# Automate Run:` title, `is_run_file` — §6 result sidecars excluded) not stamped done and reconciles each in-flight item vs `gh`/`git`/`## Status: done` BEFORE trusting a checkbox; continue/new/archive (ambiguous resume fails closed under `--non-interactive-fallback`).
- Single drain: `.auto_review:false` set before `/autonomous`, restored finally-style (config-backup deleted on clean restore, crash-restored by RECONCILE); ONE inline `/review-pr --until-mergeable` per pass (at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent)); `## Current` records `owned_drain_started`/`owned_drain_result`/`suppressed_default_dispatch:true`; no detached `dispatch-pr-review.sh` artifact for the PR.
- Dismissed findings: at every park with an open PR, `dismissed-drafts` runs and (interactive) one decision per drafted finding is asked BEFORE the park state is written and the merge watcher is armed; `--non-interactive-fallback` asks nothing and records `pending_decisions`; fix-now is one DRAIN → GATE re-pass, at most once per item; the next interactive PICK asks the undecided set (Follow-up / Drop only) before RECONCILE's `closeout` (§6 "Dismissed-findings decision step (before the park)").
- Single-open-PR invariant holds in BOTH modes, this run's trail PR included (`trail-gate` parks `trail_pr_open` at PICK): `awaiting_merge` is closed out by the merge watcher (or `--resume` RECONCILE) after a human merge and the next item waits for the owner's go, `escalated` parks until human-resolved or the item is `skipped`/`abandoned`.
- `--auto-merge` executes `gh pr merge --squash` ONLY when EVERY trusted-gate condition (§10) holds; fails CLOSED (park + notify) on any blocker (unprotected/toothless, moved SHA, `CHANGES_REQUESTED`/`REVIEW_REQUIRED`, null/unreadable `reviewDecision`, unresolved human thread, high-risk or unclassifiable diff per `classify-risk.sh` — no override, a failing/unresolved/unstamped/cmd-disabled/unreadable countable `must`-rule check per `rules-gate-verdict.sh` — no override).
- `READY`/`PASS` from `review-heal`/`review-pr`/Supervisor Phase 4.5 NEVER merge; the ONLY executed `gh pr merge --squash` is the §10 gate implemented in `automate-helpers.sh gate-eval`.
- All `/autonomous` correctness gates bubble up; `--notify` / `--non-interactive-fallback` / `--cheap` pass through to the inner `/autonomous` (`--cheap` is passthrough-only — never interpreted by the engine, never stored in `## Run Config`).
- Termination: Queue fully resolved ⇒ `## Status: done` / `remaining: 0`; `limit` reached ⇒ `## Status: paused` / `pause_reason: limit_reached` / `remaining: <unchecked>`.
- Trail PR only after merge (`closeout`), at a skip/abandon check-off, and at `## Status: done` — never at a park; `trail-pr` commits a done-stamped requirement or done/ brief only when its PR reads merged, and names every exclusion (§6 "Trail PR after merge and at run end").
- Rate-limit park: a main-scope `agent_lifecycle: failed` row with `reason: rate_limit` (or `reason: unknown` plus a `429` hint, recorded separately as `reason_hint`, never promoted into `reason`) — found in the loop's own session log, post-dating this item's "picked" line — parks the item (`status`/`pause_reason: rate_limit`) and stops BEFORE DRAIN/GATE without retrying; every other classified reason is unchanged (§6 "Rate-limit park"). Resuming it round-trips through the SAME RESUME reconcile as `awaiting_merge` (§4) — no second park vocabulary, no second reconcile path.
