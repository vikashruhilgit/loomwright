## §6 — The per-item loop

For each `- [ ]` Queue item (top-down, single-open-PR invariant permitting — §8):

1. **RECONCILE** — re-check ground truth for any in-flight item before picking (§4); never pick a new item while one has an open unmerged PR (§8). When `reconcile-item` returns `merged` for an item previously parked `awaiting_merge` (or `escalated`), the loop runs `automate-helpers.sh closeout <runfile> <item> <pr_url> --session-id <this loop's session id>` BEFORE any PICK — the `--session-id` makes closeout's own run-lock acquire RE-ENTER the `automate:<run_id>` lock this PICK already holds (it subsumes the `brief-repair` call that used to sit here; closeout's step 2 is that call). Advisory, fail-SAFE: closeout appends its own `## Progress` lines and its result never changes the reconcile verdict (see "Post-merge close-out" below). A live `<run_id>.merge-watch` marker for the in-flight PR is noted with one `progress-append` line instead of arming a second watcher. When RECONCILE instead finds the parked `## Current` item checked off `# skipped:`/`# abandoned:` by a human (§5's unblock path), it runs `automate-helpers.sh trail-pr <runfile> --reason skipped|abandoned` and appends its line, BEFORE PICK (trigger (c) of "Trail PR after merge and at run end"; idempotent — a re-run is the no-diff skip). **Validation re-check (af36-remainder/01):** when the `## Current` item reads `status: escalated` with `escalation_cause: validation_unrun` and its PR reads `OPEN` (`gh pr view <pr> --json state`), RECONCILE re-runs `validation-gate` for it before any PICK — the contract is step 4's "Re-check at RECONCILE (step 1)" paragraph below. **After RECONCILE, the PICK itself** is `current-set <runfile> --item <path> --status running --pr null --branch null --pause-reason null` FIRST, then the `<ts> picked <item>` `## Progress` line (§3 "`## Current` moves only through `current-set`" — the reverse order trips `progress-append`'s `current_not_set` guard).

   **Close-out leftover gate (automate-followups/32 — immediately after RECONCILE's `closeout`, before the trail gate and before the PICK's `current-set`; the `leftover` rows §4's `closeout-others` printed at start go through it before the first PICK).** Every `closeout` invocation's output is classified ONCE, on its own (never the interleaved output of several): `automate-helpers.sh closeout-classify --run <run_id> --item <item> --pr <pr_url> --record <runfile>` (§1.5; `closeout-others` already prints each cross-run close-out's own answer). Anything but exactly `complete` is a leftover. **One exception, at start only (automate-followups/36 A1):** a `closeout-others` answer made only of `run_lock_held` rows — that run's close-out met the run lock held by a LIVE process, usually another lane's run in this checkout — is not a leftover: it never reaches this gate, nothing is asked or parked, its record line reads `run_lock_held — …; retried at the next start`, and the next start's `closeout-others` retries it (that run's `## Current` still names the merged, not-done item). A dead holder (`… (holder pid <p> not running)`) is still a `leftover lock`. Inside the loop the close-out re-enters this PICK's own lock, so there a `run_lock_held` row reads as a leftover like any other non-`complete` answer. `complete` ⇒ go on (`--record` has appended `<ts> closeout: nothing to close out — <item>` when no step changed anything — at most one such line per item per run). Any `leftover` row ⇒ the run **never proceeds silently**. **Interactive:** ONE owner question batching ≤4 leftovers (the same ask tool §4 step 4 uses; more than 4 ⇒ further questions of ≤4), each with the options **Clean up now** / **Keep and continue** / **Stop**. *Clean up now* re-runs `closeout <that run's file> <item> <pr>` — idempotent, and it re-applies its own safety checks (a worktree or local branch is removed only when its tip == the PR's merged head, `worktree-salvage.sh` runs before any `git worktree remove`, no `--force`, no `git reset`, no stash, no `git branch -D` on a foreign tip) — then re-classifies ONCE; a leftover that survives is reported and asked **Keep and continue** / **Stop** only (no loop). *Keep and continue* ⇒ `progress-append "closeout leftover kept: <run_id> <step> <detail>"`. *Stop* ⇒ the park below. **Non-interactive (`--non-interactive-fallback`)** ⇒ the park: `## Status: paused`, `current-set <runfile> --pause-reason closeout_leftover` (the run-level form — the item line is never touched), one `closeout leftover: <run_id> <step> <detail>` `## Progress` line per leftover, then `run-lock.sh release`; no `trail-pr` at this park. The owner finishes the cleanup by hand (or answers the ask on an interactive `--resume`).

   **PICK-time trail gate (after RECONCILE, its `closeout` and any skip/abandon `trail-pr`; BEFORE the trail un-stage below).** `automate-helpers.sh trail-gate <runfile>`, its line appended to `## Progress`. The single-open-PR invariant counts this run's own trail PR (§8): `PARK — …` (an open `chore/<run_id>-trail-<n>` PR, or its state unreadable — fail CLOSED) parks the run here — `## Status: paused`, `pause_reason: trail_pr_open`, `## Current`'s other lines unchanged, then `run-lock.sh release`; no `trail-pr` at this park ("Trail PR after merge and at run end"). The owner merges (or closes) the named PR, then `--resume`. `clear — …` proceeds: the gate has already synced the primary onto the base branch with `closeout`'s own sync, which re-stages the recorded trail blobs that landed (`<run_id>.trail-staged`) before its `git pull --ff-only`, so the merged trail fast-forwards and the next item branches off a base that carries it; the un-stage below then drops whatever did not land. Before this gate nothing synced at PICK, and a hand pull after the un-stage refused (run `automate-2026-10-01-142337` item 02 re-staged the blobs by hand with `git update-index --cacheinfo`). A `sync skipped — <reason>` answer (the primary on another branch, uncommitted changes outside the trail paths, a refused pull) is reported and never parks — the sync is checkout housekeeping, exactly as in `closeout`; RUN then proceeds from the primary as it is, which is what every PICK did before this gate.

   **PICK-time trail un-stage (after RECONCILE, its `closeout` and the trail gate, BEFORE RUN).** `automate-helpers.sh trail-unstage <runfile>`, its line appended to `## Progress`. Every `trail-pr` (`closeout`'s own trail, a skip/abandon check-off, or run end) leaves this run's trail paths STAGED in the primary index (the checkout contract, "Trail PR after merge and at run end") — `closeout`'s trail runs after its sync, with the primary on `main`, which is exactly where the next item branches; `git checkout -b` carries those entries onto the next item's branch, and a plain `git commit` there commits the whole index — so without this step the next item's PR would carry the run's trail files. Fail-SAFE, advisory: it never gates the pick.

   **PICK-time run-lock acquire (red-team-hardening/06 — BEFORE anything else at PICK, including RECONCILE above).** The very first action of every PICK is `scripts/run-lock.sh acquire --owner "automate:<run_id>" --session-id "<session_id>"` (see §1.5's `run-lock.sh` row for the full path convention) — a lock already held by another run/process in this checkout PARKS the run immediately (`## Status: paused`, `pause_reason: run_lock_held`, one `## Progress` line naming the `run_lock_held owner=<label> pid=<pid> age=<s>` output) and the loop stops WITHOUT touching `## Queue`/`## Current`/`.auto_review` — it never proceeds silently. A `run_lock_degraded` stderr line on a successful acquire (the lock is TTL-only — `docs/ARCHITECTURE_CONTRACTS.md` §"Run lock") is NOT a park: note it once in `## Progress` and proceed. On success the lock is held for the rest of this item's loop and released at CHECK OFF (step 6) or any park below (the `live_lane` lane guard right below, step 2's rate-limit park, DRAIN's `drain_died`, or GATE's `awaiting_merge`/`escalated`) — see §11 for the human-only `--force-unlock` escape hatch on a stranded lock. **Lane guard — straight after the acquire succeeds (parallel-automate/05, §14):** `automate-helpers.sh pick-guard .supervisor/automate`. `ok` (exit 0 — always the answer when the directory holds no `*.lanes` table, i.e. on every checkout that never ran a `--parallel` wave) proceeds with no `## Progress` line, so a sequential run's file is unchanged. `refuse: live_lane <lane_run_id> <lane>` (exit 1 — a lane of an open wave whose process `lanes_proc_alive` verifies, or that holds an unanswered question), or any other `refuse: …` line (fail CLOSED), PARKS the run here — `## Status: paused`, `current-set <runfile> --pause-reason live_lane` (the run-level form — the item line is never touched), one `## Progress` line quoting the refusal verbatim — then `run-lock.sh release --owner "automate:<run_id>"` for the lock just acquired; no `trail-pr` at this park. It refuses even though the acquire just succeeded: that is the case it exists for — the coordinator's `automate-lanes:<run_id>` lock is keyed on its session's pid, so it is reclaimable once that session ends, while the lanes run on. The owner `--resume`s once the wave is over (`lane-status`). It never refuses a coordinator's own work (a coordinator's items run in lanes through §14's per-wave loop, never through this per-item PICK in the primary) or a lane's own PICK (a lane clone holds no `*.lanes` table, so it reads `ok`).

   **PICK-time token-ceiling check (red-team-hardening/06 — when `--max-tokens N` was passed).** Immediately after the lock acquire and the lane guard succeed, and BEFORE RECONCILE above: `automate-helpers.sh ceiling-check <runfile> <N>`. A `PARK: token_ceiling …` or `PARK: ledger_unreadable` answer PARKs the run right here — `## Status: paused`, `pause_reason: token_ceiling`, one `## Progress` line — then `run-lock.sh release` for the lock just acquired (never left held on a park). No `trail-pr` at this park ("Trail PR after merge and at run end"). An `OK …` answer proceeds to RECONCILE as normal. Skipped entirely (no check, no `## Run Config` field) when `--max-tokens` was not passed — opt-in, byte-for-byte unchanged behavior otherwise.

   **PICK-time pending-decisions ask (automate-followups/12 — after the lock acquire and the ceiling check, BEFORE RECONCILE's `closeout`).** Interactive runs only: `automate-helpers.sh dismissed-pending <runfile>`; a non-zero count OR `unknown` ⇒ `AskUserQuestion` over this run's undecided drafts (≤4 questions per call, one per draft) with the options **Follow-up (keep draft)** / **Drop** ONLY (per-finding drafts: no catalog code in the `header`, so always the owner's; a summary draft — `…--dismissed-summary*.md` — is gate `AUT-SUMMARY`: `header: "AUT-SUMMARY"`, options `Keep summary` ⇒ `follow-up` · `Drop summary` ⇒ `drop`, asked in a call of its own because a call that also carries a per-finding question is answered by the owner as a whole) — fix-now is offered only at the park (§6 "Dismissed-findings decision step (before the park)": at a sequential interactive READY park only on `park-ask-gate`'s `ask — fix-now allowed` line and with the run lock re-acquired; at an `escalated` park before the merge watcher is armed), never at PICK, where nothing re-reads the PR state, so no fix push follows a human merge. Each answer ⇒ `automate-helpers.sh dismissed-decide <runfile> <draft_path> follow-up|drop` (its one `## Progress` line is the record). It needs no merge evidence, only the undecided set, which is why it runs before `closeout`: the `closeout` trail then carries decided drafts, not undecided ones. The ask writes nothing else — no park-state rewrite, no `fix_now_reentered` change. Under `--non-interactive-fallback` it never runs and never blocks; the count stays in `## Current`.
2. **RUN** — set `.supervisor/config.json {"auto_review": false}` (the suppress contract, §7) **then** run `/autonomous --single-iteration --requirement <path>`, appending `--non-interactive-fallback` when it was passed to `/automate` (passthrough — the inner loop then passes `--non-interactive` to both its inlined Launch Pad and its inlined `/supervisor`, so their can't-ask branches fire by name), appending `--notify` when it was passed to `/automate` (passthrough, not stored in `## Run Config`, §11), appending `--cheap` when it was passed to `/automate` (pure passthrough, v15.2.0+ — the engine never interprets the flag itself and does NOT store it in `## Run Config`; the inner `/autonomous` forwards it on to `/supervisor`, §11) and appending `--max-tokens N` when it was passed to `/automate` (red-team-hardening/06 — UNLIKE `--cheap`, this one IS recorded in `## Run Config` as `max_tokens: N` so a bare `--resume` still enforces it; the inner `/autonomous` forwards it on to `/supervisor` exactly like `--cheap`, §11). The suppress MUST wrap the RUN phase: both default dispatches fire *during* `/autonomous` (Supervisor step 5.5 + the `PostToolUse[Bash]` `gh pr create` hook), so toggling at DRAIN is too late. Capture the emitted `SUPERVISOR_RESULT` (status, `pr_url`, `branch`, `rubric_score`, `heal_decision`, `heal_iterations`); when it carries a `pr_url`, record it with `current-set <runfile> --item <path> --status running --pr <pr_url> --branch <branch>` BEFORE the `<ts> ran /autonomous → PR <url>` `## Progress` line and **write its raw text VERBATIM to `.supervisor/automate/<run_id>.supervisor-result.md`** (transient, overwritten per item, same convention as the DRAIN-step artifact below) — this is the file `gate-eval`'s condition-5 rubric check (§10) parses a `rubric_score: N/M` line from itself; the gate never trusts a caller-asserted rubric verdict. **Write-time shape check (automate-followups/20, advisory):** immediately after writing the sidecar, run `automate-helpers.sh sidecar-check .supervisor/automate/<run_id>.supervisor-result.md`; when it prints `fail …`, `progress-append` that line verbatim as `<ts> sidecar-check: fail …`, so producer drift shows in `## Progress` when it happens rather than only as a later trail exclusion. Fail-SAFE: it never parks, never changes a gate input, and the loop goes on exactly as on `ok` (the sidecar is still the file `gate-eval` reads). **No PR — pinned `## Progress` line.** When `/autonomous` returns no `pr_url` (it stopped before a PR — Launch Pad blocked, a discarded brief, a Supervisor failure), write no sidecar and make the RUN line `<ts> ran /autonomous — no PR: <status_reason> (<one-line why>)`, `<status_reason>` being its `AUTONOMOUS_RUN` `status_reason` token verbatim and bare — no backticks or quotes (`docs/result-schemas/autonomous-run.md` §"`status_reason` enum"; `unknown` when it reported none), never a paraphrase: the `/lanes` timeline (`automate-lanes.sh` `_lanes_timeline`) reads that token to tell a Plan-stage stop from a Build-stage one. **Restore `.auto_review` in a finally-style cleanup immediately after `/autonomous` returns *or fails* — i.e. BEFORE the owned DRAIN below** (§7). The owned drain is inline and NOT gated by `.auto_review`, so restoring before it both keeps the suppression window tight and is safe. **Then, before proceeding to step 3 DRAIN, check for a rate-limit park** — see "Rate-limit park" below; a parked item stops the run right here and never reaches DRAIN/GATE.

   **Session-id recording for the token ledger (red-team-hardening/06).** Immediately after `/autonomous` returns (successfully or not), read `.supervisor/state.md`'s `- session_id:` field — the Supervisor session this RUN invocation just used — and `automate-helpers.sh progress-append <runfile> "session_id <id> (<item>)"`. This is what lets `read-token-ledger.sh --run-id <runfile>` (§1.5) find every session's ledger for this run, including for `--max-tokens` runs that never set a ceiling this time but might on a future `--resume`. Recorded UNCONDITIONALLY (not gated on `--max-tokens` being set) so a later `--max-tokens`-bearing `--resume` of an UN-ceilinged run still has a complete session-id trail to sum.
3. **DRAIN** — own **exactly ONE** inline `/review-pr --until-mergeable --no-auto-postmortem` on the PR per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent); §6 "Dismissed-findings decision step (before the park)" (§7). Read its terminal `REVIEW_HEAL_RESULT` synchronously; record `owned_drain_started` / `owned_drain_result` / `suppressed_default_dispatch: true` in `## Current` (their own line; the item line's `status` stays `running` — no `current-set` call at DRAIN start). **Pinned drain-start `## Progress` line:** `<ts> owned drain started — <drain invocation> @ <head sha>` (a fix-now re-drain — the driver's `{"do":"spawn","what":"fix-now re-drain"}`, step 4 — writes exactly `<ts> owned drain started (fix-now re-drain) — <drain invocation> @ <head sha>` at its start and `<ts> fix-now re-drain <READY|ESCALATED> (<termination_reason>, <n> rounds, <k> fix cycles)` at its end, the lines `dismissed-cost` reads — the same pins as `legacy-tail.md`'s decision step 3; `lane-drain-check` counts both after one optional timestamp token and tolerates the legacy `owned drain started: …` form). **Also write the terminal `REVIEW_HEAL_RESULT` block's raw text VERBATIM to `.supervisor/automate/<run_id>.review-heal-result.md`** (transient, overwritten per item — same convention as the `<run_id>.config-backup.json` sidecar, §7) — this is the artifact `gate-eval`'s condition-1 cross-check (§10) reads back and compares against the loop's own `drain_result`/`termination_reason` claim, so the drain's self-report can never merge on a bare, uncorroborated assertion. Then run the same advisory write-time `sidecar-check` on `<run_id>.review-heal-result.md` as step 2 does for its sidecar (a `fail …` line is `progress-append`ed; never parks, never changes a gate). **Then, at the END of DRAIN (BEFORE step 4 GATE), emit the engine-native learning line** — see "Learning-emit at end-of-DRAIN" below. This runs for EVERY item that produced a PR (merged OR parked); emitting here (not at step 6 CHECK OFF) covers parked items, which stop at the GATE and never reach CHECK OFF.
   - **Drain superseded by a merge (automate-followups/20).** The drain can end WITHOUT a terminal `REVIEW_HEAL_RESULT` — the case seen on #305: the owner merged the PR mid-drain and the drain was stopped (`review-heal` has no merged-PR exit of its own, so a round in flight keeps going until something stops it). When DRAIN (first drain or fix-now re-drain) returns with no terminal block, read `automate-helpers.sh reconcile-item <pr_url>`. On `merged`: write the `owned_drain_*` line with `owned_drain_result: superseded_by_merge` (keep the pass's `owned_drain_started`), append `<ts> drain superseded_by_merge — PR merged before a terminal REVIEW_HEAL_RESULT`, write NO `<run_id>.review-heal-result.md` sidecar, run NO learning-emit (it reads the terminal block's `decision`/`fix_cycles`, and there is none), and skip step 4 GATE and the dismissed-findings decision step (no block means no dismissed list; the PR is merged, so `gate-eval` is never called — and if it were, condition 1 parks every `drain_result` but `READY`, `drain_not_ready`). Then close the item out exactly as step 1 RECONCILE closes out a merged item — `closeout <runfile> <item> <pr_url> --session-id <this loop's session id>`, classified through the same Close-out leftover gate — and stop the run as a close-out leaves it (§3 "After a close-out"): `## Status: paused`, then `current-set <runfile> --pause-reason awaiting_go`, then `run-lock.sh release`. The next item waits for the owner's `--resume`. Any other `reconcile-item` verdict records nothing for the drain: the item stays `running` and the next start's RECONCILE (§4) decides from ground truth, which writes `superseded_by_merge` itself if the PR has merged by then.
4. **GATE — run next-step** (automate-speed/06). From the drain result on, the loop's tail is ONE script, invoked from the plugin root's `scripts/` exactly like every helper (§1.5): `automate-next-step.sh <runfile> --result '<the drain report as JSON>' --mode safe|auto-merge --session-id <this loop's session id>`, plus `--non-interactive` under `--non-interactive-fallback` and `--trust-unprotected` when it was passed. These flags persist for the item's tail, so a later call (an answer, a retry) keeps them without repeating them. It runs every deterministic tail step itself — the entry (driver step `gate`: an `ESCALATED` drain goes to the §9 escalated park), the validation gate (`validation`: `none` / `ok` / `waived` goes on, an `unrun` step is the `AUT-WAIVE` ask or the `validation_unrun` escalated park), the per-mode decision (safe mode's `awaiting_merge` park, or `--auto-merge`'s `gate-eval` step, whose ctx carries only §10's six loop-owned keys — the driver never merges anything itself), the "Dismissed-findings decision step (before the park)" in the order the park needs (`dismissed`, `decide`, `fix-now`: a sequential interactive READY park is written first and asked after `park-ask-gate`; an `escalated` park, every park under `--non-interactive-fallback` and a lane's READY park decide first), the park writes with the merge watcher, the notify and `run-lock.sh release` (`park`), and inside a lane the park `lane-park` prints — and prints exactly ONE JSON instruction. `{"do":"spawn",…}`: run the named work (the fix-now re-drain), then call again with `--result <its drain report>`. `{"do":"ask",…}`: ask its `questions` with their `header` and `options` through the ask tool, then call again with `--result '{"answers":[…],"note":"…"}'`; when the ask tool is unavailable, `--result '{"cant_ask":true}'` takes the named `cant_ask` outcome. `{"do":"park",…}`: the run is parked — stop. `{"do":"done",…}`: the tail is finished — `status: done` ends the run, `status: running` goes to the next PICK. A call with no `--result` re-prints the pending instruction and writes nothing. Between calls the loop writes nothing to the run file itself; a non-zero driver exit is reported, never worked around. The instruction schema is `docs/result-schemas/automate-run.md` §"next-step instruction"; the rules the driver executes are §9 / §10 and the "Re-check at RECONCILE" paragraph below; the pre-driver prose of steps 4–6 is `legacy-tail.md`, read and followed instead of the driver ONLY under `--legacy`.
   **Re-check at RECONCILE (step 1).** On `--resume`, for a `## Current` item `status: escalated` with `escalation_cause: validation_unrun` whose PR reads `OPEN`, run the read-only `validation-gate` again and `progress-append` its line. `ok` / `waived` ⇒ write the READY park this GATE would have written, through the item form of `current-set` (which drops the escalation line): sequential, `current-set <runfile> --item <path> --status awaiting_merge --pr <pr_url> --branch <branch> --pause-reason awaiting_merge` (RECONCILE runs no `gate-eval`, so an `--auto-merge` run gets the same park and a human merges); in a lane, the park `lane-park` prints: an N > 1 lane `--status ready_for_release --pause-reason ready_for_release`, then §14 "Terminal park"'s `lane-park-notify` and `lane-readiness`; a single lane `--status awaiting_merge --pr <pr_url> --branch <branch> --pause-reason awaiting_merge`, with no second watcher (the `escalated` park already armed one) and no `lane-park-notify` / `lane-readiness` call. The dismissed-findings step is not re-run (it ran before the `escalated` park), and step 1's live-marker rule arms no second merge watcher. Anything else ⇒ nothing is written and the item stays `escalated`; the re-check never asks `AUT-WAIVE`. The owner clears the park by pasting the step's fenced output into the PR body and `--resume`, or as §9 says.

5. **SYNC — run next-step.** After `gate-eval` printed `MERGE`, the driver's `sync` step runs `closeout <runfile> <item> <pr_url> --no-trail --session-id <this loop's session id>` itself (the requirement stamp, the check-off, the `main` sync) and classifies its output through the step-1 Close-out leftover gate (`leftover`: an `AUT-LEFTOVER` ask interactively, the `closeout_leftover` park under `--non-interactive-fallback`), so the next item never branches off an unsynced base silently.
6. **CHECK OFF + PROGRESS — run next-step, except a skip/abandon.** After a gate-merged item the driver's `checkoff` step appends the `## Progress` line (`closeout` already checked the item off) and `terminate` takes "Termination (two exits)" below. A `# skipped:`/`# abandoned:` check-off is still the loop's own: one atomic write (§3, `queue-checkoff` with the reason), report `remaining: N`, then `automate-helpers.sh trail-pr <runfile> --reason skipped|abandoned` (its line appended — "Trail PR after merge and at run end"), then `run-lock.sh release --owner "automate:<run_id>"` as the step's LAST action. The lock is held for at most one item's worth of loop: every other path this item's loop stops on releases it too (the driver's parks and the `limit_reached` exit release it themselves; the rate-limit park and `drain_died` in prose), so a human resuming a parked `/automate` run is never blocked by its own prior lock.

### Rate-limit park (end of RUN, before DRAIN)

Immediately after step 2 RUN captures `SUPERVISOR_RESULT` and restores `.auto_review`, and **before** proceeding to step 3 DRAIN, the loop checks its own session's JSONL log — `.supervisor/logs/{session_id}.jsonl`, the SAME file `scripts/emit-lifecycle.sh` appends to (`docs/RESULT_SCHEMAS.md` §"`agent_lifecycle` JSONL event records") — for an `agent_lifecycle` row with `state: "failed"`, `agent_scope: "main"` (no `agent_id` — for `/automate` the main thread IS this loop, so a main-scope failure is the loop's own turn dying, matching the source requirement's honest limit that every observed rate-limit `StopFailure` in this repo has been main-thread), and `reason: "rate_limit"`, timestamped AFTER this item's own `## Progress` "picked" line (never a stale hit carried over from an earlier item in the same run file). **No new script is needed for this read** — the loop reads its own session log directly, exactly the way it already reads its own `## Progress` lines; there is no PR yet at this point for a `gh`-keyed helper like `reconcile-item` to key on.

- **Classified hit (`reason: "rate_limit"`):** park immediately, following the EXISTING park shape exactly (never a new `status: parked` placeholder) — `## Current` gets `status: rate_limit` AND `pause_reason: rate_limit` via `current-set <runfile> --item <path> --status rate_limit --pause-reason rate_limit` (item-level `status` mirrors `pause_reason`, the same way `awaiting_merge`/`escalated` already do), `## Status: paused`, one `## Progress` line naming the rate-limit fact (e.g. `<ts> rate-limited — parking, resume once the window clears`), then `run-lock.sh release` (no `trail-pr` — "Trail PR after merge and at run end"), and the run **STOPS (exit 0)**. It does NOT proceed to DRAIN/GATE and does NOT retry RUN into the same wall.
- **Unknown hit with a `429` hint (fallback, `reason: "unknown"`):** the `agent_lifecycle` row itself carries no message text, so before falling through to today's unchanged handling, check the sibling `STOP_FAILURE` line in `.supervisor/logs/failures.log` for the SAME session (matched by `session_id`, the line closest-preceding the `agent_lifecycle` row's own `ts`) and read its `last_assistant_message` field for a `429` substring. A hit there records a SEPARATE `reason_hint: rate_limit` line in `## Current` — additive, **never** written into `reason` (the `agent_lifecycle` row stays `"unknown"`, untouched) and **never** promoted into `status`/`pause_reason` as if it were a classified certainty — **and** the item still parks the SAME way a classified `rate_limit` would (`status: rate_limit`, `pause_reason: rate_limit`, same `## Progress`/stop behavior above): a hint is enough to stop retrying into a wall, not enough to relabel the underlying fact as certain.
- **Every other classified reason — UNCHANGED.** `server_error` / `authentication_failed` / `model_not_found`, or `unknown` with no `429` hint, take today's existing failure/error path exactly as before (whatever `SUPERVISOR_RESULT`'s own failure status already drives, and the `/autonomous` correctness gates that bubble up per §11). This item adds exactly ONE new branch; it does not restructure any other reason's handling.

### Termination (two exits)

- **Queue fully resolved** (no `- [ ]` left) ⇒ `## Status: done`, `remaining: 0`, the `/loop` driver stops.
- **`limit` items processed** with the queue NOT empty ⇒ `## Status: paused`, `pause_reason: limit_reached`, `remaining: <unchecked count>`, loop stops.

Both exits are written by the driver's `terminate` step (§6 step 6; under `--legacy`, by the loop as this subsection says).

On the **`## Status: done`** exit ONLY, the loop runs `trail-pr --reason done`, then appends ONE `<ts> sweep (dry run): <summary line>` `## Progress` line (`progress-append`; the summary line is the last line of `automate-helpers.sh sweep` — a DRY run, never `--apply` unattended; no `sweep: summary — ` line ⇒ the line records `sweep: summary — skipped: no output`), and only then `run-lock.sh release`; the `limit_reached` exit is a park and releases the lock without a trail — see "Trail PR after merge and at run end".

(A park on `awaiting_merge`, `ready_for_release` — an N > 1 lane's READY park, §14 —, `escalated` — §8/§9 — or `rate_limit` — the "Rate-limit park" subsection above — or `drain_died` — §4 RECONCILE, a DETACHED drain that exited without a result, red-team-hardening item 04 — or `trail_pr_open` — §6 step 1's trail gate, §8 — also stops the loop with the corresponding `pause_reason`.)

All `/autonomous` correctness gates still bubble up (NO-GO, Plan Review FAIL×3, adjudication, rubric gate); `--notify`, `--non-interactive-fallback`, and `--cheap` pass through to the inner `/autonomous` (§11).

### Learning-emit at end-of-DRAIN (engine-native ground-truth signal)

At the END of §6 step 3 (DRAIN), AFTER reading the terminal `REVIEW_HEAL_RESULT` and BEFORE step 4 (GATE), append **ONE** ground-truth learning line per processed PR (merged OR parked). This replaces the GitHub-blind `/pr-postmortem` for automate'd PRs: the engine already holds the real churn, so it builds an honest line instead of reading a false `review_rounds: 0` off GitHub.

> **Execute via the helper, not a re-implementation (reference-don't-restate, to avoid mirror drift):** call `automate-helpers.sh learning-emit` (§1.5).   - **`heal_iterations` → `--self-heal-rounds`** (the Phase 4.5 self-heal churn the PR absorbed before the drain — without it a PR healed in self-heal and drained with 0 fix cycles records a false-0). The `--repo` bullet above covers one half of that silent-invisibility trap; this is the other half. Historically it was also *permanent*: the `automate_key` was keyed on `run_id`+item+`pr_url`+`source` alone, so the degraded line poisoned the key and **every** later emit carrying the real data was silently skipped (observed 2026-08-06 on PR #126). The helper still writes **at most one complete line** per run/item/pr/source, and a degraded retry *after* a complete line is skipped, so the correction cannot run backwards or duplicate. **Prefer passing real fetch data on the first call** — the correction is a safety net, not a licence to skip the fetch.
- **Visibility is gated by BOTH `changed_paths` AND `repo` (load-bearing — pass a real `--repo`).** `read-postmortem.sh` returns a corpus line as a prior-churn hit only when its `changed_paths` overlaps the queried paths **AND** (when the current repo is determinable) its `repo` matches the reader's repo case-insensitively (`read-postmortem.sh:159` [pins: `changed_paths overlap the query set`]). The helper defaults `repo` to `""` (emitted as `repo: ""`, **not** `null`), which the reader filters out whenever its own repo resolves — so an empty `--repo` produces a **silently-invisible** line, exactly the failure this feature exists to prevent. Always pass `--repo <owner/repo>` (derived above). Also pass `--plugin-version` (from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json`) so engine-native lines carry the real version, not `"unknown"`.
- **Idempotency:** pass `--run-id <run_id> --item <item> --pr-url <pr_url> --source automate_drain` so the helper's `automate_key` skip yields exactly ONE line across a crash between emit and check-off, or a `--resume` re-entry. The key is **degradation-aware** (previous bullet): exactly-once holds per (run/item/pr/source, `complete`\|`degraded`) state, which is what lets a re-entry that *recovers* the fetch data correct an earlier degraded line while a plain re-entry still writes nothing.
- **Ledger:** `.supervisor/postmortem/results.jsonl` (the same unified corpus `/pr-postmortem` appends to; the `source` field discriminates the two). It is the FIRST positional argument, before every flag: `learning-emit <ledger_path> --repo … --pr-url … --run-id … --item …`. A call that starts with a flag (or an empty path) writes nothing and prints one stderr usage line.
- **Advisory / fail-SAFE — NEVER gating.** `learning-emit` ALWAYS exits 0; the loop **ignores its exit status entirely**. A `learning-emit` failure (jq absent, unwritable ledger, fetch fail, bad arg) NEVER changes `owned_drain_result`, the step-4 GATE / merge-or-park decision, `## Status`, `## Current`, or any inner `/autonomous` gate — exactly like the `postmortem_dispatched`-is-informational invariant.
- *(Optional, advisory)* the `AUTOMATE_RUN` summary MAY carry a `learning_lines_emitted` counter; skip it if it adds risk.

### Brief-repair at RECONCILE and SYNC (merge-evidenced lifecycle repair)

### Trail PR after merge and at run end

> **Branch mode (opt-in):** with the mode on, `trail-pr` pushes to the metadata branch through `meta-sync.sh` instead of opening a PR — same triggers, same evidence gate, loud on failure; see §13.

Nothing else commits the tracked `.supervisor` trail (the run file, its result sidecars, the Queue's requirement files, their done/failed briefs, this run's ledger lines), so the engine commits it itself as ONE PR: `automate-helpers.sh trail-pr <runfile> --reason <closeout|done|skipped|abandoned>` (§1.5; implemented in `scripts/automate-trail.sh`, self-tested by `scripts/test-automate-trail.sh`).

- **When — this is the ONE authoritative trigger list (and the ONE park-path list).** Exactly three triggers, each after the evidence that the work it records is final: **(a)** inside `closeout`, after its evidence gate read the item's PR `MERGED` and after its sync, stamp and check-off (`--reason closeout`; closeout prints the line, "Post-merge close-out" below) — unless its caller passed `--no-trail` (§6 step 5 SYNC, §14's merged-lane re-run); **(b)** at the `## Status: done` termination — the Queue fully resolved — after that state is written and BEFORE `run-lock.sh release` (`--reason done`); **(c)** when an item is checked off `# skipped:`/`# abandoned:` — by the loop at §6 step 6 (before that step's lock release), or found so marked by a human at RECONCILE (§5's unblock path; before PICK) — (`--reason skipped` / `--reason abandoned`). At (b) and (c) its one output line is appended with `progress-append`. **No park calls it:** `awaiting_merge`, `escalated`, `rate_limit`, `drain_died`, `token_ceiling`, `trail_pr_open`, `ready_for_release`, `live_lane`, `closeout_leftover`, `limit_reached` write the park state and release the run-lock directly (`run_lock_held`, `resume_ambiguous` and `meta_unreachable` never held the lock). Why: at a park the item's PR is unmerged. Before automate-followups/37, Phase 4.5's completion tail had already stamped its requirement `## Status: done`/`done_with_escalation` by then (it now writes nothing to the requirement — `closeout` is the only engine writer of that stamp), and a park-time trail PR carried that stamp to `main` ahead of the feature PR, so an owner who merged the trail PR and then closed or reworked the feature PR left `main` saying the item was done — and `is_done` keeps `resolve-folder`/`reconcile-status` from ever re-queueing it (two PRs per item, with an ordering trap). A parked item's trail lands with its `closeout` (or a skip/abandon, or the run end) instead. Honest limit: under `--auto-merge` a gate-merged item is closed out at step 5 SYNC by `closeout … --no-trail` (automate-followups/38) — its requirement is stamped `## Status: done` behind the same evidence gate and checked off, but no trail PR is opened there (why `--no-trail`, in both branch modes: `legacy-tail.md` step 5) — so its trail, stamp included, rides the next `closeout`, skip/abandon check-off or run end — a run that parks for good after auto-merged items leaves their trail uncommitted until one of those fires (`/automate --resume`, or a hand `trail-pr --reason done`).
- **Lane calls (§14) — not a fourth trigger, and the one exception to "no park":** inside a `--parallel` lane, `lane-convert-ready` runs `trail-pr <the lane's run file> --reason wave-end` at the wave end (after converting an N > 1 lane's `ready_for_release` park to `awaiting_merge`, or — on its re-run once the PR merged — after `closeout … --no-trail` stamped the requirement) and `lane-remove --abandon` runs it with `--reason abandoned` on a `gone` lane — both through this same evidence gate, so no unmerged done claim rides; see §14 "Terminal park" and "removal".
- **Paths — explicit, never `git add -A`/`.`:** the run file; `<run_id>.review-heal-result.md` / `<run_id>.supervisor-result.md` only when `sidecar-check` says `ok` (a `fail` sidecar is excluded and named in the output line); every `## Queue` item that is a requirement file (`.supervisor/requirements/**.md` only — a Queue item naming any other path, e.g. a source file, is never committed, so its local WIP cannot ride into the trail PR); every `.supervisor/jobs/done|failed/*.md` brief whose `- **Source requirement:**` token equals a Queue item; `.supervisor/postmortem/results.jsonl` as the trail base's copy plus ONLY this run's lines (`automate_key` prefixed by `<run_id>`, or `run_id`), never the whole local file; and this run's dismissed-finding drafts still on disk, `.supervisor/requirements/proposed/<run_id>--*--dismissed-*.md` ("Dismissed-findings decision step (before the park)") — requirement files carrying no done heading (every finding line is `> `-quoted), so the evidence gate below never calls `gh` for them. A path `git check-ignore` reports ignored is dropped (that is how the ledger's repo-allowlist gate is honoured), and so is a path identical to the trail base.
- **Evidence-gated stamps (defense in depth — in the script, not only this prose).** A done claim rides only for merged work. **Requirements** are judged by `is_done`'s own predicate (any `^## Status: done|done_with_escalation` heading, with or without the `<!-- loomwright:requirement-closeout -->` sentinel): every `- **PR:**` in each such heading's block must read `merged` via `reconcile-item` (one `gh pr view --json state,mergedAt` per distinct URL; the value's first `https?://…/pull/<n>` token, stopping at whitespace and markdown link punctuation `[]()<>`, is what is read, so an annotated `<url> (merged by …)`, a `[<url>](<url>)` link or `<url>` works). A done heading naming no parseable PR fails closed. The ONE exemption is the exact heading `reconcile-status --apply` writes for an owner's `# abandoned:` Queue row — `## Status: done_with_escalation — ABANDONED (- [x] <path>  # abandoned: <reason>)`, em dash byte-exact — an owner decision that rides untouched; any other heading that merely contains "ABANDONED" (`done — not ABANDONED`, `done <!-- ABANDONED -->`) is a done claim like any other. **`done/` briefs** follow the same rule on their Outcome section (an `## Outcome` / `### Outcome` heading followed by whitespace, a colon or end of line — `## Outcome — ESCALATED`, `## Outcome:` — never `## Outcomes Rubric`, `##Outcome` or `## Outcome-ish`); an Outcome section naming no PR fails closed. OPEN, CLOSED, unreadable (`gh` failing — `reconcile-item` fails closed) or unparseable ⇒ the path is EXCLUDED and named (`; excluded <path> — pr not merged`). A requirement with no done heading, and a brief with no Outcome section, are unaffected (no `gh` call). The same rule covers skipped/abandoned items. **Retroactive over a reused trail branch:** when `trail-pr` reuses an open (or orphaned) `chore/<run_id>-trail-<n>` whose tip already carries a failing done claim for an excluded path — e.g. a v15.114.0/.1 park-time trail — that path — any gate-excluded path whose tip blob differs from `origin/<default>`'s CURRENT blob and itself fails the gate (so a path `main` changed after the fork also counts, harmlessly) — is put back to `origin/<default>`'s version in the new commit (removed when `main` lacks it) and named `; retracted <path>`; the retracted blob is dropped from the primary index if an earlier `trail-pr` staged it, and the checkout contract never stages a gate-excluded path. So neither a wrong-moment caller nor an older trail PR still open leaves a done claim for unmerged work at the trail tip. Honest limits: a done claim an older trail PR already MERGED to `main` is `main`'s content and is not retracted here (`reconcile-status`, run by a human, is the tool for that). The gate fails CLOSED on a transient `gh pr view` failure, so such a blip excludes — and, on a reused trail branch, RETRACTS — a legitimate MERGED stamp from the open trail PR; the next `trail-pr` restores it, but nothing restores it after the run-end (`--reason done`) trail, where the owner re-runs `trail-pr` by hand. This is deliberate: a missed done stamp is recoverable (`reconcile-status` finds merged work), a false one is not.
- **Dropped-draft retraction (a separate `git rm`, beside the evidence-gate retraction).** Only on a REUSED open (or orphaned) `chore/<run_id>-trail-<n>` branch whose tip differs from `origin/<default>`: a path matching this run's draft glob that the branch TIP carries (or `<run_id>.trail-staged` records), that is ABSENT on disk, and whose `<run_id>.dismissed-decisions` last row reads `drop`, `fix-now` or `moved` (an undecided draft retired because its finding moved to the other bucket — it rides in its new draft) is `git rm`'d in the trail worktree, dropped from the primary index if staged, and named `; retracted <path>` (PR body: `retracted (dismissed draft dropped)`, distinct from `retracted (done claim for unmerged work)`). An absent draft with NO such ledger row is left alone (never guess); never on a fresh branch cut from `origin/<default>`, and never for a draft whose blob `origin/<default>` already carries — that is `main`'s content, the owner's hand delete.
- **Branch + idempotency:** this run's trail PRs are found with `gh pr list --state all --search head:chore/<run_id>-trail` and filtered locally to `chore/<run_id>-trail-<n>`. An OPEN one is re-used — its branch is the base and the new commit is pushed fast-forward to it (`pushed <url>`). Otherwise `n` = the highest existing `n` + 1, based on fresh `origin/<default branch>`; a remote branch of that name without a PR (a crash between push and PR-open) is used as the base and its PR opened. Nothing differs from the base ⇒ `skipped — trail already up to date` (no commit, no PR). Never a force push.
- **Mechanics:** `git fetch origin`, a detached `git worktree add` in a `mktemp -d` directory, copy each path from the primary checkout by explicit path (gitignored scratch does not exist in a fresh worktree), `git add -- <paths>`, commit `chore(supervisor): <run_id> trail (<reason>)`, `git push origin HEAD:refs/heads/<branch>`, `gh pr create` (title + a body naming the run, the reason and the path list) or re-use; the worktree is salvaged (`worktree-salvage.sh`) and removed in a trap.
- **Checkout contract (proved by a fixture, not assumed).** A plain `git pull` refuses to overwrite untracked or modified local copies of the paths the merged trail PR brings in. So after a successful push — and on the no-diff `trail already up to date` skip against an open trail PR — `trail-pr` sets the primary checkout's INDEX entry of EVERY path the trail branch changes (every push on it, not only the latest delta) to that path's blob at the trail-branch TIP (`git update-index --cacheinfo`, never the working copy) and leaves the working copies alone. When the owner merges the trail PR, a plain `git checkout main && git pull` fast-forwards (index == incoming blob), and the bytes that differ BY DESIGN — Progress lines the live run file gained after the push, other runs' ledger lines — stay as ordinary unstaged local modifications. No `git reset`, no stash, no byte discarded. Those staged entries ride along in ANY commit made from the primary index — `git checkout -b` carries them and a plain `git commit -m` (the `commit` skill shape; the Supervisor Single-Agent Path commits in the primary) commits the whole index, even after an explicit `git add <file>`. So the engine drops them at PICK, before the next commit-producing phase (`trail-unstage`, §6 step 1), and `trail-pr` records every blob it stages in the gitignored `.supervisor/automate/<run_id>.trail-staged`; `closeout`'s sync re-stages, immediately before its `git pull --ff-only`, each recorded blob that the fetched `origin/main` now carries at that path (index only — bytes this run itself committed and that have landed), so the post-merge pull keeps fast-forwarding after an un-stage. The next `trail-pr` (the next `closeout`, skip/abandon check-off or run end) re-stages every path its reused trail PR carries, including those an earlier PICK dropped, so the owner's hand pull after merging that PR fast-forwards too; `trail-unstage` clears the union of the `.trail-staged` record and the current trail candidates. Honest limits: between a PICK and the next `trail-pr`, a HAND-run `git pull` over a merged trail PR refuses (closeout's sync does not; since `trail-gate`, no trail PR of this run is open across a PICK — the gate parks on one and syncs over a merged one before the un-stage — so this needs a trail PR merged outside that window); a trail PR closed unmerged leaves its entries staged until the next PICK's `trail-unstage`; **the trail branch is never rebased** — once `origin/main` moves the postmortem ledger (another run's trail PR, a postmortem line) after this run's trail branch was cut, a later pushed/no-diff re-trail stages the trail-TIP ledger blob, which lacks main's new line, so the trail PR conflicts at the ledger's EOF and both a hand pull and `closeout`'s sync refuse (fail-safe: no reset, no byte lost) until the owner resolves that trail PR by hand. When `closeout`'s `git pull --ff-only` refuses, the entries it re-staged are put back to their prior index state, so a refused sync leaves the index as it found it. `closeout`'s sync treats these trail paths as trail paths, not as uncommitted changes. **Re-examined for trail-after-merge (v15.114.2) — by fixture, every piece is still load-bearing, none removed:** `closeout`'s own trail runs after its sync, with the primary on `main`, and still stages into the primary index, so the next PICK — which branches off that `main` — still needs `trail-unstage` (without it the next item's plain commit sweeps the trail paths); the owner's hand `git pull` after merging `closeout`'s trail PR refuses without the staged tip blobs (the run file is untracked on `main` until that PR lands); and the NEXT `closeout`'s sync, after a PICK dropped those entries, refuses without the `.trail-staged` re-stage (`scripts/test-automate-trail.sh` leg D3, each with a control that turns red).
- **Output:** exactly ONE line — `trail-pr: opened <url>` / `trail-pr: pushed <url>` / `trail-pr: skipped — <reason>` — with any sidecar or evidence-gate exclusion appended to that same line as `; excluded <path> — <reason>`, and any retraction as `; retracted <path>`.
- **Advisory / fail-SAFE — NEVER gating.** Always exit 0; the loop ignores its exit status. A trail failure (gh absent or failing, fetch/push refused, nothing to commit) never blocks a close-out, a check-off or the run end, never changes a gate decision, `## Status` or `## Current`. `trail-pr` never calls `run-lock.sh`, never merges (the sole merge executor stays `gate-eval`, §11), and never force-pushes.

### Post-merge close-out (`closeout` + the merge watcher)

When the owner merges a parked item's PR, ONE deterministic script closes it out: `automate-helpers.sh closeout <runfile> <item> <pr_url> [--session-id <sid>]` (§1.5; implemented in `scripts/automate-trail.sh`, self-tested by `scripts/test-automate-trail.sh`). Its callers, never the next PICK: `--resume` RECONCILE (§6 step 1, with `--session-id`), the merge watcher (below, without it), `--auto-merge` SYNC (§6 step 5, `--no-trail --session-id`) and a merged `--parallel` lane's `lane-convert-ready` re-run (§14, `--no-trail`, inside the lane). Another run's merged `## Current` item is also closed out at start by `closeout-others`, which runs `closeout` for that run without `--session-id` (§4 start order, §8 "Other runs' merged items"). It never merges anything and never picks the next Queue item — the owner's explicit go still starts the next item (the run file then reads `paused` / `awaiting_go`, §3). It does not tick `_BACKLOG.md` either (§2 "The engine never ticks the backlog doc") — the requirement stamp it writes is what `resolve-backlog` reads.

- **Guards:** missing run file ⇒ `closeout: skipped — run file not found`; `gh` absent or `gh auth status` failing ⇒ `closeout: skipped — gh unavailable`. Then the evidence gate: `reconcile-item <pr_url>` must say `merged`, else ONE `closeout: skipped — pr not merged (<state>)` line and nothing else runs.
- **Steps (execution order):** brief repair (the `brief-repair` line, passed through) → run-lock acquire → **3a** each linked worktree on the PR's `headRefName` (never the primary) whose HEAD == the PR's `headRefOid` (the same squash-safe tip check as 3b — a same-named branch at another tip is kept and named, never salvaged or removed, because `git worktree remove` deletes GITIGNORED content that `worktree-salvage.sh` skips by design): `worktree-salvage.sh`, then `git worktree remove` only when it is clean after salvage — a still-dirty worktree is kept and named → **4 sync**: refused when a TRACKED path outside the trail paths (the same set `trail-pr` commits, including the entries it staged) is modified, or the primary is on neither `main` nor the PR head; else `git checkout main` + `git pull --ff-only` — a refusal is a `skipped` line, never a reset → **3b** the local head branch: `git branch -D` ONLY when its tip == the PR's `headRefOid` (one `gh pr view --json headRefName,headRefOid`); squash merges make ancestry useless, so `-d` and "0 commits outside origin/main" are never used; a checked-out branch is kept → **stamp** the requirement with the close-out block whose byte shape is the step-5 `printf` in `scripts/automate-trail.sh` (the shape's one authority: sentinel + `## Status: done` + Completed/Brief/PR, the Brief being the newest `.supervisor/jobs/done/` brief whose `- **Source requirement:**` equals the item; none ⇒ `skipped — no done brief`; a real stamp block already present — the sentinel alone on its line, the NEXT line a `## Status: done` / `done_with_escalation` heading — ⇒ `skipped — already stamped`; a sentinel quoted in prose, or followed by anything else, does not count (automate-followups/38)) — the ONLY engine writer of a requirement's done stamp (Phase 4.5 writes nothing to the requirement, `skills/self-heal-advisory/SKILL.md` completion-tail step 2.5) → **check off** with `queue-checkoff <runfile> <item>` (NO reason argument — a reason writes the excluded `# skipped:` form) → **reconcile `## Current`**: ONLY when `## Current`'s `- item:` line names THIS item AND its `pr:` equals THIS `pr_url` (both compared exactly, after the same `./` strip the item gets), rewrite that line's `status:` to `done` and the `- pause_reason:` line to `awaiting_go` when `## Status: paused` (`null` otherwise — §3 "After a close-out"), through `current-set <runfile> --item <the stored item> --status done --pause-reason <awaiting_go|null>` (the validated atomic write, §3 "`## Current` moves only through `current-set`" — the item is unchanged, so the line's `pr:`/`branch:` are kept), every other line byte-unchanged; a `## Current` naming a different item or PR (a watcher firing after a later item was picked) is NEVER touched (`skipped — ## Current is <item> (<pr>), not this item/PR`), nor is `## Current` touched unless the Queue reads `- [x] <item>` (a failed check-off leaves it as is), and one already reading `status: done` with the target `pause_reason` is `skipped — ## Current already done`; `## Status` is never rewritten → `progress-append` one line per step, ONLY when an item step changed something (`removed`/`stamped`/`checked`/`reconciled`, or a non-skip brief repair) — a `synced` line alone never appends → **trail** via `automate-helpers.sh trail-pr <runfile> --reason closeout` (`--no-trail` skips this step alone: `trail-pr: skipped — --no-trail`) → release. The check-off runs before the trail so the trail PR records the closed-out item; the trail line is printed but not appended to `## Progress` (that append would leave the run file one line ahead of the trail, and every re-run would push again).
- **Output:** one line per step — `closeout: removed|synced|stamped|checked|reconciled|skipped — <detail>`, plus the passed-through `brief-repair:` and `trail-pr:` lines. **Idempotent:** a second run prints only `skipped — …` item lines (the trail reads `skipped — trail already up to date`) and leaves the run file byte-identical. Its sync may still print `synced — main at <sha>` — `main` moved since the first run, most often because the owner merged that run's own trail PR — and that line never appends to `## Progress` by itself: a sync is checkout housekeeping, not close-out progress, and counting it made every re-run after a trail merge append its skip lines and open a fresh trail PR holding only them (run `automate-2026-10-01-142337`, trail PR #330). **Always exit 0.**
- **Concurrency:** steps 3–7 run under `run-lock.sh acquire --owner automate-closeout:<run_id>` (plus `--session-id <sid>` when given, which RE-ENTERS the PICK's `automate:<run_id>` lock — outer owner unchanged). Release is `run-lock.sh release --owner automate-closeout:<run_id>` ONLY, in a trap — never `--session-id`, which would release the outer PICK lock mid-RECONCILE. A held, non-re-enterable lock ⇒ one `closeout: skipped — run lock held by <owner>` line for steps 3–7.
- **The merge watcher — `scripts/automate-merge-watch.sh <runfile> <item> <pr_url>`.** Armed at §9's `awaiting_merge` park AND at its `escalated` park (both modes; automate-followups/31), with the SAME launch line, after the park state is written and before `run-lock.sh release`. Launched detached, pure bash, no Claude session, no tokens: `env -u CLAUDE_PID -u CLAUDECODE nohup bash <plugin root>/scripts/automate-merge-watch.sh <runfile> <item> <pr_url> </dev/null >.supervisor/automate/<run_id>.merge-watch.log 2>&1 &` (not `setsid`, absent on stock macOS). It polls `gh pr view <url> --json state,headRefOid,statusCheckRollup` every `LOOMWRIGHT_MERGE_WATCH_INTERVAL` seconds (default 60; a `gh` error doubles the wait up to 15 min, reset on success). `MERGED` ⇒ `closeout` (no `--session-id`); a TRANSIENT guard skip — `skipped — run lock held`, `skipped — gh unavailable`, `skipped — pr not merged (…)` (the forge disagreeing with the watcher's own `MERGED` read is a blip), or no output at all — is retried on a later poll (backoff doubling to 15 min) within the lifetime cap; any OTHER lone guard skip (`run file not found`, `not a git checkout`, …) is terminal: one `## Progress` line + a notify naming the skip, exit, never the success notify. Only a closeout that got past its guards gets the success notify (`notify-desktop.sh` + `send-webhook.sh`, both fail-safe), exit. `CLOSED` ⇒ one `gone` `## Progress` line + notify, exit, no cleanup (§4's `gone` rules stand). Lifetime cap `LOOMWRIGHT_MERGE_WATCH_MAX_SECONDS` (default 72h) ⇒ one `## Progress` line, exit; when the watcher HAS read `MERGED` but `closeout` kept returning a transient skip until the cap, that line and a failure-style notify both say the PR is merged and name the last skip reason (`/automate --resume` closes it out). **Settle re-check (automate-followups/31):** while `OPEN`, when `## Current` names this item + PR and carries `- escalation_cause: check_pending|check_red_unrelated` with a check + a sha that is still the PR's `headRefOid` (else latched silent — a stale line), each poll also reads that ONE check (`gh run view <run_id>`, else `gh api …/commits/<sha>/check-runs` by name — never an extra `gh pr view`); `check_pending` reports at the first completed attempt ≥ the recorded one, `check_red_unrelated` only at a NEWER attempt (a human rerun); `now mergeable` also needs every OTHER rollup check settled green. The report is ONE `## Progress` line — `merge-watch: now mergeable: <check> green on <sha> (attempt <n>)` or `merge-watch: still failing: <check> <conclusion> — rerun: gh run rerun <run_id> --failed (attempt <n>)` — plus ONE notify of gate type `automate_escalation_recheck` (`docs/TELEMETRY.md`), latched per line content (a re-park's fresh line re-arms it; across a restart the gitignored `<run_id>.merge-watch-reported` sidecar silences only that identical line); it then keeps watching for the merge. It never reruns, merges, pushes or approves — the CI rerun stays human (owner decision, 2026-10-07). Any other cause or no line ⇒ no check polling — `validation_unrun` included (its blocker is missing PR-body evidence, not a check), so the watcher never reports it `now mergeable`; RECONCILE's re-check (step 4 "Re-check at RECONCILE (step 1)") is its only re-check.
- **Single instance per run:** marker `.supervisor/automate/<run_id>.merge-watch` (TSV `pid`/`pr_url`/`started`, gitignored because it is not `*.md`). A live marker pid counts only when `ps -ww -p <pid> -o command=` shows an `automate-merge-watch.sh` process carrying the marker's `pr_url` — a recycled pid is never signalled, the marker is reclaimed as stale. Same `pr_url` ⇒ `merge-watch: already running pid=<p>`, exit. A DIFFERENT `pr_url` (the run parked a later item) ⇒ the old watcher is replaced: TERM (its sleeps are interruptible, its trap removes its marker), KILL only if it is still alive after 60s, one `## Progress` line naming the PR that is no longer watched (`/automate --resume` closes it out after it merges), then the new watcher starts. `ps` unavailable ⇒ not verifiable ⇒ `already running`. A dead pid is reclaimed; the marker is removed on every exit, and a launch removes only the marker it inspected. A park → fix-now re-drain → re-park of the same PR therefore keeps ONE watcher. Count watchers by the marker pid or `ps -o ppid` lineage, never `pgrep -f` — every `$(…)` subshell of the watcher shares its argv (the s3-g "two watchers" sighting was that counting artifact).
- **Why `CLAUDE_PID`/`CLAUDECODE` are unset and the holder is pinned (the launcher unsets them; the watcher unsets them too and pins the holder):** closeout's lock must name the closeout process itself, or a closeout that died without its trap leaves a lock nobody can reclaim while its recorded holder lives. With them set, `run-lock.sh` would record the launching Claude session; and since its ancestor walk is ungated, a watcher under any live non-shell would record THAT. So the watcher runs closeout with `LOOMWRIGHT_HOLDER_PID` set to closeout's own pid (`bash -c '…=$$; exec env "$@"'`) — the lock meta records `pid_source holder_env`, a pid dead once closeout exits, so a crashed closeout's lock is reclaimable (dead pid + the TTL). Lane close-out does the same (`automate-lanes.sh` `_lanes_no_host_identity`); resolution order: `docs/ARCHITECTURE_CONTRACTS.md` §"Run lock".
- **Rejected alternative:** an in-session `Monitor` until-loop dies with the session and is not verified headless.
- **SessionStart surfacing (`session-resume.sh`, automate-followups/32):** on every SessionStart, one `automate: merge watcher live pid=<p> PR <url> (run <run_id>)` line per LIVE watcher (its marker's pid alive AND `ps -ww -p <pid> -o command=` showing `automate-merge-watch.sh` with the marker's `pr_url` — the watcher's own liveness test; stale markers are ignored, never cleaned) — local only, so the `startup` arm stays offline; on `resume`/`clear`/`compact` only, one `automate: <run_id> item <item> PR <url> merged but not closed out — /automate --resume closes it out` line per run whose `## Current` PR reads MERGED while its item is not `done`, from at most 5 time-bounded `gh pr view` calls (each bounded by `LOOMWRIGHT_SR_GH_TIMEOUT` seconds, default 5, and all of them together by ONE overall deadline, `LOOMWRIGHT_SR_GH_DEADLINE` seconds, default 8 — automate-followups/36 A2; test seam `LOOMWRIGHT_GH_BIN`) (an absent/failing/slow `gh`, an item past the cap, or one reached after the deadline is spent — no call is made then — prints `… merge state unverified` — never a guess). Nothing to report ⇒ nothing printed. The marker and the lifetime cap still bound the watcher.

## §7 — Single drain (no double-dispatch) + the config-toggle contract

`/autonomous` already triggers Supervisor's **default detached until-mergeable drain** (Phase 4.5 step 5.5 **and** the `PostToolUse[Bash]` `gh pr create` hook backstop). If the engine *also* drains, two until-mergeable loops race the branch (HIGH risk). The engine therefore **suppresses the default dispatch and owns exactly ONE inline drain per pass** — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent) (§6 "Dismissed-findings decision step (before the park)").

### Suppress window (wrap the RUN phase)

- Set `.supervisor/config.json {"auto_review": false}` **BEFORE** invoking `/autonomous` and restore it in a **finally-style cleanup** immediately after `/autonomous` returns *or fails* — i.e. **BEFORE the engine's own inline `/review-pr --until-mergeable` drain** (§6 step 3). Both default dispatches fire *during* `/autonomous`, so setting it at DRAIN is too late; the owned drain is inline and not gated by `.auto_review`, so restoring before it is correct and keeps the suppression window tight.

### Config-toggle contract (byte-for-byte; absent-delete; malformed-abort)

> **Execute via the helper, not a re-implementation:** suppress with `automate-helpers.sh config-suppress <config_path> <backup_path>`, restore with `automate-helpers.sh config-restore <config_path> <backup_path>`, and read the original with `automate-helpers.sh config-orig <config_path> [<backup_path>]` (§1.5) — **pass the backup path whenever suppress has already run** (next bullet). The prose below is the SPEC those subcommands implement.

- **Backup:** byte-for-byte copy the existing `.supervisor/config.json` to a **transient** `<run_id>.config-backup.json`. Record its path + the original `.auto_review` value in `## Run Config` (`auto_review_original: <true|false|absent>`, `config_backup: <run_id>.config-backup.json`). **Record absence** (`auto_review_original: absent`) if there was no prior config.
- **Read the original from the BACKUP once suppress has run (call-order hazard).** The sequence above is backup → suppress → record, so the value is read *after* the live `config.json` has already been rewritten to `auto_review: false` — at that point the live file reports `false` for EVERY original, and only the byte-for-byte backup (or its `__ABSENT__` marker) still holds the truth. **`config-orig <config_path> <backup_path>` prefers the backup when it exists and falls back to the live config when it does not**, so it returns the true original in either call order; a corrupted backup ABORTS (exit 2) rather than fabricate a value. Calling the one-arg form after suppress records a WRONG original — observed 2026-09-04 on a real run, where a config with no `auto_review` key was recorded as `false` instead of `absent`. This matters because RECONCILE (§4 step 3) is the consumer of that recorded value; the *restore* path itself is unaffected (it is byte-for-byte from the backup and never consults `config-orig`). Guarded by `scripts/test-automate-helpers.sh` §A7. A backup path that is **given but missing** falls back to the live config rather than aborting — missing is the normal state of a correct *pre*-suppress call, so aborting on it would re-introduce call-order dependence in the other direction (a *malformed* backup still aborts; it can never be legitimate). **The caller must therefore record `auto_review_original` before the backup is deleted** — a backup lost after suppress puts the reader back on the live config and back on the wrong answer. Both arms pinned in test §A7f.
- **Restore:** overwrite `config.json` from the backup **OR delete `config.json` if it was originally absent** — **never leave a partial `config.json` shadowing the legacy `notify-config.json`** (the new path wins when both exist, so a stray empty `config.json` would mask `notify-config.json`).
- **Malformed pre-existing config ⇒ ABORT.** If the existing `config.json` is not parseable JSON, do not blindly overwrite it — abort the tick (the user has a hand-edited config we must not clobber).
- **Crash-restore:** RECONCILE (§4) restores a crash-stranded backup on the next start.
- On clean restore, **delete** the transient backup sidecar.

### Own ONE inline drain

After suppression, DRAIN owns **exactly ONE** inline `/review-pr --until-mergeable --no-auto-postmortem` per pass — at most one owner-requested fix-now re-drain per item, strictly sequential (never concurrent); the re-drain runs only after the first drain returned and its result was read, and is itself one inline drain under the same `.auto_review` contract (the standalone review-and-heal drain — authority is `skills/review-heal/SKILL.md` §"Until-Mergeable Mode"). The **`--no-auto-postmortem`** flag suppresses the owned drain's churn-gated Postmortem Dispatch Tail: inside `/automate` the engine emits its OWN honest engine-native learning line (§6 step 3 "Learning-emit at end-of-DRAIN"), so the owned drain must NOT also append a GitHub-blind false-0 postmortem line for the same PR — one honest line, not honest + false-0. (Outside `/automate`, a standalone `/review-pr --until-mergeable` keeps its Postmortem Dispatch Tail unchanged.) Its **terminal `REVIEW_HEAL_RESULT` is read synchronously** and written to `## Current`:

- `owned_drain_started: <ts>`
- `owned_drain_result: READY | ESCALATED | superseded_by_merge`  (`superseded_by_merge` only when the drain ended with no terminal block and the PR reads `merged` — §6 step 3 "Drain superseded by a merge"; otherwise the `--until-mergeable` terminal decision — `READY` is "ready, left open for a human"; it **never merges**. `READY`'s bound is now **mechanized** via `scripts/drain-rounds.sh`, the same shared ledger both `/review-pr` entry paths call — `review-heal/SKILL.md` §U4 — and `READY` carries a `termination_reason` of `converged` or `sub_floor_converged`; ONLY `sub_floor_converged` is excluded from the §10 trusted-merge gate, condition 1, below)
- `suppressed_default_dispatch: true`

**Verifiable** via those `## Current` fields **plus the absence of any detached `dispatch-pr-review.sh` artifact for the PR** (no `.supervisor/review-dispatch/` marker for the PR URL, no `pgrep -lf review-pr-runner` for it).

> The drain is inline (`/review-pr`), not the detached `--agent` form — the engine runs on the main thread and reads the result synchronously to gate on it. `/review-pr --until-mergeable` **NEVER merges** (it is `READY`-terminal); the ONLY place that executes `gh pr merge --squash` is this engine's `--auto-merge` gate (§10/§11).

## §8 — Single-open-PR invariant (BOTH modes)

**While ANY item has an OPEN unmerged PR — status `awaiting_merge` OR `escalated` — or this run's own trail PR is open, the loop MUST NOT PICK a new item.** At most ONE open PR exists at any time, the engine's trail PR included.

- **Lanes (`--parallel N`, §14 — a single lane, `--parallel 1`, holds exactly one item): one open PR per lane.** Each lane is its own clone running its own run file, so this invariant holds per lane — a lane never PICKs a second item while its PR is open — and a wave has at most one open item PR per lane. The coordinator itself opens no item PR.
- **`awaiting_merge`:** the run is stopped (`paused` also stops a `/loop` driver, §12), so nothing re-checks the PR on its own except the **merge watcher** armed at the park (§6 "Post-merge close-out"): when a human merges, it runs `closeout` (cleanup, `main` sync, stamp, check-off, trail) and notifies. An `/automate --resume` RECONCILE runs the same `closeout` if the watcher has not. Either way **the owner's explicit go is still required before the next item is picked**; it then branches off **fresh `main`**. (`--auto-merge` skips this park by merging at the gate — §10 — but still parks on `escalated`.)
- **Other runs' merged items (`closeout-others`, §4 start order).** At start — before any PICK and before the run lock is taken — every OTHER run file whose `## Current` names a not-`done` item whose PR reads `merged` is closed out (cleanup, sync, stamp, check-off, trail), so a merged PR of a paused run does not wait for that run's own `--resume`; anything that close-out could not safely finish goes through §6 step 1's close-out leftover gate. It is deliberately not repeated per PICK: inside the loop the PICK holds `automate:<run_id>`, which another run's close-out (its own `automate-closeout:<other>` owner, no `--session-id`) cannot enter.
- **`escalated`:** the run stays **paused** (`## Status: paused`, `pause_reason: escalated`) until a human resolves it (§9). An escalated PR is open + unresolved; stacking a second PR would violate this invariant.
- **This run's trail PR (`trail_pr_open`).** `closeout` opens the trail PR right after the item's merge (§6 "Trail PR after merge and at run end"); if the owner gives the next go first and merges the trail PR while the next item's PR is open, that merge moves the base under it. With `strict` required status checks (classic protection's "Require branches to be up to date before merging") the item PR then reads `mergeStateStatus: BEHIND` and cannot merge until someone merges the base into it (run `automate-2026-10-01-142337`: trail PR #345 under PR #347). So the PICK-time trail gate (`automate-helpers.sh trail-gate`, §6 step 1) parks `pause_reason: trail_pr_open` while a `chore/<run_id>-trail-<n>` PR is open — or its state cannot be read (fail CLOSED) — and, once none is, syncs the primary over the merged trail before the next branch is cut. The owner's go then means "merge the trail PR, then `--resume`", which is the close-out order the owner already asked for. Options considered — this gate is (b)'s first form, PICK refuses while the trail PR is open:
  - **(a) Refresh a READY-but-BEHIND PR by a regular merge of `origin/main` plus one confirming required-check pass — rejected.** Not the drain's job: `review-heal` §U4's READY is defined over review signals and required checks, `mergeStateStatus` is corroborating-only and never the basis of a READY/ESCALATED verdict (`review-heal` §"Until-Mergeable Mode", "Corroborating-only fields"), the drain pushes only fixes for validated findings, and `/review-pr` also runs on PRs outside this engine, where merging the base into the head branch is the repository owner's policy call. As an engine step at GATE it would cover only a base that moved before the park — in safe mode the trail lands after the park, while the PR waits for the human merge the engine never sees — and under `--auto-merge` the merge commit is a new head the drain never verified, so `gate-eval`'s `head_sha_moved` (§10) would have to accept a `ready_sha` the drain did not produce: a weaker condition 2, an owner decision rather than a fix.
  - **(b)'s second form, hold the trail until run end — rejected.** `closeout`'s trail exists so a merged item's stamp, run file and drafts reach `main` per item, before the next one starts (trail-after-merge, v15.114.2); holding it would leave every stamp off `main` for a run that parks for good, and the run-end trail PR would carry the whole run at once.
  - **(c) Exempt `.supervisor/**`-only changes from the up-to-date requirement — not possible.** Classic branch protection's `required_status_checks.strict` is one boolean per protected branch with no path filter, and a ruleset's "require branches to be up to date" (`strict_required_status_checks_policy`) has none either: any commit on the base makes every open PR `BEHIND`, whatever paths it touched.
  - **Honest limits.** The gate covers this run's trail PR only: another merge to the base while an item's PR is open (a hand-merged PR, another run's trail PR) still leaves it `BEHIND` under `strict` — the owner updates the branch (GitHub's "Update branch" button, or a hand merge of the base), and under `--auto-merge` the gate's `gh pr merge --squash` fails and parks `merge_command_failed`. Under `--auto-merge` a skip/abandon check-off opens a trail PR mid-run, so an unattended run parks `trail_pr_open` at the next PICK until the owner merges it.
