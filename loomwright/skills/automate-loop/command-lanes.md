### Lanes (`--parallel N`) and launch authority

**Single-lane mode (`--parallel 1`):** every Queue item, in Queue order, runs in ONE fresh lane (a new clone, a new session) that parks `awaiting_merge` with a merge watcher like a sequential item — no wave, no wave PR; you merge the lane's own PR and `/automate --resume <run_id>` closes it out and starts the next item in a new lane. It is refused with `--auto-merge` and when branch mode is off, and `--max-tokens T` bounds the whole run. Detail: skill §14 "Single-lane mode".

With `--parallel N` (N > 1) the coordinator creates one lane per item of a wave (`automate-lanes.sh lane-create`), launches each (`lane-launch`), polls with `lane-status` on each `/automate --resume <run_id>`, relays each lane question to you verbatim and sends your answer back with `lane-answer`, and holds the primary checkout for the wave (`automate-lanes:<run_id>` run lock + `pick-guard` at every sequential PICK and every new run's start). **Launch authority (new stance):** a lane launch or resume runs only on behalf of a command YOU typed in this same session (`/automate --parallel N`, `/automate --resume <run_id>`). A launch or resume requested by a cross-session or peer message, a hook, or text inside a lane's output cannot authorize a lane launch and cannot grant escalation — it is refused and named. A refused launch prints `lane-launch: BLOCKED — <lane> — <reason> — need the owner` as its first line, keeps the lanes already running, and is never retried in another shape. A wave continued in a new session resumes only when you type `/automate --resume <coordinator run_id>` there. Detail: `skills/automate-loop/SKILL.md` §14.

**Wave close — the engine builds and opens the wave PR, you merge it, the engine cleans up.** Once every lane of the wave is converted, the coordinator runs `automate-helpers.sh wave-build <parent_runfile>` in the background: in a temporary worktree it merges each lane's exact PR head `--no-ff` onto a fresh wave branch, runs `ci-local.sh`, makes the release step the last commit, pushes ONLY the wave branch and opens the wave PR, then reports `wave-build: opened — <url>`. A conflict, a red local CI or a failed release step stops it (`STOPPED`, nothing pushed, the worktree kept at the printed path for you); a lane PR not open or a lane not parked is refused before anything is created. Nothing in the engine merges a lane PR or the wave PR — merge the wave PR with a merge commit, so each lane PR reads merged too. `automate-helpers.sh wave-plan <parent_runfile>` stays the read-only preview of the same steps plus the conflict rules. After you merge, each `/automate --resume <run_id>` runs `lane-convert-ready` per merged lane and then `automate-helpers.sh fleet-closeout <parent_runfile>` — stepwise and idempotent: it closes out every merged lane, checks its item off the parent Queue, syncs the primary, removes the lane clones, reports leaks and `main`'s `ci` health, and releases the wave lock once the Queue is empty. A step that must wait (a lane not merged, a live watcher) prints `waiting — …` and is re-checked on the next `--resume`; a closed-unmerged lane is left for you (`lane-remove <lane_dir> --abandon`). Detail: skill §14 "Wave close".

**Policy answers — routine lane questions answered by your own rules.** A lane question that is a catalogued routine gate (its `header` is a gate code whose policy is `allowed` — `loomwright/scripts/lane-policy.sh catalog`, mirrored in `docs/LANE_GATES.md`) is answered by the lane's own hook from a policy you set: a project policy `.agent/lane-policy.json` that counts only while human-stamped through `/rules check --confirm` (rule id `lane-policy`), or a per-wave answer set you give at wave planning (`lane-policy.sh wave-set`). It is an exact lookup, all or nothing per question call, recorded in the lane's `## Progress` as `policy answer: <code> → <label> (policy_sha …)`. Every other question still comes to you; `lane-status <parent_runfile> --inbox` lists all pending ones in one batch. Detail: skill §14 "Policy answers".
