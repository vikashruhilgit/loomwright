# Supervisor Config Protocol (Supervisor Phase 0 INIT)

> **Read at phase entry (Phase 0) — deliberately NOT preloaded.**

This skill is the single source of truth for the Supervisor's **Phase 0 INIT** (interactive
configuration) protocol: environment auto-detection, resume-state loading behind the fail-closed
Resume validation gate, cost-profile resolution (`--cheap`), the base-branch + non-interactive
preamble (flag parsing/defaults + crash-recovery flag clearing), `.supervisor/` directory
bootstrap, Context-Keeper initialization, and job-brief loading. The Supervisor reads this file at
Phase 0 entry and executes the protocol below; `agents/supervisor.md` keeps only a short phase
stanza with the entry/exit conditions. The protocol prose below is moved verbatim from the
Supervisor prompt.

> **Driver path (automate-speed/11).** With a `job:` brief on a fresh start (not `--legacy`, `--continue` or `--sdk-runner`), steps 3a, 4, 5, 5a.0.5–5a.2.5, 5a.3–5a.5, 6 and 7 below are `scripts/supervisor-next-step.sh`'s `init` step: the flags become its own flags, every Context-Keeper operation becomes ONE `context-keeper` spawn instruction, and it never writes `state.md`. Run step 5a.0 (the run-lock acquire) first, then call the driver per `commands/supervisor.md` §"Next-step driver (Phases 0–4)". Steps 1, 2 (resume + the Resume validation gate), 3 (the config questions and their can't-ask branch), 5a.2.6–5a.2.10 (the Phase 4.5 flags — except 5a.2.9b, the base branch, which the driver's `init` step resolves) and 5a.6 (the echo) stay yours on every path. The pre-driver text of every driver-owned step is in `docs/supervisor-legacy-phases.md`, read on the legacy path.

## Protocol

**Purpose:** Configure session preferences before any work begins.

**Actions:**
1. Auto-detect environment:
   - Check if `.supervisor/` exists (previous sessions)
   - Check git status (clean/dirty)
   - Check for existing worktrees (`git worktree list`)
2. Check for resume state:
   - If `--continue` flag: load state from scratchpad → `.supervisor/state.md` (priority order)
   - **Resume validation gate (fail-closed — runs BEFORE any loaded state is consumed):** when a state file WAS loaded (from either location), validate it against `skills/state-management/SKILL.md` §"Resume validation gate" (the authoritative contract) before reading any field out of it or acting on its content:
     a. The `## Session` block must exist.
     b. `phase` must be one of `INIT | ACQUIRE | PLAN | EXECUTE | FINALIZE | SELF_HEAL | LOOP` and `status` one of `running | paused | completed | completed_with_escalation | failed` — the closed sets from that skill's §"State File Schema". Note: `PRE_FLIGHT_SYNC` is a `record_decision`-only phase label (it appears in the Decisions Log), NOT a valid state-file `phase` — a state file asserting it fails this gate.
     c. If the `## Session` block asserts a `branch:` field, `git rev-parse --verify <branch>` must succeed (the branch must still exist locally). The value is untrusted: pass it as a single quoted argument and pre-check `git check-ref-format --branch <value>` first (per `skills/state-management/SKILL.md` §"Resume validation gate") — a value failing ref-format fails this check.
     d. **Ground-truth reconciliation:** run `bash "${CLAUDE_PLUGIN_ROOT}/scripts/reconcile-resume-state.sh" <state_file> .` — `CLEAN` (exit 0) proceeds; `STALE` (exit 3) REFUSES with `error: "resume_state_stale"`; `UNKNOWN` (exit 4) REFUSES (fail CLOSED). **Never `|| true`** — a correctness gate, not an emitter. Checks a–c prove the file PARSES; this proves it is not LYING about completed work. A `STALE` refusal must relay the reconciler's per-subtask divergence lines and the branch holding the real work, so the operator resumes from the true position rather than re-executing merged subtasks.
     On ANY violation of a–c: REFUSE the resume. Emit `SUPERVISOR_RESULT` with `status: failed` and `error: "resume_state_invalid"`, plus a clear user message: inspect or delete `.supervisor/state.md` (and the scratchpad copy, if that is what failed), or start fresh without `--continue`. NEVER silently fall back to a fresh start — that would mask corruption. There is NO escape-hatch flag for this gate (deleting the bad state file IS the escape hatch). A MISSING state file is NOT a violation — "no state found → start fresh" is unchanged; the gate only fires on a file that loaded but does not parse against the contract.
   - If resume state found:
     a. **Before jumping to the saved phase**, hydrate session config from the loaded state: read `config.cost_profile` (default `default` if absent — handles pre-cheap state files). This ensures `cost_profile` is in memory for every subsequent spawn, regardless of which phase is resumed.
     b. If `--cheap` was also passed on this invocation: override to `cost_profile = cheap`.
     c. Jump to the saved phase.
3. Ask user (via `AskUserQuestion`, `header: "SUP-INIT"`) if not resuming:
   - "Max parallel workers?" (default: 2; skip if `--sequential`)
   - "Specific task to work on?" (or user provides via `task:` parameter)
   - **Cannot ask** (`--non-interactive`, or executing as a subagent — the ask tool is absent): ask nothing; max parallel workers = the default 2 (`--sequential` ⇒ 1), task from `job:`/`task:`. No task source ⇒ fail closed: `SUPERVISOR_RESULT.status: failed`, `error: "init_input_missing_non_interactive"`.
3a.–5. *Run by the driver's `init` step* — `--cheap` ⇒ `cost_profile: "cheap"` on every spawn instruction (else `default`); the `.supervisor/` directory bootstrap (`.supervisor/` must stay ignored — a bare line, or `/setup memory`'s managed block; the bare line is appended only when git does not already ignore the directory's contents); the Context-Keeper `initialize` with `{max_workers, mode, cost_profile}`. Pre-driver text: `docs/supervisor-legacy-phases.md`.

5a. **Base-branch + non-interactive preamble (v14.0.0):**

   This preamble runs on **every** Phase 0 entry — both fresh start and `--continue` resume. The two `clear_flag` calls implement the **read-on-start, clear-on-start invariant** (see `skills/state-management/SKILL.md` §"Phase Flags") for crash-recovery flags: any pre-existing flag left over from a crashed prior session is cleared before this session can act on it.

   0. **Run-lock acquire (red-team-hardening/06 — FIRST action of this preamble, before any other step below).** `scripts/run-lock.sh acquire --owner "supervisor:<session_id>" --session-id "<session_id>"`, where `<session_id>` is the Claude Code runtime session id for THIS `/supervisor` invocation — known at session start, i.e. BEFORE this preamble derives/loads the later `state.md` `session_id` field, which is a distinct value. This mirrors `/automate` PICK's own acquire call exactly (`skills/automate-loop/SKILL.md` §6 step 1: `run-lock.sh acquire --owner "automate:<run_id>" --session-id "<session_id>"`). The explicit `--session-id` populates the lock's meta `session_id` field, which is what lets `close-stranded-run.sh` (crash recovery — matches by `session_id`, not `owner`) release a stranded lock; omitting it leaves that field empty and defeats crash recovery for this acquirer. A lock already held by another run/process in this checkout PARKS Phase 0 immediately: emit `SUPERVISOR_RESULT` with `status: failed`, `error: "run_lock_held"`, quoting the printed `run_lock_held owner=<label> pid=<pid> age=<s>` line verbatim — the run NEVER proceeds past this point silently. A `run_lock_reentrant owner=<outer> …` line (exit 0) is NOT a park: the lock is held by the `/automate`/`/autonomous` run that inlined this one in the same session — proceed; this run's own completion-tail release is then a no-op and the outer run frees the lock. A `run_lock_degraded` stderr line (exit 0; the lock is TTL-only — `docs/ARCHITECTURE_CONTRACTS.md` §"Run lock") is NOT a park either — note it once and proceed. On success, the lock is held for the rest of the session and released at the Phase 4.5 completion tail (or any Phase 4 abort exit) — see `agents/supervisor.md` Phase 0 for the short phase-stanza mirror of this step and `docs/ARCHITECTURE_CONTRACTS.md` §"Run lock" for the shared `run-lock.sh` contract (also used by `/automate` PICK and `/autonomous` INIT).
   0.5.–2.5. *Run by the driver's `init` step from its own flags* — `--max-tokens N` (the `max_tokens` Phase Flag, re-read by Phase 3), `--base-branch B` (the flag step of the base-branch resolution in 2.9b — there is no hardcoded default), `--non-interactive` — or `--subagent`: subagent context counts as the flag (the Can't-ask rule), recorded with source `subagent_context` — and `--skip-preflight-sync` (the Phase 1.5 skip). Pre-driver text: `docs/supervisor-legacy-phases.md`.
   2.6. Parse `--no-auto-review` and `--auto-review` from argv. Default: **neither** (record `AUTO_REVIEW_FLAG = none`). If `--no-auto-review` is present record `AUTO_REVIEW_FLAG = suppress`; else if `--auto-review` is present record `AUTO_REVIEW_FLAG = force`. (`--no-auto-review` wins if both appear.) Consumed by the Supervisor's Phase 4.5 completion-tail review-drain dispatch step. **As of the until-mergeable default (AC7), the post-`/supervisor` review drain dispatches BY DEFAULT** on a PASS/normal completion that produced a PR — `AUTO_REVIEW_FLAG == suppress` (or `.supervisor/config.json` `.auto_review == false`; legacy `.supervisor/notify-config.json` is still read as a fallback, the new path wins when both exist) is now the OPT-OUT; `--auto-review` / `.auto_review == true` are the legacy explicit-enable signals, now redundant with the default but still honored. This only controls the post-`/supervisor` standalone review-and-heal dispatch — it never affects the in-Supervisor Phase 4.5 review-and-fix loop.
   2.6a. Parse the **until-mergeable** flags (consumed by the same Phase 4.5 dispatch step): `--no-until-mergeable` (record `UNTIL_MERGEABLE_FLAG = suppress`; else `none`) opts the dispatched drain out of `--until-mergeable` (the runner then runs the plain diff-only `/review-pr`); when `none`, `.supervisor/config.json` `.auto_until_mergeable` decides (**DEFAULT true** — the drain runs until-mergeable). Also capture the optional tuning values `--check-wait-timeout N` (record `CHECK_WAIT_TIMEOUT`) and `--review-check-pattern <glob>` (record `REVIEW_CHECK_PATTERN`); both are forwarded to the dispatcher ONLY when set and thread to the runner via the S2-pinned env-var signal contract (`skills/review-heal/SKILL.md` §"Until-Mergeable Dispatch Signal").
   2.7. Parse `--no-red-team` and `--red-team` from argv (mirrors the auto-review flag-pair precedent above). Default: **neither** (record `RED_TEAM_FLAG = none`). If `--no-red-team` is present record `RED_TEAM_FLAG = suppress`; else if `--red-team` is present record `RED_TEAM_FLAG = enable`. (`--no-red-team` wins if both appear.) When `RED_TEAM_FLAG == none`, `.supervisor/config.json` `.red_team_high_risk` (boolean; default false/absent) decides. Resolve and record `RED_TEAM_ENABLED = true` iff (`RED_TEAM_FLAG == enable`) OR (`RED_TEAM_FLAG == none` AND config `.red_team_high_risk == true`); otherwise `RED_TEAM_ENABLED = false`. Consumed by the Supervisor's Phase 4.5 **Advisory red-team lens** step — an OPT-IN, DEFAULT-OFF, FAIL-SAFE, strictly NON-GATING advisory pass for high-risk integrated diffs. It NEVER changes `heal_decision`, never drives the fix task, never gates, and never blocks the PR/run.
   2.8. Parse `--sdk-runner` from argv (**EXPERIMENTAL — opt-in, default OFF**). Default: `false` if absent. Record as `SDK_RUNNER` in session memory at Phase 0 INIT like the other flags. Consumed by the Supervisor's Phase 3 EXECUTE `--sdk-runner` branch: when `true`, Phase 3 shells out to the quarantined spike runner (`node "${CLAUDE_PLUGIN_ROOT}/sdk-spike/dist/runner.js" --brief <brief path> --branch <feature branch>` — cwd stays the user project; CLI contract: `sdk-spike/README.md`) instead of Task-spawning `execute-manager` (or the inline Single-Agent/Sequential-path worker loop). **Fail CLOSED at Phase 3:** if `node` is unavailable, `"${CLAUDE_PLUGIN_ROOT}/sdk-spike/dist/runner.js"` is absent, or the SDK dependency does not resolve (`(cd "${CLAUDE_PLUGIN_ROOT}/sdk-spike" && node -e "require.resolve('@anthropic-ai/claude-agent-sdk')")` fails — catches `node_modules/` pruned after the build) when the flag is passed, the run aborts with `error: "sdk_runner_unavailable"` — never a silent fallback to the default path (`dist/` is gitignored and marketplace installs ship source only — build once with `npm install && npm run build` inside `${CLAUDE_PLUGIN_ROOT}/sdk-spike`). Zero change to the default path when the flag is absent.
   2.9. Parse `--multi-voter-heal` and `--no-multi-voter-heal` from argv (mirrors the red-team flag-pair precedent in 2.7). Default: **neither** (record `MULTI_VOTER_FLAG = none`). If `--no-multi-voter-heal` is present record `MULTI_VOTER_FLAG = suppress`; else if `--multi-voter-heal` is present record `MULTI_VOTER_FLAG = enable`. (`--no-multi-voter-heal` wins if both appear.) When `MULTI_VOTER_FLAG == none`, `.supervisor/config.json` `.multi_voter_heal` (boolean; default false/absent) decides. Resolve and record `MULTI_VOTER_HEAL = true` iff (`MULTI_VOTER_FLAG == enable`) OR (`MULTI_VOTER_FLAG == none` AND config `.multi_voter_heal == true`); otherwise `MULTI_VOTER_HEAL = false`. Consumed by the Supervisor's Phase 4.5 review-and-fix loop's **Multi-voter verification** step (`skills/self-heal-advisory/multi-voter.md` §"Multi-voter verification") — an OPT-IN, DEFAULT-OFF second independent reviewer (a `red-team-reviewer` verification vote alongside the gating `code-reviewer`) plus a second-opinion refute check that decides WHICH BLOCKING/HIGH `new` findings get fixed. It NEVER changes heal_decision semantics, `--heal-iterations` bounds, never-merge, or the completion tail. Distinct from and independent of the standalone `--red-team` advisory lens (step 2.7) — the flags do not alias each other; the interaction authority is that skill section.
   2.9a. Parse `--voter-provider <name>[:<model>]` from argv (only meaningful when `MULTI_VOTER_HEAL == true`, resolved in 2.9 above; flag-vs-config precedence mirrors 2.6a). If the flag is present, record `VOTER_PROVIDER = <its value>` (flag wins over config). Else if `.supervisor/config.json` `.voter_provider` (string) is present and non-empty, record `VOTER_PROVIDER = <config value>`. Else (both absent), record `VOTER_PROVIDER = ""` (the DEFAULT — absent-both keeps the existing behavior unchanged). Consumed by the Supervisor's Phase 4.5 **Multi-voter verification** step (`skills/self-heal-advisory/multi-voter.md` §"Multi-voter verification"): `VOTER_PROVIDER == ""` spawns the `loomwright:red-team-reviewer` Task exactly as before (byte-identical default); `VOTER_PROVIDER != ""` (e.g. `cursor:gpt-5`) instead shells out via Bash to `${CLAUDE_PLUGIN_ROOT}/scripts/adapters/providers/lens-run.sh --provider "$VOTER_PROVIDER" --role review ...`, normalizing that CLI's findings into the same `issues[]` shape the merge rule consumes. The refute check, merge rule, and `heal_decision` derivation are UNCHANGED by which branch ran — this only changes WHICH CLI produced the second opinion, never the gate shape.
   2.9b. Resolve the **base branch** — the branch the run branches from, targets with `gh pr create --base` and diffs against. Run the plugin's `scripts/resolve-base-branch.sh` (from the install root, like the other scripts this protocol runs; on the driver path the driver's `init` step makes this call) as `resolve-base-branch.sh --flag "<the --base-branch value, or empty>" --brief "<the job: brief path, or empty>" --repo .` and record its one stdout line as `BASE_BRANCH` (a bare branch name, no `origin/` prefix). Precedence — the script header is the authority, restated here for the operator: the `--base-branch` flag > the brief's `## Configuration` line `- **Base Branch:** <name>` > `.supervisor/config.json` `.base_branch` (string; set with `/setup base-branch set <branch>`, an absent key or `null` is "not configured") > `origin/HEAD` (one `git remote set-head origin -a` is tried when it is unset) > `gh repo view`'s default branch. There is **no hardcoded default**: when nothing answers, the script exits 1 with `base_branch_unresolved` on stderr and the run STOPS before any work; an explicit flag, brief or config value that is not a valid branch name exits 2 with `base_branch_invalid:<flag|brief|config>` and never falls through to a lower step. `resolve-base-branch.sh --explain` prints `<branch> (source: <step>)` — the form `/setup base-branch status` shows. `.supervisor/` is gitignored, so `.base_branch` is per-checkout: a teammate's clone does not inherit it.
   2.10. Resolve the **fix floor** — the lowest finding severity the Phase 4.5 review-and-fix loop FIXES (anything below it passes as a dismissed follow-up; BLOCKING is always fixed): run the plugin's `scripts/fix-floor.sh` (from the install root, like the other scripts this protocol runs) as `fix-floor.sh resolve --flag "<the --fix-floor value, or empty when absent>" --root .` and record its one stdout line as `FIX_FLOOR` (`HIGH` | `MEDIUM` | `LOW`; flag > `.supervisor/config.json` `.fix_floor` > default `MEDIUM`). On exit 2 (an invalid flag or configured value — the script never substitutes the default for an explicit value it cannot honour) STOP before any work: report `fix_floor_invalid` with the script's stderr line and change nothing. Consumed by the Phase 4.5 review-and-fix loop (`skills/self-heal-advisory/SKILL.md` Part 2). The SAME setting governs Launch Pad's plan-review save and `/review-pr`, so one `.fix_floor` makes every step agree.
   3.–5. *Run by the driver's `init` step* — after `initialize`, its Context-Keeper instruction carries `clear_flag base_mismatch_detected` (W-NEW-14) and `clear_flag non_interactive` (W-NEW-15) on every entry, then `set_flag non_interactive` (`value: {set_at, source}`) when `--non-interactive` / `--subagent` was passed (W-NEW-10). Pre-driver text: `docs/supervisor-legacy-phases.md`.
   6. **Echo the resolved values prominently** (placed AFTER environment detection, BEFORE the Status output, so later phases can re-derive these values via LLM recall even if scratchpad state is summarized away):
      ```markdown
      ### Session Configuration (echoed for cross-phase recall)
      - **BASE_BRANCH:** {BASE_BRANCH — the value step 2.9b resolved}
      - **NON_INTERACTIVE:** {true or false}
      - **RED_TEAM_ENABLED:** {true or false}
      ```

   > **Other INIT-parsed flags:** the loop-shaping flags `--skip-self-heal` and `--heal-iterations N` (default 3) are also parsed here at INIT and recorded in session memory — they are consumed by the Supervisor's Phase 4.5 SELF_HEAL (the `skip_self_heal_requested` invariant is "set once from INIT-parsed flags, never mutated").

6.–7. *Run by the driver's `init` step* — the `job:` brief moves `pending/` → `in-progress/` (a brief outside `pending/` is used where it is); `guard-arm.sh arm supervisor` runs and its outcome is recorded as `guard_armed: ok` / `guard_armed: failed: <stderr>` (a failed arm is logged, never fatal — surface `guard: unarmed` in the completion tail's outcome line). A run with no `job:` brief is a legacy-path run. Pre-driver text: `docs/supervisor-legacy-phases.md`.

**Output:**
```markdown
## SUPERVISOR v4: Starting Parallel Workflow

## ENVIRONMENT
- **Path:** {project_path}
- **CLAUDE.md:** ✓ Found | ✗ Missing
- **Git:** clean | dirty ({N} files)
- **Branch:** {current_branch}
- **Worktrees:** {count} existing
- **Config:** workers={N}, mode={parallel|sequential}
```
