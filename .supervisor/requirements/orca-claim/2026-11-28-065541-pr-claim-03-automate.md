# PR claim 03 — `/automate` item claim and the `loomwright:parked` signal on a gate PARK

## Status: pending

Owner approval: 2026-11-28, request from `orca-plugin-dev` (relayed by the Orca coordinator). Contract: `vikashruhilgit/loomwright-orca` `docs/CLAIM.md` (v1), reference implementation `src/claim.ts` (PR #1, merged); park: `docs/HANDOFF.md` §5; guard: `docs/GUARD.md`. Counterpart on loomwright-orca main: PR #7 (`a1de67b`, `claim-step.js handover`) and PR #9 (`5ad9434`, `loomwright@*` merges on a `loomwright: true` project, no push to a set-up project's base). Design note: `loomwright/docs/SPIKES/ORCA_PR_CLAIM_DESIGN.md`. Set: 01 helper → 02 drains → 03 /automate.

**As a** repo owner running both Orca bots and Loomwright on my `vikashruhilgit` repos,
**I want** `/automate` to hold the claim across an item's drain and gate, and to hand the PR to the `pr-merge` bot when the trusted auto-merge gate parks instead of merging,
**so that** the shared PR-merge bot gets exactly the PRs Loomwright's gate declined, with no gap in the claim, and nothing else touches a PR mid-item.

## Acceptance Criteria

**Part D — `/automate` (item-level claim, gate park signal)**

- [ ] **One holder per run, in every session's env.** INIT resolves `pr-claim.sh holder --run-id <run_id>`: the coordinator session's `$LOOMWRIGHT_CLAIM_HOLDER` when set (it must start with `loomwright@`, else exit 2), else a generated `loomwright@<host>/<run_id>`. It writes it once to `## Run Config` as `claim_holder:`. `--resume`, `--merge-parked` and every later step read that line and never regenerate it, so a resumed run renews its own live claim. Under `--parallel N` each lane has its own `run_id`, so it has its own holder. Test: two lanes of one wave get two distinct holders, and a resume keeps the recorded one.
- [ ] **The holder is in the env of every session that writes to the PR; a command prefix never stands in for it** (loomwright-orca `docs/GUARD.md` §"Who the session is": the guard reads the session's own env and ignores a prefix for merges when that is set). Each path, each with a test leg:
  - **fresh phase sessions** (`phase-launch`, `automate-lanes.d/phase.sh`): `LOOMWRIGHT_CLAIM_HOLDER=<claim_holder>` is in the launched session's `env` for every phase (launch-pad, supervisor, drain), so the session and its Task fix workers inherit it;
  - **lanes** (`lane-launch`, `automate-lanes.d/launch.sh`): the same, with the lane's own holder;
  - **runtime Orca settings travel with it:** when the coordinator's env has `LOOMWRIGHT_ORCA_DEV_BOT`, `LOOMWRIGHT_ORCA_CHECKOUT`, `LOOMWRIGHT_ORCA_MERGE_BOT` or `ORCA_CLI_COMMAND`, each launched phase and lane session gets the same value, so a park inside a lane hands off the same way as one in the coordinator. When `LOOMWRIGHT_ORCA_CHECKOUT` is unset the launchers pass nothing for it: each park resolves the checkout itself through story 01's order (env, then the installed claim guard's entry, then the fallback), so the engine never copies a derived path into a session env and never writes to the checkout. Test legs: coordinator env set ⇒ the launch env carries it; unset ⇒ the launch env has no `LOOMWRIGHT_ORCA_CHECKOUT` and a lane park with a settings fixture holding the guard entry still prints `checkout=claim_guard`;
  - **sessions the engine did not start** (the `--inline-phases` drain and the coordinator's fix-now re-drain run in the owner's session, whose env Loomwright cannot set): in scope, INIT runs `pr-claim.sh session-check <claim_holder>`. Under `--inline-phases` a mismatch stops INIT with `claim_holder_not_in_session` and a message naming the fix (start Claude Code with `LOOMWRIGHT_CLAIM_HOLDER=loomwright@<host>/<label>`, or drop `--inline-phases`). In fresh-phase mode a mismatch records `coordinator_holder: absent` in `## Run Config`, and the fix-now offer reads `fix-now unavailable: holder not in this session` (its findings are followed up), so no inline drain ever runs without the holder. The drain invocation still carries `--claim-outer --claim-holder <claim_holder>`, and the driver's own `session-check` (story 02) is the second line of defence;
  - **the merge**: `gate-eval`'s `gh pr merge` runs inside `automate-helpers.sh`, out of the guard's sight; the `gate-eval` step still runs it with `LOOMWRIGHT_CLAIM_HOLDER=<claim_holder>` in its env, and the coordinator never hands the model a merge command. On a project set up with `loomwright: true` the guard's rule 1 admits `loomwright@*` merges alongside `pr-merge`, so a direct merge as the holder would pass too;
  - **engine-posted PR comments and label writes** go through scripts with the holder in their env.
  The test asserts each captured launch env names the holder (and the Orca settings when the coordinator has them), and that no model-facing instruction the engine prints carries a `LOOMWRIGHT_CLAIM_HOLDER=` prefix.
- [ ] **No path pushes to the base branch** (loomwright-orca `docs/GUARD.md` rule 2a: nobody pushes to a set-up project's base, `pr-merge` included). The engine's pushes go to the item's PR branch, its own `chore/<run_id>-trail-<n>` branch, a wave branch, or the metadata branch, never to `<base>`. A test runs every step that prints or runs a `git push` and fails on a destination of `<base>`, `HEAD:<base>`, `refs/heads/<base>` or a bare `git push` from a checkout on `<base>`.

- [ ] Given an item with a PR, when `automate-next-step.sh`'s `drain` step runs, then it takes the claim before printing the owned-drain spawn and passes `--claim-outer --claim-holder <claim_holder>` in the drain invocation (the drain session's env carries the same holder, above); `held` ⇒ the item parks `pause_reason: claimed` with the park message `claimed by <holder> (lease until <ts>)`, run lock released, no drain spawned; `unreadable` ⇒ the same park with `claim_unreadable`.
- [ ] The fix-now re-drain, `--resume` RECONCILE of an open-PR item, and `--merge-parked` each take (or renew) the claim before touching the PR, with the same `claimed` park on `held`.
- [ ] Given `--auto-merge`, when the `gate-eval` step runs, then it first runs `pr-claim.sh assert`; not held ⇒ park `claimed` (gate-eval not called). `automate-helpers.sh gate_eval()` is byte-for-byte unchanged (a test diffs its body against a pinned hash).
- [ ] Given `gate-eval` prints `PARK: <reason>` (the loop's gate and `--merge-parked`'s merge-gate), when the park writes run, then `pr-claim.sh release <pr_url> --parked --holder <claim_holder> --reason "<reason>"` runs once, with `<reason>` the text after `PARK: ` exactly as gate-eval printed it. That one call does the HANDOFF.md §5 park (story 01 Part B): `claim-step.js handover --to pr-merge` (no gap, never two holders), then `loomwright:parked`, then the handoff to `bot:pr-merge`, whose body names `dev-bot:` from `$LOOMWRIGHT_ORCA_DEV_BOT` (else `none`) and `holder: <claim_holder>`. A refused or skipped handover falls back to release plus the label. pr-merge removes the label once it holds the claim. The park's Progress line records `claim <handed to pr-merge|released> (handover: done|refused|skipped, parked label: added|failed, handoff: sent|skipped|failed[ <why>])`. Any outcome other than `handover: done, handoff: sent` is also appended to the session log as one `pr_claim_handoff` line (handover status, handoff status, reason, PR). The park itself is unchanged: same `pause_reason`, same park message, same exit, same notify. Neither a refused handover, a failed handoff nor a missing Orca CLI ever fails or re-parks the run.
- [ ] Given `gate-eval` prints `MERGE`, or the item parks in safe mode (`awaiting_merge`) or as `escalated`, or as `claimed`/`claim_unreadable`/`claim_holder_not_in_session`, then plain `release` runs (no handover, no `loomwright:parked` label, no handoff).
- [ ] **The park handoff is engine-only and stays in the helper.** `automate-next-step.sh` never builds an `orca` or `claim-step.js` command itself and never resolves the checkout; it only passes `--parked --reason`. Out of scope (a repo owner not in `LOOMWRIGHT_CLAIM_OWNERS`) the helper skips the handoff together with the claim, so a non-`vikashruhilgit` run makes no Orca call.
- [ ] **Tests** (a stub orca named by `ORCA_CLI_COMMAND` and a stub `claim-step.js` under a temp checkout, named by `LOOMWRIGHT_ORCA_CHECKOUT` or by a settings fixture's guard entry, both logging argv and stdin to one shared log; stub gh as in story 01):
  - loop-gate `PARK: <reason with spaces>` with `LOOMWRIGHT_ORCA_DEV_BOT=lw-dev`: the log shows one `handover --holder <claim_holder> --to pr-merge`, then the label add, then exactly one orca send. Its `--subject` is `handoff <owner/repo>#<n>`, the body's `dev-bot:` is `lw-dev`, its `holder:` the run's `claim_holder` from `## Run Config`, `round: 1`, and `reason:` the gate's reason verbatim. The Progress line says `claim handed to pr-merge (handover: done, parked label: added, handoff: sent)`;
  - the same with `LOOMWRIGHT_ORCA_DEV_BOT` unset: `dev-bot: none`;
  - `--merge-parked` merge-gate `PARK:`: the same single handover and send;
  - a lane's gate `PARK:`: the lane session's launch env carried `LOOMWRIGHT_ORCA_DEV_BOT` and `LOOMWRIGHT_ORCA_CHECKOUT`, and the send's body names the lane's own holder;
  - handover refused (stub `claim-step.js` exits 1 `lost-race`, or prints anything but `"ok": true`): release, then label, no orca send; Progress `claim released (handover: refused, parked label: added, handoff: skipped lost-race)`;
  - no checkout resolved (env unset, fixture with no guard entry) or no `claim-step.js` in it: no `node` call, release then label, Progress `handover: skipped, … handoff: skipped claim_step_unavailable`;
  - `MERGE`, a safe-mode `awaiting_merge` park, an `escalated` park and a `claimed` park: the `claim-step.js` and orca logs are empty;
  - orca absent (`ORCA_CLI_COMMAND` unset and no `orca` on PATH): no handover, release then label. The run file's park block (`## Current`, `pause_reason`, park message) is byte-identical to the stub-present leg, the Progress line says `handover: skipped, … handoff: skipped orca_unavailable`, the session log has the `pr_claim_handoff` line, and the step exit code is unchanged;
  - stub orca exits 1: handover, label, send, hand-back, release; `handoff: failed <first stderr line>`, otherwise the same as the absent leg;
  - `--inline-phases` in scope with the coordinator env unset: INIT stops `claim_holder_not_in_session` before any claim read; fresh-phase mode with it unset: the fix-now offer is `unavailable: holder not in this session`.
- [ ] `pause_reason: claimed` and `claim_unreadable` are added to the run-file template's list, `docs/result-schemas/automate-run.md` and every surface that restates the enum, and `claim_holder_not_in_session` to INIT's refusal list, in the same change.

## Non-goals
- Changing `gate-eval`'s seven conditions, its PARK reasons or its merge command.
- Claiming during Supervisor Phase 4.5 / FINALIZE pushes inside `/autonomous` RUN (the PR is brand new; no drain is working it yet).
- A background renew heartbeat process.
- Implementing the merge bot, or enforcing claims for other tools (the Orca worker and `claim-guard` hook do that).
- Repos outside `LOOMWRIGHT_CLAIM_OWNERS`.

## Owner decisions
- 2026-11-28 (owner, via orca-plugin-dev): adopt CLAIM.md v1; `kind=loomwright`; scope is `vikashruhilgit` repos only; park signal is either a marker field or a `loomwright:parked` label, implementer's choice with justification — chosen: the label (release deletes the marker, so a marker field would vanish with it).
- Fail mode: fail-OPEN (no GitHub call) out of scope and when `gh` is absent; fail-CLOSED in scope when the claim cannot be read or written. Agreed by orca-plugin-dev 2026-11-28.
- 2026-11-28 (orca-plugin-dev answers): only a trusted-auto-merge gate PARK adds `loomwright:parked` (after release); safe-mode `awaiting_merge` and escalated parks never do.
- 2026-11-28 (orca-plugin-dev, via the coordinator; order superseded by the final answer below): the label cannot wake `pr-merge` (Orca's `github.labeled` ignores the owner's own labels), so a gate PARK also sends a direct handoff to `bot:pr-merge`, after the release and the label, through the story 01 helper. The same parks only (gate PARKs, never `awaiting_merge` or `escalated`), in scope only, fail-safe. Any Loomwright take removes a stale `loomwright:parked`. 60-min lease, half-life renewal, 120-min soft cap.
- 2026-11-28 (owner, via the coordinator): the `claim-guard` hook is installed in `~/.claude/settings.json` on this Mac for `vikashruhilgit` repos. and admits a PR write only when the writer is the live holder.
- 2026-11-28 (orca-plugin-dev, final answer; supersedes "release, then label, then send" and the command-prefix path): on a gate PARK run `claim-step handover --to pr-merge`, then add `loomwright:parked`, then send; a refused handover falls back to release plus the label; pr-merge removes the label once it holds the claim. The body is HANDOFF.md v1 (`head` the live 40-hex SHA, `round: 1`) plus `reason:` and `holder: loomwright@<host>/<run_id>`. `dev-bot` is an Orca bot from `LOOMWRIGHT_ORCA_DEV_BOT` (`lw-dev` for loomwright, `studio-dev` for loomwright-studio, set by whoever starts the run), else `none`; replies go to the dev bot, never to the Loomwright run. Loomwright sessions carry `LOOMWRIGHT_CLAIM_HOLDER=loomwright@<host>/<run_id>` in their environment; a command prefix does not count. On a `loomwright: true` project the guard admits `loomwright@*` merges alongside pr-merge; nobody pushes to a set-up project's base branch. Counterpart on loomwright-orca main: PR #7 `a1de67b`, PR #9 `5ad9434`.
- Inline drains without the holder in the owner's session (implementer's choice): `--inline-phases` refuses at INIT; in fresh-phase mode the fix-now re-drain is withheld rather than run unguarded.
- Holder granularity (implementer's choice, design note §"Holder id"): one holder per run (`loomwright@<host>/<run-id>`), not one per machine.

## Priority: MVP
**Rationale:** Orca bots already honour and enforce the claim; until Loomwright takes it, a drain can be refused mid-round by the `claim-guard` hook, and the merge bot has no signal.

## Assumptions
- `gh` is authenticated as an account whose `author_association` on in-scope repos is OWNER/MEMBER/COLLABORATOR.
- GitHub's add-labels endpoint creates a missing label (the reference `src/gh.ts` relies on this).
- The drain driver is called at least once per fix-worker spawn, so a 60-minute lease with half-life renewal covers the longest single step; a fix worker longer than the lease ends `claim_lost` at its pre-push assert rather than pushing unclaimed.

## Dependencies
- Depends on: none (contract merged in loomwright-orca PR #1).
- Blocks: the shared PR-merge bot's wake-on-park.

## Risks
- A spawn path that does not carry the holder has its PR writes refused by the installed `claim-guard` mid-drain. Each path has its own AC and test, a session the engine did not start is checked before it claims, and the live validation runs with the real hook installed.
- `--inline-phases` on in-scope repos now needs the owner to start Claude Code with `LOOMWRIGHT_CLAIM_HOLDER` set, and a fresh-phase run started without it loses the fix-now re-drain. Both are stated in the INIT message so the owner knows why.
- Clock skew eats into the lease (UTC everywhere, `date -u`).

## Validation (must pass before merge)
1. **Static — engine:** the `test-automate-next-step*.sh` suites and `bash loomwright/scripts/test-automate-helpers.sh` pass with new legs for the drain-step take, the `claimed` park, `--claim-outer` in the drain invocation, `release --parked` after a `PARK:` (loop gate, `--merge-parked`, a lane) with the handover-label-send order and the refused-handover fallback, plain release after `MERGE` / safe park / escalated park, the per-run holder in `## Run Config` across a resume, the holder (and the Orca settings) in every phase/lane launch env, `claim_holder_not_in_session` for `--inline-phases` and the withheld fix-now, no push to `<base>`, no `LOOMWRIGHT_CLAIM_HOLDER=` prefix in any printed instruction, and the pinned `gate_eval()` body hash; the `gh pr merge --squash` invariant grep is unchanged; the story 01 one-place grep for `orchestration send` and `claim-step.js` still passes; `bash scripts/ci-local.sh --affected` green.
2. **Running system — park signal:** a `/automate --auto-merge` item on `studio-sandbox` whose gate parks (e.g. `--trust-unprotected` absent on an unprotected branch) ends with one claim marker, the merge bot's (a throwaway bot through `LOOMWRIGHT_ORCA_MERGE_BOT` if the shared `pr-merge` bot does not exist yet), and `loomwright:parked` present. Its Progress line says `handover: done … handoff: sent`, and the handoff shows in that bot's Home Chat with a v1 body naming the PR, its head, the gate's reason, `dev-bot:` the run's `LOOMWRIGHT_ORCA_DEV_BOT` and `holder:` the run's holder. The same park with the bot name pointed at a bot that does not exist ends with no marker and the label on (`handoff: failed … restored=true`). A safe-mode item that parks `awaiting_merge` sends none; an item whose PR carries a live `orca-bot` claim parks `claimed` before any drain. With the installed `claim-guard` active, a default fresh-phase item and an `--inline-phases` item (session started with `LOOMWRIGHT_CLAIM_HOLDER` set) each drain (fix pushed) and reach the gate with no guard refusal; `--inline-phases` from a session without it stops at INIT. Evidence appended to `docs/evidence/pr-claim-live.md`.
