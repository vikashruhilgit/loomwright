# `/verify` can target a pull request's preview deployment

## Status: pending

Written 2026-11-09 against main `8ec200e` / v17.35.1. Part of the `qa-evolution/` set (`00-overview.md`); the owner's standing rule applies — requirements are automated, implementation needs explicit approval. **This item has no measured baseline:** no `/verify` run exists anywhere under `~/Documents/work`, no repo there carries `.agent/verify.json`, and the plugin has never read a GitHub deployment. Its evidence is a market-tracker gap row and a limit of story 04, nothing measured.

**As the** owner (Vikash), running `/verify` on a repo whose app is not runnable on this machine but gets a hosted preview per pull request,
**I want** `.agent/verify.json` to declare a preview environment by its GitHub deployment environment name, and `verify-run.sh preflight --pr <url>` (or `--head-sha <sha>`) to resolve that head's latest successful deployment URL, prove it non-prod under the same contract a static URL gets, record the resolved URL and deployment id on the evidence, and stop with a browser-less BLOCKED verdict when no deployment exists yet,
**so that** `/verify` — standalone, or inside the loop once story 04 lands — can walk acceptance criteria where the app only runs in a preview, with `gh` read-only and no token ever printed.

### Problem (read on main `8ec200e`)

- **The contract only knows a static URL.** `docs/result-schemas/verify-env.md`: `base_url: string # required — where the app under test is reached; non_prod_assert.base_url_matches is evaluated AGAINST it`. A per-PR preview URL (`<branch>-<hash>.vercel.app`, a Render preview host) is not known when the contract is committed, so such a repo cannot write a valid contract today, and `propose-verify.sh` refuses to default `base_url` by design ("a guessed localhost placeholder would let the non-prod gate pass against a URL the app is not actually at").
- **An override exists at the end of the pipeline, nothing at the start.** `verify-run.sh walk` takes `--base-url <url>` ("(1) base_url - the flag wins; else the contract THROUGH the reader"), but nothing resolves a URL; `verify-env.sh`'s flags are `--store --repo --state-dir --ready-timeout-s` only, so `start` (health polling), `auth-probe` and `assert-non-prod` always use the store's `base_url`; the qa-executor's VERIFY MODE skips Phase 3 with the reason "`base_url` is the contract's, through `read-verify.sh`"; and `commands/verify.md`'s pause instruction prints the contract's `base_url`.
- **Evidence (owner-supplied).** `loomwright-archive/market-watch/snapshots/tracker-page-source-latest.canvas.tsx`, gaps table: `{ gap: "Deploy / preview environments", who: "Jules (Render)", layer: "Loomwright", prio: "P2", owner: "Loomwright Operator", note: "Point /verify at a preview URL when the repo has one." }`; capability matrix row "Deploy / preview environments" (category "Code delivery"): ours "None.", Jules "Render preview integration.", the rest "Not verified." / "Not found.". And story 04's step can only run where the contract's `start` can bring the app up on this machine; a repo whose app lives only in a hosted preview records `aborted (env_start_failed)` or has no contract at all.
- **GitHub's deployment surface (read 2026-11-09 at the GitHub REST "deployments" reference page):** `GET /repos/{owner}/{repo}/deployments` filters by `sha` ("The SHA recorded at creation time"), `ref`, `task`, `environment`; a deployment carries `sha`, `ref`, `environment`, `transient_environment` ("specific to the deployment and will no longer exist at some point in the future", default false) and `production_environment` ("one that end-users directly interact with", default true when the environment is production). `GET /repos/{owner}/{repo}/deployments/{deployment_id}/statuses` returns statuses with `state` ∈ `error | failure | inactive | pending | success | queued | in_progress`, `environment` and `environment_url` ("The URL for accessing the environment"). Users with pull access can read both.

### Scope

- **Contract (VERIFY_ENV, additive):** an OPTIONAL top-level `preview` object, `{ "environment": "<GitHub deployment environment name>" }`. The reader accepts it when present and well-typed (an object whose `environment` is a non-empty string), refuses it otherwise with `[type_invalid:preview.environment]` (MALFORMED, empty stdout — the reader's existing strictness), and is byte-identical to today when the key is absent. `base_url` stays required: it is the local/static URL and the only URL used when preflight is given neither `--pr` nor `--head-sha`. `propose-verify.sh --preview-env <name>` writes the key; it is never scanned or guessed.
- **Resolution — `verify-run.sh preflight <ticket> [--pr <url> | --head-sha <sha>]`** (mutually exclusive; either requires `preview` in the contract, else exit 2 `[preview_not_declared]`), a step 3.5 between minting the run dir and the non-prod gate:
  1. `--pr <url>` ⇒ `gh pr view <url> --json headRefOid,headRefName` gives the head sha and branch (`run_start.head_sha` / `run_start.branch`; `--branch` still overrides the branch name); `--head-sha` uses the sha directly. `owner/repo` from the PR URL, else `gh repo view --json nameWithOwner`.
  2. `gh api "repos/<o>/<r>/deployments?sha=<head>&environment=<name>&per_page=10"`, newest first; a deployment counts only when the RESPONSE says `.sha == <head>` and `.environment == <name>` (the query filters are not trusted alone). `.production_environment == true` ⇒ refusal `[preview_is_production]` (an `env` `non_prod_assert` fail line, exit 1 — nothing started), whatever else is true.
  3. For the first counting deployment, `gh api "repos/<o>/<r>/deployments/<id>/statuses?per_page=10"`: the newest status with `state == "success"` and a non-empty `environment_url` is the resolved URL. None ⇒ try the next deployment; none at all ⇒ `preview_unavailable`.
- **Same non-prod contract, against the resolved URL.** `verify-env.sh` gains `--base-url <url>` (precedence flags > env > store, as its other overrides); `preflight` calls `assert-non-prod --base-url <resolved>`, so `non_prod_assert.base_url_matches` is tested against the resolved URL and `env_var_equals` / `cmd` behave exactly as today. A resolved URL the regex rejects is `non_prod_assert_failed`, exit 1, nothing started — the contract author declares what a non-prod preview host looks like (`\.vercel\.app$`, `-pr-[0-9]+\.onrender\.com$`), and the plugin never relaxes it.
- **Evidence.** The passing `env` `step: non_prod_assert` line gains four additive keys: `resolved_base_url`, `deployment_id`, `deployment_environment`, `deployment_sha` (documented as OPTIONAL additive keys in `docs/result-schemas/verify-evidence.md`; the validator already tolerates additive keys — "Unknown additive keys are tolerated on every event", read 2026-11-09). Every later consumer of the base URL in that run reads the resolved URL from the run's evidence, never the store's `base_url`: `verify-env.sh start` / `auth-probe` through `--base-url`, `verify-run.sh walk`'s generated `baseURL` (its `--base-url` flag still wins), `verify-run.sh auth-check`, and the pause instruction the executor and `commands/verify.md` print. `start` is expected to be `null` for a hosted preview (the app is already running); a non-null `start` still runs — it is the author's contract.
- **Unavailable is BLOCKED, never FAIL, never a guess.** No counting deployment, no `success` status, an empty `environment_url`, `gh` absent or exiting non-zero (`[gh_unavailable]` / `[deployment_read_failed]` named on stderr) ⇒ `preview_unavailable`: one `env` line `step: non_prod_assert, outcome: skipped, reason: preview_unavailable`, then `verify-run.sh verdict <run_dir> <ac_id> BLOCKED --reason preview_unavailable` (classification `ENVIRONMENT_ISSUE`, the browser-less default) for every AC in `acs.json` order, `finish --status aborted`, and preflight exits with a NEW documented code `6` printing `run_dir=<path>` last. `assert-non-prod` is NOT called on this path (there is no URL to assert against, and the store's static `base_url` is never substituted). `commands/verify.md` step 2's rc table gains the row: print `summary.md`'s counts row and STOP — no executor spawn. The owner re-runs when the deployment exists; nothing polls or waits.
- **`gh` read-only, no token.** Only `gh pr view`, `gh repo view` and `gh api` GETs (no `-X` / `--method`); `LOOMWRIGHT_GH_BIN` honoured (the seam `automate-next-step.sh`, `automate-helpers.sh`, `automate-lanes.sh`, `automate-trail.sh` and `automate-merge-watch.sh` already use). Raw `gh` output is never echoed: only jq-extracted fields (`headRefOid`, `headRefName`, `nameWithOwner`, `id`, `sha`, `environment`, `production_environment`, `state`, `environment_url`) reach stdout, stderr or the evidence.
- **Surface.** `/verify <ticket> --pr <url>` passthrough (Parameters row, rc-6 row); `--resume` unchanged — the `env` line already carries the URL. `skills/verify-walkthrough/SKILL.md` §8's pause instruction and `agents/qa-executor.md`'s VERIFY MODE steps 3/5 read the resolved URL from the run when present. Budgets re-measured for `commands.verify` (6276/5705 — 571 headroom, two new rows ⇒ the row moves), `skills.verify-walkthrough` (9454/8594), `agents.qa-executor` (53332/48483) and the `ARCHITECTURE_CONTRACTS.md` mirror rows; a `changelog.d/verify-preview-deployment.md` fragment.
- **Story 04 may use it, does not require it:** once both exist, the loop passes `--pr <pr_url>` when the contract carries `preview`. Neither story depends on the other.

## Non-goals
- Creating, triggering or waiting for a deployment; polling until one appears (one read per preflight; the owner re-runs).
- Any provider API other than GitHub Deployments (no Vercel, Render or Netlify API; a provider that reports previews only through commit statuses or check runs reads as `preview_unavailable`, honestly).
- Bypassing a preview's protection (a Vercel protection-bypass token, basic auth): the plugin never handles credentials; a protected preview takes the existing `storage_state` auth pause.
- The loop wiring (`04-verify-runs-inside-the-delivery-loop-in-shadow.md`), the `--folder` queue, or any change to the four verdicts.
- Reading `transient_environment` (not required for a preview to count; recorded nowhere in v1).

## Risks
- **Protected previews.** Vercel/Render previews are often behind a password or SSO; the walk then hits the auth pause and a human signs in — the right behaviour, but a preview that cannot be reached by a browser at all (IP allow-list) reads as every-AC BLOCKED after `start`'s health poll, not as `preview_unavailable`. Mitigation: the `env` line names which step failed.
- **Shared mutable state.** A hosted preview is one shared instance; `seed` / `reset` strings run against it after the non-prod assert, by the author's declaration. Mitigation: the V7 rule is unchanged — mutations only in `--verify` mode after the gate; the contract author owns the strings.
- **Stale `environment_url`.** A provider may keep a `success` status whose URL has since been torn down; the walk then BLOCKs on navigation. Mitigation: the deployment id and sha are on the evidence, so the owner can see which deployment was used.
- **Provider mismatch.** A repo whose preview provider does not create GitHub deployments gets `preview_unavailable` forever. Mitigation: the reason is named; a second provider is a new item, not a silent fallback.
- **Prompt budget.** `commands/verify` has 571 proxy tokens of headroom and gains two rows. Mitigation: the row moves in the same change.
