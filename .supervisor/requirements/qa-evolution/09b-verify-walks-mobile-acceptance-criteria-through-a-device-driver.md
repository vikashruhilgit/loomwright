### Scope

**Part 1: the `mobile` object in the contract (PO default), reader and bootstrap.**
- `docs/result-schemas/verify-env.md` documents, for `target: mobile`, a REQUIRED `mobile` object: `platform: enum [ios, android]`; `driver: enum [maestro]` (the only v1 value — a second driver is a new enum value behind the same seam); `app: object` — for `ios`: `bundle_id: string` (required) and exactly one of `app_path: string` (a built `.app` directory) or `build: string` (a shell string that produces it; the path it produces is `build_output: string`); for `android`: `package: string` (required) and exactly one of `apk: string` or `build: string` + `build_output`; `device: object` — `ios_simulator: string` (a name or UDID) for `ios`, `android_avd: string` for `android`; `boot_timeout_s: number` (optional, default 300 applied by the driver); `deep_link_scheme: string` (optional). `base_url`/`health` are not required (as `09a` made them for electron); `start`/`stop`/`seed`/`reset`/`auth` keep their types (`start`/`stop` = a backend; `auth.method` must be `none` — `[auth_method_unsupported_for_target]`, `09a`'s rule).
- Simulator/emulator ONLY: a `device` naming anything else, or a resolved device that is physical (`adb` serial not `emulator-*` / `ro.kernel.qemu` ≠ 1; `simctl` device not a Simulator), is refused `[physical_device_refused]` by the driver — D1's rule, no flag overrides it.
- `non_prod_assert` required as in `09a`: `base_url_matches` unusable (`[member_unusable_for_target:base_url_matches]`); `env_var_equals` or `cmd`; plus the simulator-only rule as the target-intrinsic half.
- `read-verify.sh` types all of it (`[required_key_missing:mobile]`, `[type_invalid:mobile.platform]`, `[type_invalid:mobile.driver]`, `[mobile_app_ambiguous]` when both `apk`/`app_path` and `build` are given or neither, `[type_invalid:mobile.device]` when the platform's device key is missing); `test-verify-seam.sh` gains the cases. `propose-verify.sh` gains `--target mobile --mobile-platform ios|android --mobile-driver maestro --mobile-bundle-id|--mobile-package <id> --mobile-app-path|--mobile-apk <path> | --mobile-build <cmd> --mobile-build-output <path> --mobile-ios-simulator|--mobile-android-avd <name> [--mobile-boot-timeout-s <n>] [--mobile-deep-link-scheme <s>]`; the dry run prints `BLOCKED` when the platform's required keys are missing.

**Part 2: one driver seam, Maestro first — `loomwright/scripts/verify-device.sh` + `test-verify-device.sh`.**
- Binaries resolved via `LOOMWRIGHT_MAESTRO_BIN`, `LOOMWRIGHT_ADB_BIN`, `LOOMWRIGHT_EMULATOR_BIN`, `LOOMWRIGHT_XCRUN_BIN`, else `PATH`, so `test-verify-device.sh` PATH-stubs them (the `test-verify-walkthrough.sh` `npx` convention). The script loads the contract through `read-verify.sh` (never re-parses), never runs a contract shell string itself (`app.build` is run by `verify-env.sh`, after `gate_non_prod`), and never contacts the network.
- `doctor [--repo <dir>]`: changes nothing, always exit 0, prints `key=value` lines — `platform=`, `driver=`, `maestro=<path|absent>`, `maestro_version=`, and per platform `adb=`, `emulator=`, `avd=<present|absent>` or `xcrun=`, `simulator=<present|absent>`, `simulator_udid=`, `booted=<0|1>` — ending `doctor=ready` or `doctor=not_ready reasons=<comma list>`.
- `start --run-dir <dir> [--repo <dir>]`: refuses before launching anything when `doctor` is not ready; boots the named simulator (`xcrun simctl boot <udid>`, headless — no `open -a Simulator`) or AVD (`emulator -avd <name> -no-window -no-audio -no-snapshot-save`), polls boot (`simctl` `Booted` state / `getprop sys.boot_completed`) inside one bounded loop against a `date +%s` deadline (≤ `boot_timeout_s`, never a foreground `sleep N`), installs the app (`simctl install <udid> <app_path>` / `adb -s <serial> install -r <apk>`), and records `udid=`/`serial=` plus whether THIS run booted it under `<run_dir>/device/` (the `verify-env.sh` pid-record shape). A device that was already booted is used and NOT shut down by `stop` (`booted_by_run=false`).
- `stop --run-dir <dir>`: shuts down only the device this run booted; never another; `not_running` is reported, not a success.
- `run <flow.yaml> --run-dir <dir> --report <path> --screenshots <dir>`: wraps `maestro test --format junit --output <report> --test-output-dir <screenshots> <flow.yaml>` against the recorded device (`--udid`/`--device` — the device-selection flag is an Assumption, see below); the exit status is ignored, the report file is the oracle (the `walk` rule).
- `test-verify-device.sh` (hermetic): stubbed `maestro`/`adb`/`emulator`/`xcrun` log argv and replay fixture outputs (`simctl list -j`, `adb devices`, `getprop`, a canned JUnit XML); asserts argv, the device record, the physical refusal, the boot timeout, the no-sudo/no-install rule (D1's mutation AC (b): never `sdkmanager --install`, never `xcodebuild`).

**Part 3: per-AC flow files and `walk` dispatch by target.**
- `<run_dir>/specs/<ac_id>.flow.yaml` is the mobile analogue of `<ac_id>.spec.ts`: the flow's `name` is `[<ac_id>] <AC text>` (the ingest key), `appId` is the contract's `bundle_id`/`package`, and the same `spec-replay` rule applies (byte-identical reuse per `ac_id` across same-ticket runs). Every flow's Then is ≥1 Maestro assertion step (`assertVisible` / `assertNotVisible` / `assertTrue` / `assertWithAI` excluded — PO default: a model-judged assertion is not an observation) followed by `takeScreenshot: <ac_id>-then`.
- `verify-run.sh walk` dispatches on the env line's `target` (`09a`): `mobile` ⇒ `verify-device.sh run` once per flow (sequential; `workers: 1` is implicit), then ingests the JUnit report into the SAME `ac` evidence lines with the same shape: `passed` ⇒ `PASS`; `failed` ⇒ `FAIL`/`REAL_BUG` with `reason` = the first line of the failure message and ≥1 screenshot artifact copied from `--test-output-dir` into `artifacts/<ac_id>/`; `error`/`skipped`/no testcase ⇒ `BLOCKED`/`ENVIRONMENT_ISSUE` (`flow_error: <msg>` / `flow_skipped` / `flow_not_run`); the driver's own refusals (`physical_device_refused`, `boot_timeout`, `device_unavailable: <reasons>`) ⇒ `BLOCKED`/`ENVIRONMENT_ISSUE` for every remaining id (the `walk_block_remaining` path).
- D2's rules carried: a flow with no assertion step is refused at ingest — `BLOCKED`/`ENVIRONMENT_ISSUE` `flow_no_assertion`, never `PASS`; a visual-only AC (looks right / smooth / laid out / animates) is verdicted by the agent `NOT_VERIFIABLE --reason needs_human_visual_signoff` BEFORE `walk`, with the run's screenshots attached and listed under "Needs your sign-off" in `summary.md`. `PASS`/`FAIL` are written only by `walk`'s ingest (`pass_requires_observation` holds).
- `verify-env.sh`: `start` on a mobile target runs `app.build` (when given, after the gate) then the backend `start` (when non-null), then `verify-device.sh start`; `stop` runs `verify-device.sh stop` then the backend `stop`. `env` lines gain `step` values `device_doctor`, `device_start`, `device_install`, `device_stop` (`verify-evidence.md` enum extended; `validate-verify-evidence.py` accepts them).
- `agents/qa-executor.md` VERIFY MODE: step 2 (Playwright presence) is skipped on mobile and replaced by `verify-device.sh doctor` (not ready ⇒ every AC `BLOCKED device_unavailable: <reasons>`, `finish --status aborted`, EMIT — the `playwright_unavailable` shape); steps 3/5/8/9 get the mobile clause; step 6 authors `<ac_id>.flow.yaml` per the skill's §2 mobile variant; step 7's NOT_VERIFIABLE list gains "visual-only ⇒ `needs_human_visual_signoff`"; the agent never calls `maestro`, `adb` or `xcrun` directly (an Error-Handling row names the rule; D2's mutation (c)). `skills/verify-walkthrough/SKILL.md` §2 gains the flow template (verbatim, ≤ 20 lines) and §3 the visual-signoff row; `skills/qa-strategy/SKILL.md` line 164 becomes "mobile UI is verified through `/verify`'s `target: mobile` (Maestro driver); the exploratory lane still globs backend API files only". `commands/verify.md` §Requirements names Maestro and the platform tools as the project's/owner's installs; §"Purpose" names the three targets.
- `docs/ARCHITECTURE_CONTRACTS.md`: budget mirror rows for `qa-executor`, `verify`, `verify-walkthrough`, `qa-strategy`; a §"Question-gate inventory" row only if a new can't-ask status appears (none is expected — `doctor` not ready is a BLOCKED verdict, not a question). `changelog.d/verify-target-mobile.md`.

## Non-goals
- Desktop-native apps through computer use or screenshots; a new agent; browser MCPs; the desktop app's iOS Simulator MCP tools; any gating.
- Physical devices (refused, no flag), cloud device farms, CI runners for iOS (macOS-only — a Risk), installing Maestro, the Android SDK, Xcode, simulators or system images (owner actions; `doctor` names what is missing).
- A model-judged PASS from a screenshot (`assertWithAI` excluded; visual-only ⇒ `NOT_VERIFIABLE needs_human_visual_signoff` — D2's OQ-V1 default, kept).
- Unity in-engine automation bridges (AltTester-style) or logcat/`dumpsys`-based assertions (D1/D2's hand-rolled observation verbs are superseded by Maestro's; Unity's in-game UI has no accessibility tree, so most Block Paradise ACs will be visual-only ⇒ `NOT_VERIFIABLE` — a stated limit, not a defect).
- A second driver (`mobile-mcp`, Callstack's `agent-device`, Appium) — the `driver` enum is the seam; v1 is `maestro` only.
- The exploratory `/qa-executor` lane on mobile (story `07` owns its environment model; mobile exploratory QA is a later item).
- An impact pass (§9) on mobile in v1: reported `impact: skipped (mobile)` (D2's OQ-V5 default).
- Deep-link helpers beyond passing `deep_link_scheme` through to the agent for flow authoring (Maestro's `openLink` is the project's step).
- A committed `.agent/verify.json` in this repo or in any dogfood repo.

## Risks
- **Maestro is not installed here and its CLI details are partly unverified** (device flag, JUnit naming, screenshot dir). Mitigation: `doctor` names the absence; the stubbed suite pins the argv the story expects; the implementer re-verifies against the installed version and amends the story, never the guard.
- **iOS runs are macOS-only.** No Linux CI can boot a simulator; the hermetic suite never does. Mitigation: stated as a non-goal; the Running-system proof is the owner's Mac.
- **Unity apps yield mostly `NOT_VERIFIABLE`.** Stated as a limit; the owner can add accessibility labels or accept visual sign-off.
- **Three shell surfaces (`app.build`, backend `start`, the driver) in one `start`.** Mitigation: `app.build` and `start` run only in `verify-env.sh` after `gate_non_prod`; the driver never runs a contract string (AC "No contract string is ever run by the driver").
- **A shared simulator left booted by another process is used, not isolated.** Mitigation: `booted_by_run=false` is recorded and shown in `summary.md`.
- **Emulator/simulator resource use on a shared machine.** Mitigation: `-no-snapshot-save`; `stop` kills only its own device; the boot wait is bounded.
- **Prompt growth across `09a` + `09b`** (twelve clauses in `qa-executor.md`). Mitigation: one sentence each; re-baseline where the gate trips.
- **Experimental-vs-stable drift in Maestro's JUnit shape.** Mitigation: the ingest reads `testcase` `name` and `failure`/`error` children only; a fixture XML pins the shape.
