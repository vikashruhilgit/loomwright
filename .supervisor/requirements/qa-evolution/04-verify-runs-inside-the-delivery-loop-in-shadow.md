# `/verify` runs inside the delivery loop in shadow

## Status: pending

Written 2026-11-09 against main `8ec200e` / v17.35.1 (the checkout was on a feature branch; every file cited was read at that main). Part of the `qa-evolution/` set (`00-overview.md`); the owner's standing rule applies — requirements are automated, implementation needs explicit approval.

**As the** owner (Vikash), merging PRs that `/automate` opened,
**I want** the loop to run ONE `/verify` pass per item against the repo's declared non-prod environment once the drain has left the PR head final, record its outcome in the run file without asking or gating, and — only when I switch it on — put a FAIL to me as one more dismissed finding,
**so that** a PR's acceptance criteria are walked in the running app as part of delivery, the run exists for the merge-verdict row (archive-approved 05) and the PR scorecard (archive-approved 10) to read unchanged, and `/verify` stops being a shipped command nobody runs.

### Problem (read on main `8ec200e`)

- **Shipped, never run.** `.supervisor/requirements/verify-walkthrough/` items 01–07 are `## Status: done` (`verify-env.sh`, `verify-helpers.sh evidence-append`, `verify-run.sh` acs/preflight/auth-check/pause/spec-replay/walk/verdict/finish/impact, `commands/verify.md` with `--resume --notify --no-impact --impact-limit --no-replay --folder --cheap`, qa-executor `--verify <run_dir>`, `propose-from-verify.sh`). On 2026-11-09 `find ~/Documents/work -maxdepth 4` found zero `.supervisor/verify/` directories and zero `.agent/verify.json` files. `verify-walkthrough/operator-run/08-dogfood-on-real-app.md` is still pending.
- **Nothing in the delivery loop calls it.** `grep` of `agents/supervisor.md`, `skills/automate-loop/*.md`, `skills/autonomous-loop/*.md` and `commands/automate.md` for `/verify` or `verify-run` finds nothing (only `verify-provides.sh`, an unrelated helper). `skills/automate-loop/SKILL.md` §1 "Non-goals (v1)" lists "QA-in-loop" as out of scope (loop-inventory row `AL-004`). `docs/QA_SYSTEM_BLUEPRINT.md` §"Level 4: Autonomous" names a "Supervisor Phase 3.5 QA Gate (post-merge, pre-PR)" that was never built.
- **Two approved stories read a run nothing produces.** `archive-approved/05-gate-verdict-mode-judges-any-pr-head-without-merging.md`'s `/verify` row reads "the newest `.supervisor/verify/<run>/` under `--root` whose `run_start` line in `evidence.jsonl` has `head_sha` equal to the judged head". `archive-approved/10-pr-scorecard-builder-single-comment-upsert-with-header-line.md`'s verify row keys on `run_start.branch` equal to the PR head branch, marks `current`/`stale` by `run_start.head_sha` against the live head, and `incomplete` when no `run_end` exists.
- **A hole in the shipped preflight.** `verify-run.sh` `preflight_cmd` resolves the head with `git -C "$repo" rev-parse --verify -q "$branch^{commit}"` and, when that fails, **silently falls back to `HEAD`** (the two `head_sha=` lines directly after the `--branch` default). After FINALIZE the primary checkout is back on the base branch (`agents/supervisor.md` Phase 5 step 3, `git checkout "$BASE_BRANCH"`), and the local feature branch lags the heal commits the drain pushed from its own worktree — so a run minted there with an unresolvable or stale branch would record the wrong head with no error, and story 10 would read it as `stale` or, worse, `current` for the wrong code.
- **Where the app would run from.** `preflight` mints the run dir under `--repo`'s own tree (`run_dir="$repo/.supervisor/verify/$run_id"`), and `verify-env.sh` / `verify-run.sh walk` start and drive the app in `--repo`. The drain already runs in a detached sibling worktree at the PR head (`dispatch-pr-review.sh` header: `git worktree add --detach <path> <sha>`), where the gitignored `.supervisor/` and any installed dependencies are absent. So "run `/verify` after the drain" has two checkouts in play: the one the app starts from (must be at the PR head) and the one the run dir must live under (the primary, which stories 05 and 10 read).
- **The verify side forbids the reverse direction.** `skills/verify-walkthrough/SKILL.md` §10 "Never shares state with `/automate`": a verify queue never reads `.supervisor/automate/`, `.supervisor/config.json` or `.supervisor/state.md`, and "running a verify queue inside an `/automate` tick … is an explicit Phase 2 question — this item forbids it by omission … none should be added without a new decision record". `test-verify-queue.sh` arm N pins it (`find .supervisor/automate .supervisor/state.md -newer <marker>` empty). This story is that decision record, for the single-ticket `/verify` only, in one direction: `/automate` calls `/verify`; `/verify` stays ignorant of `/automate`.

### Scope

**Part 1 — the step (driver, run file, config).**
- A new `automate-next-step.sh` step `verify`, reached only from a `drain-result` whose report is `READY` with a `ready_sha` (`## Current`'s durable READY record), before `gate`. On `ESCALATED` the step is not reached and the item's `## Current` carries no `verify_in_loop` line. It prints ONE `{"do":"spawn","what":"verify pass",…}` whose `invocation` is `/verify <item> --branch <## Current branch> --head-sha <ready_sha>` (plus `--cheap` in cheap mode), and takes ONE `--result` (the `VERIFY_RESULT` text or a path to it, or `no_result: true`). It never prints an `ask`.
- **Config key** `.supervisor/config.json` `verify_in_loop`: `"off" | "shadow" | "on"`; **absent ⇒ `shadow`** (the `heal-review-scope.sh` precedent: `mode shadow | files | full (absent key/file => shadow)`); any other value ⇒ `off`, the value named in the Progress line (fail toward not starting an app). Read by the driver only — `/verify` never reads it (the §10 direction).
- **Outcomes**, one `## Progress` line `<ts> verify_in_loop: <outcome> — <detail> @ <ready_sha>` and one OPTIONAL `## Current` line `- verify_in_loop: <outcome> | verify_run: <run_id|null>` (written through `runfile-write` the way `ready_sha` is; the `pending_decisions` OPTIONAL-line precedent):
  - `skipped_off` — key `off`, an unrecognised value (`skipped_off (value unrecognised: <v>)`), or a lane checkout (`skipped_off (lane)`; one app port per machine — v1 does not run verify inside `--parallel` lanes).
  - `skipped_no_contract` — `read-verify.sh --repo <root>` prints nothing; `preflight` would exit 3; nothing minted, no spawn.
  - `skipped_no_acs` — `verify-run.sh acs <item>` exits 2 (no `## Acceptance Criteria`); nothing minted, no spawn.
  - `completed` — detail is `<run_dir>/summary.md`'s counts row (`PASS: n · FAIL: n · BLOCKED: n · NOT_VERIFIABLE: n · total: n`) copied byte for byte; the driver never tallies.
  - `paused_needs_auth` / `paused_session_expired` — the executor's `VERIFY_RESULT` `status: paused` with its `pause_reason`; detail is the exact resume line `/verify --resume <run_id>`. **The loop continues to GATE**; the owner resumes later, standalone.
  - `aborted (<reason>)` — the run's own token where one exists: `non_prod_assert_failed`, `head_mismatch` (the minted `run_start.head_sha` ≠ `ready_sha`), `env_start_failed`, `playwright_unavailable`, `executor_no_result` (no `VERIFY_RESULT` returned), `run_dir_unparsed`. When a run dir exists it is finished with `verify-run.sh finish --status aborted` so no run is left `incomplete` by the loop.
- **Head pinned, never guessed.** `verify-run.sh preflight` gains `--head-sha <sha>`: `run_start.head_sha` is that sha verbatim and `run_start.branch` is `--branch`'s value (so story 10's branch match and story 05's sha match both hold); a sha not present in the repo's object store is refused (exit 2 `[head_sha_unavailable]`, nothing minted). An **explicit** `--branch` that does not resolve is refused (exit 2 `[branch_unresolved]`) — the `HEAD` fallback survives only for the implicit no-`--branch` path, which cannot fail to resolve. The step itself re-checks `run_start.head_sha == ready_sha` after preflight and records `aborted (head_mismatch)` otherwise.
- **Two checkouts.** The app under test is started from a checkout whose HEAD is `ready_sha`; the run dir lives under the primary `--root`'s `.supervisor/verify/` (what stories 05 and 10 read). How the plan obtains the head checkout (fetching the PR head into the primary and reusing the drain's sibling-worktree pattern, or another) is the plan's; what is pinned is the outcome and the failure name (`aborted (env_start_failed)` when the contract's `start` cannot bring health to 2xx there).
- **`on` mode.** `/verify`'s own step 5 already runs `propose-from-verify.sh <run_dir>` on a completed/aborted run with ≥1 FAIL or `issue` line, writing `proposed/verify-<run_id>-<ac_id>-<slug>.md` drafts — the step keeps that behaviour in every mode that reaches a verdict (it IS what a standalone `/verify` does). Under `on`, the item's `AUT-DISMISS` question lists those FAIL drafts as extra numbered entries after the dismissed-finding drafts, with the SAME options (`Fix none (follow-up all)` / `Fix all listed on this PR` / `Fix selected on this PR?`); a fix-now answer on one runs the SAME single owner-requested fix-now re-drain the item already has (never a second); undecided ones are counted in `pending_decisions`; can't-ask / `--non-interactive` ⇒ exactly the existing can't-ask behaviour (`decisions not asked …`, `pending_decisions` recorded). Under `shadow`, the drafts are written and never listed or counted. **A FAIL is never a park reason, never a gate condition, never an `escalation_cause`.**
- **Invariants kept, and tested:** exactly ONE owned drain per item (the verify spawn is not a drain: `owned_drain_*`, the pinned drain lines and `lane-drain-check`'s counts are unchanged); the `auto_review` toggle wraps RUN only; `gate-eval`'s seven conditions and its six-key ctx are unchanged (a ctx carrying a verify key fails the existing leg C); `merge-verdict` (archive-approved 05) and the scorecard (10) are not edited; the `/verify --folder` queue is not used; nothing under `.supervisor/verify/` is read by `/verify` from `/automate`'s state.

## Risks
- **Fresh checkouts have no dependencies.** A bare worktree at `ready_sha` has no `node_modules`; the contract's `start` must install or the pass aborts. Mitigation: a named outcome, the dogfood item measures it, and `shadow` makes an abort cost one Progress line.
- **Wall clock before the park.** A verify pass (start, health, walk) adds minutes between READY and the park or the `--auto-merge` gate. Mitigation: `off` is one config key; the pass runs once per item and never re-runs on `--merge-parked`.
- **Silent drafts in shadow.** FAIL drafts accumulate in `proposed/` with nobody asked. Mitigation: `summary.md`'s `## Proposals` section and the Progress line name them; `on` is the switch.
- **Port collisions.** A dev server the owner left running on the contract's port makes health answer for the wrong code. Mitigation: out of scope here, named for the dogfood item.
- **Prompt budget.** `skills/automate-loop` has ~5.3k proxy tokens of headroom, `commands/verify` 571. Mitigation: the rows move in the same change; `check-token-budget.sh` fails closed.
