**As the** owner (Vikash), approving a Launch Pad brief before the Supervisor builds it,
**I want** a brief that introduces a new dependency, a new module, a new external integration, a cross-cutting mechanism, or hand-rolls something the project already has to carry a `## Design decisions` section — the way chosen, at least one way rejected and why, the evidence, and when to revisit — with the Plan Reviewer verifying the entry and the Red Team asking whether the code reinvents a mechanism the platform already provides,
**so that** "why not use X / the platform already does this" is answered at plan time instead of costing a review round, and the rate story `01` measures goes down.

### Scope

**Part 1: the brief section (template + protocol split file).**
- `skills/supervisor-readiness/SKILL.md` §"Supervisor-Ready Brief Template": an OPTIONAL `## Design decisions` section after `## Task` and before `## Acceptance Criteria`, documented in §"Section Requirements" beside the other optional sections, and named in the Quality Checklist. One entry per TRIGGER, each a bullet group:
  `- decision: <what had to be chosen>` · `  chosen: <way>` · `  rejected: <way> — <why>` (one or more lines) · `  evidence: <repo grep command and hit | manifest/lockfile line | Context7 lookup | docs URL>` · `  revisit when: <condition>` · `  status: confirmed | unconfirmed` (`unconfirmed` = recorded under the Can't-ask rule, the owner has not seen it).
- **Triggers (closed list — the ONLY times the section is required; its authority is the split file):** (T1) a new dependency not in the project's manifest or lockfile (Phase 2.5 already rates it CAUTION); (T2) a CREATE path that is a new script or module of its own (Phase 3 action 13 §"Module layout" names it); (T3) a new external integration — an API, service, webhook or MCP server; (T4) a cross-cutting mechanism — auth, caching, queueing, retry, scheduling, state persistence; (T5) hand-rolling something the project's manifest, the harness (Claude Code / the plugin's own scripts) or a stackpack skill already provides. Bug fixes, docs, prompt-only edits and small changes never trigger it; no trigger ⇒ no section.
- New split file `loomwright/skills/supervisor-readiness/design-decisions.md` (counted under `skills.supervisor-readiness`, NOT under `agents.launch-pad` — the agent row folds only `SKILL.md`): the trigger list with one detection rule each (T1 from Phase 2.5 check 1/2 CAUTION rows; T2 from the File Impact Map's CREATE rows; T3–T5 from the goal and `## Task`), the candidate rule (2–3 candidates per trigger, in this order: something already in the repo — grep first; a library / platform / harness feature; hand-roll), the FIXED scoring axes (fits the CLAUDE.md stack; already in the lockfile or manifest; blast radius = files touched; test cost; reversibility / lock-in — each `yes | partial | no`, no weights), the evidence sources (repo grep — the `missing_context` preventer; `skills/context7-lookup/SKILL.md` for library candidates, within that skill's 2000-token budget; WebSearch ONLY under `--discovery`), the entry format, and the Can't-ask rule below.
