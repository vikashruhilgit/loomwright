## Premise correction (read first)
The owner's draft assumed "every review lens in the plugin is the same model family that wrote the code." That was
true before PR #239. As of `main @ 05823bf` the plugin ships a provider seam:
`loomwright/scripts/adapters/providers/lens-run.sh` + `provider-{claude,codex,cursor,gemini}.sh` (one file per
provider — adding a provider = adding a file), `lens-compare.sh`, `--voter-provider <name>[:<model>]` /
`.supervisor/config.json .voter_provider` (`skills/supervisor-config/SKILL.md` step 2.9a), wired into Phase 4.5's
multi-voter verification (`skills/self-heal-advisory/SKILL.md` §"Multi-voter verification"). Source requirement:
`.supervisor/requirements/orca-derived/07-provider-lens.md` (`## Status: done`), whose "Probe result — DEFERRED /
RESOLVED 2026-09-20" and lens-run's `SAFETY POSTURE` header say read-only isolation of the external CLI is
**detected** (sandbox + `.git` integrity check), not **enforced**.

Its contract is deliberately **fail-SAFE**: `lens_status ∈ {provider_unavailable, lens_mutated_tree,
lens_unparseable}` degrades that iteration to the single Claude voter ("voter errored/timed out"), and the voter
never decides `heal_decision` (delay-vs-decide invariant). Two of the draft's constraints therefore collide with
what merged: "never hard-coded provider names in plugin text" (the seam IS per-name files) and "quota/unavailability
⇒ ESCALATED, never silent fallback" (the seam's documented degradation IS that fallback).

**So this is not a new seam. It is a POLICY INVERSION of an existing fail-safe path into a fail-closed one, for
exactly one case.** CLAUDE.md §"Failure-Mode Invariants" treats such inversions as security-relevant decisions, not
bug fixes — which is why this stays a design until an owner decides.

## The case
When BOTH hold — `scripts/classify-risk.sh "$BASE_BRANCH" HEAD` says `high_risk: true` (its `null` = unclassifiable
already PARKs the `/automate` gate with no override) AND project config sets `external_review: required` — an
external lens that did not run (`provider_unavailable`, `lens_mutated_tree`, `lens_unparseable`, timeout) makes the
run terminate `ESCALATED` instead of silently proceeding on self-review.

## Design to capture (open questions marked ?)
1. **Config key.** `.supervisor/config.json .external_review: "required" | "optional" | "off"`, default `optional`
   (= today's behaviour, byte-identical). `required` is honoured ONLY when `high_risk: true`; on `high_risk: false`
   the lens still runs if configured but its absence degrades as today. ? Should `required` live in user scope
   (`~/.claude/loomwright/…`) per red-team-hardening R2 rather than a repo-writable file — the guarded thing (the
   worker/model) can write `.supervisor/config.json`.
2. **Which statuses count as "ran".** Only `lens_status: ok`. `lens_unparseable` is ambiguous (the provider ran
   but its output is unusable) — ? treat as not-ran (fail-closed) or as ran-with-zero-findings. Proposal: not-ran.
3. **Marker lines in `REVIEW_HEAL_RESULT` / `SUPERVISOR_RESULT`** (optional, additive):
   `external_lens: {provider, model, status, policy: required|optional|off, high_risk}`; on the fail-closed path
   `termination_reason`/`error`: `external_review_required_unavailable`. `/automate` gate-eval must PARK on it
   (verify cond 1/1b handle the new value — same pattern as harness-port/07).
4. **Interaction with `code-reviewer` in Phase 4.5.** The external lens is the multi-voter VOTER, not a replacement
   for the code-reviewer; `heal_decision` still never derives from voter output. ? Under `required`, does a
   surviving BLOCKING voter finding at the iteration bound become ESCALATED (today: "can only delay finalization
   within the existing bound")? Proposal: yes, but only under `required` + `high_risk`.
5. **Adversarial third lens + tie-break** (the harness had one). ? Out of scope for v1 — `lens-compare.sh` exists
   for A/B; a tie-break rule is a new decision surface and NORTH_STAR says "nothing gating". Record as deferred.
6. **Cost honesty.** lens-run reports `cost: "unknown"` (D11) — a `required` policy on every high-risk diff is an
   unbudgeted external spend; ? gate it behind `--max-tokens` (red-team-hardening/06) or a per-run lens cap.
7. **Safety prerequisite.** Because isolation is detected not enforced, `required` means an unattended path
   INVOKES an external CLI on every high-risk diff. Prerequisite: `07-provider-lens.md`'s probe findings re-read,
   and the `lens_mutated_tree` path proven to abort BEFORE any push (test exists — `test-lens-run.sh`
   "lens_mutated_tree isolation proof"; confirm it covers the `required` branch).
8. **Portability.** Provider NAMES stay in `provider-<name>.sh` filenames (that is the adapter layer, allowed by
   `portability-core-vs-adapter`); CORE text (skills/agents/commands) refers to `<provider>` only. ? Is the
   default `voter_provider` example `cursor:gpt-5` in `supervisor-config/SKILL.md` a core-text violation to fix.

## Non-goals (for the eventual implementation)
No new agent. No merge path. No change to `heal_decision` derivation outside the `required` + `high_risk` branch.
No tie-break lens in v1.
