## Problem
A host has no stable way to learn what the installed Loomwright offers. It can't see which agents (and the exact `agent_type` the runtime reports, e.g. the doubled `loomwright:loomwright:worker`), commands, skills, result schemas and hooks exist, or what each hook writes. The only sources are internal files whose shape is Loomwright's to change. `docs/CAPABILITY_BASELINE.json` is **not** this. It records the Claude Code features Loomwright *uses* (inbound, for `/capability-check`). This item is Loomwright's *outward* promise to hosts, so keep the two clearly separate in names and docs.

## Goal
Every release ships `loomwright/capabilities.json`. It is generated from the plugin's own sources, never hand-edited. It has a documented, versioned schema and a compatibility policy, so a host can rely on it across releases.

## Scope
- A generator script (for example `loomwright/scripts/build-capabilities.sh`, or `.py` if the repo prefers Python for JSON). It reads `plugin.json`, `agents/`, `commands/` and `skills/` frontmatter, `hooks/hooks.json` and `docs/RESULT_SCHEMAS.md`, and writes `loomwright/capabilities.json`. The output is deterministic: sorted keys and lists, no timestamps, so an unchanged plugin regenerates byte-identical output.
- The schema is documented in a new `loomwright/docs/CAPABILITIES_CONTRACT.md`, with a pointer from `docs/ARCHITECTURE_CONTRACTS.md`. Minimum fields:
  - `contract_schema_version` (integer) and `plugin_version` (string, equal to `plugin.json`'s version);
  - `agents[]`: `name`, `runtime_agent_type` (exactly as the runtime reports it in hook payloads), `model`, `tools[]`, and `result_block` (the result block name it emits, or null);
  - `commands[]`: `name` and a one-line description;
  - `skills[]`: `name`;
  - `result_schemas[]`: `name` and `schema_version`;
  - `hooks[]`: `event`, `matcher` (or null), `script`, `blocking` (true only for fail-CLOSED hooks without `|| true`), and `writes[]`. `writes[]` lists repo-relative paths or settings keys the hook may create or modify in the session's working directory, e.g. `.claude/settings.local.json#env.OTEL_RESOURCE_ATTRIBUTES` and `.supervisor/logs/<session>.jsonl`. Use an empty list when the hook writes nothing there.
  - `host_switch`: `null` in this item. Item 02 fills it in.
- **Compatibility policy**, written in the contract doc: adding fields or entries is non-breaking, so the version stays the same. Removing or renaming a field, or changing its meaning, bumps `contract_schema_version`. Hosts must ignore fields they don't know.
- A **staleness check** in CI and `scripts/ci-local.sh`: regenerate, then diff against the committed file, and fail with a one-line "run build-capabilities and commit" message when they differ. That way the contract can never drift from the plugin.
- Tests (`loomwright/scripts/test-*.sh` style):
  - generation is deterministic;
  - every agent, command, skill and hook in the plugin appears exactly once;
  - `plugin_version` matches;
  - a hook that writes into the repo has a non-empty `writes[]`. Seed this from an audit (see 02) of at least `set-otel-resource-attrs.sh`, `emit-lifecycle.sh`, `emit-token-ledger.sh` and `stamp-requirement-status.sh`.
  - A mutation control: delete an agent file, and the staleness check fails.

## Acceptance criteria
1. `loomwright/capabilities.json` exists, is generated by the script, and validates against the documented schema.
2. Regenerating on an unchanged tree gives byte-identical output.
3. CI fails when the committed contract is stale. A test proves it by mutating a source file.
4. `runtime_agent_type` values match what the runtime reports. Cite the existing doubled-prefix evidence (`loomwright:loomwright:worker` in the SubagentStop decision-shape fixture), and don't guess.
5. Every hook entry's `writes[]` is filled in from reading each script, not assumed. A hook whose writes can't be determined is listed with `writes: ["unknown"]`, and the doc says so. Never leave it silently empty.
6. `CAPABILITIES_CONTRACT.md` documents the schema, the compatibility policy, and that `CAPABILITY_BASELINE.json` is a different, inbound file.
7. Additive only: no existing behaviour changes. Ships a `changelog.d` fragment only — no version bump in the item's PR (it runs as a wave lane; the wave branch carries the one bump, S3 run rule P7; amended 2026-10-06, owner decision).

## Non-goals
