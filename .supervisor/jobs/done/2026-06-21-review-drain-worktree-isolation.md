## Task
**Goal:** End the until-mergeable review-drain dispatch saga (#67/#70/#71/#72) by removing the *root hazard* instead of adding a 5th dispatch guarantee. Isolate the detached drain (`review-pr-runner`) in its OWN git worktree so it never shares a working tree/index with the inline Phase 4.5 self-heal, retire the now-unnecessary "suppress-during-self-heal" rationale, and add an advisory net that surfaces a silently-dropped drain.

**Root cause (this session's investigation):** The 4 prior PRs all hardened *whether the drain dispatches*. PR #74 still missed it for a different reason — the agent set `.supervisor/config.json {"auto_review": false}` to dodge a real hazard, then restored config but never re-dispatched (verified: no marker for `pull/74`, `until_mergeable_dispatched: false`). The hazard is real and never fixed: the drain runs in the SAME working tree as inline self-heal (`skills/review-heal/SKILL.md:13` "no worktree fan-out"; runner does `git checkout "$HEAD_REF"` in the same checkout; `agents/supervisor.md:1038` admits "concurrent with self-heal"). ## Acceptance Criteria
- [ ] **AC1 (isolation — scoped to the DETACHED dispatched drain):** Given an inline `/supervisor` self-heal is running on the feature branch, when the until-mergeable drain is **dispatched (the detached `review-pr-runner` launched by `dispatch-pr-review.sh`)**, then that drain operates in its OWN git worktree (separate working dir + index) and never checks-out / stages / commits in the inline session's working tree. **Scope note:** isolation targets the *detached dispatched* path — the only one that runs CONCURRENT with self-heal. A user running `/review-pr` **inline in their own session** has no concurrent self-heal to collide with and stays worktree-free (this is why the "no worktree fan-out" phrasing is *scoped*, not blanket-deleted — see AC4).
- [ ] **AC2 (same-branch checkout):** Given the drain's PR head branch equals the inline session's current branch, when the worktree is created, then it uses a **detached-HEAD checkout at the PR head SHA** (`git worktree add --detach <path> <sha>`) so `git worktree add` does not fail with "branch already checked out", and (for a **same-repo** PR) pushes via an **explicit refspec** (`git push origin HEAD:<head_ref>`, **regular push, never `--force`**).
- [ ] **AC2a (fork PRs degrade safe):** Given the PR is **cross-repo / from a fork** (`gh pr view --json isCrossRepository,headRepositoryOwner` ⇒ head is not on `origin`), when the drain would push, then it does NOT push to `origin` (which would update the wrong ref or fail) — it degrades to **review-only** and exits `ESCALATED` with a posted comment, UNLESS the design explicitly supports pushing to the fork's remote. The default-diff-only `/review-pr` loop is similarly fork-aware. (This closes a latent gap: the current bare `git push` at `review-heal/SKILL.md:141` has no fork awareness.)
- [ ] **AC2b (worktree path — sibling, never nested):** Given the worktree is created, then its path is a **plugin-owned SIBLING of the primary checkout, OUTSIDE the repo's tracked tree** — mirror the existing worker convention `../{project}-{id}` (`agents/supervisor.md:1499`), e.g. `../{project}-review-{pr_hash}`. It must NOT be created **nested under the repo working dir** (a nested worktree can be swept by the inline session's `git add -A`, re-creating the very collision this change removes, and pollutes `git status`). The path is deterministic from the PR hash so AC3 cleanup can target exactly it.
- [ ] **AC3 (cleanup, executable + scoped):** Given the detached drain reaches a terminal state (READY/ESCALATED) or errors/**crashes**, when its process exits, then its worktree is removed by a **`trap cleanup EXIT`-owning wrapper process** (NOT a prompt-only "remove on exit" instruction the agent can skip — the very prompt-reliability failure this whole saga is about). Cleanup removes **ONLY the dispatcher-created, PR-hash-keyed worktree path** it owns — no broad `*-review-*` glob sweep that could catch an unrelated/concurrent drain's worktree. A bounded `git worktree prune` of provably-stale dispatcher-owned paths is the only additional safety net.
- [ ] **AC4 (retire the race rationale + reconcile ALL THREE "no worktree fan-out" surfaces):** Given isolation removes the same-checkout collision, when docs are updated, then the **three byte-identical "no worktree fan-out" claims** — `skills/review-heal/SKILL.md:13` (the single source of truth), `commands/review-pr.md:13`, and `docs/RESULT_SCHEMAS.md:1763` (REVIEW_HEAL_RESULT section) — are reconciled to the SAME scoped wording: the *inline* `/review-pr` session has no worktree fan-out, but the *detached dispatched* until-mergeable drain runs in its own dispatcher-created worktree. (All three must change together or they drift — the project's mirror-drift / consistency-audit discipline.) Also, `agents/supervisor.md` Phase 4.5 step 5.5 timing note no longer relies on "concurrent-with-self-heal is safe-by-degradation" as the collision mitigation, and no repo guidance recommends writing `auto_review:false` to suppress for the self-heal race. (The `auto_review` config flag itself **remains** as a general opt-out — only the suppress-for-the-race *rationale* is retired.)
- [ ] **AC4a (marker reflects real dispatch — atomic claim, then marker-after-success):** Two distinct guards, because moving the marker later would otherwise weaken the existing double-dispatch protection. **PIN this exact fail-safe order — do NOT reorder (it preserves today's short-circuits at `dispatch-pr-review.sh:250` and `:277`):** ① **existing-marker-wins:** if a marker already exists for the PR → `exit 0` immediately, BEFORE taking the lock or creating any worktree; never launch again (today's `:250`). → ② verify `CLAUDE_BIN`/the wrapper is **launchable**; missing `claude` → `exit 0` with **NO marker** (today's `:277`, which sits before the marker write — a missing binary must never leave a marker). → ③ take the atomic lock (i). → ④ create the sibling worktree. → ⑤ write the RUN_LOG header. → ⑥ write the marker (ii). → ⑦ launch the detached wrapper. (DRY-RUN is the ONLY exception: it writes the marker without a real launch, for tests — `dispatch-pr-review.sh:262-274` — and must stay test-only.) The two guards:
  - **(i) Atomic claim BEFORE worktree creation, with stale-lock recovery.** The dispatcher first takes a per-PR **atomic lock** — `mkdir "$DISPATCH_DIR/<pr_hash>.lock"` (or `set -C`/`noclobber`), which fails atomically if a concurrent dispatch (step 5.5 vs the PostToolUse hook) already holds it. Only the winner proceeds; the loser logs one line and `exit 0`. On the normal path the winner **removes its own lock** at the end (the AC3 `trap` wrapper clears worktree + lock together). The lock body **records metadata**: `pr_url`, the dispatching/wrapper `pid`, `ts`, and the planned worktree + RUN_LOG paths.
    - **Stale-lock reclaim (closes the crash-between-mkdir-and-marker wedge):** because a crash AFTER `mkdir <hash>.lock` but BEFORE the marker/wrapper would otherwise leave a permanent lock that wedges the PR forever, a later dispatch that finds an existing lock MAY reclaim it (clear it and proceed) — but **ONLY when ALL hold**: (a) **no durable marker** exists for this PR (a marker means a dispatch genuinely started — never reclaim over a marker; the marker is the real idempotency guard), (b) the recorded `pid` is **not alive** (`kill -0` fails / it is not a running `review-pr-runner` wrapper), AND (c) the lock `ts` is **older than a conservative TTL**. Reclaim clears only THAT hash-keyed lock, never a broad sweep. This replaces the old marker-as-claim role that "write marker before launch" ([dispatch-pr-review.sh:289](ai-agent-manager-plugin/scripts/dispatch-pr-review.sh:289)) used to serve, without inheriting its permanent-wedge-on-crash behavior.
  - **(ii) Marker only AFTER real dispatch.** The durable per-PR **marker** under `.supervisor/review-dispatch/` is written **only after** the worktree is successfully created AND the RUN_LOG header is in place, but still **before** the detached `claude -p` launch. So a marker can never claim a dispatch that did not actually start — otherwise the AC5 audit reads the false marker and MISSES the dropped drain. (Lock = "someone is dispatching"; marker = "a dispatch genuinely started".)
- [ ] **AC5 (missing-drain reconciliation — classified, not accusatory):** Given a PR carries a heal outcome (`## Outcome` block / heal signal) but has NO dispatch marker under `.supervisor/review-dispatch/`, when `/insights` (`build-insights.sh`) runs, then it surfaces that PR in an advisory **`## Missing-drain reconciliation`** section with a **reason classification** — NOT a blanket "dropped" accusation:
  - `opted_out` ONLY when there is **durable RUN-TIME-recorded** opt-out evidence for THAT PR (e.g., a recorded `--no-auto-review` / suppression line in that run's dispatch log or the job's `## Outcome` block). **Never inferred from the *current* `.supervisor/config.json`** — that file is mutable and reflects NOW, not the state at dispatch time, so reading it would mislabel a genuine later drop as a deliberate opt-out;
  - `unknown_or_opted_out` as the default whenever no marker exists AND no durable run-time opt-out evidence is available (it may have been a silent drop OR an unrecorded opt-out — the audit does not have enough to accuse, and must NOT guess from live config);
  - (a genuine silent drop like #74 surfaces under `unknown_or_opted_out`, which is the signal to investigate).
  Read-only, advisory, SUPPRESSED entirely when no heal-signal/marker corpus exists (no fabricated zeros, per the existing heal-signal-section precedent). Correctness depends on AC4a: a present marker must mean a dispatch genuinely started.
- [ ] **AC6 (invariants preserved + proof gates green):** All dispatch paths still ALWAYS `exit 0` / fail-safe (never gate, never block the PR, never change `heal_decision`); the drain still NEVER merges and NEVER `--force`-pushes; the audit is advisory-only. **All `## Executable Acceptance` gates G1–G5 pass** (lifecycle unit tests, real stubbed-launch test, failure-injection matrix, integration sweep, dogfood). Doc-currency passes: bump to the **next available minor version above the base branch's `plugin.json`** at finalize time (do NOT hard-code — see Configuration re: the #74 collision), and make every count claim match **`scripts/check-doc-currency.sh`'s `Authoritative → …` output** (it counts skill DIRECTORIES, not `*/SKILL.md`) — this change adds **no** agent/command/skill/hook, so the counts are whatever the gate reports for the base branch. No `schema_version` bump.
