Provider routing for write seats
The worker, Phase 4.5 fix and drain fix seats can now run their code edits on a granted, write-eligible non-Claude CLI. `resolve-routing.sh write-seats` is the one home of the write-seat ids, and a write seat resolves like a read seat plus a separate per-seat write grant (`repos.<slug>.write_grants.<seat>`, surfaced as `resolve-egress-config.sh`'s `PROVIDER_WRITE_GRANTS`; `write_not_granted` otherwise). `setup-routing.sh apply` refuses a write seat or `--grant-write` for any provider not graded exactly `usable for write seats` (`provider_not_write_usable`). The new `scripts/adapters/providers/write-run.sh` runs only the edit step, only through `launch_provider_cli isolated`, with an allow-list pin and no shell tool. It refuses a dirty tree or a repo-side `.claude` settings file before launch, restores the tree on every non-`ok` outcome, and reports `write_git_tampered` when the provider moved HEAD or changed refs, remotes, config or hooks. The launcher never copies a `.claude/` login file into the isolated HOME, because the 2026-10-31 probe showed Grok 1.0.70 reads `~/.claude/settings.json`, where `permissions.defaultMode: "auto"` overrides `--permission-mode dontAsk`. `git_integrity_fingerprint` moved into the shared `git-integrity-lib.sh` with an `own` refs scope for write runs. The Claude worker and fix tasks still spawn as before and run every post-edit gate and commit themselves. The worker seat is resolved once per run at Phase 3 entry and never falls back to a Claude edit mid-run, and a tampered edit stops the whole run (`SUPERVISOR_RESULT.error: write_seat_tampered`, brief moved to `failed/`). `docs/PROVIDER_ROUTING.md` gains a `## Write seats` section with the contract and its honest limits, and `docs/FAILURE_ESCALATION.md` gains the `write_seat_failed` and `write_seat_tampered` rows.
