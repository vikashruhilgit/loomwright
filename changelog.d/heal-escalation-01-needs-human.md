One NEEDS_HUMAN finding no longer strands the fixable findings beside it
On PR #876 a Phase 4.5 review returned NEEDS_HUMAN on one HIGH judgment call with two at-floor MEDIUMs beside it. The heal loop escalated before any fix round, the owned drain ignored the escalation comment because it comes from the operator's own login, and `/automate` parked with "nothing to decide", because escalated findings existed only as the `heal_remaining_issues` count. Two changes close this. First, `CODE_REVIEW_RESULT` issues gain an optional `needs_human` boolean (v3 rule o in `validate-code-review-result.py`: a boolean, and `true` only under NEEDS_HUMAN; an unmarked NEEDS_HUMAN block stays valid and reads as all-human, today's behaviour). The reviewer marks exactly the issue(s) a human must rule on, and Phase 4.5 runs ONE fix round for the other at-floor findings, then re-reviews and escalates only on the held items. A HELD FOR A HUMAN reviewer line keeps a re-raised held item marked, so no fix task ever decides it, and a clean re-review still escalates because the owner never ruled. Second, every ESCALATED exit of the heal loop itemises the at-floor findings it leaves unfixed in `heal_dismissed` with the new reason `escalated_unfixed`: the human item is prefixed `needs your ruling: `, and a final-iteration fix never re-reviewed is prefixed `fix not re-reviewed (final heal iteration): `. `/automate`'s dismissed-findings decision step then drafts and asks about each one (new leg A3e in `test-automate-dismissed.sh`). The drain's trust model is unchanged: it still fixes bot-authored findings only.
