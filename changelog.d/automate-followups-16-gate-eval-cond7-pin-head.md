gate-eval condition 7 pins the checkout to the PR head and a clean tree before trusting the rules verdict
automate-followups/16. Condition 7 of the `--auto-merge` gate ran `rules-gate-verdict.sh --root <checkout>` on whatever was checked out, so a stale checkout (an older commit, or `main`) or a dirty one (an un-pushed local fix to a bound file) could answer `ok` for a PR head whose bound files fail, and the gate would merge. `gate-eval` now checks the checkout first, before the helper runs. If `git rev-parse HEAD` at `--root` differs from the live `headRefOid` condition 2 confirmed, or cannot be read (not a checkout, no commit), it parks `rules_gate_head_mismatch`. If `git status --porcelain -uall`, read from the repo top level so a subdirectory `--root` still sees dirt anywhere, lists a tracked edit, a staged change or an untracked non-ignored file outside `.supervisor/` and `.claude/agent-memory/`, or fails, it parks `rules_gate_dirty_tree`. Both fail CLOSED with no override, and neither calls the helper. The two excluded paths are the engine's run file and sidecars and the `memory: project` agent stores, both legitimately written mid-item. Honest limit: a rule `binds` path under either excluded path is not covered by the cleanliness pin. The git calls unset `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` and the pathspec-mode variables, because `GIT_LITERAL_PATHSPECS=1` would otherwise make the `:(exclude)` magic literal. On the normal path the owned inline `/review-pr` drain leaves the main-thread checkout on the PR branch, so the pin passes. `skills/automate-loop/SKILL.md` §10 condition 7 and the `gate_eval` header list both reasons. `test-automate-helpers.sh` moves the gate harness onto a real git checkout whose HEAD the `gh` stub reports. Every earlier case is unchanged.
