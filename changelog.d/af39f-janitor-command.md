/janitor: one read-only report of everything the plugin left running or lying around, acting only on the rows the owner picks
The new `/janitor` command prints one grouped report built only from the existing readers, each run once: registered processes and unregistered look-alikes (`proc-registry.sh list --scan`), run locks of the primary and every lane, lanes and their leak check (`lane-status --leaks` in compare mode, never `--snapshot`), worktrees and branches (the `sweep` dry run), and stale run state (`retention-sweep.sh`, stranded config backups, stale merge-watch markers, metadata-push failures). Plugin-adjacent rows (CI-slot holders, a keep-awake) and not-the-plugin's rows (the host's own sessions, other python processes) are listed report-only. Every row carries its owner, age, state, evidence and a suggested action with the reason, as text or as one JSON object. A reader that fails shows as an `unknown` row, never as a clean group. In an interactive session one `JAN-ACT` multi-select question, with nothing pre-selected, picks the rows to act on. `janitor-report.sh act --confirm` re-reads each picked row first and runs its one guarded helper: `proc-registry.sh reap` or `stop-unregistered` (with the recorded lstart and command-line hash), `sweep --apply`, `lane-remove`, `config-restore`, or a run-lock reclaim through `acquire` plus `release`. A force-unlock needs a second confirmation. Without `--confirm`, under `--report`, or with `CI` set, it acts on nothing. `proc-registry.sh` gains `list --scan` rows and the guarded `stop-unregistered`, both sharing the one scan predicate and the one TERM/KILL path. `JAN-ACT` is a human-only catalog gate with its can't-ask row (report only, nothing acted on).
