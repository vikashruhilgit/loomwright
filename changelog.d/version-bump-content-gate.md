The version-bump rule checks content, not commit position: a CI gate verifies the version files, a re-run re-folds a late fragment, and every sequential push re-folds first (#512)
Decision P7 required the bump to be a PR's LAST commit. On a sequential run, Phase 4.5 heal and `/review-pr` drain commits always land after the bump, so the rule broke whenever a heal round fixed anything (#367), and a fix that added a fragment could not be folded without hand-editing the bump. The rule now checks content. `scripts/bump-version.sh --check`, run in CI through the new `scripts/check-version-bump.sh` on a deepened checkout, verifies that at any commit the three version files and `capabilities.json`'s `plugin_version` are either untouched or exactly ONE bump over the merge base. Its CHANGELOG entry must be the fold of fragments the branch carried (read back from history), and no fragment may be left pending. It names a hand-edited version file or entry, a fragment added after the bump, and a capabilities drift; it exits 2 (fail closed) when it cannot check. Re-running `bump-version.sh` on a branch that already carries a bump now re-folds into that ONE bump instead of double-bumping (`--refold` does only that, and is a no-op on a fragments-only lane). The new `loomwright/scripts/release-refold.sh` runs it and commits the result before every sequential-path push: FINALIZE step 5.5, each Phase 4.5 heal push, and each `/review-pr` fix push. The parallel wave release lane is unchanged.
