loomwright-lanes: the /lanes pane as an optional sibling plugin, and lane-status --json carries every question's options and the lane's branch (parallel-automate/14)
A fourth sibling plugin in the atelier marketplace, `loomwright-lanes` (v0.1.0), ships the `/lanes` pane that until now existed only as per-session dev mods: every lane's state, PR, branch, latest message, last actions, CI-slot position and merge-readiness, a machine-health line with a HIGH-LOAD alert, and an inbox of every lane's pending question, oldest first, with its wait time, one button per option, an optional note delivered to the lane with the answer, and a replace path for an answer already held. It is a Claude Code mod (a hooks module) that reaches Loomwright only through `lane-status --json`, `lane-feed` and `lane-answer` (answers are recorded `via: lanes-addon`; a button press counts as the owner answering), finds the installed Loomwright through `claude plugin list --json` or the `loomwrightRoot` option, and holds no state that matters, so the lanes run identically without it (decision P9). In the core, `lane-status --json` gains, on each pending question, `items` — every question of the call in answer-key order with its header, `multiSelect` and option labels and descriptions, exactly what `lane-answer` accepts — and, on each lane, `branch` from the run file's `## Current` line; both are additive. `scripts/test-lanes-addon.sh` (new CI step) holds the module to the three lane commands with mutation controls, checks that nothing under `loomwright/` names the add-on, and runs `claude plugin validate` / `claude plugin test` where the CLI exists (SKIP with the reason otherwise). Like `stackpack` and `mysql-mcp`, the add-on is outside the vendor-coupling ratchet's scan roots (sibling plugins are deliberately unscanned).
