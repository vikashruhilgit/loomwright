Three --parallel lane guardrails and two wave-close fixes: a Stop hook keeps the coordinator's lane watcher armed, a lane's question banner names the command that answers it, a resume can no longer silently drop the test-integrity guard's opt-out, fleet-closeout finalizes the parent run when its Queue empties, and the leak check no longer reports a merge watcher that is not running
Running wave W3 on 2026-10-11 showed three gaps around lanes. First, re-arming `lane-wait` after every event was prose the coordinator model had to remember; when it forgot, lane questions went unseen again. A new `Stop` hook, `scripts/guard-lane-wait-armed.sh` (`type: command`, fail-SAFE, always exit 0), now sends ONLY the coordinator session back to arm the watcher: it blocks when the payload is a plain main thread (no `agent_type`, `stop_hook_active` not true) whose `session_id` equals the session recorded on the `automate-lanes:<run_id>` run lock, the wave is open, some lane is live (lane-wait's own `_LANES_WAIT_LIVE` set) or holds a question lane-wait has not reported, and no live watcher exists. `lane-wait` now writes a `<run_id>.lane-wait.pid` liveness marker (removed by its EXIT trap only while it still names its own pid; a reused pid does not count). The hook reads the lane table, lane process liveness and the inbox through the new `_lanes_quick_state` (no `gh`, no full `lane-status`); measured about 0.2 s on the block path and about 25 ms for any other session. Second, inside a lane the AskUserQuestion desktop banner was generic, so the owner did not learn which session answers it. `notify-desktop.sh` now detects a lane clone (a valid `.supervisor/lane.json`) and titles the banner `Lane <L> needs your answer`, with the question header (else its first 80 characters) and `answer in the coordinator session: /loomwright:automate --resume <parent_run_id>`, sized so the command is never truncated. Outside a lane nothing changes. Third, a lane inherits the environment of whoever launches or resumes it, so a lane launched with the test-integrity guard's opt-out and resumed from a shell without it was silently blocked by the guard. `lane-launch` now records only the FACT that the opt-out was set at a lane's first launch, in a coordinator-side `<run_id>.<lane>.gate-optout` file (never `lane.json`). Every resume path (`lane-answer`'s resume, `--deliver-pending`, `--resume-run`, `--continue`) refuses `BLOCKED` (exit 3, no spawn) when the current environment lacks it, and `lane-answer` keeps the validated answer pending exactly as on HELD. `--without-gate-optout` resumes without the opt-out and clears the fact. The opt-out is never added to a resume's environment. Two wave-close fixes followed from the same wave. Fourth, `fleet-closeout` checked off the last item and released the wave lock but left the parent run file `## Status: running` with its `- wave:` line, so the coordinator had to write `done` and run its trail by hand; once the parent Queue is empty it now finalizes the parent under the still-held wave lock, as §6 "Termination" ends a sequential run (`current-wave --wave null`, `## Status: done` and `pause_reason: null` in one validated `runfile-write`, a `wave closed — Queue empty, run finalized` Progress line, `trail-pr --reason done`, and `trail-unstage` when branch mode is off); a re-run on a `done` parent writes nothing, and a refused write prints `finalize FAILED` and still releases the lock. Fifth, the leak check's `merge-watch` section matched process names with `pgrep -lf automate-merge-watch`, so a `grep` whose arguments named the script read as `leaks: found — merge-watch` with no watcher running; the section (now headed `## merge-watch v2`) lists only live watchers read from the `*.merge-watch` markers of the primary and of every lane in the table, and a wave-start snapshot written in the old format is reported as `merge-watch not compared` instead of being diffed into a false `found`.
