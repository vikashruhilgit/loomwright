Telemetry posts one thread per review target and skips validator-rejected stops
Telemetry used to open one issue per review round, post the attempt a result-block validator had just rejected and then post its retry again (#422/#423, #461/#462, bodies reading `- [HIGH] >-`), and count findings from its rendered `new` lines, so drift-only FAILs posted zero findings (#373, #378). The cause was a second, permissive parser in `send-telemetry-core.sh` running beside the validator in the same `SubagentStop` group, with dedup keyed on finding text in a per-cwd log that died with every worktree. The core now resolves and parses the block with the shared `result_block_parser.py`, runs the group's own sibling validator on the same payload and skips a stop it blocks (`validator_rejected`, decided from the verdict, not hook order), and counts every parsed issue by severity and category, `drift` included. Posting follows the owner's 2026-10-13 decision: the first non-pass round for a review target (source repo + branch, or the drain's `LOOMWRIGHT_PR_HEAD_REF`) opens an issue titled `[Telemetry] <agent> thread`, later rounds comment on it, and the final pass adds a closing comment (verdict, rounds, per-round finding totals), the `telemetry:healed-in-loop` label, and closes it. The thread key lives only in the user-scope map `~/.claude/loomwright/telemetry-threads.json`, written atomically under an exclusive lock so concurrent worktrees open one issue; an unreadable map posts nothing. No repo, branch, PR or key appears in any post. Per-finding fixed / dismissed / deferred counts are not recorded yet (no telemetry hook receives `REVIEW_HEAL_RESULT`), which `docs/TELEMETRY.md` §"Posting policy" states. New suite `test-telemetry-threads.sh` with four mutation controls.
