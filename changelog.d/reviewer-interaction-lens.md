Code Reviewer static interaction-behaviour lens, and `cannot_determine` needs a reason (#433)
The reviewer's frontend checklist only asked what an element has (alt text, labels, contrast), and `cannot_determine` had no admission rule, so focus and state handling could be filed as "runtime-only" with no reason. A reviewer PASS did exactly that while the diff unmounted the focused button with nothing restoring focus. Review Process step 3 now carries a six-question interaction-behaviour lens (`focus_on_unmount`, `busy_state_cleared`, `async_state_distinct`, `unsaved_exit_parity`, `state_reset_on_input_change`, `actionable_failure_persists`), decided from the code for every changed UI component. A hit is an ordinary finding under step 6's severity rule, with no new decision state. The same ids appear in `commands/code-reviewer.md` and in a new `frontend-ui` skill section (skill 1.1.0). `cannot_determine` is now an optional `CODE_REVIEW_RESULT` field of `{item, reason}` entries (schema version stays 3). It is admissible only for what needs a rendered page, a real run, or evidence outside the diff (such as a criterion only the PR body shows), and it replaces the brief-conformance summary line. `validate-code-review-result.py` v3 rule n rejects an entry with an empty, missing or bare "runtime-only" reason. Pinned by `test-reviewer-interaction-lens.sh` (position, outcome, id parity, five mutants) and `test-validate-code-review-result.sh` sections N and O.
