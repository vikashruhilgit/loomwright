curation-status consumed-set lookups no longer race grep -q into a stderr Broken pipe
Every consumed-set and ledger membership test in `curation-status.sh` piped `printf` into `grep -qx`. `grep -q` exits on its first match; a `printf` still writing then hit EPIPE, and on a runner that hands SIGPIPE down ignored (GitHub Actions) bash printed "printf: write error: Broken pipe" to stderr, failing `test-curation-status.sh`'s `--json` stderr-is-empty check at random (ci run 37126834145). Locally the writer dies silently under the default SIGPIPE disposition, which is why it passed 5/5. All four sites are now here-strings (`grep -qxF -- "$id" <<<"$consumed"`, same bytes, bash 3.2 safe), and leg (n) pins it deterministically: SIGPIPE ignored, the match on line one of a 5000-id consumed set, red on the pipe form across `status --json`, `unconsumed` and `pending-ids`. `test-no-pipefail-grep-q.sh` missed it because it only scanned test files that set pipefail; it gains a rule 2 that flags a `printf`/`echo` writer piped into `grep -q` in every shell script, pipefail or not, with continued lines joined, fixture controls proving the no-pipefail shape turns red, and a per-file count ratchet over the 30 pre-existing occurrences in 13 files so the number can only shrink.
