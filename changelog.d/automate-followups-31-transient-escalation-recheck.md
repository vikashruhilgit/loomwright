Transient-escalation re-check: an escalated /automate park records why, and its merge watcher reports once when the check settles (automate-followups/31)
An until-mergeable drain that ends ESCALATED now names its cause. The new `automate-helpers.sh escalation-cause` classifier (in `automate-helpers.d/escalation.sh`, fed by a new opt-in `wait-for-checks.sh --names` snapshot) returns `check_pending`, `check_red_unrelated` (every failing test file of a red required or review-producing check is outside the PR's changed files, and so is its tested `<stem>.sh`), `check_red`, `findings` or `other`. Every unreadable case fails closed to `check_red`. `REVIEW_HEAL_RESULT` carries `escalation_cause` plus `escalation_check`, `escalation_run_id`, `escalation_attempt` and `escalation_sha`, and `sidecar-check` accepts them. The park's `## Current` gains one optional `- escalation_cause:` line, written only by the validated `current-escalation` helper. Replaying the two S2 drains gives `check_red_unrelated` (PR #381, a 1-second `ci-slot` timeout in an untouched test) and `check_pending` (PR #386, `claude-review` still running at the 1200 s bound). Deliberate behavior change: a sequential `escalated` park now arms a merge watcher, with the same documented launch line as `awaiting_merge`, so a merged escalated item closes out without a manual `--resume`. While the PR is open, that watcher re-checks a `check_pending` or `check_red_unrelated` check through `gh run view` (or the commit check-runs API). A pending check reports at the first completed attempt; an unrelated red check reports only at a newer attempt, meaning a human rerun. It writes exactly one `## Progress` line, `merge-watch: now mergeable: <check> green on <sha> (attempt <n>)` or `merge-watch: still failing: <check> <conclusion> — rerun: gh run rerun <run_id> --failed (attempt <n>)`, and sends one notify of the new gate type `automate_escalation_recheck`, so the at-most-one `automate_merge_watch` count is unchanged. The report is latched per escalation line, also across a restart (a gitignored `<run_id>.merge-watch-reported` sidecar). Owner decisions (2026-10-07): the CI rerun stays human, so the watcher prints the `gh run rerun` command and nothing in this change executes it, merges, pushes or approves; the cause and the verdict live in the run file only, and no `lane-status` surface is built. S3 record gap 6 ("two merge watchers" in s3-g) is diagnosed as a counting artifact, not a guard gap: the lane archive shows one launch, one marker and one closeout, and every `$(…)` subshell of the watcher shares its argv, so `pgrep -f` shows two processes for one watcher. This diagnosis comes from the archive and was not reproduced live. The existing same-PR single-instance guard is now regression-tested for park, fix-now re-drain, re-park (the already-running line, first pid alive, marker pid unchanged, one closeout), with a valid mutant that deletes that branch, and the docs say to count watchers by the marker pid or `ps -o ppid`, never `pgrep -f`.
