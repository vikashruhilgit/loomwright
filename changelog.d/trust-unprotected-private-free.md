`--trust-unprotected` covers a private repo on GitHub Free, and the auto-merge gate reads CI when no check is required
Condition 4 of the `--auto-merge` gate now reads GitHub's paid-plan refusal (HTTP 403, "Upgrade to GitHub Pro or make this repository public to enable this feature.") as branch protection that is not enforceable, so `--trust-unprotected` covers it; before, it parked `protection_unreadable`. A 404 is now matched by gh's `(HTTP 404)` status rather than by any `404` in the error text, so a 500 that mentions 404 parks `protection_unreadable` instead of reading as unprotected. Any other error, any other 403 included, still parks `protection_unreadable`, and condition 6 still has no override. Condition 5 is stricter for every existing `--auto-merge` user whose branch has no required status checks (no protection, the paid-plan 403, or reviews-only protection): the gate used to treat an empty required list as green whatever CI said, and now reads the whole status-check rollup, so a failing or pending check parks `checks_not_green` (an empty rollup still passes). A failing check that is not required, `claude-review` under a billing block or the weekly cap included, now parks runs that merged before. This is a gate-level fix: the drain's own protection read in `wait-for-checks.sh` is unchanged and still reports the paid-plan 403 as `required=unknown`, so on a private Free repo the owned drain escalates before the gate runs unless `--required-checks all-non-neutral` is set.
