reconcile-status takes a PR body citation only from an implements line
`automate-helpers.sh reconcile-status` counted any PR body that mentioned a requirement's path as evidence the PR implemented it. On 2026-10-11 the dry run planned five false `## Status: done` stamps: PR #470 listed af/36, af/39 and pa/18 in a `plan-waves` example, PR #482 named the `proposed/twin-remediation-11` draft it filed, and PR #457 named a task plan. `--apply` would have made them permanent, and `is_done` would then have hidden the three pending items from every later intake. It also missed real work. PR #484 cites `automate-followups/27-…` without the `.supervisor/requirements/` prefix or `.md`, and GitHub search returns nothing for the full path, so the PR was never even a candidate. A citation now counts only on a line that opens with `Implements`, `Closes`, `Resolves`, `Fixes`, `Ships`, `Lands`, `Requirement:` or `Source requirement:`, only in that line's first clause, and only on a path boundary, with or without the prefix and suffix. The candidate search uses the short form. A `proposed` draft or `parked` item (`is_not_ready`) is never stamped; every other not-done heading stays promotable. A top-level `<slug>-plan.md` task plan is never a candidate. Against the live repo, the dry run now prints no false rows and still finds #483, #484, #446, #468 and #470. Tests: `test-automate-helpers.sh` H9, with mutation controls that restore the any-mention rule, the full-path search, the status gate and the task-plan skip, each red.
