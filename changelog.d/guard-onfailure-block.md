A crashing fail-CLOSED guard now blocks instead of failing open
The test-integrity guard and the finalize-publish guard blocked only on their own deliberate `exit 2`. Any other outcome (the script missing, a `set -u` abort, a bad interpreter, a timeout) was the host's non-blocking error, so the guarded Bash, Write or Edit call went through. Each guard failed open on its own crash. The three fail-CLOSED `PreToolUse` leaves in `hooks.json` now carry `"onFailure": "block"` (Claude Code 2.1.295+), which turns that failure into the same block as `exit 2`. A live probe on 2.1.286 and 2.1.296 (`scripts/fixtures/onfailure-block-probe.json`) shows that an older host ignores the key and still runs the hook, so nothing changes there, and that on 2.1.296 a crashing hook blocks the tool call while a clean `exit 0` still allows it. New `test-guard-onfailure.sh` derives the fail-CLOSED set from `hooks.json` and requires the key on every leaf in it, and never on a fail-SAFE `|| true` emitter. It checks its model of the host against the recorded probe. It runs each leaf's exact command with the guard missing and with the guard aborting after `set -u`, and expects a block every time, plus an inert payload that must still exit exactly 0. A mutation control removes the key and expects every crash case to read as allow again. `docs/HOOKS.md` and `CLAUDE.md` state the rule, and `CAPABILITY_BASELINE.json` moves the field from the scan's candidates to `features_used`.
