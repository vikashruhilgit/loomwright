Fleet operations — a --parallel wave closes itself after the owner merges, and stamped policy answers handle routine lane questions
Part A (wave close). A merged lane's lane-convert-ready re-run now also finalizes the lane run file (finalize-empty, branch mode only). The new read-only wave-plan subcommand prints the owner's wave-branch integration commands (each lane's exact PR head merged --no-ff, ci, the release step as the last commit, push, PR) and the conflict rules; it runs no git mutation, push or gh write. The new fleet-closeout subcommand, re-run on each coordinator --resume, closes the wave stepwise and idempotently: it backstops each merged lane with lane-convert-ready, checks the item off the parent Queue, syncs the primary, removes the lane clones, reports leaks and main's ci health, and releases the automate-lanes lock once the Queue is empty. Nothing in the engine merges or pushes a lane branch; the merge-executor invariant is unchanged.
Part B (policy answers). Every engine question gate now has a stable code, with one authoritative catalog (lane-policy.sh catalog, mirrored in docs/LANE_GATES.md). The routine gates (resume, Queue confirm, summary drafts, Launch Pad save on a clean PASS, Supervisor children unsettled) are asked with their code as the header. A project policy (.agent/lane-policy.json) counts only while stamped through the existing rules-check.sh stamp valve (new read-only --stamp-state mode), and the owner can set a per-wave answer set with lane-policy.sh wave-set. lane-create carries the resolved policy into lane.json, and the lane's own relay hook answers a catalogued routine gate by exact lookup, recorded source policy with its sha. Every other question still reaches the owner, batched by lane-status --inbox. A lane no longer asks the one-item Queue confirm on the backlog lane-create wrote.
