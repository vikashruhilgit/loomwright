The lane timeline shows Heal once the Supervisor opens its PR, not Build · EXECUTE
On 2026-10-16 (run automate-2026-10-15-163325), lanes L8 and L9 sat in Phase 4.5 with PRs #577 and #575 open while the `/lanes` timeline read "Build · EXECUTE" for hours. There were two causes. First, `build-state.sh`, the only writer of `## Session` `phase:` after creation, projects it from two session-log events only (`subtask_complete` → EXECUTE, `session_end` → LOOP), so `phase:` reads EXECUTE through FINALIZE and Phase 4.5. Second, the timeline read only Decisions Log bullets carrying a timestamp, while the canonical log is a table with no timestamp, so no row ever matched. `_lanes_timeline` now reads two more sources. It reads the Supervisor's first `pr_created` event at or after the pick: the hook writes it into the state's own session log, FINALIZE opens the PR, and Phase 4.5 always follows, so that event dates Heal's start. It also reads the Decisions Log table rows as undated evidence that a step was reached (SELF_HEAL / LOOP → Heal, any other phase → Build), trusted under the same rule as `phase:`. A step whose only dated line comes after it ended now reads a null start instead of one later than its end. `build-state.sh` is unchanged: no session-log event marks Phase 4.5 entry, and projecting one from `pr_created` would be inference. The fix was checked against 8 real runs: every lane's `pr_created` is its own item PR, and the only change is a real Heal start where there was none. Tests AJ8d–AJ8m, including three mutation controls.
