A must rule's check must prove it can fail before it is written
New `loomwright/scripts/prove-rule-check.sh` runs a candidate rule check on the current tree (it must pass) and on a throwaway `git worktree` copy of HEAD with a hand-written counterexample patch applied (it must fail), then prints one verdict: `PROVEN`, `VACUOUS`, `FAILS_NOW` or `UNPROVABLE (<reason>)`. Exit 0 means `PROVEN` only, and every could-not-examine path is `UNPROVABLE` with exit 2. The script is confirm-gated like `rules-check.sh --confirm`: it shows the check and the patch, and without an argv `--confirm` or a TTY `y` nothing runs. It takes the check from argv only, never reads `.agent/rules/`, and writes no stamp. It removes its scratch worktree and verifies it is gone, never prunes the user's other worktrees, and leaves the user's worktree list and status as it found them. `add-rule.sh` now refuses a `--enforcement must` add with `--check` unless `--proof` names a `PROVEN` proof for that exact check string. It re-hashes the check and refuses a missing, non-`PROVEN` or mismatched proof. Advisory and check-less adds are unchanged. A candidate that does not prove `PROVEN` is offered as an advisory rule, with its check kept as data. `/rules add` and `/dreaming`'s "Accept rule WITH check" run the proof first, the harvester's WITH-check invocation now ends in `--proof "$PROOF"`, and the proof is recorded in the commit or PR body, not in the rule. Evidence: `docs/evidence/verified-rule-checks.md`.
