A countable rules fail that turns unstamped mid-loop now escalates instead of passing silently
Owner decision Option A (automate-followups/18). A stamped countable `must`-rule check that FAILED in one Phase 4.5 iteration or drain round could be cleared by the fix itself: editing a file the rule `binds` moves the stamp hash, the next round read `unstamped` (passable), and Phase 4.5 reached PASS or the drain reached READY with only a `rules_check: unstamped` line. Both loops now keep a `rules_failed_seen` set of every countable id seen failing (Phase 4.5 persists additions with a `rules_failed_seen: added` decision so the set survives resume). A later `unstamped` while that set is non-empty escalates `rules_fail_then_unstamped`: Phase 4.5 ends ESCALATED and names the remembered ids, and the drain ends ESCALATED with `termination_reason` unset at the main rules step, and the sub-floor re-read can no longer reach `sub_floor_converged` READY. The escalation fires on ANY such `unstamped`, not only when the remembered id is still countable. This is a deliberate fail-closed broadening of the requirement's "on that rule" wording: an `unstamped` verdict never runs the replay, so `rules.failing` is empty, and `rules-gate-verdict.sh` reports countability drift as `unstamped`, so a fix that also dropped the rule's countability would otherwise clear the fail silently. A rule never seen failing in the loop stays advisory when `unstamped` (D3 otherwise unchanged). Honest limit: `cmd_disabled` after a `fail` keeps passing. Reaching it needs an environment change mid-loop, not a branch edit. `CLAUDE.md`, `skills/rules/SKILL.md` §8.1 and the `rules_gate` row of `RESULT_SCHEMAS.md` state the exception. `test-rules-gate-seams.sh` gains pins P9 and P10 with their mutation controls.
