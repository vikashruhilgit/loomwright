`test-setup-ui.sh` no longer leaks Python HTTP servers, and its leak assertion can see every process the run starts
On 2026-10-02, 21 orphaned `python3 -` request handlers (parent = init, the oldest 26 days old) were found serving `mktemp` fixture dirs of this suite that no longer existed, each holding a port. Twenty came from the (s13) mutation control: its mutant engine is named `engine-mut.sh` and orphans its handler by design. That handler's command line carries neither `setup-ui.sh` nor `http.server`. The case's own reap, the teardown detector and `kill_if_fixture` all required one of those two names, so all three passed over it, (p1) printed green, and one server leaked per run. A local run reproduced it deterministically.
The fix makes the identity the path: anything whose command line names a path under this run's `$TMPROOT/` is a fixture process, whatever its binary is called. The new `fixture_pids` replaces `fixture_serve_pids` and also fails closed. A `ps` that cannot be read three times returns non-zero, and (p1) then reports UNVERIFIED instead of treating an unread process table as clean. The teardown sweep (`reap_fixture_pids`) now escalates from TERM to KILL and re-checks. (s13) reaps its orphan by fixture directory.
(p1) now covers every process under the temp root, not only servers. Three new controls each fail when one part of the fix is reverted: (p4) for a name-based detector, (p5) for a fail-open `ps`, (p6) for a single-TERM sweep. Reverting (s13)'s reap turns (p1) red.
The single `ui-badreg` (l15) leak did not reproduce on current main (0 of 180 serve-then-stop cycles, 10-way parallel). Its shape matches the stop-refusal leak that the `SERVE_PIDS` registry closed on 2026-09-05 (commit 55bed49). The fail-open `ps` read and the never-escalated sweep fixed here were the remaining teardown paths that could still let such a server escape.
