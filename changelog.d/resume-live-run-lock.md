A second session's `--resume` no longer resets a live run's next-step sidecar
`automate-next-step.sh --resume` reset the target run's `<run_id>.next-step.json` to a fresh AUT-RESUME ask without looking at the run lock, so a second `/automate` session clobbered a run whose coordinator held the PICK lock and had a phase in flight: the coordinator's next `--result` was refused (`resume: answer must be Continue, Start new or Archive`) and its saved Launch Pad brief was orphaned, forcing a full re-plan (run `automate-2026-11-08-175120`, 2026-11-08). The `--resume` entry now asks the new read-only `run-lock.sh probe --session-id <id>` (acquire's own re-entrancy rules, then `holder_alive`) before the reset and refuses with exit 2 `run_lock_held owner=automate:<run_id> pid=<p> — …`, nothing written past the start steps, when that run's lock is held by a running holder in another session — the same rule by which `resume-glob --finalize` leaves a locked run unfinalized. The holder's own session, a fresh phase session of its coordinator, a dead holder and another run's lock are not refused; an unreadable probe answer fails closed (`run_lock_unreadable`). Pinned by `test-automate-next-step.sh` P17 (+ its pin mutant) and `test-run-lock.sh` case 36.
