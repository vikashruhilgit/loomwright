/janitor reports leftover lane-wave folders, prunable worktree records and stray sibling folders
Janitor used to skip a wave once its lane table said every lane was removed, without checking the disk, while lane-remove deliberately leaves each wave's stream logs, stdin files and salvage/ in `<primary>-lanes/<wave>/` and nothing else removes them, so gigabytes of finished-wave residue never showed up. The lanes group now lists each such folder as a `wave` row; when its lane table confirms every lane removed, its run says done and it holds nothing a lane run does not write, the new `wave-prune` action moves salvage/ to an archive (LOOMWRIGHT_JANITOR_ARCHIVE, else $XDG_STATE_HOME/loomwright/lane-salvage), deletes only the logs and stdin files and rmdirs the folder, refusing when that wave is already archived; anything else is report-only and says why. A worktree record whose folder is gone is now a `wtp` row with a `worktree-prune` action (`git worktree prune`) instead of an "origin unknown" row, and `<primary>-*` folders and files beside the checkout that are neither its lanes folder nor its worktrees, such as hand-made clones, are listed report-only with their origin, branch and uncommitted and unpushed counts.
