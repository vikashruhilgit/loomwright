A countable rules `fail` that turns `unstamped` mid-loop now escalates instead of passing
Owner decision Option A (automate-followups/18, 2026-10-01). Before this change, a fixer could edit a file a failing stamped `must` rule `binds` (or change the countable set), which moved the stamp hash, and the next replay's `unstamped` let Phase 4.5 reach `PASS` or the `--until-mergeable` drain reach `READY` with only a `rules_check: unstamped` line and no record that an earlier round failed. Both loops now keep a loop-local `rules_fail_seen` list of every gate-countable id the rules gate reported `fail`: across the iterations of one Phase 4.5 review-and-fix loop, and across the rounds of one drain run, where both the §U4 read and the sub-floor re-read feed it. A later `unstamped` while that list is non-empty ends the loop `ESCALATED` under the named reason `rules_fail_then_unstamped` and posts the remembered ids and the two human ways out (re-run `/rules check --confirm` on the fixed branch, or revert the edit to the bound file) to the PR. The drain's `termination_reason` stays unset and `rules_gate` still carries the raw `unstamped`. The trigger is store-wide, meaning ANY countable id that failed earlier in the loop, because `unstamped` carries no per-id attribution and demoting or unbinding the failing rule drops its id from the live `countable` set, so intersecting with that set would fail open. A store never seen failing keeps today's behaviour, and `RULES_PASSABLE` is unchanged. Honest limit: Phase 4.5's memory does not carry into a later drain, which is a separate loop; under `/automate`, `gate-eval` condition 7 still parks `rules_unstamped` across that seam. Every surface that said `unstamped` stays advisory now names the exception, and `test-rules-gate-seams.sh` gains pins P9 and P10 plus the MSUB mutant, which pins the sub-floor leg on its own.
