Finalize-publish guard gates only the live run's own session and checkout
The fail-CLOSED `PreToolUse[Bash]` guard `guard-finalize-publish.sh` denied `git push` and `gh pr create` from an unrelated Claude Code session working in its own linked worktree while another session's Supervisor run was live (2026-11-12, issue #890's fix had to be pushed by hand). Two causes, both fixed at the root. First, the scope read HEAD and the branch from the session's project dir, not from the checkout the publish runs in: a session whose cwd was the run's checkout ran `cd <own worktree> && git push`, and the guard judged the run's branch. The command walk now tracks the directory each publish runs in (payload `cwd`, then `cd` / `pushd` / `git -C`, with `( … )` and `$( … )` restoring it); an unresolvable target stays in scope (fail CLOSED), and a non-git dir, another repository, a detached sibling or another branch is out of scope. Second, every session that was not the run's log owner was armed as a "resumed run (log owner differs)". The session join now reads the owner the way the rest of the plugin does (the `<id>.owner` run-creation seed first, then the log's first line) and allows a different Claude Code session; the owner's own session, its subagents and its workers (same payload `session_id`), and an unknown owner stay gated. Accepted consequence: `/supervisor --continue` resumed in a new Claude Code session is no longer gated, matching the emitters and the SessionEnd close-out, which already treat it as foreign. `onFailure: block` and exit-0-on-allow are unchanged; `test-guard-finalize-publish.sh` adds the incident, foreign-session, foreign-worktree, subagent/worker and fail-closed unknown-target cases with four mutation controls, and the owner-seed parity check now covers the guard's copy.
