Finalize-publish guard judges the checkout a publish runs in, not the session's project dir
The fail-CLOSED `PreToolUse[Bash]` guard `guard-finalize-publish.sh` denied `git push` and `gh pr create` from an unrelated Claude Code session working in its own linked worktree while another session's Supervisor run was live (2026-11-12, issue #890's fix had to be pushed by hand). The cause, fixed at the root: the scope read HEAD and the branch from the session's project dir, not from the checkout the publish runs in: a session whose cwd was the run's checkout ran `cd <own worktree> && git push`, and the guard judged the run's branch. The command walk now tracks the directory each publish runs in (payload `cwd`, then `cd` / `pushd` / `git -C`, with an unquoted `( … )` and `$( … )` restoring it, and a quoted paren making the target unknown so a stray `:)` in a commit message cannot pop the stack early); an unresolvable target stays in scope (fail CLOSED), and a non-git dir, another repository, a detached sibling or another branch is out of scope. Owner decision: a publish that runs in the run's own checkout on the run's own branch stays gated for every session (the owner, its subagents and workers, any other session, a resumed `--continue`), while a publish from another worktree or checkout, or on another branch, is allowed for every session. The session join now only names the publishing session in the deny reason ("this session", "owner unknown", "another session"), reading the owner the way the rest of the plugin does: the `<id>.owner` run-creation seed first, then the log's first line. `onFailure: block` and exit-0-on-allow are unchanged; `test-guard-finalize-publish.sh` adds the incident, foreign-worktree, every-session-on-the-run-checkout, subagent/worker and fail-closed unknown-target cases with mutation controls, and the owner-seed parity check now covers the guard's copy.
